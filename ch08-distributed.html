1分布式 vs 并行：两个假设被打破

难度 ★★★★★重要后两讲的动机，读懂就行

分布式数据库打破了两个假设：通信很快，通信可靠。5:25 回到 #14 那张对照表，现在把它讲透。

Send(node_b, msg);                       // 并行数据库：一定送到，而且极快
auto reply = WaitFor(node_b, timeout);   // 分布式：可能很慢，也可能丢
if (!reply) { /* 它死了？还是只是慢？分不清 */ }
// 考点：分布式和并行数据库，在通信速度和通信可靠性上的假设不同

并行数据库像在同一间办公室里喊话。分布式数据库像寄平信，可能慢，也可能寄丢。

并行数据库（#14） 分布式数据库（本讲）
通信速度 极快（IPC / 共享内存） 慢几个数量级。绕半个地球受光速限制，要 100–300 毫秒。最坏几十秒，甚至几分钟
通信可靠性 一定送达。送不到说明 CPU 在烧 可能丢。网线断了，丢包了……
扩资源为了什么 性能 性能 + 容错 / 可用性。挂一台，应用还能跑

一个特别阴险的失败模式

节点没响应时，你分不清它是死了，还是在忙。6:51 这是分布式系统一切困难的根源。

你把消息发给另一个节点。它跑的是 Go 或 Java，这时候 GC 启动了。

堆很大的 JVM，垃圾回收可能把整个执行阻塞 10 到 30 秒。

在你看来，那个节点像是死了。其实它只是在收拾垃圾。收拾完，它还会回来处理你的消息。

t=0s    发消息给节点 B
t=0s    B 的 JVM 开始 GC，整个执行停住
t=20s   你以为 B 已经死了（示意）
t=30s   B 收拾完垃圾，回来处理你的消息
考点：JVM GC 造成的失败模式，揭示"没响应"和"死了"分不清

这像打电话时对方突然不出声。你不知道是信号断了，还是对方在找东西。

四个核心设计问题

设计分布式数据库，绕不开四个问题。8:07

  1. 应用怎么找到数据？ 也就是连哪个节点。
  2. 资源怎么切分？ 也就是分区。
  3. 查询怎么执行？ 数据不在本地时，是推查询过去，还是拉数据过来。
  4. 怎么保证一致性和正确性？ 有些系统的回答是"我们不保证"。
SELECT * FROM orders WHERE id = 200;
-- 1. 连哪个节点？   2. 数据切在哪？
-- 3. 推查询还是拉数据？   4. 一致性谁来保证？
-- 考点：分布式系统的四个核心设计问题

踩坑：前面二十二讲的一切，在这里依然有效。 只是现在还要处理硬件异构。比如那个数据中心的节点核数更少，优化器和调度都得考虑。

2四种系统架构

难度 ★★★★★重要总览；清单只要 §3 §4 这两种的对比

四种架构的区别，只看 CPU、内存、磁盘三者归谁。11:16 这套术语来自 1980 年代。

架构 CPU 内存 磁盘 说明
Shared-Everything 本地 本地 本地 本学期前二十二讲讲的全都是这个。就是单机
Shared-Nothing 本地 本地 本地 节点之间只能靠网络发消息。不能直接读对方的内存或磁盘
Shared-Disk 本地 本地 全局共享 数据的最终归宿，在一个所有节点都能读写的存储上
Shared-Memory 无状态 全局共享 全局共享 只存在于学术文献里。Andy 不知道有哪个真实系统这么干，高性能科学计算除外 
Shared-Everything:  [CPU 内存 磁盘]                        -- 单机
Shared-Nothing:     [CPU 内存 磁盘] ~网络~ [CPU 内存 磁盘]
Shared-Disk:        [CPU 内存] [CPU 内存] → 共享存储
考点：四种架构的 CPU / 内存 / 磁盘归属，Shared-Memory 只存在于文献里

这像合租。Shared-Nothing 是各住各的，各有冰箱。Shared-Disk 是各住各的，共用一个大冰箱。

网络通常就是 TCP/IP。 少数用 UDP，个别玩 Mellanox / RDMA。

谁在用

老系统多是 Shared-Nothing，新系统多是 Shared-Disk。

架构 情况
Shared-Nothing Stonebraker 1986 年的论文力推。此后 20–30 年，分布式数据库都这么建。但因为云（S3）的出现，它正在衰落
Shared-Disk 过去十年绝大多数新系统都是这个，尤其是分析型

补充：界线会模糊（16:15 课堂提问）。Google Spanner 是 shared-nothing，但它读写的是 Borg 那套共享文件系统。

3Shared-Nothing

难度 ★★★★★必会清单明列它与 shared-disk 的对比

Shared-Nothing 里每个节点只管自己那份数据，要别人的数据只能发消息。16:58

应用 ──→ 目录 / 元数据服务（告诉你数据在哪）
          │
   ┌──────┴──────┐
   [节点 P1: id 1-150]   [节点 P2: id 151-300]
      └── 只能发网络消息 ──┘

查询 id = 200，直接发给节点 P2。本地处理完就返回，完美。

查询 id IN (100, 200)，先发给节点 P1。P1 知道拓扑，于是给 P2 发消息。要么说"你帮我跑这段查询"，要么说"把数据发过来我来跑"。细节见第 5 节。

优点：性能最好

每个节点只处理自己的数据，不用跨节点取数据。

这像各家用自己的冰箱。拿东西不用出门。

缺点：扩容要搬数据

Shared-Nothing 加节点，必须真的把数据搬过去。20:22

加一个新节点 → 必须【物理搬运】数据：从 A 和 C 各切一半过来
             → 然后更新目录

考点：shared-nothing 的优点是性能最好，核心缺点是扩容要搬数据

这像合租屋来了新室友。你得真的把柜子里的东西腾出一半。

踩坑：节点故障恢复，也是同样的问题。

三个重要的课堂问答

课上有三个问题值得记。应用要不要知道分区？目录是什么？索引怎么放？

问题 回答
应用需要知道数据范围吗？ 理想情况是不知道。 单机上能跑的 SQL，搬到分布式上应该一个字不改还能跑。 数据怎么切，对应用完全透明。
目录（catalog）是什么？ 就是另一个数据库。 除了表结构、约束，现在还要放分区方案和网络拓扑。你对应用数据要的那些事务保证，对目录数据同样要。
索引怎么办？ 每个节点持有自己那部分数据的索引。但二级索引可能和分区方式对不齐。 那就只能放在某个专门的节点上，或者在所有节点复制一份。 
SELECT * FROM users WHERE id = 200;   -- 单机能跑，分布式上一字不改也要能跑
-- 考点：应用不需要知道数据怎么分区，分区对应用透明
-- 考点：目录额外存分区方案和网络拓扑，也要事务保证

踩坑：有一段历史值得记（23:17）。MongoDB 在 2010 年代初火起来，很大程度上靠"自动分片（auto-sharding）"。 它能自动发现某个分片太满或太热。然后切一块出去，重新平衡。

但那是个彻头彻尾的 hack。 它不保证目录和搬完的数据是同步的。 于是两个节点上可能都有同一份数据。两个查询各自更新，结果全错。另一种做法是锁住整个数据库再搬。那也算一种"解决"。

搬数据：[101-150] 已经从 A 复制到 B（示意）
目录：  还没更新，仍说 [101-150] 在 A
查询 1 改了 A 上那份，查询 2 改了 B 上那份    -- 结果全错
考点：MongoDB 的自动分片为什么是个 hack，会导致什么后果

4Shared-Disk

难度 ★★★★★必会清单要和 shared-nothing 比，扩容是重点

Shared-Disk 里，数据都放在共享存储上，节点负责计算。26:04 本地 SSD 只当缓存。

   [节点A]  [节点B]  [节点C]      ← 各有 CPU、内存，本地 SSD 只当【缓存】
      └────────┼────────┘
    ┌──────────┴──────────┐
    │   共享存储（S3 等）   │      ← 数据的最终归宿
    └─────────────────────┘

这像公共图书馆。书都在馆里，读者来了借，走了还。读者换了人，书一本不少。

补充：数据湖和 Serverless 架构就长这样。 Snowflake、Databricks、Firebolt、Yellowbrick 全是这个形态。

扩容只需改目录

Shared-Disk 加节点，不用搬任何数据。

加新节点 → 【不用搬任何数据】，只在目录里做一次【逻辑分配】
        → "从现在起，这个范围归新节点负责"

考点：shared-disk 的结构，扩容为什么这么容易

存储无限

共享存储的容量，可以看成是无限的。Andy 的原话是这样的。

"想加容量，就给 Amazon 更多钱。你的信用卡会先刷爆，Amazon 的存储空间不会先用完。"

节点是无状态的

Shared-Disk 的节点是无状态的。

某个节点被杀掉或崩溃，数据一点不丢。因为最终归宿在共享存储上。

kill  node_b    -- 节点 B 崩了
start node_d    -- 新起一个节点，从共享存储接着读
考点：为什么说 shared-disk 的节点是"无状态"的

代价

Shared-Disk 的代价是：性能不如 shared-nothing，还得处理缓存一致性。

问题 说明
性能不如 shared-nothing 要走网络去别的设备取数据。OLTP 的缓解办法，是每个节点都缓存
缓存一致性 28:56 我更新了 page 101，别的节点也缓存着它。怎么让它们知道？

Andy 引导学生想了一个反例。

提议：让所有节点都能改任意数据
追问：那锁放哪？
回答：到处都是
结果：锁一个东西，要向所有人广播。这是好主意吗？
考点：shared-disk 的缓存一致性问题，"让所有节点都能改"错在要全网广播锁

所以才要有"某个节点是这份数据的主（primary）"这个概念。 改动先到主节点那里，再由它负责扩散。

这像一群人共用一份文档。谁都能改的话，每改一个字都得喊一嗓子。不如指定一个负责人，改动都先交给负责人。

5查询执行：推还是拉

难度 ★★★★★重要#24 分布式连接的铺垫；S3 案例不考

数据不在本地时，要么把查询推过去，要么把数据拉过来。32:19

做什么
把查询推到数据那边（Push） 切一段计划片段（plan fragment）发过去。那边算完，把结果发回来
把数据拉过来（Pull） 把字节通过网络复制到本地，当作本地数据来跑 
Push：发 "WHERE id BETWEEN 101 AND 200" 给节点 B，B 只回传结果
Pull：从 B 把整块数据拷过来，在本地算
考点：推查询和拉数据分别是什么，为什么说界线在模糊

推查询像请厨师上门做饭。拉数据像把菜买回家自己做。

补充：两者不互斥，而且界线正在模糊。因为存储层本身也开始能算了。

S3 Select 的故事

S3 Select 能让 S3 先在原地过滤数据。可惜新账号已经申请不到了。33:43

S3 曾有一个功能叫 S3 Select。 请求数据时，可以捎带一段 SQL。S3 会在数据所在的地方先做处理，只把结果子集发回来。

  • 好处：能做谓词下推，大幅降低网络出口（egress）费用。
  • 限制：做不了连接这类复杂计算。
  • 现状：老账号还能用，新账号申请不到了。
-- S3 Select：请求里捎带一段 SQL，S3 原地过滤（示意）
SELECT * FROM s3object s WHERE s.age > 30;
-- 考点：S3 Select 是什么，它的好处、限制、现状

Andy 的评价是这样的。

"作为数据库设计，我觉得砍掉它是个坏主意，这功能超有用。 但确实没多少系统真的在用它。"

有学生犀利地反问了一句（35:07）。

"这意味着你的数据库有一个核心组件，跑到你的掌控之外了。"

Andy 承认，这和整学期"别信任 OS"的说法冲突。 "我一直说别信操作系统，现在又说去信 Amazon 帮你做对事情。"

但账要这么算。 本地只有 20 核。如果能同时向 S3 发一千个并发请求，会怎样？那就相当于一千个核在并行过滤。

当然你要为此付钱。 自己算可能更便宜。但又得算上把 PB 级数据搬出 S3 的费用。 再加上本地 SSD 缓存的成本。全是权衡。

本地算：      20 核，不额外付钱，但要把数据搬出 S3
S3 Select：   一千个并发请求，相当于一千个核在过滤，按次付钱
考点：学生的反问是什么，Andy 怎么算这笔账

补充：不用 S3 Select，也能少读数据（37:07）。#15 谓词下推 / 投影下推、#13 Zone Map 全都还管用。

Parquet 文件的 footer 里就有元数据，约 1 MB。先读 footer，再决定要不要读文件其余部分。

"是 S3 还是本地磁盘，不改变任何原则。只是变难了。"

读 footer（约 1 MB 的元数据）
  → 看 Zone Map：这个文件里有没有符合条件的行？
  → 没有就整个跳过，有才读其余部分
考点：不用 S3 Select 也能少读数据，靠谓词下推、投影下推和 Zone Map

计划片段下推的例子

计划片段下推，就是让有数据的节点先算好，只回传结果。

        [节点A：最终合并结果]
              ↑ 只回传【局部连接的结果】
        ┌─────┴─────┐
   下推计划片段："帮我算 R ⋈ S 在 id 101–200 这段"
        ↓
   [节点B：本地有这段数据 → 算完 → 上传]

补充：在 shared-disk 下也一样。 只是 B 要先从共享存储，把数据拉进自己的缓存，再算。

关于 Parquet 的一段插曲

Parquet 的价值，是让应用绕过数据库，直接往 S3 写数据。43:13

有学生问："整学期都在讲自己的页格式，怎么突然说起 Parquet 了？"

Andy 的回答是这样的。 Parquet 只是一种开源列式文件格式。在云上的 shared-disk 分析系统里，它最常见。它的价值是：应用可以绕过数据库服务器，直接往 S3 写数据。数据库随后就能查它。

app → 把 events.parquet 写进 S3                     -- 不经过数据库服务器（示意）
db  → SELECT ... FROM 's3://bucket/events.parquet'   -- 随后直接能查
考点：Parquet 在分布式数据库里扮演什么角色，最关键的价值是什么
考点：定制格式只服务一个应用，通用数据库要找最低公分母

学生追问："自己定制的格式，不是永远更好吗？"（45:21）

Andy 的回答很有分量。 如果你只服务一个应用，当然可以定制到极致。 但数据库是通用软件。 你得找一个"最低公分母"，能覆盖足够多的应用，才卖得出去。

Parquet 是 2013 年的东西。 在当时它是最先进的，对手是 JSON 和 CSV。但它没跟上后来的压缩和列访问技术。 所以才有了 Vortex 这些新格式。

Snowflake 的战略选择

Snowflake 选了 shared-disk，把存储交给 S3，自己专心做计算。45:21 这是本讲最值得记的一段商业判断。

Snowflake 明确决定：我们不做 shared-nothing，我们做 shared-disk。

理由是，做 shared-nothing 就得自己造一套容错、同步的分布式存储。Snowflake 决定不干这件事。

"我们把一切建在 S3 上，前面加缓存来掩盖延迟。然后把公司全部工程力量，投入到把计算做到最快。Amazon 每把 S3 改进一点，我们就免费获益。"

存储：S3（容错、同步，Amazon 负责）
缓存：本地 SSD，掩盖延迟
计算：全部工程力量砸在这里
考点：Snowflake 为什么选 shared-disk，它和"别把控制权交出去"冲突吗

这像开餐馆租商场的铺面，不自己盖楼。省下的钱全花在厨师身上。

踩坑：这和"别把控制权交出去"的原则相反。但对分布式 OLAP，这是对的。 对创业公司来说，这是少造一个轮子。

对 OLTP 可能就不行了。 那里延迟是命门。

6分区

难度 ★★★★★必会清单明列分区方案，一致性哈希从它引出

分区分两种：Shared-Nothing 用物理分区，Shared-Disk 用逻辑分区。40:29

物理分区 逻辑分区
架构 Shared-Nothing Shared-Disk
含义 数据真的存在那个节点上 只是"当前由这个节点负责"。数据最终还在共享存储上

分区的粒度可粗可细。 细到按表的某几列，也就是分区键。粗到按文件。Snowflake 和 Yellowbrick 就是决定"哪个节点负责哪些 Parquet 文件"。

物理分区：node_a 的磁盘上，真的存着 id 1-100
逻辑分区：node_a 只负责 file_01.parquet，文件还在 S3 上（示意）
考点：物理分区对应 shared-nothing，逻辑分区对应 shared-disk

物理分区像把书分给每个人带回家。逻辑分区像书都留在图书馆，只分好谁负责哪几排书架。

表级分区（粗粒度）

表级分区就是一个节点负责一整张表，甚至一整个数据库。

踩坑：表大到单个节点装不下，就完蛋。 而且跨表查询很麻烦。

补充：但它有真实用例（50:17）。Andy 遇到过一个客户，有一张纯粹用来写日志的表。只插入，从不读。 这个客户把它单独放在一个节点上。插入能跑到最快，也不干扰其他节点的更新。

补充：另一种用法是复制小表。比如邮编表，才三万多条。 在每个节点上都复制一份，任何查询都能用本地副本。

有人问："那更新成本呢？" 回答是："美国邮政一年才更新四次邮编表。"

-- 邮编表在每个节点都有一份，连接时直接用本地副本（示意）
SELECT o.id, z.city FROM orders o JOIN zipcodes z ON o.zip = z.zip;
-- 考点：表级分区什么时候有用，"只写日志的表"和"邮编表"各说明了什么

水平分区（分片 Sharding）：最常见

水平分区最常见，就是在一张表内部按分区键切开。50:56

目标有两个：每个节点的数据量均衡，查询量也均衡。

踩坑：这两个目标可能冲突。 某个节点数据少但查询多，你就不该再往它上面塞数据。

方案 做法 常见度
哈希分区 hash(key) mod N 最常见
范围分区 按连续值区间切 常见
谓词分区 用 WHERE 子句定义归属 少见
轮转分区 轮流分配 少见 
int node = std::hash<int>{}(key) % N;   // 哈希分区：算出这条记录去哪个节点
// 考点：水平分区的两个均衡目标，它们可能冲突

这像按身份证尾号分窗口办业务。人数均匀了，但某个窗口的人可能事特别多。

哈希分区的两个问题

哈希分区有两个硬伤：范围查询只能广播，增删节点要大搬家。55:06

问题 说明
① 查询里没有分区键 只能广播给所有节点。就算有分区键，如果是范围查询也不行。哈希把连续值打散了
② 增删节点 mod 4 变成 mod 5，几乎所有数据的归属都变了 
// 4 个节点变成 5 个，key 的归属几乎全变（示意）
// key = 6:  6 % 4 = 2  →  6 % 5 = 1
// key = 7:  7 % 4 = 3  →  7 % 5 = 2
// 考点：哈希分区的两个问题，为什么范围查询也不行

踩坑：范围分区也有第二个问题。 加节点就要重新洗牌，而且影响面不局限于一个分区。

7一致性哈希与 Rendezvous 哈希

难度 ★★★★★必会HW6 Q3 直接考一致性哈希

这两种哈希专门解决一件事：增删节点时，尽量少搬数据。56:35

一致性哈希（Consistent Hashing）

一致性哈希把键空间画成一个环。键顺时针走，归给遇到的第一个分区。

把键空间画成一个从 0 到 1 的【环】
        ↓
hash(key) → 落在环上某一点
        ↓
顺时针往前走，遇到的第一个分区，就是它的归属

考点：一致性哈希怎么工作

所以，两个分区之间的那段弧，归后一个分区负责。

这像围着圆桌发牌。牌落在桌边某一点，顺时针数到的第一个人就收下它。

补充：一致性哈希出自 MIT 1997/98 年的论文（Chord 项目）。Amazon 在 2000 年代发 DynamoDB 论文时，说自己用的就是它。 随后，2010 年前后那批 NoSQL / shared-nothing 系统全跟进了。

Andy 现场调查了一下，不到一半的学生听说过它。

加节点时会发生什么

加一个节点，只有相邻那一段弧的数据要搬。

在 P3 和 P2 之间插入新分区 P4
        ↓
只需要把【从 P2 顺时针到 P4 这段弧】的数据从 P3 搬到 P4
环上其他所有分区【完全不受影响】

考点：加节点时为什么只影响一个分区
考点：数据不均衡，用虚拟分区解决

踩坑：课堂上有人问：数据会不会不均衡？ 办法是用虚拟分区。让环上很多个点，都映射到同一个物理节点。点足够多，分布就足够均匀。除非数据本身极度倾斜。

环还能顺便管复制

环还能顺便决定副本放哪：顺时针接着往下走就行。1:00:07

hash(key) 落在 P1 → 主副本在 P1
        ↓ 顺时针继续走
副本放到 P6 和 P2（想要 3 副本就取接下来 2 个）

考点：环怎么顺便处理复制，哪些系统在用，哪个系统的 logo 泄露了这一点

查询时，这三个副本里任意一个都能读。 但它们同步不同步，是另一回事，见第 8 节。

用一致性哈希的系统有：Snowflake（分配文件给 worker）、Couchbase、Cassandra、Riak。

补充：有个细节。Riak 的 logo 就是一个环，加上向外辐射的副本。 这等于明示自己用一致性哈希。

踩坑：注意，DynamoDB 在四五年前的后续论文里，已经宣布不用它了。

Rendezvous 哈希（最高随机权重）

Rendezvous 哈希让 key 和每个节点各算一次哈希。分数最高的节点拿走它。1:02:16

对每个 key，和【每个节点 ID】拼在一起分别做哈希：
    hash(key + "node1") = 0.71
    hash(key + "node2") = 0.93   ← 最高
    hash(key + "node3") = 0.12
        ↓
归属：node2

考点：Rendezvous 哈希怎么工作，它和一致性哈希是什么关系

加节点时，重算一遍。 只有"新节点排到第一"的那些 key 才需要搬，其余不动。

这像几家公司抢人。每家都给求职者出个价，出价最高的那家拿走这个人。新公司进场，只抢走它出价最高的那些人。

补充：它其实比一致性哈希早一年发表。而且理论上，一致性哈希是 Rendezvous 哈希的一个特例。

踩坑：课上说 Rendezvous 查找是 O(log n)，一致性哈希是 O(n)。这说反了。

上面这种基础 Rendezvous，要和每个节点都哈希一遍，是 O(n)。一致性哈希把节点排成有序的环，再二分查找，是 O(log n)。Rendezvous 要做到 O(log n)，得用分层的变体。

for (auto &n : nodes) score[n] = Hash(key, n);   // 基础 Rendezvous：每个节点算一遍，O(n)
auto it = ring.lower_bound(Hash(key));           // 一致性哈希：有序环上二分，O(log n)
// 考点：查找复杂度一致性哈希更好，课上说反了

8复制

难度 ★★★★★必会清单明列复制配置

世界上绝大多数"分布式数据库"，其实是单机 shared-everything 加复制。1:05:03

primary（单机 shared-everything）
   └── 改动 → replica1, replica2
考点：世界上绝大多数"分布式数据库"其实是什么形态

这像一个店长带几个影子店员。店长拍板，影子照抄。

复制有四个设计维度。

① 副本配置

最常见的是主-副本：所有写先到主节点，再由它扩散。

方案 说明
主-副本（Primary-Replica） 最常见。每个对象有一个主节点。所有写必须先到主节点，再由它扩散给副本。主挂了，要跑领导者选举
多主（Multi-Primary） 任意节点都能写，然后解决冲突。少见

补充：领导者选举本身，看起来就像一次事务。 有一张表记录"每个对象的主是谁"，用一个事务原子地更新它。Paxos / Raft / 两阶段提交就用在这里，见 #24。

主-副本的典型用法：读写都走主库。但只读查询可以分流到副本，让主库专心处理写。

INSERT INTO orders VALUES (...);   -- 写：必须先到主库
SELECT * FROM orders;              -- 只读：可以分流到副本，但可能读到旧数据
-- 考点：主-副本和多主的区别，领导者选举本身像一次事务

这像班长收作业。大家都交给班长，班长再抄送给各组长。

踩坑：代价是，副本上可能读到过期数据。

② K-Safety

K-Safety 规定：存活副本少于 K 个，就停止接受更新。

K 是系统保持可用所需的最少存活副本数。

副本掉到 K 以下，就停止接受更新。 宁可停机，也不要写进去然后丢掉。

if (alive_replicas < K) RejectWrites();   // 宁可停机，也不要写进去然后丢掉
// 考点：K-Safety 是什么，副本不够时系统该怎么办

这像飞机的最低起飞条件。能用的发动机少于规定数，宁可不飞。

③ 传播方式：同步 vs 异步

同步复制要等副本确认，安全。异步复制不等，可能丢数据。1:11:26 这是本节最重要的权衡。

同步（强一致） 异步（最终一致）
流程 主库改动，发给副本。等副本确认"已落盘"，才告诉应用"提交成功" 主库改动，发给副本。立刻告诉应用"提交成功"，不等
安全 安全 存在窗口。你说提交成功了，然后主库被抹掉，日志也没了。改动根本没传出去
谁用 在乎数据的系统 NoSQL 那批人。理由是"我们不想等事务提交"。NoSQL 本来也没有事务的概念 
同步：commit → 发给副本 → 等副本确认落盘 → 回复应用   -- 安全，要等
异步：commit → 回复应用 → 发给副本                     -- 快，主库一挂就可能丢
考点：同步和异步的流程和风险，NoSQL 选了异步，折中是等多数副本

同步像挂号信，签收了才算寄到。异步像平信，投进邮筒就当寄到了。

补充：有一个实用折中。一主三副本，只要两个副本确认就放行，不等第三个。

④ 传播时机

多数系统边执行边推改动，提交时只发一条 commit。

方案 说明
连续（Continuous） 多数系统用这个。事务执行期间就不断把改动推给副本，提交时只发一条 commit
提交时（On Commit） 全部攒在主库，提交时一起发。等待更久，但不用让副本回滚任何东西 
连续：   UPDATE → 推   UPDATE → 推   COMMIT → 只推一条 commit
提交时： UPDATE   UPDATE   COMMIT → 一次推全部
考点：连续传播和提交时传播各有什么优缺点

9分布式控制：集中式 vs 去中心化

难度 ★★★★★重要#24 协调者的铺垫，作业和清单都没列

只碰单个节点的事务很简单，各自跑本地并发控制就行。1:15:49 难的是跨节点的事务。

UPDATE accounts SET bal = bal - 100 WHERE id = 1;     -- 在 P1（示意）
UPDATE accounts SET bal = bal + 100 WHERE id = 250;   -- 在 P3
-- 两条要么都成，要么都不成，这就要跨节点协调

单节点事务像自己家里记账。跨节点事务像两家银行之间转账，得有人居中对账。

① 集中式协调者

集中式协调者手握全局锁表。事务要锁、要提交，都得先问它。

应用 ──① 请求锁──→ [ 协调者 ] ←── 维护全局锁表和事务视图
     ←──② 授予────┘
     ──③ 直接发查询给各分区──→ [P1] [P2] [P3]
     ──④ 请求提交──→ [ 协调者 ] ──询问各分区"能提交吗"──→ [P1][P2][P3]
     ←──⑤ 允许提交──┘

考点：集中式协调者的流程，TP Monitor 的 "TP" 原本是 Telecom Processing

补充：在 1980-90 年代，分布式数据库就是这样造的。那些产品叫 TP Monitor。

词源很有趣。TP 最初指 Telecom Processing（电信处理）监视器。 后来这个缩写，被改成了 Transaction Processing（事务处理）。

1990 年代还标准化了一个协议，叫 Open XA。 有了它，一个 TP Monitor 能同时协调 Oracle、TimesTen、NonStop SQL 上的分布式事务。各系统跑各自的本地协议。

代表产品有三个。BEA，被 Oracle 收购。Transarc，出自 CMU 的 Andrew 项目，被 IBM 收购。还有 Omid，跑在 HBase 上。

② 中间件（更常见的变体）

中间件把所有查询都揽过来，对应用假装自己是一个数据库。

应用 ──→ [ 中间件 ] ──→ [P1] [P2] [P3]
          ↑ 所有查询都走它，由它路由 + 管锁表
    对应用来说，它看起来就是【一个】数据库实例

考点：中间件方案是什么，Google 和 Facebook 分别怎么用它

这像酒店前台。客人只跟前台打交道，不知道后面有几个仓库。

补充：在 Spanner 之前，Google 分片 MySQL 就是这么干的。

Facebook 今天仍然这么干。 它跑着世界上最大的 MySQL 集群。 靠中间件，整个集群看起来像一个逻辑数据库。

③ 去中心化协调者

去中心化协调者没有固定的老大。谁来协调，靠领导者选举临时决定。

事务可以在任意节点发起 → 通过领导者选举决定谁来协调
        ↓
提交时，由该领导者去和涉及的分区确认"能不能提交"

踩坑：这种方式没有全局的事务视图。

联邦数据库（Federated Database）

联邦数据库是中间件的一个变体。1:21:34 下面挂的不是同一种数据库。 而是 MySQL、PostgreSQL……各种系统，中间件把它们伪装成一个。

现实中，Trino / Presto 的 connector、PostgreSQL 的 foreign data wrapper，大致做的就是这件事。

-- PostgreSQL 的 foreign data wrapper，把 MySQL 的表挂进来（示意）
SELECT * FROM mysql_orders WHERE id = 1;
-- 理想：下推成 MySQL 上优化过的 WHERE id = 1
-- 现实：常常退化成 SELECT *，把数据全抽上来
-- 考点：联邦数据库是什么，Andy 为什么说它效果不好，核心困难是什么

这像一个翻译同时对接十种语言。最后只能用大家都懂的几个词，说不了细话。

Andy 的评价：不常见，而且效果不好。这想法从 1990 年代就有了。

核心困难在于下推。 理想情况下，谓词和投影都能下推。每个目标系统拿到的，都是为它优化过的查询。但往往做不到。最后退化成 SELECT *，把数据全抽上来。

1一个关键前提：非拜占庭

难度 ★★★★★重要Paxos 成立的前提，不单独考

本讲默认所有节点都归我们管，而且都守规矩。9:18 现实工程里也是这么假设的。

Vote v = node->Prepare(txn);   // 节点回了 OK
// 回了 OK，就不会反悔，也不会偷偷捣乱

// 考点：节点之间不能互信时，要换成拜占庭容错（BFT）协议

这就像同一个公司的同事开会。有人会请病假，但没人会故意投假票。

"行为良好"不是说硬件不会坏。硬件当然可能坏。它说的是，没人在跑一个恶意改造过的数据库版本。一个节点说它同意提交，就不会反悔，也不会捣乱。

节点之间不能互信怎么办？那就得上拜占庭容错（BFT）协议。

Andy 对区块链的评价

区块链跑的就是本讲这套事务，只是它不信任别的节点。9:56 所以它要额外背上一堆东西。

区块链 = 本讲的事务
       + BFT 协议，让多数派达成一致
       + Merkle 树
       + 不可篡改的账本（其实就是不可回退的预写日志）
考点：Andy 说这门课只记两件事就够，数据库别用 mmap，也别用区块链数据库

这好比每次转账都要全村人当面点钞。安全是安全，就是太慢。

"任何真实系统都不会跑在区块链上。因为它比今天讲的东西慢 5 到 10 倍。"

"如果这门课你只记住两件事：① 数据库里别用 mmap。② 别用区块链数据库。"

2原子提交协议

难度 ★★★★★必会HW6 Q3 判断题考 2PC / Paxos 保证强一致

原子提交协议（Atomic Commit Protocol）就是分布式系统里的共识协议（Consensus Protocol）。11:47 两个名字，说的是同一个东西。

分布式系统的人管它叫"状态机"。我们关心的状态，就是事务的提交顺序。定好顺序，写进日志。谁按这个顺序重放，都能得到同一个状态。

log = [T1 commit, T2 commit, T3 abort]   // 大家先对这个顺序达成一致（示意）
replay(log) on node A  ->  state S
replay(log) on node B  ->  state S       // 按同一顺序重放，结果必然一样
// 考点：原子提交协议就是共识协议，数据库里的状态就是事务的提交顺序

这像几个人各自照着同一份菜谱做菜。步骤顺序一样，端出来的就是同一道菜。

踩坑：不管数据是被复制的，还是被分区的，都要跑这个协议。

协议家族

事务的状态机

事务一旦走到"已提交"或"已中止"，所有节点都认，谁也不能反悔。

        [ 工作中 Working ]
              │ 应用发出 COMMIT 请求
              ↓
        [ 准备中 Preparing ]
           ↙        ↘
   [ 已提交 ]      [ 已中止 ]     ← 终态：一旦到达，【所有节点同时认可，不可反悔】

考点：终态一旦到达，所有节点同时认可，不能反悔
考点：活性假设只保证时间在前进，不保证事务能提交

这像比赛的终场哨。哨声一响，比分就定了，谁也改不了。

踩坑：活性（liveness）假设是说，总有足够的节点活着。系统因此能往前推进。它不代表事务一定能提交。可能一直有节点掉线，事务不断中止。但时间总在前进。

中止的流程

只要有一票反对，协调者立刻中止，也立刻告诉应用。

第一阶段：节点1 说 OK，节点2 说 ABORT（比如违反了完整性约束）
        ↓
【立刻】切到中止阶段，不等节点3 投票了（反正必须全票）
        ↓
【立刻】告诉应用"已中止"，不等各节点确认清理完
        ↓
各节点陆续回报"已中止"

考点：提交走两阶段全票，中止只要一票反对

这像拼单点外卖。只要有一个人退出，单就拼不成，不用等剩下的人表态。

有节点不回话，协调者只能干等到超时，然后中止。21:24

第一阶段：节点1、节点3 说 OK，节点2 【没有回应】
        ↓
协调者只能【等】，直到超时
        ↓
超时 → 自动切到中止阶段 → 告诉应用"已中止"

考点：2PC 的致命伤是一个节点挂了，全体都得等
考点：挂了和卡住了分不清，所以要有应用层心跳

踩坑：这就是 2PC 的致命伤。一个节点挂了，整个系统就得卡在那儿等。

踩坑：而且"挂了"和"卡住了"分不清。想想 #23 那个 JVM GC 的例子。ping 得通，那是硬件层。但数据库软件三十秒不响应。 所以还需要应用层的心跳。

三个课堂问答

这三个问答，把 2PC 最容易想歪的地方过了一遍。

问题 回答
"已中止"要先告诉应用，还是先等节点确认？ 先告诉应用，让它早点去准备重试。对正确性没影响，只是微秒级差别
既然要中止，为什么还要收"已中止"的确认？ 为了留痕。 万一协调者崩了再起来，得知道这些节点到底被通知过没有。没有确认，就无从判断
第二阶段有个节点说"不"呢？ 那个节点被视为故障，应该崩掉。事务仍然是已提交的，因为第一阶段全票通过了。系统要另起一个节点替代它。新节点重放日志，学到"这个事务已提交" 
phase1: all OK               -> 事务已经定为提交
phase2: node2 says NO        -> node2 按故障处理，崩掉
replace(node2); replay(log)  -> 新节点从日志里学到"已提交"
// 考点：收"已中止"的确认是为了留痕，协调者重启后才知道谁被通知过
// 考点：第二阶段有节点说"不"，事务照样算提交

这像全票通过的决议。事后有人反悔，决议照样生效，反悔的人自己出局。

崩溃恢复

谁崩了，就看它崩在哪个阶段。协调者崩了，最省事的办法是直接中止。

谁崩了 怎么办
参与者在 prepared 状态崩了 起来后问协调者：这个事务后来怎么样了？
参与者还在运行中就崩了 该事务中止
协调者崩了 最简单的做法：把事务中止，然后选一个新协调者。 理论上，可以让参与者们自己重组，查明是不是本来该提交。但多数系统不干。因为重组期间谁都不能提交新事务，不划算 
void OnCoordinatorCrash(Txn *txn) {
  Abort(txn);              // 最简单：直接中止
  ElectNewCoordinator();   // 再选一个新协调者
}
// 考点：多数系统不去聪明地重组，因为重组期间谁都不能提交新事务

这像会议主持人中途离场。最省事的办法是这场会作废，换个人重开。

42PC 的两个优化

难度 ★★★★★重要记住两个优化即可，作业和清单都没列

两个优化都是为了让应用少等一会儿。29:31 一个罕见，一个常见。

① 提前投票（Early Prepare Voting）：罕见

提前投票是在最后一条查询上，顺手捎带投票请求。这招很少用。

发最后一条查询时【捎带】："这是我最后一条了，顺便把提交票投给我"
考点：提前投票的前提是应用能确定地说出"这是最后一条"

这像点完最后一道菜，顺手就把单买了。

踩坑：前提是应用必须能确定地告诉系统"这是最后一条查询"。不能是猜测。 存储过程可以做到，因为所有逻辑都在数据库里。

② 提前确认（Early Acknowledgement）：常见

第一阶段一过全票，就立刻告诉应用"已提交"。这招很常见。

标准 2PC：第一阶段全票 → 跑完第二阶段 → 才告诉应用"已提交"
提前确认：第一阶段全票 → 【立刻】告诉应用"已提交" → 再去跑第二阶段
考点：提前确认之后，第二阶段照样要跑

这像快递显示"已签收"，其实还在楼下往上送。单号登记好了，基本不会丢。

理由：只要日志记好了，"最后没能提交成"的概率极低。

踩坑：第二阶段还是要跑。而且这个事务提交完之前，不能提交别的事务。

一个被反复追问的边界情况

  1. 用 Paxos 做领导者选举时，可以忽略少数派。 那种场景不会有完整性冲突。
  2. 用 Paxos 做事务提交时，情况不同。 如果真会产生完整性冲突，就得在事务运行中检查掉。不能拖到提交阶段。

if (!DryRun(txn)) return Abort(txn);   // 先空跑一遍：不改数据，只查约束

// 考点：多数派通过但掉线节点本该反对，所以约束要在运行中查完

这像出门前先查好证件。到了登机口才发现过期，已经来不及了。

补充：DynamoDB 的"侦察事务"就是干这个的（#19）。先把查询跑一遍，但不真改数据。 这时就能发现约束违规。提交时才真正应用改动。于是提交阶段不会再冒出完整性冲突。

        ↓
之后【只有 leader】能提议提交事务
        ↓

Spanner 约 10 秒
CockroachDB 约 5 分钟

租约像会议室预订。到点不续，别人就能订走。

踩坑：为什么要定期续租？因为你得知道 leader 还活着没有。续得太勤，时间全花在选举上。续得太稀，leader 挂了要等很久才发现，事务全卡住。

两个节点同时想当 leader 怎么办？用指数退避。被拒了就等 50 毫秒，再被拒就等 100 毫秒，以此类推。

int wait_ms = 50;
while (!TryBecomeLeader()) {
  SleepMs(wait_ms);   // 被拒了就等一会儿
  wait_ms *= 2;       // 50, 100, ... 一次比一次等得久
}
// 考点：租约大约是 Spanner 10 秒，CockroachDB 5 分钟，TiDB 10–15 秒

补充：大家都不是恶意的。只是需要一个简单机制，让节点们错开。

Raft

Raft 高层看和 Multi-Paxos 一样，只差两点。

  1. 领导者选举看"谁的日志最新"。 日志最全的，最有资格当 leader。
  2. 课上说"学习者"改叫"追随者（Follower）"。这个对应不准。Raft 的追随者会投票。选 leader 时投票，日志也要多数派确认。所以它更接近 Paxos 的接受者，不是没有投票权的学习者。
// Raft 选主（示意）：日志最全的最有资格
if (candidate.log_newer_or_equal(my_log)) VoteFor(candidate);
else Reject(candidate);
// 考点：Raft 选主看谁的日志最新，追随者会投票
// 考点：Raft 更流行，是因为开源实现多

这像选班长，只选笔记记得最全的那位同学。

7CAP 定理

难度 ★★★★★必会HW6 Q3 直接考网络分区时的取舍

CAP 说的是一致性、可用性、分区容忍，三个最多只能占两个。49:10

pick(C, A, P)  ->  最多拿两个
网络真断了     ->  只能在 C 和 A 里二选一（见下面两种选择）
// 考点：C 是一致性，A 是可用性，P 是分区容忍
// 考点：Andy 的类比是挑对象，好看、聪明、不疯只能得其二

CAP 是 Eric Brewer 在 1990 年代末提出的。Brewer 是伯克利教授。当时 Brewer 在创业，团队需要推理分布式系统的各种状态。

三个属性，最多取其二：

字母 含义
C 一致性（Consistency） 提交后，任何副本上都能立刻读到
A 可用性（Availability） 有节点挂了，系统照样服务
P 分区容忍（Partition Tolerance） 网络断了还能工作

Andy 的类比："就像挑对象。好看、聪明、不疯，三者只能得其二。"

真正的问题：网络分区时怎么办

网络一断，两边各自选主，就会冒出两个主库。50:32 这就叫脑裂。

主库 ─────╳──────  副本            ← 网络断了
  │                 │
  │                 └→ "主库肯定挂了" → 选举 → 【我现在是主库】
  └→ "我还是主库"

        ↓ 两边各自接受写入并提交
        ↓ 网络恢复
两个"主库"都认为自己有最新数据，而两边的事务都已经对外宣称提交成功了

考点：脑裂是网络断开后，两边各认一个主库，各自提交

这像一个班被分在两间教室，各选了一个班长。合班时才发现，两边发的通知不一样。

踩坑：这就是脑裂（split brain）。

两种选择

网络分区时，传统关系库选一致性，NoSQL 选可用性。

选择 做法 谁选
保一致性 失去多数派就宣布系统不可用，禁止一切修改。只读查询还可以跑。等节点回来、凑够多数派再恢复 所有传统关系数据库和新一代 Distributed SQL 系统
保可用性 两边都继续读写，恢复后再合并 NoSQL 那批人

怎么合并：

方法 说明
最后写入者胜（Last Writer Wins） 比时间戳，最新的赢。多数 NoSQL 用这个
向量时钟（Vector Clocks） 读的时候把整条版本链返回给客户端。由客户端自己决定该用哪个版本 
node A: x = 1 @ t=100                  // 示意时间戳
node B: x = 2 @ t=105
merge(Last Writer Wins) -> x = 2       // 比时间戳，最新的赢
merge(Vector Clocks)    -> 两个版本都返回，客户端自己挑
// 考点：分区时传统关系库保一致性，NoSQL 保可用性
// 考点：Andy 反对向量时钟，因为普通程序员不会推理不一致的状态

最后写入者胜，像两份草稿以最后保存的为准。向量时钟，像把两份草稿都塞给你，让你自己去对。

Andy 对向量时钟的评价：Riak 用过。别这么做。

"你那位普通的 JavaScript 程序员，根本不知道向量时钟是什么。也不会推理数据库状态的正确性。"

"你还不如干脆骗程序员说'最后写入者胜'。把问题留到以后处理。或者干脆停机，等节点齐了再说。"

8PACELC：把延迟也算进来

难度 ★★★★★了解CAP 的补充，作业和清单都没提

PACELC 在 CAP 上加了一维：延迟。55:54 它是 2010 年提出的，因为 CAP 太简化了。

CAP 没覆盖这个权衡：我可以一直等到系统恢复，来保证一致性。但那样延迟就是几分钟甚至几小时，不现实。

主库改了数据 → 发给两个副本（在不同的数据中心）
        ↓ 主库该等多久？
   不等      → 延迟低，但没有一致性保证
   等一个    → 折中（另一个可能在大洋彼岸）
   等全部    → 强一致，但延迟高

考点：PACELC 比 CAP 多了延迟这一维，因为一直等着保一致性不现实

这像寄东西。挂号信要等对方签收，明信片丢进邮筒就走。

踩坑：实践中会设超时。到点还没等到，就要决定：是中止事务，还是接受一个临时状态。

补充：判断标准还是那句老话。银行账户要一致性，别丢钱。Reddit 上的帖子，晚几秒谁在乎。

Facebook 那个经典的"障眼法"

Facebook 早期把用户刚发的动态存进 cookie，假装数据已经到位了。58:36

Facebook 早期只有一个主数据中心，在美国。所有写入都要打到美国，再复制到各大洲的 MySQL 集群。

后果：南美用户发一条动态，写请求跑到美国。数据还没复制回南美的数据中心。用户刷新页面，看不到自己刚发的东西，以为坏了。

user.Post(msg)          -> 写请求打到美国的主数据中心
user.Refresh()          -> 南美的 MySQL 还没复制到，看不到
cookie.Save(msg)        -> Facebook 的解法：先存进浏览器 cookie
Render(cookie.msg)      -> 刷新时从 cookie 读出来显示
// 考点：一致性问题可以在应用层掩盖掉，换来更低的延迟

这像餐厅先给你上一盘凉菜。后厨还没开火，你已经觉得菜上了。

补充：Facebook 的解法是把这条动态存进用户浏览器的 cookie 里。刷新时从 cookie 读出来，显示给用户看。用户以为一切正常，实际上数据还没传播到位。

Facebook 后来改成了多主架构。但这个技巧有个启示。一致性问题可以在应用层掩盖掉，换来更低的延迟。

9分布式连接

难度 ★★★★★必会HW6 Q3 直接考，清单明列

分布式 OLAP 里最贵的算子就是连接，诀窍是少搬数据。1:00:00

SELECT * FROM R JOIN S ON R.id = S.id;
-- 最蠢：把 R 和 S 全拷到一个节点，再用单机算法算
-- 正确：先把数据搬到位，再在每个节点上跑本地连接
-- 考点：#12 的嵌套循环、哈希、排序归并，一个都没变

这像几个仓库对账。能各自先对，就别把账本全寄到总部。

踩坑：最蠢的做法，是把所有数据复制到一个节点。然后用单机算法算。并行度全丢了，而且可能一个节点根本装不下。

目标是尽量少传数据。然后在本地跑我们学过的那些连接算法。 #12 的嵌套循环、哈希、排序归并，一个都没变。

情形 ①：一张表分区，另一张表全复制 最简单

小表每个节点都有一份，所以每个节点就地连接，零传输。

R 按 id 分区（大表）
S 在【每个节点上都有完整副本】（小表，比如三万条的邮编表）
        ↓
每个节点用本地数据算局部连接，零数据传输
        ↓
各节点把局部结果发给指定的协调节点 → UNION（就是拼字节，很便宜）→ 返回

踩坑：更新那张复制表时，要跑 2PC / Paxos。但那不常发生。

情形 ②：两张表都按连接键分区 也很简单

两张表都按连接键分区，只要分区边界对齐，同样零传输。哈希分区则天然对齐。本地算完再合并就行。

node1: R[id 1..100]    S[id 1..100]      // 分区边界对齐（示意）
node2: R[id 101..200]  S[id 101..200]
-> 每个节点本地连接，再合并，零传输
// 考点：情形 ① ② 零传输，是因为要配对的元组本来就在同一个节点

这像两个班的花名册，都按同样的学号段分好了。同一段的人，本来就在同一间教室。

情形 ③：没按连接键分区：麻烦来了

表没按连接键分区，就得先搬数据再连接。

踩坑：这很常见。建表时选的分区键，当时看着合理。后来用户开始用你没预料到的方式做连接。

广播连接（Broadcast Join）

广播连接就是把小表复制到每个节点，退化成情形 ①。

识别出其中一张表【足够小】
        ↓
把它【复制到每一个参与连接的节点】
        ↓
退化成情形 ① → 本地连接 → 合并

考点：一张表足够小时用广播连接
考点：broadcast join 只是修饰词，准确说是 broadcast hash join

这像开会发讲义。一页纸的讲义，复印给每人一份最省事。

补充："广播"只是个修饰词。底下还是某种基本连接算法。所以准确说是 broadcast hash join 或 broadcast sort-merge join。但大家嘴上说"broadcast join"时，通常指哈希连接。

踩坑：shared-disk 下还有个成本问题（1:05:29）。理论上，每个节点都可以自己去共享存储取。但 S3 按读取次数收费。让 50 个节点各读一遍同一份数据，是在浪费钱。 更便宜的做法是一个节点读，再广播出去。或者用 S3 之外的本地缓存。

Shuffle 连接（Shuffle Join）

两张表都太大，又都没按连接键分区。这时就按连接键现场重新分区。

按连接键【在线重新分区】
        ↓
R：每个节点把自己那份按新的连接键 hash / range 切开，发给对应的节点
S：同样处理
        ↓
退化成情形 ② → 本地连接 → 合并

考点：shuffle 连接和 MapReduce 是同一个东西，但分布式数据库早得多

这像全校按学号重新分座位。每个人去对应的教室，到齐了再点名。

补充：同理，准确说法是 shuffle hash join。

有学生问："这不就是 MapReduce 吗？"1:07:39 Andy 说是同一个东西，但分布式数据库比 MapReduce 早得多。

"MapReduce 出来的时候，大家惊呼开天辟地、前所未见。这是 80、90 年代的分布式数据库就有的东西。map 函数基本就是一次 GROUP BY 加排序。"

10半连接

难度 ★★★★★必会清单明列半连接，含 Bloom Filter 版

半连接不搬整份数据，只搬计算连接所必需的最少信息。1:08:22

SELECT d.*, f.price                           -- 示意表名
  FROM fact f JOIN dim d ON f.zip = d.zip
 WHERE d.zip = '15213';
-- 维度表的列全都要，事实表只要 price 一列，别搬整条元组

这像找人。先把名单发过去让对方点名，别把整栋楼的人都叫过来。

先补两个概念（#25 详讲）：

含义
事实表（Fact Table） 巨大。比如"每一笔亚马逊订单"，一行一笔
维度表（Dimension Table） 小的、通常只读的旁表。比如商品名、描述、邮编

流程

先在维度表那边筛，再把筛剩的一小撮发过去，过滤事实表。

① 在【维度表所在节点】先跑一个子查询：筛出 zip = '15213' 的记录
        ↓ 只把这一小撮发过去
② 【事实表所在节点】用它做过滤，挑出真正需要的行
        ↓ 而且只带走【需要的列】（投影下推）
③ 把这一小份发回去，才真正计算连接

考点：半连接只搬算连接必需的最少信息，例子是事实表连维度表

踩坑：关键在于看清最终输出要什么。例子里，维度表的列全都要，但事实表只要 price 一列。那就别搬整条元组。 这是 #15 谓词/投影下推 在分布式场景的用法。

更狠的优化：发 Bloom Filter

第 ① 步别发记录列表，改发一个 Bloom Filter。1:10:28

Bloom Filter 在网络上传输极其紧凑。对面拿它做过滤，再把结果发回来。

这就是 #12 Bloom Join 在分布式环境下的完全体。

BloomFilter bf = BuildFilter(dim_rows);   // 维度表那边建过滤器
Send(fact_node, bf);                      // 发出去的只是一小串位
auto hits = fact_node.Probe(bf);          // 事实表那边过滤完，再把结果发回来
// 考点：更狠的半连接是发 Bloom Filter，不发记录列表
// 考点：半连接由优化器自动决定，SEMI JOIN 不在 SQL 标准里

这像寄一张小纸条，代替寄一整本名册。

补充：谁来决定用半连接？优化器自动决定。 有些系统在 SQL 里提供 SEMI JOIN 算子。但它不在 SQL 标准里。 上面那个例子的 SQL 里，并没有写半连接。是优化器自己推出来的，还连带做了谓词和投影下推。

11Shuffle：真正的瓶颈

难度 ★★★★★重要#14 Exchange 的分布式版，作业和清单没列

分布式 OLAP 里真正最贵的是 shuffle，不是连接本身。1:11:10 这是 Andy 的自我更正。

cost(join) = cost(shuffle) + cost(local join)
             ^^^^^^^^^^^^^ 大头在这里：数据要过网络
// 考点：Andy 更正说，连接里真正最贵的是 shuffle 阶段

这像做饭。最费时的不是炒，是去菜市场买菜。

"我刚才说连接是分布式 OLAP 里最贵的东西。这不完全是实话。真正最贵的是 shuffle。"

你之所以要 shuffle，是因为要做连接。所以技术上讲是连接最贵。但在连接内部，shuffle 阶段才是最大的瓶颈。 你在把数据拷贝到网络上，送到别处去。

Shuffle 的第二个作用：解决倾斜

shuffle 还能把倾斜的数据重新摊平。

before: node1 = 90%   node2 = 5%    node3 = 5%    // 示意比例
shuffle ->
after:  node1 = 33%   node2 = 33%   node3 = 34%
// 考点：shuffle 除了搬数据，还能解决数据倾斜

这像超市收银。一个窗口排长龙，就把人分到空着的窗口去。

踩坑：如果数据高度倾斜，某个节点握着绝大部分数据。别的机器全在闲着等它。

shuffle 阶段能把数据重新分布、重新平衡。 之后每个节点都只处理本地数据。

两种使用策略

多数系统偶尔才插 shuffle，BigQuery 在每个阻断点都插。

策略 系统
偶尔用一次。只有 shuffle join 之类，才插入 shuffle 算子 多数系统
每个流水线阻断点都显式插入一个 shuffle BigQuery。这样能在查询运行中途决定要更多还是更少的节点。shuffle 被当成中间检查点 
scan → shuffle → agg → shuffle → join → shuffle → ...   // BigQuery 的做法
// 每到一个 shuffle，就能重新决定下一段用几个节点
// 考点：BigQuery 把 shuffle 当中间检查点，还为它上了专用硬件

架构

shuffle 层夹在两批 worker 中间。前后两批 worker 的数量可以不一样。

第一阶段 workers（从本地盘 / 共享盘读数据、处理）
        ↓ 按分区键 hash，mod shuffle 节点数
   [ shuffle 节点 ]  ← 内存不够就溢写到共享存储
        ↓ 前后两阶段的 worker【不必一一对应】
第二阶段 workers（数据变少了？那就只用 3 个 worker）

考点：shuffle 层把"怎么搬数据"抽象掉了，本地用普通哈希连接就行

shuffle 层像快递分拣中心。寄件人不用知道收件人在哪，交给分拣中心就行。

补充：shuffle 层把"怎么搬数据"这件事抽象掉了。 所以不需要专门写一个"分区感知"的哈希连接算子。只要 shuffle 完了，每个节点用普通的本地哈希连接就行。
