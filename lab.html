2你需要的 C++ 知识

后面四个 Project 的代码，全都建立在 RAII 上。资源跟着对象走，对象一销毁，资源自动归还。

class ReadPageGuard {
  ReadPageGuard(const ReadPageGuard &) = delete;   // 禁止拷贝
  ReadPageGuard(ReadPageGuard &&that) noexcept;    // 允许移动
  ~ReadPageGuard();                                // 析构时自动解 latch、unpin
};
// 考点：P1 的 page guard 是 RAII 的典型应用，必须可移动、不可拷贝

RAII 像酒店的房卡取电。人一走，卡一拔，灯和空调自动断电。你不用记着挨个去关。

必须熟练

下面这些，写 P1 之前就要用顺手。

主题 为什么后面用得到
智能指针（unique_ptr / shared_ptr） P1 的 page guard 就是 RAII 的典型应用

建议了解

标准库里有现成的 latch，不用自己造。

std::shared_mutex rw_latch;     // 读写 latch：多个读者，或者一个写者
std::atomic_flag spin_latch;    // 自旋 latch：抢不到就原地转圈
std::mutex latch;
std::scoped_lock guard(latch);  // 出作用域自动解锁，这种写法你会写很多
  • std::shared_mutex 就是 #10 讲的读写 latch。
  • std::atomic_flag 就是 #10 讲的自旋 latch。
  • std::lock_guard / std::scoped_lock，你会写很多。

补充：这是一个来自课堂的观察（#10 43:25）。后面所有讲 latch 的内容，都不关心你用哪种具体实现。只要有一个能保护临界区的原语就行。所以先把 std::mutex 用熟就够了。

3关于 Fall 2025 的题目

难度 ★★★★★必会P0 要实现 Count-Min Sketch

Fall 2025 的 P0 里，有一个 Count-Min Sketch 要实现。这一点从课堂内容就能确认。

#16 39:21 讲统计信息的概览（Sketch）时，Andy 说了这么一句：

"你在 Project 0 里已经见过一个 sketch 了，就是 Count-Min Sketch。"

Count-Min Sketch 是什么

它是一种概率型数据结构。它用极小的空间，估计每个元素出现了多少次。

维护一个 d × w 的计数矩阵，配 d 个独立哈希函数
        ↓ 插入 x
对每一行 i：counter[i][ h_i(x) % w ] += 1
        ↓ 查询 x 的频次
取 d 行里【最小】的那个计数值

在 BusTub 里，用起来是这样的：

CountMinSketch<std::string> cms(width, depth);  // w 列、d 行
cms.Insert("apple");                            // 每一行都在对应格子上 +1
auto n = cms.Count("apple");                    // 取 d 行里最小的那个
// 考点：为什么取最小值？冲突只会让计数偏高，不会偏低

为什么取最小值：哈希冲突只会让计数偏高，不会偏低。所以最小的那个，最接近真实值。它只会高估，不会低估。这和 #09 Bloom Filter 的"只有假阳性" 是同一个道理。

好比 d 个人各记一本账。别人的账混进来，数只会多，不会少。所以信数最小的那本。

它在数据库里，是给优化器做统计用的。

用途 在哪一讲
查询优化器的统计信息，找"最频繁的值" #16 第 7 节
（对比）HyperLogLog，估"有多少个不同值" #16 第 7 节

补充：所以 P0 不只是 C++ 练习。它是 #16 统计信息 的伏笔。

1你要造的是什么

难度 ★★★★★重要组件全景，动手前看懂就行

你要写的是缓冲池管理器（BPM）。它夹在执行引擎和磁盘中间，负责把页搬进搬出。#04 那一讲，基本就是这个 Project 的设计文档。

auto guard = bpm->ReadPage(page_id);     // 上层只说"我要这一页"
auto *node = guard.As<BPlusTreePage>();  // 拿到的是内存里的某一帧
// 这页在不在内存、要不要淘汰别人、要不要写盘，全是 BPM 的事

缓冲池像图书馆的阅览室。书库在地下，就是磁盘。阅览桌就那么几张，就是帧。读者只管要书，管理员负责调书、收书。

2先把三对概念分清楚

难度 ★★★★★必会P1 守卫和淘汰都按 pin、脏、可淘汰来写

P1 最容易混的，是下面三对概念。它们也是后面所有 Project 的地基。

① 页表（Page Table） vs 页目录（Page Directory）

页表管内存，页目录管磁盘。只有页目录要持久化。

std::unordered_map<page_id_t, frame_id_t> page_table_;  // 页表：page_id → 帧，只在内存里
// 页目录：page_id → 磁盘上的位置，必须落盘
// 考点：页表和页目录哪个需要持久化？页目录

页表像管理员脑子里记的"哪本书在哪张桌上"。下班忘了也没关系。页目录是书库的索书号目录，丢了就再也找不到书。

是什么 在哪
页表 page_id → 内存中的 frame_id 内存里，不持久化
页目录 page_id → 磁盘上的位置 磁盘上，必须持久化

出处见 #03 第 3 节 和 #04。

② Pin vs Latch

Pin 管"别换走"，Latch 管"别乱改"。这是本 Project 最重要的区分。

frame->pin_count_++;        // pin：别把这一页换出去，很多人可以同时 pin
frame->rwlatch_.lock();     // latch：我在写，别人别动
// 持 latch 之前一定先 pin，不然读到一半页被换走了
// 考点：改 dirty flag 只要 pin，不用给整页上写 latch

Pin 像图书馆的"在读"标签。贴上了，书就不会被收走，谁都能贴。Latch 像你把书按在手底下写批注，这时不许别人翻。

含义 语义
Pin（引用计数） "别把这一页换出去" 计数器，可以有多个持有者
Latch（闩） "别在我读/写的时候改它" 读/写互斥

踩坑：两者完全正交。 你可以只 pin、不持 latch，比如只是想让它别走。 但持 latch 就必须先 pin 住。不然你正读着，它就被换走了。

补充：#10 那个课堂问答说得很清楚。改 dirty flag 需要 pin，但不用给整页上写 latch。因为只有 buffer manager 会读那个标志。

③ Dirty vs 可淘汰（Evictable）

Dirty 说的是"改没改过"，Evictable 说的是"还有没有人在用"。两件事互不相干。

if (frame->pin_count_ == 0) {
  replacer_->SetEvictable(frame_id, true);  // 没人用了，可以考虑淘汰
}
// is_dirty_ 这时照样可能是 true，淘汰前先刷盘就行
含义
Dirty 内容被改过，淘汰前必须写盘
Evictable pin count == 0，可以被替换器考虑

踩坑：一个页可以既 dirty 又 evictable。改完了，但没人用它。淘汰时刷盘就行。

3实现顺序建议

难度 ★★★★★必会P1 三个 Task 的实现顺序和取页主流程

先做两个能单独测的零件，再把它们粘起来。

① ARC 替换器     ← 独立、好测、先做
② 磁盘调度器      ← 独立、好测
③ 缓冲池管理器    ← 把前两个粘起来
④ 页守卫（Guard） ← RAII 包装，让上层好用

这就像装电脑。内存条和硬盘先单独测好，再插到主板上。

① ARC 的核心（#04 第 5 节）

ARC 把页分成两拨，再用一个目标大小 p 调两拨的比例。

  • 只被访问过一次的页，放进 mru_，体现最近性。
  • 被访问过不止一次的页，放进 mfu_，体现频率。
  • 目标大小 p 决定 mru_ 该占多少帧。
std::list<frame_id_t> mru_;        // 只来过一次的页
std::list<frame_id_t> mfu_;        // 来过不止一次的页
std::list<page_id_t>  mru_ghost_;  // 从 mru_ 踢走的页号，不占帧
std::list<page_id_t>  mfu_ghost_;  // 从 mfu_ 踢走的页号，不占帧
size_t mru_target_size_;           // 就是 p
// 考点：ARC 比 LRU 多解决了什么？ghost 列表和 p 各起什么作用？

它解决的正是 #04 里讲的 LRU 的死穴：顺序泛洪（sequential flooding）。一次全表扫描，就把整个缓冲池冲掉了。

全表扫描像一大群只来一次的游客。LRU 让游客把常客的座位全占了。ARC 给游客单独划一片区，常客的座位就保住了。

下面两个地方必须处理对。

  1. p 靠两个 ghost 列表自己调。每个 ghost 只记被淘汰页的页号，不占帧。命中 mru_ghost_，说明 mru_ 再大一点就命中了，于是 p 增大。命中 mfu_ghost_，p 就减小。
  2. 淘汰时按 p 选边。|mru_| ≥ p 时，先淘汰 mru_ 表尾。否则先淘汰 mfu_ 表尾。被 pin 的跳过。一侧全被 pin，就换另一侧。两侧都不行，返回 std::nullopt。
auto ArcReplacer::Evict() -> std::optional<frame_id_t> {
  bool from_mru = mru_.size() >= mru_target_size_;  // |mru_| ≥ p，先看 mru_
  // 从选中那一侧的表尾往前找，跳过被 pin 的
  // 这一侧全被 pin，就换另一侧再找
  return std::nullopt;                              // 两侧都不行
}

② 磁盘调度器

磁盘调度器把读写请求交给后台线程。调用方拿着一个 future 等结果。

调用方：发一个请求 { is_write, data, page_id, promise }
              ↓ 塞进线程安全队列
后台线程：取出 → 调 DiskManager 读/写 → promise.set_value(true)
              ↓
调用方：future.get() 阻塞等待

auto promise = disk_scheduler_->CreatePromise();
auto future = promise.get_future();
std::vector<DiskRequest> reqs;
reqs.push_back({false, data, page_id, std::move(promise)});  // false 表示读
disk_scheduler_->Schedule(reqs);
future.get();                    // 阻塞，等后台线程 set_value(true)

这像餐厅点单。你把单子交给后厨，拿一个号。号一叫，你再去取餐。

这就是 #04 讲的"用多线程掩盖磁盘停顿"。它也是 #10 开头那个"为什么要多线程" 的动机。

踩坑：析构时，记得给队列发一个"停止"信号，比如塞一个 std::nullopt。然后 join 后台线程。不然程序退不出去。

③ 缓冲池管理器的三条主流程

取页的核心就三步：查页表，没有就腾出一帧，再从磁盘读进来。

取一个已有的页（CheckedReadPage / CheckedWritePage）：

① 查页表
   ├─ 命中 → pin++ → 通知替换器"这一帧不可淘汰" → 返回
   └─ 未命中 ↓
② 找一个空闲帧
   ├─ 空闲列表里有 → 直接用
   └─ 没有 → 让替换器挑一个 →【如果是 dirty 就先写盘】
③ 从页表里【删掉旧 page_id 的映射】
④ 从磁盘读入新页 → 建立新映射 → pin = 1
⑤ 放掉 bpm_latch_ → 再构造页守卫（守卫要拿帧锁，可能阻塞）→ 返回

考点：② 的先写盘、③ 的删映射、⑤ 的先放大锁，对应下一节的坑 2、1、6

这像酒店前台排房。客人来了先查有没有空房。没有，就请一位退房的客人走人，打扫干净，再让新客人入住。

新建一个页更简单。NewPage() 只用原子计数器分配一个新页号。它不碰帧，也不碰磁盘。等之后第一次取这个页时，才走上面的流程，把它带进缓冲池。

page_id_t pid = bpm->NewPage();      // 只是 next_page_id_ 加一，不占帧
auto guard = bpm->WritePage(pid);    // 第一次取，它才真正进缓冲池

踩坑：取不到页时，返回 std::nullopt。所有帧都被 pin 住时就会这样。这种情况必须正确处理，而且不能留下任何副作用。

# 坑 说明
1 淘汰时忘了删旧映射 页表里留着僵尸条目，指向已被复用的帧。结果读到别人的数据
2 淘汰 dirty 页时没写盘 静默丢数据。最难查的一类 bug

6 死锁：抱着 bpm_latch_ 去等帧锁 帧锁在别人手里，你拿着大锁等它。别人又要大锁才能放页，于是卡死。DeadlockTest 专门测这个。先放 bpm_latch_，再构造守卫。做 I/O 期间，一直持有大锁是允许的。writeup 说从头到尾持有就够了，除非要提前放掉防死锁
7 Guard 的移动语义写错了 移动之后，源对象必须"失效"。否则会析构两次，造成双重 unpin

Andy 亲口给的性能建议

5页守卫（Page Guard）为什么重要

难度 ★★★★★必会P1 要实现守卫，page_guard_test 直接测

页守卫把 pin 和 latch 绑在一个对象的生命周期上。出了作用域，自动收尾。

// 错误写法：假如没有 guard（BusTub 早年的写法，Fall 2025 已经没有这两个函数）
//    到处都要记得 unpin，一个 early return 就漏了
auto *page = bpm->FetchPage(pid);
if (something_wrong) { return; }          // 泄漏！
bpm->UnpinPage(pid, false);

// 正确写法：Fall 2025 里，页数据只能通过 guard 访问，RAII 自动收尾
{
    auto guard = bpm->ReadPage(pid);       // 自动 pin + 加读 latch
    ...                                    // 随便 return / 抛异常
}                                          // 出作用域自动解 latch + unpin
// 考点：Page Guard 解决了什么问题？就是这种 early return 漏掉的 unpin

guard 像自动门。你走出去，门自己就关上了。不用记着回头锁门。

ReadPage / WritePage 取不到页时，会直接终止进程，所以只在测试里用。可能缺帧的地方，用 CheckedReadPage / CheckedWritePage。它们返回 std::optional。

补充：后面 P2 的 latch crabbing 会大量依赖它。#10 的 crabbing 协议 要求你按精确的顺序拿 latch、放 latch。手动管理，几乎不可能不出错。

ReadPageGuard(const ReadPageGuard &) = delete;   // 禁用拷贝
ReadPageGuard(ReadPageGuard &&that) noexcept;    // 实现移动，that 要置空
~ReadPageGuard();                                // 先解 latch，再 unpin
// 考点：为什么必须可移动不可拷贝？拷贝一份，析构时就会多 unpin 一次

踩坑：实现要点有三条。禁用拷贝，实现移动，移动后源对象置空。析构里按解 latch → unpin 的顺序收尾。

3单线程阶段的四个难点

难度 ★★★★★必会P2 要实现分裂、合并、迭代器和根处理

单线程阶段难在四处：分裂、合并、迭代器、根节点。

① 插入导致分裂

叶子满了就分裂。父节点也满了，就一路往上分裂，最坏分到根。

叶子满了
   ↓
把 key 分成两半，新建一个叶子
   ↓
把【中间 key 的副本】提升到父节点（叶子分裂是【复制】，不是移动）
   ↓
父节点也满了 → 递归往上分裂
   内部节点分裂时，中间 key 是【移动】上去的，不留副本
   ↓
一直分裂到根 → 新建一个根，树高 +1

// 叶子分裂：中间 key 复制一份给父节点，叶子里还留着它
InsertIntoParent(old_leaf, new_leaf->KeyAt(0), new_leaf_pid);
// 内部节点分裂：中间 key 直接移上去，自己不留
InsertIntoParent(old_node, middle_key, new_node_pid);
// 函数名是示意。考点：两种分裂，中间 key 的处理不一样

叶子里的 key 是真货，往上报时只能复印一张给父节点。内部节点的 key 本来就是路牌，直接摘下来挂上去就行。

踩坑：叶子分裂和内部节点分裂的处理不一样。这是最常写错的地方。

② 删除导致合并 / 重分配

删完不够半满，先找兄弟借。借不到，再合并。

删完之后节点不足半满
   ↓
① 先看兄弟能不能【借】一个（重分配 redistribute）
   ├─ 能借 → 借一个，【更新父节点的分隔 key】
   └─ 不能借（兄弟也只有下限）↓
② 【合并（merge）】两个节点
   → 从父节点里删掉一个分隔 key
   → 父节点可能因此不足半满 → 递归往上
   ↓
根节点只剩一个孩子 → 让那个孩子当新根，树高 −1

if (sibling->GetSize() > sibling->GetMinSize()) {
  Redistribute(node, sibling);   // 兄弟有富余：借一个，再改父节点的分隔 key
} else {
  Merge(node, sibling);          // 兄弟也只有下限：合并，父节点少一个分隔 key
}
// 函数名是示意。考点："重分配"和"合并"各在什么条件下发生

这像找邻居借米。邻居家米多，就借一碗。邻居家也见底了，两家干脆搭伙过。

③ 迭代器

迭代器就是沿着兄弟指针，在叶子层做顺序扫描。

for (auto it = tree.Begin(key); !it.IsEnd(); ++it) {
  auto [k, rid] = *it;   // 这个叶子读完，就顺着兄弟指针跳到下一个
}
// 考点：Begin()、Begin(key)、End() 三种入口都要对

这像翻一本活页本。每页底下都写着下一页放在哪。

踩坑：Begin() / Begin(key) / End() 三种入口都要对。End() 的相等判断，尤其要小心。

④ 根节点的特殊处理

根节点是唯一允许不足半满的节点。它还有三种情况要特殊处理。

  • 空树：第一次插入，要创建根。
  • 根是叶子：分裂时，要造一个新的内部节点当根。
  • 根只剩一个孩子：要塌缩。
auto header_guard = bpm_->WritePage(header_page_id_);     // 根页 ID 单独存放
auto *header = header_guard.AsMut<BPlusTreeHeaderPage>();
header->root_page_id_ = new_root_id;                      // 改根的时候要额外小心
// 考点：根节点在哪三种情况下需要特殊处理

补充：实现上，通常有一个"根页 ID"要单独存放和保护。改根的时候要额外小心，多线程阶段尤其如此。

4多线程阶段：Latch Crabbing

难度 ★★★★★必会Task 4 必做乐观版，并发和写页数都测

Latch crabbing 就是像螃蟹那样走路。先抓住下一个节点，再松开上一个。

补充：完整理论在 #10 第 7–9 节，这里只列实现要点。

悲观版（先实现这个）

悲观版的写操作一路拿写 latch。碰到安全的节点，才把上面的 latch 放掉。

操作 协议
查找 一路取读 latch。拿到孩子的读 latch 后，立刻释放父亲的
插入 / 删除 一路取写 latch。孩子"安全"，就释放上面【所有】latch

"安全"的判据见 #10 第 7 节：

INSERT：节点【未满】     → 安全（下面冒上来的 key 我装得下）
DELETE：节点【超过半满】 → 安全（下面删一个我也不会跌破下限）

ctx.write_set_.push_back(bpm_->WritePage(child_id));  // 先抓住孩子
if (IsSafe(child, op)) {                              // IsSafe 是示意
  while (ctx.write_set_.size() > 1) {
    ctx.write_set_.pop_front();                       // 孩子安全：从上往下，放掉祖先的 latch
  }
}
// 考点："安全节点"对 INSERT 是未满，对 DELETE 是超过半满

这像攀岩。新的落脚点踩稳了，才敢松开下面那只手。

三个必须做对的细节

# 细节 说明
1 释放顺序：从上往下 #10 50:32：先放 A 再放 B。这不影响正确性，但影响并发度。因为只要你还持有父亲的 latch，别人根本到不了孩子
2 用一个"latch 栈/队列"记录路径 不安全时，路径上的 latch 全留着。安全时，一次性全放掉
3 根页 ID 需要单独的保护 树高变化时会改它。通常需要一把专门的根 latch

乐观版（必做：Task #4 要求）

乐观版先赌叶子不用分裂，一路只拿读 latch。赌输了，就从根重来。

一路取【读】latch 下去（照常 crabbing）
        ↓ 到叶子才取【写】latch
检查假设：这个叶子真的不需要分裂/合并吗？
   ├─ 猜对 → 直接改，全程只锁了一个叶子
   └─ 猜错 →【释放全部 latch，从根重来】，改走悲观协议

if (!TryOptimisticInsert(key, value)) {   // 读 latch 一路下去，只给叶子上写 latch
  ReleaseAllLatches(&ctx);                // 猜错了：手里的 latch 全放掉
  return PessimisticInsert(key, value);   // 从根重来，走悲观协议
}
// 函数名是示意。考点：乐观 crabbing 猜错之后，为什么必须从根重来

这像去窗口买票先不排队，直接问一句。有票就买走。没票，再老老实实回去排队。

踩坑：这不是可选优化。writeup 的 Task #4 要求用乐观 latch coupling / crabbing，也不许用全局 latch。测试还会数写页次数。

  • b_plus_tree_insert_test.cpp:60 的 DISABLED_OptimisticInsertTest，要求向不满的叶子插入时只写 1 页。
  • b_plus_tree_delete_test.cpp:94 的 DISABLED_OptimisticDeleteTest，要求从富余的叶子删除时只写 1 页。

名字里的 DISABLED_ 前缀只是默认跳过，要你自己打开。

踩坑：#10 明确说过，不要试图"从记录的路径中间续上"。上面的读 latch，你已经全放掉了。别人可能已经改了树的结构，你记下的路径不再可信。

"往往最简单的做法就是最好的做法。"

叶子层扫描的死锁风险

叶子层横着走，可能死锁。唯一正确的应对是 no-wait，拿不到就放弃重来。过程见 #10 第 9 节：

沿兄弟指针横向走时：
必须【先拿到下一个的 latch，再释放当前的】
        ↓ 但兄弟指针是双向的
两个线程可能【面对面走来】→ 死锁
        ↓ 唯一正确的做法
【no-wait】：拿不到就立刻放弃、释放全部 latch、整个操作重试

if (!TryLatch(next_page_id)) {   // 下一个叶子的 latch 拿不到
  ReleaseAllLatches(&ctx);       // 不等，手里的全放掉
  return Retry();                // 整个操作从头再来
}
// 函数名是示意。考点：唯一正确的应对是 no-wait，不能"杀掉对方"

这像窄桥上两辆车对开。谁都不让，就堵死了。no-wait 就是一看对面有车，立刻倒回去，等会儿重来。

踩坑：绝对不要试图"等待"或"杀掉对方"。#10 详细解释了为什么做不到。

5常见的坑

BusTub 用的是迭代器模型，也叫火山模型。数据从下往上，一批一批被拉上来。

踩坑：注意，Fall 2025 的 BusTub 是它的批量版。Next() 一次吐一批，最多 BUSTUB_BATCH_SIZE = 20 条，不是一次一条。

              │ 调根算子的 Next()
        [ 投影 Projection ]

这像流水线上的工人。上游喊一声"给我一批"，下游才动手干活。

2算子分成两类

难度 ★★★★★必会决定聚合、连接的活放在 Init 还是 Next

算子分流式和阻断两类。这决定了活儿是在 Init() 里干，还是在 Next() 里干。

类别 特点 例子
流式（Pipeline） Next() 里现算现吐 顺序扫描、索引扫描、过滤、投影、LIMIT
阻断（Pipeline Breaker） Init() 里就要把子节点【全部抽干】 排序、聚合、窗口函数、Grace 哈希连接的分区阶段

流式算子像传菜员，菜一出锅就端走。阻断算子像排座位，人没到齐，就没法排。

补充：对照 #13 第 1 节，看它们为什么阻断。

  • 排序：全部数据没看完，根本不知道顺序。
  • 聚合：组没扫完，算不出最终值。
  • 哈希连接 build 侧：哈希表没建完就探测，会出假阴性。

所以阻断算子的典型写法如下。这是外部归并排序的骨架。

void ExternalMergeSortExecutor::Init() {
    child_->Init();
    std::vector<Tuple> batch; std::vector<RID> rids;
    while (child_->Next(&batch, &rids, BUSTUB_BATCH_SIZE)) {  // 一批一批抽干
        // 写进排序页，一页满了就对这一页 std::sort，写出去成为一个 run
    }
    // 两两归并这些 run，直到只剩一个。用完的页要删掉
}
auto ExternalMergeSortExecutor::Next(std::vector<Tuple> *tuple_batch,
                                     std::vector<RID> *rid_batch, size_t batch_size) -> bool {
    tuple_batch->clear(); rid_batch->clear();
    // 沿最终的 run 往下读，最多放 batch_size 条
    return !tuple_batch->empty();
}
// 考点：流式和阻断的区别。举三个阻断算子，说明各自为什么阻断

4万圣节问题

难度 ★★★★★重要表堆迭代器的终点已挡住，懂原理即可

万圣节问题就是，一条 UPDATE 把同一行改了两次。

踩坑：#13 第 10 节 里，Andy 明确说："你必须在 Project 3 里处理这个。"

UPDATE people SET salary = salary + 100 WHERE salary < 1100;
-- 假设扫描走的是【建在 salary 上】的索引

① 索引扫描找到 Andy，salary = 999
② 改成 1099 → 因为索引就建在 salary 上，这条记录被【挪到了叶子层更靠后的位置】
③ 扫描游标继续往前 → 又碰到了 Andy（1099 仍然 < 1100）
④ 再加 100 → 1199，这才不再满足 WHERE → Andy 被改了两次（课上原话是 "update it twice"，不是无限循环）

这像排队发奖品。领完的人又排到了队伍后面。发奖的人一路往后发，就给同一个人发了两次。

两种解法

最省事的解法是先抽干再改。先把要改的 RID 全部收集完，再动手改。

  while (child_executor_->Next(&batch, &rids, BUSTUB_BATCH_SIZE)) {
    pending_rids_.insert(pending_rids_.end(), rids.begin(), rids.end());  // 只收集，先不改
  }
}
// pending_rids_ 是自己加的成员，Next() 里再逐条改
// 考点：描述万圣节问题的发生过程，以及你选了哪种解法

# 坑
1 阻断算子把逻辑写在了 Next() 里。每次调用都重排一遍，直接超时
2 Init() 忘了调用子算子的 Init()，或者重新 Init() 时状态没清零。NLJ 右侧的算子会被反复 Init()，p3.12-repeat-execute.slt 专门测这个
3 修改数据后，忘了更新索引。索引和表对不上，后续查询就查不到
4 万圣节问题。见上
5 Next() 返回 false 之后又被调用，还返回了数据。这破坏了契约
6 哈希连接一个 key 匹配多条时，只吐了一条。要用"当前匹配列表 + 游标"续着吐
7 空表上的聚合返回错。COUNT(*) 应该是 0，SUM/MIN/MAX/AVG 应该是 NULL
8 NULL 的比较语义。参考 #02 和 #25 客座讲座。NULL 的坑，连 SQL 标准都没搞清楚
9 和 P1 的 pin 不平衡。扫描算子会 fetch 大量页。用 Page Guard
10 优化器规则写成了"无条件重写"。比如把不是等值连接的 NestedLoopJoin，也换成了 HashJoin。必须先判断谓词形式（#12 只讨论等值内连接）

txn_mgr->Commit(txn);              // 提交时才拿到 commit_ts，决定我写的对谁可见
// 考点：为什么需要两个时间戳

read_ts 像你进场看展的时间。你只能看到进场前就挂好的画。commit_ts 像你挂画的时间，挂上之后，后进场的人才看得见。

补充：#19 19:16 讲透了为什么要两个。物理顺序 ≠ 逻辑顺序。

② 版本链

表堆里永远放最新版本。旧版本要靠 undo 日志，一条条补回去。

踩坑：注意，BusTub 用的是 #20 讲的增量式（Delta）存储，不是 PostgreSQL 那种追加式。

表堆里：永远是【最新版本】
              ↓ 指向
undo 日志 1  ←── 记录"要退回上一版，需要改哪几个字段"
              ↓
undo 日志 2
              ↓
            (nil)

要读旧版本，就从最新版本出发。逐条应用 undo 日志，"打补丁"回去（#20）。

auto [meta, base] = table_heap->GetTuple(rid);                        // 最新版本
auto old = ReconstructTuple(&schema, base, meta, undo_logs);          // 逐条打补丁，退回旧版本
// 考点：BusTub 用的是哪种版本存储？为什么它比追加式好？

这像改作文留的修订记录。正文永远是最新稿。想看初稿，就把修订一条条撤回去。

补充：为什么用增量式？一千个字段只改了一个，就只存那一个的旧值。这正是 #19 说的 OCC 私有工作区的痛点。

③ 可见性规则

可见性判断只做一件事，就是判断"我该看到哪一版"。输入是一个事务的 read_ts，加一条版本链。

① 表堆里的元组，它的 ts 是什么？
   ├─ ts == 我自己的事务 ID       → 我自己写的，看得见
   ├─ ts <= 我的 read_ts          → 在我开始前就提交了，看得见
   └─ 否则 ↓
② 顺着 undo 链往回走，逐条应用补丁
   直到找到一个 ts <= read_ts 的版本 → 这就是我该看到的
   走到链尾都没有 → 这条记录在我开始时【还不存在】→ 看不见

if (meta.ts_ == txn->GetTransactionId()) { return tuple; }  // 自己写的，看得见
if (meta.ts_ <= txn->GetReadTs()) { return tuple; }         // 我开始前就提交了，看得见
// 否则顺着 undo 链往回走，直到某一版的 ts <= read_ts
// 考点：完整写出可见性判断的逻辑

这像翻相册找某一天的样子。从最新那张往回翻，翻到那天之前拍的第一张，就是答案。

补充：这就是快照隔离。你看到的，是你开始那一刻已提交的一致快照。

④ 冲突检测

两个事务改同一条记录，先写的赢，后写的中止。这就是 #20 的裁决规则：First Writer Wins（先写者胜）。

我要改一条记录：
① 看表堆里那条元组的 ts
② 如果它是【另一个未提交事务】的 ID  → 写冲突 → 我中止
③ 如果它 > 我的 read_ts（别人在我开始后提交了）→ 写冲突 → 我中止
④ 否则 → 可以改

if (IsOtherUncommitted(meta.ts_, txn) || meta.ts_ > txn->GetReadTs()) {
  txn->SetTainted();   // 写冲突，我中止
}
// IsOtherUncommitted 是示意。考点：两种冲突情况分别是什么

这像抢车位。车位上停着别人还没熄火的车，你不能抢。你到之后别人刚停进来的，你也不能抢。

更新前先查冲突，再把旧值存进 undo 日志，最后覆盖表堆。

① 冲突检测（见上）
② 建一条 undo 日志，记录【被修改字段的旧值】+ 一个"哪些字段被改了"的位图

这像打游戏存档。同一关重打一遍，覆盖原来的存档就行。再新开一个存档，读档时就会退到更早的地方。

踩坑：同一个事务第二次改同一条记录时，不要再建 undo 日志。要去更新自己已有的那条。否则回滚会退过头。

在元组头打【删除标记】，ts = 我的事务 ID

这像图书馆下架一本书。书不扔，只贴一张"已下架"的标签。

提交

提交就是拿一个 commit_ts，把我写过的元组全改成它。

① 拿一个 commit_ts
② 把我写过的所有元组的 ts 【改成 commit_ts】
③ 更新事务状态表：COMMITTED

for (const auto &[table_oid, rids] : txn->GetWriteSets()) {

}
// 考点：忘了改 ts，别人永远看不到你的改动

中止

中止就是顺着我的 undo 日志，把所有改动退回去。

① 顺着我的 undo 日志，把所有改动【打补丁退回去】
② 事务状态表：ABORTED
我建的那些版本要能被垃圾回收识别并清掉（#20 第 10 节）

索引

索引拿到 RID 只是第一步。回表之后，还要再判一次可见性。#20 第 11 节讲了三点。

  • 主键索引指向版本链头。在 BusTub 里，就是表堆里的那条记录。
  • 索引里的条目，可能指向"对我不可见"的元组。所以拿到 RID 之后，还要再做一次可见性判断。
  • 索引不会因为版本变化而失效。这是增量式存储的好处：表堆里的位置不变。

水位线以前的旧版本，没人还会看，可以回收。做法见 #20 第 10 节。

        ↓
都不可能被任何活跃事务看到 → 可以回收

5常见的坑

难度 ★★★★★必会可见性、重复 undo log，txn 测试直接抓

P4 最难查的坑，是可见性判断有漏洞。最常见的漏洞，是忘了自己能看见自己的写。

if (meta.ts_ <= txn->GetReadTs()) { return tuple; }   // 只写了这一条
// 漏了 meta.ts_ == 我的事务 ID：事务改完再读，读不到自己的改动
# 坑
1 可见性判断有漏洞。这是最难查、表现最诡异的一类。单独测透它
2 忘了"自己能看见自己的写"。事务改完再读，读不到自己的改动
3 同一事务重复修改时，又建了一条 undo 日志。回滚会退过头
4 提交时忘了把 ts 从"事务 ID"改成 "commit_ts"。别人永远看不到你的改动
5 中止时，没把版本链退干净
6 索引拿到 RID 后，没做可见性判断。查到了不该看到的行
7 主键"删了又插"没处理。见 #20 第 11 节
8 垃圾回收把还有人要看的版本清掉了。水位线算错了
9 写偏斜，见 #20 第 5 节。快照隔离【本来就有】这个异常。除非 writeup 明确要求可串行化，否则不用管
10 和 P3 的算子没接好。每个扫描算子都要接入可见性判断
11 并发。版本链的修改需要保护。先加大锁跑通（同 P1 的建议）

关于"要不要做到可串行化"

默认的 MVCC 只给到快照隔离。它会出现写偏斜。#25 20:27 Andy 确认：

默认的 MVCC 给的是【快照隔离】。它【会】出现写偏斜，所以不是可串行化的。

要做到可串行化，还得额外维护一张依赖图。它要识别"我要写的东西，我读到的是它的旧版本"。PostgreSQL 就是这么做的（SSI）。

UPDATE marbles SET color = 'black' WHERE color = 'white';  -- T1
UPDATE marbles SET color = 'white' WHERE color = 'black';  -- T2
-- 两边改的不是同一行，First Writer Wins 拦不住
-- 考点：你实现的隔离级别是什么？它有写偏斜吗？要消除它还需要什么？

所以先看 writeup 要求的是哪一档。
