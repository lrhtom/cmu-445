1先弄清评分规则和通用流程

难度 ★★★★★重要不考知识点，但列序、次关键字错了就丢分

自动评分比的是输出的元组集合。列的顺序有关系，列名无所谓。作业网页写明了这一点，还规定每个文件只能有一条语句。

SELECT name, cnt FROM t;   -- 示意：列序和标准答案一致，算对
SELECT cnt, name FROM t;   -- 列名一模一样，顺序反了，整题算错
-- 考点：评分按位置比列，列名随便起

评分脚本像一台对答案的阅卷机。它只看每一格填了什么，不看表头写的是什么。

由此能推出几条最容易白丢分的细节：

细节 为什么会丢分
列顺序 评分按位置比列。name, cnt 写成 cnt, name 就全错
排序的第二关键字 题目常写「先按 X 降序，再按名字升序」。漏掉第二关键字，并列的行顺序就是随机的。配上 LIMIT，连选中哪几行都会变
拼字符串的格式 空格、括号要一字不差。而且 NULL 参与 `
边界 「after 某年」「since 某年」是 > 还是 >=，要和题意一致

通用流程如下，每道题都这么走一遍：

① 结果的一行代表什么？（一个人？一个 (队, 年)？一对 (人, 队)？）
   这决定 GROUP BY 的键
② 需要哪些表、靠什么键连起来？画一张小草图
③ 把需求拆成几个子问题，每个写成一个 CTE，单独跑一下看结果对不对
④ 先聚合再连接，还是先连接再聚合？
   连接会把行"复制"，聚合前要想清楚（第 4、6 节）
⑤ 排序：主关键字 + 所有并列时的次关键字
⑥ 最后才加 LIMIT

补充：这就是 #01 关系代数 的思路。先想清楚 σ / π / ⋈ / γ 怎么组合，再翻译成 SQL。CTE 让你一个算子一个算子地写，一段一段地验。这是本作业最值得养成的习惯，见 #02 §9 CTE。

CTE 就像炒菜前备料。每样料先单独切好、尝一口，最后再下锅。

3题型一：过滤 + 去重 + 排序（热身）

难度 ★★★★★必会HW1 第一题就是它，用来核对输出格式

第一题是送分题。它真正的用处，是确认输出格式和评分脚本对得上。它考 SELECT DISTINCT、WHERE、ORDER BY，见 #02 §6 输出控制。

-- 2022 年出现过的所有队，按字母序
SELECT DISTINCT team FROM games WHERE yr = 2022 ORDER BY team;
-- BLU
-- RED

DISTINCT 去重时看的是整行。

SELECT DISTINCT team FROM games;       -- 2 行：BLU、RED
SELECT DISTINCT team, yr FROM games;   -- 4 行：按 (team, yr) 组合去重
-- 考点：DISTINCT 管的是整行，不是第一列

这像比对两张照片。整张一模一样才算重复，只有一个角相同不算。

踩坑：DISTINCT 作用于整行，而不是第一列。SELECT DISTINCT team, yr 去重的是 (team, yr) 这对组合。

4题型二：先聚合再连接：每人的最大值 + 拼名字

难度 ★★★★★必会HW1 题型二直接考；扇出和 NULL 拼接易错

这类题最稳的做法分两步。先在 CTE 里把每个子问题聚合成"一人一行"，再连接。

需求（自编）：只看在浙江（prov = 'ZJ'）的学校读过书的人。找出这些人单季进球数的最大值，取前 3 名。按最大值降序，再按名字升序。名字拼成 first (given) last。

这题考的点很多。CTE 拆子问题，GROUP BY 加 MAX，还有多表连接。另外是 || 拼接，以及多关键字排序加 LIMIT。对应 #02 §3 聚合与分组 和 §4 字符串拼接。

这就像先让每个班交一份汇总表，再拼年级总表。各班先算好，拼的时候就不会把人数重复。

解题步骤

先拆成两个子问题，各自收拢成"一人一行"，最后再合并。

子问题 A：哪些人在 ZJ 的学校读过？        → 一行 = 一个人（必须去重！）
子问题 B：每个人单季最多进几个球？        → 一行 = 一个人：GROUP BY pid, MAX(goals)
合并：   people ⋈ A ⋈ B，拼名字，排序，LIMIT 3

WITH zj AS (                       -- A：一定要 DISTINCT
  SELECT DISTINCT st.pid
  FROM studied st JOIN schools s ON s.sid = st.sid
  WHERE s.prov = 'ZJ'
),
best AS (                          -- B：每人一行
  SELECT pid, MAX(goals) AS best FROM games GROUP BY pid
)
SELECT p.first || ' (' || p.given || ') ' || p.last AS name, b.best
FROM people p JOIN zj ON zj.pid = p.pid JOIN best b ON b.pid = p.pid
ORDER BY b.best DESC, p.first
LIMIT 3;
-- Cat (Catherine) Ma | 6
-- Ann (Anna Mae) Lee | 5
-- Fay (Fiona) He     | 5        ← Ann 和 Fay 并列 5，靠第二关键字 first 决定先后
-- 考点：zj 不去重，Ann 就会占掉两行

易错点

连接会"扇出"，这是本节第一个坑。

踩坑：不加 DISTINCT 的话，Ann 在 studied ⋈ schools 里有两行（s1、s3）。整条结果里 Ann 就出现两次，LIMIT 3 直接被占掉两个位置。

「曾经满足某条件」是存在性条件。它要写成去重后的集合，或者写成 EXISTS / IN（半连接）。不要用普通连接。

SELECT COUNT(*) FROM people p
JOIN studied st ON st.pid = p.pid
JOIN schools s  ON s.sid = st.sid
WHERE s.prov = 'ZJ';
-- 返回 4：Ann 两行、Cat 一行、Fay 一行
-- 考点：连接按"读书记录"产生行，Ann 读过两所 ZJ 学校就有两行
-- 考点：要数"在 ZJ 读过书的人数"，得写 COUNT(DISTINCT p.pid)，结果是 3

踩坑：NULL 会吃掉整串。'Eve' || ' (' || NULL || ') ' || 'Li' 的结果是 NULL。作业要求的格式就是带括号的那种，这里只是提醒。自己的数据里有 NULL 又想保住名字，就用 coalesce(given, '') 或 concat_ws。

SELECT 'Eve' || ' (' || NULL || ') ' || 'Li';   -- NULL：整串没了
SELECT concat_ws(' ', 'Eve', NULL, 'Li');       -- 'Eve Li'：跳过了 NULL

NULL 像一滴墨水滴进清水。拼接里只要混进一个 NULL，整串就全黑了。

踩坑：先聚合还是先连接，要看聚合函数。这里 MAX 不怕重复，重复一行最大值不变。换成 SUM / COUNT，先连接后聚合就会把 Ann 的数字翻倍。

最安全的习惯是：先在 CTE 里把每个子问题聚合到"一人一行"。然后再连接。

SELECT p.first, SUM(g.goals) FROM people p
JOIN studied st ON st.pid = p.pid JOIN schools s ON s.sid = st.sid AND s.prov = 'ZJ'
JOIN games g ON g.pid = p.pid GROUP BY p.pid, p.first;
-- Ann：2 条 ZJ 读书记录 × 2 条出场记录 = 4 行
-- SUM = (3 + 5) × 2 = 16，真实值是 8
-- 考点：MAX 换成 SUM，又不分 CTE 先连接再聚合，Ann 的数字就翻倍

本节对应下方演示的第 1 个场景。画面依次是：GROUP BY 收拢，连接时 Ann 冒出两行，去重，排序截断。

5题型三：相关子查询：比自己所在组的平均值高

难度 ★★★★★必会HW1 题型三直接考，要分清内层平均谁

相关子查询就是内层引用了外层的列。外层每来一行，内层就重新算一次。

需求（自编）：找出出场数高于本队平均出场数的出场记录。只看 2021 年以后。按 (人, 队) 统计这样的赛季有几个。按个数降序，再按名字升序。

这题考 #02 §7 相关子查询。内层查询引用了外层的列 g.team。所以对外层的每一行，都要重新求一次。

这像老师改卷子。每拿起一张，都要翻回去查一下这个班的平均分。

SELECT p.first, g.team, COUNT(DISTINCT g.yr) AS yrs
FROM games g JOIN people p ON p.pid = g.pid
WHERE g.yr >= 2021
  AND g.played > (SELECT AVG(g2.played) FROM games g2      -- 内层：这支队的平均
                  WHERE g2.team = g.team AND g2.yr >= 2021) -- ← 引用外层的 g.team
GROUP BY p.first, g.team
ORDER BY yrs DESC, p.first;
-- Ann | RED | 2      （RED 平均 8.2，Ann 两季 10、12 都高于它）
-- Bob | BLU | 1      （BLU 平均 6.8）
-- Cat | BLU | 1
-- 考点：内层引用外层的 g.team，外层每一行都重算一次

另一种写法是窗口函数，见 #02 §10。它一次算出每行所在队的平均值，不用"每行跑一次子查询"：

SELECT first, team, COUNT(DISTINCT yr) AS yrs
FROM (SELECT p.first, g.team, g.yr, g.played,
             AVG(g.played) OVER (PARTITION BY g.team) AS team_avg
      FROM games g JOIN people p ON p.pid = g.pid
      WHERE g.yr >= 2021) t
WHERE played > team_avg
GROUP BY first, team ORDER BY yrs DESC, first;

易错点

平均值算的是哪些行，最容易和题意对不上。

踩坑：平均值的范围要和题意一致。内层子查询的 WHERE 决定"平均谁"。外层只看 2021 年以后，内层却平均了全部年份，数字就变了。读题时把「平均的是哪些行」单独写下来。

踩坑：数"不同年份"要用 COUNT(DISTINCT yr)。一个人同一年可能有多行，比如多条出场或多个奖。COUNT(*) 会数多。

补充：#02 §7 讲过一个坑。优化器要是不会改写，相关子查询就是逐行执行的嵌套循环。DuckDB 的优化器会把它去相关（decorrelate）成连接。所以在作业的数据量上不必担心。

6题型四：拆子问题 + HAVING + EXISTS：「同一组同一年同时满足两件事」

难度 ★★★★★必会HW1 题型四直接考；两层分组加防扇出

两个条件要分开写。一个用 HAVING 筛分组，另一个用 EXISTS 只问有没有。

需求（自编）：定义事件 E。某支队在某一年里，至少有 2 名不同的球员获奖。并且这一年这支队里，有人单季进球 ≥ 5。统计每支队发生过几次 E。按次数降序、队名升序。

这题考 GROUP BY … HAVING（#02 §3）和 COUNT(DISTINCT …)。还考 EXISTS（#02 §7），以及用 CTE 把两个条件分开写。

HAVING 像班级评优，先按班分组，再看每班够不够格。EXISTS 像点名，只问"有没有人到"，不管到了几个。

WITH many AS (                          -- 条件 1：一行 = 一个 (队, 年)
  SELECT g.team, g.yr
  FROM prizes pr JOIN games g ON g.pid = pr.pid AND g.yr = pr.yr
  GROUP BY g.team, g.yr
  HAVING COUNT(DISTINCT pr.pid) >= 2    -- 数「人」，不是数「奖」
)
SELECT m.team, COUNT(DISTINCT m.yr) AS times
FROM many m
WHERE EXISTS (SELECT 1 FROM games g2    -- 条件 2：只问「有没有」，不连接
              WHERE g2.team = m.team AND g2.yr = m.yr AND g2.goals >= 5)
GROUP BY m.team
ORDER BY times DESC, m.team;
-- BLU | 1      （BLU 2022：Bob、Cat、Fay 三人获奖，Bob 进 7 球）
-- RED | 1      （RED 2021：Ann、Bob、Cat 三人获奖，Cat 进 6 球）
-- 考点：条件 1 用 HAVING 数人，条件 2 用 EXISTS 不扇出

把 COUNT(DISTINCT) 写成 COUNT(*) 会怎样

一个人拿了几个奖，就会被当成几个人，RED 因此多算一次。prizes ⋈ games 按 (队, 年) 分组后是这样：

team yr COUNT(*)（行数） COUNT(DISTINCT pid)（人数）
BLU 2022 4 3
RED 2021 3 3
RED 2022 2 1 ← 只有 Ann 一个人，拿了两个奖

用 COUNT(*) >= 2 会把 RED 2022 也算进去。最终 RED 变成 2 次，这是错的。

把门槛改一改，结果是这样：

HAVING COUNT(DISTINCT pr.pid) >= 3   -- 结果不变：BLU 1、RED 1
HAVING COUNT(DISTINCT pr.pid) >= 4   -- 结果为空
-- 考点：RED 2021 和 BLU 2022 都恰好 3 人，所以门槛改成 3 也不变

易错点

第二个条件一旦写成连接，计数就又被放大了。

踩坑：第二个条件用 EXISTS，别用 JOIN。把 games g2 普通连接进来会怎样？这支队这一年里，每个进球 ≥ 5 的人都会让 (队, 年) 多出一行。后面的计数又被放大了。EXISTS 只回答"有没有"，天然不扇出。

踩坑：两个 HAVING 的层次别混。内层 HAVING 过滤的是"(队, 年) 这一组"。外层 HAVING 过滤的是"队这一组"，比如题目要求「发生超过 k 次」时。两个分别写在两层 GROUP BY 后面。

GROUP BY g.team, g.yr HAVING COUNT(DISTINCT pr.pid) >= 2   -- 内层：筛 (队, 年)
GROUP BY m.team       HAVING COUNT(DISTINCT m.yr) > k      -- 外层：筛队，k 为示意

本节对应演示的第 2 个场景。

7题型五：每组取一个：LATERAL、窗口函数、QUALIFY

难度 ★★★★★必会HW1 题型五直接考；LIMIT 层次和并列易错

每组取一个，就是对外层每一行跑一次带 ORDER BY … LIMIT 1 的子查询。

需求（自编）：对每个获过奖的人，找出最早的队友。队友是同队同年、不是自己的人。同一年有好几个队友，就按拼好的名字取字母序第一个。

这正是 #02 §8 LATERAL JOIN 的典型用途。等价写法是窗口函数 ROW_NUMBER()。

LATERAL 像给每个获奖者单独排一次队。排好以后，只叫排头那个人出来。

写法一：LATERAL

LATERAL 子查询能看到外层这一行，所以能"每人跑一次"。

WITH winners AS (SELECT DISTINCT pid FROM prizes)
SELECT me.first || ' (' || me.given || ') ' || me.last AS who, t.mate, t.yr
FROM winners w
JOIN people me ON me.pid = w.pid
JOIN LATERAL (
    SELECT b.yr, q.first || ' (' || q.given || ') ' || q.last AS mate
    FROM games a                                   -- 我的出场
    JOIN games b ON b.team = a.team AND b.yr = a.yr AND b.pid <> a.pid   -- 同队同年的别人
    JOIN people q ON q.pid = b.pid
    WHERE a.pid = w.pid                            -- ← 引用外层这一行
    ORDER BY b.yr, mate
    LIMIT 1                                        -- 每个外层行只要第一个
) t ON TRUE
ORDER BY who;
-- 考点：LIMIT 1 写在子查询里面，才是每人取一个

写法二：窗口函数（DuckDB 还可以用 QUALIFY 省一层子查询）

窗口函数先给每个人的候选队友编号，再只留 1 号。

WITH pairs AS (
  SELECT a.pid AS me, b.yr, q.first || ' (' || q.given || ') ' || q.last AS mate
  FROM games a JOIN games b ON b.team = a.team AND b.yr = a.yr AND b.pid <> a.pid
  JOIN people q ON q.pid = b.pid
  WHERE a.pid IN (SELECT pid FROM prizes)
)
SELECT me, mate, yr FROM pairs
QUALIFY ROW_NUMBER() OVER (PARTITION BY me ORDER BY yr, mate) = 1;   -- DuckDB 特有

me 换成名字之后，两种写法结果一样：

who 最早的队友 年份
Ann (Anna Mae) Lee Bob (Robert) Wu 2021（同年还有 Cat，B 在 C 前）
Bob (Robert) Wu Ann (Anna Mae) Lee 2021
Cat (Catherine) Ma Ann (Anna Mae) Lee 2021
Fay (Fiona) He Dan (Daniel) Xu 2021

同样的套路还能求每支队进球最多的人。并列时取名字字母序第一个，输出 team, first, goals。

SELECT team, first, goals FROM (
  SELECT g.team, p.first, g.goals,
         ROW_NUMBER() OVER (PARTITION BY g.team ORDER BY g.goals DESC, p.first) AS rn
  FROM games g JOIN people p ON p.pid = g.pid) t
WHERE rn = 1;          -- BLU: Bob 7，RED: Cat 6
-- 考点：每组取第一，并列规则写进 ORDER BY

SELECT g.team, arg_max(p.first, g.goals), max(g.goals)
FROM games g JOIN people p USING (pid) GROUP BY g.team;
-- 考点：arg_max 写起来短，但并列时不保证取字母序第一个

踩坑：arg_max 在并列时不保证取字母序第一个。需要并列规则时，还是用窗口函数。

易错点

排序关键字写不全，"第一个"就不确定了。

踩坑：自己不是自己的队友。漏掉 b.pid <> a.pid，每个人的"最早队友"就是自己。

踩坑：LIMIT 1 写在哪一层很关键。写在 LATERAL 子查询里面，是「每人取一个」。写在整条查询最后，是「全表只要一行」。前者才是题意。

踩坑：排序关键字要写全，先按年份，再按名字。只按年份排的话，同一年的几个队友谁排第一是不确定的。

SELECT me, MIN(mate) FROM pairs GROUP BY me;   -- 错：和年份无关
-- MIN(mate) 会在所有年份的队友里挑字母序最小的
-- 题意是先看年份最早，再在那一年里挑名字
-- 考点：两个关键字有先后，必须 ORDER BY yr, mate 再取第一个

补充：NULL 在排序里的位置因系统而异。Eve 的名字拼出来是 NULL。PostgreSQL、DuckDB 默认把 NULL 放在升序的末尾，SQLite 放在开头。需要确定时，写 ORDER BY mate NULLS LAST。

8题型六：UPSERT：INSERT … SELECT … ON CONFLICT

难度 ★★★★★必会HW1 题型六直接考，插入和更新都要对

UPSERT 就是一条语句里同时完成「不存在就插入、存在就更新」。

需求（自编）：表 team_years(yr, team, fans)，主键是 (yr, team)。把 2022 年的每支队复制一份成 2023 年的记录。如果 2023 年已经有这支队，就把已有那行的 fans 加上 2022 年的值。

这像银行记账。新客户就开一个新户头，老客户就在原户头上加钱。

CREATE TABLE team_years (yr INT, team VARCHAR, fans INT, PRIMARY KEY (yr, team));
INSERT INTO team_years VALUES (2022,'RED',120), (2022,'BLU',90), (2023,'RED',150);

INSERT INTO team_years
SELECT yr + 1, team, fans FROM team_years WHERE yr = 2022
ON CONFLICT (yr, team) DO UPDATE SET fans = fans + EXCLUDED.fans;

SELECT * FROM team_years ORDER BY yr, team;
-- 2022 BLU  90
-- 2022 RED 120
-- 2023 BLU  90      ← 新插入
-- 2023 RED 270      ← 冲突：150 + 120
-- 考点：一条语句里既插入了 BLU，又更新了 RED
部分 含义
INSERT INTO t SELECT … 用查询结果当作要插入的行
ON CONFLICT (yr, team) 冲突目标：哪个主键 / 唯一约束撞了算冲突。建议显式写出
DO UPDATE SET … 撞了就改已有那一行。EXCLUDED.列 指"本来想插入的那一行"的值
DO NOTHING 撞了就跳过

换成 DO NOTHING，结果是这样：

ON CONFLICT (yr, team) DO NOTHING;
-- 2023 RED 仍然是 150：冲突的行被跳过，不改
-- 2023 BLU 照常插入
-- 考点：DO NOTHING 撞了就跳过，DO UPDATE 撞了才改

易错点

UPSERT 要同时管好插入和更新两种行。

踩坑：从同一张表读、往同一张表写，数据库替你挡住了。INSERT INTO t SELECT … FROM t 里的 SELECT，读的是语句开始前的数据。它不会读到自己刚插进去的行，否则就会无限复制下去。这正是 #13 §10 万圣节问题 在插入上的版本。

踩坑：一条语句里别让两行撞同一个键。SELECT 产生的两行如果都撞上同一个已有主键，PostgreSQL 会直接报错。DuckDB 也不允许同一条语句把同一行更新两次。写之前确认 SELECT 的结果在冲突键上是唯一的。

踩坑：评分是"改完之后再查表"。作业会用一条固定的 SELECT … ORDER BY … 把表读出来比对。所以你的 UPSERT 要让插入的行和被改的行都正确。两种情况缺一不可。

本节对应演示的第 4 个场景。

2题型一：slotted page 和日志结构存储各有什么毛病

难度 ★★★★★必会HW2 Q1 直接考两种存储的代价判断

slotted page 原地改，毛病是碎片和随机写。日志结构只追加，毛病是写放大。

UPDATE t SET v = 2 WHERE id = 1;     // 示意
// slotted page：找到 id = 1 所在的页，原地改
// LSM：往 MemTable 里追加一条新版本，旧的留着
// 考点：一个原地改、一个只追加，代价因此完全不同

slotted page 像在笔记本上用涂改液改字，改多了页面坑坑洼洼。LSM 像记流水账，只往后写。账本攒多了，就得定期誊抄一遍，这就是压实。

先把两种方式的写路径摆在一起

把插入、更新、删除、读、后台维护并排一看，差别就清楚了。

slotted page（元组导向） 日志结构（LSM）
插入 找一个有空位的页，写进去，登记 slot 追加到内存里的 MemTable，满了整体刷成一个 SSTable
更新 原地改。改不下就删了重插 再追加一条新版本，旧的留着
删除 标记 slot 为空，页里留下空洞 追加一条墓碑
读 一次索引定位 → 一页 MemTable → L0 → L1 …… 可能翻好几层
后台维护 页内整理 / VACUUM 回收空洞 压实：把多层合并重写

各自的代价（这正是判断题在问的）

判断题问的，就是下面四种代价各落在谁身上。

代价 slotted page 日志结构 为什么
写放大 不是主要问题 有，核心代价 同一条记录先进 L0，再一路压实到 L1、L2。每下沉一层就被重写一次（#05 §8）
碎片 有 不是这种碎片 删除和变长更新，在页里留下大小不一的空洞。LSM 从不原地改，只是旧版本暂时占空间，等压实回收
随机写 有 没有 要改的元组散在不同的页里，刷脏页就是一堆随机写。LSM 永远顺序追加
随机读 可能有 读多但顺序 相关元组分散在不同页时，要跳着读。LSM 要多翻几层，但每个 SSTable 内部是顺序读的

自编算例 A：写放大。一条 100 字节的记录写进 LSM，要经历下面几步：

写 WAL                第 1 次落盘
MemTable 刷成 L0      第 2 次落盘
压实进 L1             第 3 次落盘
压实进 L2             第 4 次落盘
// 考点：同一份字节至少落盘 4 次，这就是写放大

同一份字节至少落盘 4 次。分层压实时还有额外开销。合并进下一层时，下一层里键范围重叠的部分也要重写。所以实际倍数更高。

自编算例 B：碎片。空闲空间总量够，但不连续，照样放不下。

8 KB 的页塞了 26 条 300 字节的元组，剩下的零头已经放不下一条新元组
删掉其中不相邻的 5 条：多出 1500 字节空闲，但被切成 5 个 300 字节的洞
来一条 600 字节的新元组：哪个洞都放不下
// 考点：除非先做一次页内整理，把空洞挤到一起

这像停车场里零散空出 5 个车位。来了一辆要占两个车位的大巴，还是停不进去。

比较两者时常见的几种说法，逐条想清楚

五种说法逐条过一遍。变长和维护这两条，两者一样。其余几条要单独看。

  • 都支持变长元组吗？ 都支持。slotted page 靠 slot 数组里的偏移加长度支持变长（#03 §9）。日志记录本来就是一条条变长的。
  • 谁更省磁盘空间？ 不能一概而论。LSM 在压实之前，同时留着新旧版本和墓碑。slotted page 有空洞。哪个大，取决于负载和压实时机。
  • 纯追加（只插不改不删）负载下呢？ 两者差不多。slotted page 每次都写到最后一页的末尾，一页满了就开新页。行为上就退化成了顺序追加。
  • 模式（schema）要不要跟着每条元组存？ 不用。模式在系统目录（catalog）里。元组头里只放 NULL 位图等少量信息（#03 §11）。
  • 大量增删改之后谁需要维护？ 两个都需要。LSM 要压实。slotted page 也要整理空洞、回收几乎空了的页，PostgreSQL 的 VACUUM 就是干这个的。
INSERT ...   // 只插入：新元组总放在最后一页的末尾
INSERT ...   // 满了就开新页，从不回头改旧页
// 考点：这和日志一路往后追加，是同一种 I/O 模式
// 考点：区别只是 slotted page 还额外维护着 slot 数组

踩坑：判断「随机读」时，别被"要翻好几层"骗了。翻的次数多 ≠ 随机。题目问的是 I/O 的访问模式，不是 I/O 的次数。

3题型二：NSM / DSM 下一条查询要读几页

难度 ★★★★★必会HW2 Q2 直接考，最少最多页和缓冲池都要算

行存读一列，就得把整行一起读进来。列存只读用到的列。数页数，就是把每列实际要读的页数加起来。

NSM 像一摞完整的档案袋，想看一页纸也得把整袋抽出来。DSM 像按科目分开的成绩册，只翻你要的那几本。

先把模型建起来

自编表：Q(k, x, y)，k 是主键，三列等宽。一共 12,000 条元组，用 NSM 存正好占 120 页。不考虑页头、元组头。没有索引，缓冲池无限大，开始时内存里一页都没有。

存储模型 布局 页数
NSM（行存） 一页放 100 条完整元组 120 页
DSM（列存，隐式偏移） 每列单独存。三列等宽 → 每列占总量的 1/3 每列 40 页，每页 300 个值 
int page = i / 300;   // 第 i 条元组，在每一列里都落在这一页
int slot = i % 300;   // 页内第几个值
// 考点：三列等宽，同一个 i 在 k、x、y 三列里页号相同

补充：「隐式偏移」是什么意思？第 i 条元组的 x，就在 x 列的第 i 个位置（#06 §5 方案 A）。三列等宽时，第 i 个值在三列里落在同一个页号上。后面所有「最少几页」都靠这条性质。

这像三本页码对齐的花名册。第几页第几行，在三本里都是同一个人。

读懂两条假设：「内容最坏」+「顺序任意」

「最少要读几页」问的是：取值按最坏的来，排列挑最好的。这样还要读几页？

内容最坏：WHERE x = 7 命中每一行     // 取值由出题人定死
顺序任意：命中的行怎么排，由你挑       // 最少挑最好的排列，最多挑最坏的

这像打牌。发到手里的是最差的一手牌，但怎么排顺序由你定。

这类题通常同时给两条假设，必须分开理解：

假设 含义 影响
内容最坏 元组的取值总让查询干最多的活。比如过滤条件全部命中 谓词命中多少行由它定死，不能指望"只命中一行"
顺序任意 元组在文件里的排列顺序可以随便换 「最少」= 挑最有利的排列。「最多」= 挑最不利的排列

例 1：带过滤的全表聚合

没有索引，过滤列得整列读完。内容最坏，输出列也得整列读完。

SELECT MAX(y) FROM Q WHERE x = 7;
-- 考点：NSM 读 120 页，DSM 读 40 + 40 = 80 页
模型 计算 页数
NSM 每条元组都要检查 x。x 和 y 跟整行一起存 → 整张表读一遍 120
DSM 先读完 x 列判断谁命中：40 页。内容最坏 → 每行都命中 → y 列 40 页也全要读。k 列一页都不用碰 40 + 40 = 80

踩坑：这里没有「最少」和「最多」之分。没有索引，x 列必须读完。内容最坏，又让 y 列必须读完。

过滤列和输出列换个位置，算法一样：

SELECT k FROM Q WHERE y > 100;   -- 内容最坏
-- NSM：120 页，整行一起存
-- DSM：y 列读完 40 页判断条件，全部命中 → k 列 40 页，共 80 页
-- 考点：换成 y 过滤、输出 k，页数和例 1 一样

例 2：几个主键的点查

DSM 的「最多」不是每列读满。知道偏移就能直接跳到那一页，只读命中的那几页。

SELECT x, y FROM Q WHERE k = 5 OR k = 77 OR k = 900;
-- 考点：k 列要扫，x、y 两列按偏移跳着读

这像查字典时已经知道页码。直接翻过去，不用从第一页翻起。

模型 最少 最多
NSM 1：三条元组恰好都在第 1 页。k 是主键，三个值都找到了就可以停 120：其中一条在最后一页，前面的页一页也省不了
DSM 3：三个键都在 k 列第 1 页（1 页）。它们的偏移都小于 300 → x、y 也各只在第 1 页（1 + 1） 46：最后一个键在 k 列最后一页（40 页）。三个键分散在三个不同的页。所以 x 要读 3 页，y 也要读 3 页（40 + 3 + 3）

踩坑：这是最容易错的地方。DSM 的「最多」里，x、y 不是各读 40 页。知道了偏移，就能直接跳到那一页，只读命中的那几页。要读几页，取决于命中的元组分散在几个页里。

只查一个键时，命中的行只落在一个页里：

SELECT * FROM Q WHERE k = 42;
-- DSM 最少：k 第 1 页找到（1 页）+ x、y 各 1 页 = 3
-- DSM 最多：k 在最后一页（40 页）+ x、y 各 1 页 = 42
-- 考点：只有一个键，x、y 各只读 1 页

踩坑：列不等宽时，这条捷径就失效了。假如 y 是 k 的两倍宽。同一个偏移在 y 列落在哪页，要按宽度换算。「三列同页」不再成立。

宽度比 k : x : y = 1 : 1 : 2，总量还是 120 页，总宽 4 份
k、x 各占 1/4 → 30 页
y 占 2/4 → 60 页
// 考点：列不等宽，每列的页数按宽度比来分

例 3：嵌套子查询 + 缓冲池

同一页第二次访问会命中缓冲池，不算磁盘读。所以内层读过的列，外层再读不花钱。

SELECT MIN(k) FROM Q WHERE y = (SELECT MAX(y) FROM Q);

用 DSM：

内层：求 MAX(y) → y 列 40 页全部读进缓冲池（40 次磁盘读）
外层：再扫一遍 y 找等于最大值的行 → y 列已经在缓冲池里（缓冲池无限大）→ 0 次磁盘读
     命中的行要取 k → 内容最坏 = 所有行的 y 都相等 = 全部命中 → k 列 40 页
合计：40 + 0 + 40 = 80 页
考点：缓冲池无限大，同一页只算一次磁盘读

换成 NSM：内层读 120 页，外层全在缓冲池里。合计 120 页。

补充：「缓冲池无限大」这条假设，就是让你别把同一页算两次。第二次访问命中缓冲池（#04 §2），不算磁盘读。

缓冲池像桌上摊开的书。第二次要看，低头就行，不用再跑一趟图书馆。

本节对应下方演示的前三个场景。第 4、5 个场景讲的是第 4 节的压缩。

数页数的通用步骤

把下面五步走一遍，「最少」和「最多」各算一次。

① 算出每种布局下每列 / 每表占几页
② 哪些列是"必须读完"的？（没有索引的过滤列、内容最坏下要输出的列）
③ 哪些列是"按偏移跳着读"的？命中的行最少落在几页、最多落在几页？
④ 同一页第二次访问：缓冲池里有没有？
⑤ 把每列的页数加起来，"最少"和"最多"各算一遍

4题型三：列式压缩

难度 ★★★★★必会HW2 Q3 直接考保序字典和排序的影响

压缩题只问一件事：这种编码的大小，取决于什么。

保序字典编码：怎么判断一组编码合不合法

保序字典要求编码的大小关系，和原值的大小关系一致。这样范围查询可以直接在编码上做。

这是 #06 §9 字典编码 里讲的「保序」。比如 city >= 'C' 可以变成 code >= 某个数。

保序字典像发号码布。先按身高排好队再发号，号码大的人一定更高。比号码，就等于比身高。

自编例子：一列城市名 [Xian, Beijing, Shanghai, Chengdu, Beijing]。

① 取出不同值并排序：Beijing < Chengdu < Shanghai < Xian
② 依次给出严格递增的编码：Beijing=0, Chengdu=1, Shanghai=2, Xian=3
③ 按原列顺序替换：[3, 0, 2, 1, 0]

WHERE city >= 'C'    -- 原来要比字符串
WHERE code >= 1      -- 保序后直接比整数：Chengdu=1 是第一个 >= 'C' 的值

判断一组编码合不合法，只查两件事。一是相同的值编码相同。二是按原值排好序后，编码严格递增。数字本身是多少、中间有没有空隙，都无所谓。

候选编码 合法吗 理由
[3, 0, 2, 1, 0] 合法 标准答案
[40, 5, 30, 12, 5] 合法 5 < 12 < 30 < 40，顺序对，空隙无所谓
[1, 2, 3, 4, 2] 不合法 这是「按出现先后编号」。Xian 得到最小的 1，顺序反了
[3, 0, 1, 2, 0] 不合法 Shanghai 拿到 1、Chengdu 拿到 2，两者顺序颠倒
[3, 0, 2, 1, 4] 不合法 两个 Beijing 编码不同 
[30, 2, 20, 10, 2]   // 合法：Beijing=2 < Chengdu=10 < Shanghai=20 < Xian=30
[3, 0, 2, 1, 1]      // 不合法：第二个 Beijing 编成了 1，和 Chengdu 撞了
// 考点：两条都要查，相同值编码相同，排好序后编码严格递增

踩坑：只做点查（=）就不需要保序。只要求一一对应，哈希式的字典就够了。保序是为了范围查询和排序。

先排序再压缩：哪些编码会变好

压缩效果取决于相邻值之间的关系，排序就有帮助。只取决于整列的值域或不同值个数，排序就没用。这就是判断标准。

RLE 原列：   B A B C A B A C B A   → 10 个游程
RLE 排序后： A A A A B B B B C C   → 3 个游程
// 考点：RLE 吃的是相邻值，排序让相同值连成段

排序像把同色袜子收在一起。RLE 清点时只要报"白的几双、黑的几双"，越整齐越省事。

编码 排序有帮助吗 自编例子
RLE 游程编码 有 [B,A,B,C,A,B,A,C,B,A] 一个连续段都没有 → 10 个游程。排序后 [A×4, B×4, C×2] → 3 个游程
Delta 增量编码 有（数值型） [105,101,108,102,107] 相邻差是 −4、+7、−6、+5。排序后 [101,102,105,107,108]，差变成 +1、+3、+2、+1。每个差 2 位就够
Bit-packing 位打包 没有 位宽只取决于最大值：108 无论排在哪都要 7 位
Mostly 编码 没有 取决于「大多数值能不能塞进小位宽、例外有几个」，与顺序无关
Bitmap 位图 没有 每个不同值一张位图，每行一位。总大小 = 行数 × 不同值个数，与顺序无关
字典编码 没有 字典大小 = 不同值个数，每行一个定长编码，与顺序无关

位图的大小和顺序无关，算一下就清楚：

1,000,000 行，5 个不同值，只用位图编码，不再叠加别的压缩
5 张位图 × 1,000,000 位 = 5,000,000 位
排序后：还是 5,000,000 位
// 考点：位图本身的大小与顺序无关

补充：如果在位图上面再套一层 RLE 之类的压缩，排序确实有用。位图里会出现长串的 0 和 1，压得更小。但那是叠加的第二种编码的功劳。读题时看清问的是哪一种编码本身。

几种编码的适用场合（判断题常考）

下面五种说法，前四种都站不住，只有 RLE 那条成立。

// 位图编码：插入一行，值为 v
for (int j = 0; j < num_distinct; j++)
  bitmap[j].push_back(j == code(v));   // 每一张位图都要追加一位
// 考点：开销正比于不同值个数，高基数列上很贵
说法类型 想清楚这一点
「Delta 适合压长文本」 Delta 存的是相邻值的差。对数值、时间戳这类相邻值接近的数据有效。长字符串之间的"差"并不小，用它没意义
「Bitmap 在高基数列上增删改没有开销」 高基数 = 不同值很多 = 位图很多。插入一行要给每一张位图都追加一位。开销正比于不同值个数
「点查必须用保序字典」 点查只需要等值匹配，不需要保序。见本节开头的保序字典编码
「更新多时字典 / Delta 总要重新编码」 新值已经在字典里，就不用动字典，只改那一行的编码。「总是」这种词通常是陷阱
「RLE 适合低基数整数列」 不同值少 → 相同值容易连成段（尤其排过序时）→ RLE 有效

2题型一：线性探测与墓碑

难度 ★★★★★必会HW3 Q1 直接考，要手动模拟

线性探测删除时不能清空槽，要留墓碑。否则后面的键会被"截断"，再也查不到。

规则

插入可以复用墓碑，查找遇到墓碑不能停。

插入 x：从 h(x) 开始往下找第一个「空槽或墓碑」放进去（到底了绕回槽 0）
查找 x：从 h(x) 开始往下找，直到「找到 x」或「遇到真正的空槽」为止
         遇到墓碑不能停，要继续往下
删除 x：先查找到它，然后把那个槽标成墓碑，而不是清空

讲义 #07 §5 的说法是：墓碑在查找时当"被占用"，插入时可以复用。

墓碑像停车位上的"此位暂空"牌。找车的人看到牌子，要继续往后找。停车的人看到牌子，可以直接停进去。

自编例子：5 个槽，h(x) = x mod 5

下面一路插入、删除、查找，看墓碑怎么起作用。

操作 过程 槽 0 槽 1 槽 2 槽 3 槽 4
插入 12 h = 2，空 12
插入 7 h = 2 占了 → 3 12 7
插入 22 h = 2 → 3 → 4 12 7 22
插入 3 h = 3 → 4 → 绕回 0 3 12 7 22
删除 7 在槽 3 找到 → 留墓碑 3 12 墓碑 22
查找 22 2 不是 → 3 是墓碑继续 → 4 命中 3 12 墓碑 22
插入 17 h = 2 占了 → 3 是墓碑 → 复用 3 12 17 22

在这张最终的表上查找 7：

h(7) = 2
槽 2（12，不是）→ 槽 3（17，不是）→ 槽 4（22，不是）
→ 槽 0（3，不是）→ 槽 1（空）→ 停，7 不存在
考点：查找一直走到真正的空槽才停，中途要绕回槽 0

踩坑：删除 7 时如果直接把槽 3 清空，就会出错。查找 22 从槽 2 出发，到槽 3 看见空槽就停下，误判 22 不存在。这就是墓碑存在的原因。

踩坑：别忘了绕回。插入 3 时从槽 3 往下走到底，要回到槽 0。

补充：要求键唯一的表里，复用墓碑有个前提。插入前还得先确认后面没有同一个键。比如 17 早就在槽 4 之后的某处。作业的题一般不考这一层，但写 Project 时要注意。

3题型二：布谷鸟哈希

难度 ★★★★★必会HW3 Q1 直接考，含死循环判断

布谷鸟哈希查找只看两个位置，所以是 O(1)。代价是插入时可能一路踢人，甚至死循环。

规则（作业的写法，本例沿用）

满了就把旧键踢走，被踢的键去自己的另一张表。

两张表 T1、T2，各有自己的哈希函数 h1、h2
插入 x：
  ① T1[h1(x)] 空 → 放进去
  ② 否则 T2[h2(x)] 空 → 放进去
  ③ 都满 → 把 T1[h1(x)] 里的旧键踢出来，x 占它的位置
     被踢的键去「它的另一张表」，如果那里也有人，就继续踢……直到落进空位
查找 / 删除：只看 T1[h1(x)] 和 T2[h2(x)] 两个位置，保证 O(1)

这像抢座位。你坐了别人的位子，被挤走的人去找自己的备用座。备用座上要是有人，再把那人挤走。

自编例子：每张表 4 个槽，h1(x) = x mod 4，h2(x) = (x >> 2) mod 4

先算出每个键的两个候选位置，后面的踢人过程就一目了然：

键 二进制 h1 = 最低 2 位 h2 = 第 2–3 位
6 0110 2 1
10 1010 2 2
26 11010 2 2
42 101010 2 2

依次插入 6、10、26：

插入 6  ：T1[2] 空 → T1[2] = 6
插入 10 ：T1[2] 被 6 占 → T2[2] 空 → T2[2] = 10
插入 26 ：T1[2]（6）和 T2[2]（10）都满 → 踢出 T1[2] 的 6，26 进 T1[2]
          6 去另一张表：T2[h2(6)] = T2[1] 空 → 落定
结果    ：T1 = [ -, -, 26, - ]    T2 = [ -, 6, 10, - ]

再插入 42：

42 进 T1[2]，踢出 26 → 26 去 T2[2]，踢出 10 → 10 去 T1[2]，踢出 42
→ 42 去 T2[2]，踢出 26 → 26 去 T1[2] …… 永远停不下来

怎么一眼判断会不会死循环

k 个键的候选位置加起来不到 k 个，就一定死循环。

把每个键的候选位置写成 (T1 槽, T2 槽)。有 k 个键，候选位置加起来却不到 k 个，就一定放不下。上面 10、26、42 三个键的候选位置都是 (2, 2)。3 个键只有 T1[2]、T2[2] 两个位置。

这像 3 个人抢 2 把椅子。怎么换座，总有一个人站着。

4  = 000100 → (0, 1)
20 = 010100 → (0, 1)
36 = 100100 → (0, 1)     // 3 个键只有 T1[0]、T2[1] 两个位置：会死循环
                         // 第三个键插入时开始无限踢
4、21、38 → (0, 1)、(1, 1)、(2, 1)   // h1 各不相同，三个键都直接进 T1：不会
// 考点：先写出每个键的 (h1, h2)，再数候选位置够不够

踩坑：反过来，「很多键的 h1 相同」不一定死循环。比如 3、7、11、15 的 h1 都是 3，但 h2 分别是 0、1、2、3。4 个键有 5 个候选位置，每个子集也都够放，就不会死循环。

补充：真实实现会记录踢了几次。超过阈值就判定为循环。然后扩容或换哈希函数重建（#07 §6 两个细节）。

4题型三：可扩展哈希（按最低位分桶）

难度 ★★★★★必会HW3 Q2 直接考，连续翻倍最容易算错

只有「满桶且 d = g」时，目录才翻倍。其他满桶只分裂自己。

目录像楼层的房间索引牌，桶像房间。房间满了，先隔成两间。索引牌的位数不够区分新房间了，才换一块大一号的牌子。

规则

全局深度 g 管目录有多大。局部深度 d 管桶里的键有几位相同。

全局深度 g：目录有 2^g 个格子，看哈希值的最低 g 位决定去哪一格
局部深度 d：这个桶里的键，最低 d 位都相同
插入到一个满桶：
  · d < g：只分裂这个桶（d+1），按第 d 位重新分配，把一半目录指针改指新桶
  · d = g：先把目录翻倍（g+1，新格子复制旧格子的指针），再按上一条分裂
  · 分裂完如果还是全挤在一边，就继续分裂（可能连着翻倍好几次）

作业里哈希函数就是键本身，本例也这样假设。

自编例子：每个桶最多 2 个键，从 g = 0、一个空桶开始

一串低位相同的键，会逼着目录连续翻倍。下面的 13 就把 g 从 1 一路推到了 3。

插入 发生了什么 g 各桶（后缀 · 局部深度 · 内容）
5, 9 唯一的桶装得下 0 无后缀 d=0 [5, 9]
6 桶满且 d = g → 目录翻倍。按最低 1 位分：6 是 …0，5、9 是 …1 1 0 d=1 [6] · 1 d=1 [5, 9]
13 进 1 桶，满且 d = g → 翻倍到 g=2，分成 01 和 11。5（0101）、9（1001）、13（1101）低 2 位都是 01。全挤在 01，11 是空的 2 还没插进去
13（续） 01 仍然满且 d = g → 再翻倍到 g=3，分成 001 和 101。9 → 001，5、13 → 101 3 0 d=1 [6] · 001 d=3 [9] · 101 d=3 [5, 13] · 11 d=2 [ ]

最终的目录（8 格）：

000 ─┐
010 ─┤
100 ─┼─→ 桶 …0   d=1  [6]        ← 4 个格子指着同一个桶
110 ─┘
001 ───→ 桶 …001 d=3  [9]
101 ───→ 桶 …101 d=3  [5, 13]    ← 满了，而且 d = g
011 ─┐
111 ─┴─→ 桶 …11  d=2  [ ]

接着插入谁会怎样

落进的桶有空位，就直接放。只有落进 …101 这个满桶，目录才会翻倍。

下一个键 最低 3 位 落进的桶 结果
4 100 …0，只有 1 个 直接放，不分裂
3 011 …11，空的 直接放，不分裂
1 001 …001，只有 1 个 直接放，不分裂
21 101 …101，满且 d = g 分裂并且目录翻倍到 g = 4（5 和 21 的低 4 位都是 0101，13 是 1101） 
if (bucket->IsFull()) {
  if (bucket->local_depth == global_depth) DoubleDirectory();  // 只有这种情况 g + 1
  SplitBucket(bucket);                                          // d < g 时只分裂自己
}
// 考点：满桶且 d = g 才翻倍，满但 d < g 只分裂桶

补充：全局深度什么时候增加？桶是满的，并且它的 d 等于 g，两条同时成立才会。满但 d < g 的桶只分裂自己，目录不变。

踩坑：一串低位相同的键，会让目录连续翻倍。比如 16、32、48 的低 4 位全是 0000。要一直分到 g = 5，每个桶才不超过 2 个。第 4 位上，16、48 是 1，32 是 0。算这类题时把键写成二进制，从最低位开始一位一位看。

16 = 10000     低 4 位 0000，第 4 位是 1
32 = 100000    低 4 位 0000，第 4 位是 0
48 = 110000    低 4 位 0000，第 4 位是 1
g = 5 时：16、48 一桶，32 一桶
考点：从空表插入 16、32、48，最终全局深度是 5

5题型四：B+ 树插入、删除与 latch

难度 ★★★★★必会HW3 Q3 直接考插删模拟和 latch 判断题

先把阶 d 换算成具体门槛。再按三条规矩走：叶子复制上推，借键改路标，借不了就合并。

先把门槛算出来

作业给的是阶 d，每个节点最多 d 个指针、d−1 个键。还给了两条下溢规则：叶子按键数算，内部节点按指针数算。代进去算出具体数字，后面就不会算错。以 d = 4 为例：

int d = 4;
int max_keys     = d - 1;                 // 3：每个节点最多 3 个键
int leaf_min     = ceil((d - 1) / 2.0);   // 2：叶子键数 < 2 就下溢
int internal_min = ceil(d / 2.0);         // 2：内部节点指针数 < 2 就下溢
上限 下溢门槛
叶子 最多 3 个键 键数 < ⌈(d−1)/2⌉ = 2 就下溢
内部节点 最多 4 个指针（3 个键） 指针数 < ⌈d/2⌉ = 2 就下溢

这和 #08 的演示 用的是同一组门槛：最多 3 个键，叶子至少 2 个。

自编例子

下面四步，把插入、分裂、合并、借键各走一遍。初始树：

                 [20]
           /            \
     [8 | 14]            [30]
    /    |    \          /    \
 [2,5] [8,11] [14,17] [20,25] [30,40,50]

① 插入 3。叶子 [2,5] 有空位，变成 [2,3,5]。什么都不分裂。

② 插入 45。叶子 [30,40,50] 已满，加上 45 变成 4 个键。平分成 [30,40] 和 [45,50]。再把右半边的第一个键 45 复制上推给父节点：

                 [20]
           /            \
     [8 | 14]            [30 | 45]
    /    |    \          /    |    \
[2,3,5] [8,11] [14,17] [20,25] [30,40] [45,50]

补充：叶子分裂是复制上推，45 在叶子里还在。内部节点分裂是推走中间键，它不再留在下层。见 #08 §7 的演示。

叶子分裂像复印一张路标贴到楼上，原件还留在楼下。内部节点分裂，是把路标整个搬上楼。

③ 删除 25。叶子 [20] 只剩 1 个键，下溢。同一个父节点下的兄弟是 [30,40]。它只有 2 个键，借出一个自己就下溢。所以借不了，只能合并：[20] + [30,40] = [20,30,40]。父节点删掉路标 30，变成 [45]。还剩 2 个指针，不下溢。

                 [20]
           /            \
     [8 | 14]             [45]
    /    |    \          /    \
[2,3,5] [8,11] [14,17] [20,30,40] [45,50]

④ 删除 11。叶子 [8] 下溢。左兄弟 [2,3,5] 有 3 个键，借一个还剩 2。所以借最大的 5 过来，变成 [5,8]。父节点里分隔这两个叶子的路标，从 8 改成 5：

                 [20]
           /            \
     [5 | 14]             [45]
    /    |    \          /    \
 [2,3]  [5,8] [14,17] [20,30,40] [45,50]

在这棵树上再删除 3：

叶子 [2,3] 变成 [2]，下溢
同父的右兄弟 [5,8] 只有 2 个键，借不了 → 合并成 [2,5,8]
父节点 [5 | 14] 删掉路标 5 → [14]，还剩 2 个指针，不下溢
考点：先看能不能借，借不了才合并，合并后检查父节点

易错点

借完不改路标、找错兄弟、忘了往上检查，是最常见的三种错。

if (sib->GetSize() - 1 >= leaf_min) {   // 兄弟借出一个后仍不下溢
  Borrow(node, sib);
  parent->UpdateSeparator(node, sib);   // 考点：借完必须改父节点的路标
} else {
  Merge(node, sib);                     // 考点：合并后父节点少一个指针，要再检查
}

踩坑：借键之后一定要改父节点的路标。不改的话，查 5 会被引到左边的叶子里去，找不到。

踩坑：只看同一个父节点下的紧邻兄弟（#08 §8 实现上的细节）。③ 里 [20,25] 左边的叶子 [14,17] 挂在另一个父节点下，不能找它借。

踩坑：合并会让父节点少一个指针。父节点也可能因此下溢，再往上借或合并。最坏一直传到根，树变矮一层。做选择题时每一层都要检查一次。

踩坑：两个兄弟都借得起时，先找谁？课上和作业通常会在题干里说清楚。没说的话，就看选项里哪种树符合「先左后右」或「先右后左」。别凭感觉。

latch 判断题的知识点

latch 题考的是拿放纪律。最要紧的一条是：先拿到下一个，再放当前这个。

auto child = bpm->ReadPage(child_id);   // 先拿孩子的 latch
cur.Drop();                             // 再放当前页的 latch
// 考点：顺序反过来，中间那一瞬间别人可能把指针改掉

这像攀岩。先抓牢下一个岩点，再松开手里这个。

说法类型 想清楚这一点 讲义
释放 latch 必须按获取顺序 不需要。为了并发，通常越早放上层越好。放的顺序没有正确性要求 #10 §7 释放顺序
乐观 crabbing 下写线程什么时候拿根的写 latch 第一遍一路拿读 latch，只在叶子拿写 latch。猜错了重来时，才从根开始一路拿写 latch #10 §8
读线程能不能先放当前页再拿下一页 不能。必须先拿到孩子（或兄弟）的 latch，再放当前的。否则中间那一瞬间，别人可能把指针改掉 #10 §9 单线程横扫
叶子横扫拿兄弟 latch 用 no-wait 对方持有不兼容的 latch，就拿不到。拿不到就立刻放弃、释放自己的、整体重试。不会死等，所以不会死锁 #10 §9
内部节点页和叶子页用不同的缓冲池 节点类型在 B+ 树里永远不变，叶子不会变成内部节点。所以分开管理很容易。分开后，OLAP 式的大范围叶子扫描不会把内部节点挤出缓冲池。OLTP 点查仍然快 #05 §1 多缓冲池 · #04 §5 顺序泛洪

6题型五：Bloom filter

难度 ★★★★★必会HW3 Q4 直接考置位、查询和判断题

Bloom filter 说「不在」，就一定不在。说「在」，只是可能在。

这像一排灯。每个人进门会按亮几盏。有一盏是灭的，这人肯定没来过。全亮着，也可能是别人顺手按亮的。

规则

插入只把几位置 1，查询看这几位是不是全为 1。

m 个位，初始全 0，k 个哈希函数
插入 x：把 h1(x) mod m、h2(x) mod m …… 这几位置 1
查询 x：这几位全是 1 → 「可能在」（可能是假阳性）
        有任何一位是 0 → 「一定不在」（不会有假阴性）

自编例子：8 个位，两个哈希函数（数值为示意）

下面插入两个词，再查两个词，正好碰到一次假阳性。

词 h1 h1 mod 8 h2 h2 mod 8
苹果 37 5 106 2
香蕉 49 1 61 5
西瓜（查询） 14 6 33 1
葡萄（查询） 29 5 42 2 
插入 苹果：置位 5、2      位 0..7 = 0 0 1 0 0 1 0 0
插入 香蕉：置位 1、5      位 0..7 = 0 1 1 0 0 1 0 0   （位 5 被两人共用）
查 西瓜：位 6 是 0               → 一定没插入过
查 葡萄：位 5、2 都是 1          → 「可能插入过」，其实没有：假阳性

再查一个 h1 = 22、h2 = 9 的词：

22 mod 8 = 6，9 mod 8 = 1
位 6 是 0 → 一定没插入过
考点：先取模再看位，有一位是 0 就一定不在

踩坑：Bloom filter 不能删除。想删掉苹果，就得清掉位 5、2。可位 5 也是香蕉的。再查香蕉，位 5 是 0，得出「一定不在」。这就出现了假阴性，是 Bloom filter 绝对不允许的（#09 §3）。

判断题的知识点

下面四种说法，前两种站不住，后两种成立。

说法类型 想清楚这一点
精确匹配查询上它比哈希索引好 不对。它只能回答「可能在 / 一定不在」。还得再去真正的索引或数据里找。精确查找本身用哈希索引
哈希函数越多假阳性率越低 不一定。函数多了，每次插入置更多的位。位图很快就满是 1（见下面的补充）
能减少磁盘 I/O 对。说「一定不在」，就不用去读那个文件 / 分区。LSM 每个 SSTable 配一个，见 #05 §6
插入和查询可以并行 对。几个哈希函数各算各的、各查各的位。插入用原子的置位操作即可

补充：下面是标准结论，课上没有推导。m 位、插入 n 个、k 个哈希函数时，假阳性率约为 (1 − e^(−kn/m))^k。代入上面的 m = 8、n = 2，结果如下。

k = 1    约 22%
k = 2    约 15.5%
k = 3    约 14.7%
k = 4    约 16%       // 反而升了
k = 5    约 18.5%
最优 k 约为 (m/n)·ln 2 ≈ 2.8
考点：哈希函数不是越多越好

7题型六：其他索引结构该用在哪

难度 ★★★★★必会HW3 Q5 直接考各索引适用的查询

LIKE '%top%' 这种中间匹配，什么树都救不了。这些结构都要求从键的开头比起。

这像查字典。知道开头几个字母好查，只知道中间几个字母就得整本翻。

结构 擅长 不擅长 / 注意 讲义
基数树 / 字典树 前缀查询（LIKE 'lap%'）。键有大量公共前缀时，比 B+ 树省空间。不需要重新平衡，每层也没有半满之类的要求 子串查询（LIKE '%top%'）一样要全扫 #09 §5
跳表 插入删除只改几根指针，平均比 B+ 树的分裂合并便宜 查找是期望 O(log n)，靠概率，不是保证。范围扫描不如 B+ 树，因为 B+ 树叶子页里键是连续存放的 #09 §4
倒排索引 关键词 / 全文检索：词 → 出现它的文档列表 维护成本高，要分词器 #09 §6
B+ 树 等值、范围、前缀 中间匹配（%x%）用不上有序性 #08
哈希索引 等值 范围、前缀都不行 #07

自编例子：表 items(name) 上有一个 B+ 树索引。

查询 索引能不能帮上忙
WHERE name = 'laptop stand' 能。B+ 树、哈希都行
WHERE name LIKE 'lap%' 能。B+ 树（转成范围 ['lap', 'laq')）、基数树
WHERE name LIKE '%top%' 不能。B+ 树、哈希、基数树、Bloom filter 都不行，它们都要求从键的开头比起。该换的是倒排索引，或按 n-gram 切词的索引

前缀能用，后缀不能，原因在叶子层的排列：

WHERE name LIKE 'lap%'   -- 能用：'lap' 开头的键在叶子层是连续的一段
WHERE name LIKE '%lap'   -- 不能：以 'lap' 结尾的键散落在整棵树各处
-- 考点：B+ 树的键按字典序排，定位到起点后顺着扫，只对前缀有效

踩坑：把非聚簇 B+ 树换成聚簇 B+ 树，也救不了。聚簇只改变数据在磁盘上的排列。%top% 照样得扫全部。

2题型一：连接算法的 I/O 成本

难度 ★★★★★必会HW4 Q1 直接考，公式和向上取整都要对

记号与假设（和讲义 #12 §3 一致）

成本只数磁盘 I/O。公式里的字母分「外层」和「内层」，不分具体哪张表。

int M, N;  // 外表、内表的页数
int m, n;  // 外表、内表的元组数
int B;     // 缓冲池页数
// 块嵌套循环：1 页读内表，1 页写输出，外表能用 B - 2 页
// 考点：谁在外层，谁的页数就填 M

M、N 像座位号，不是人名。谁坐在外层，谁的页数就填进 M。

符号 含义
M、N 外表（outer）、内表（inner）的页数
m、n 外表、内表的元组数
B 缓冲池页数。块嵌套循环里 1 页读内表、1 页写输出。外表能用 B − 2 页
不计 最终结果写回的成本。CPU 开销

踩坑：公式里的 M、N 跟着「谁在外层」走，不跟表名走。题目问「X 在外、Y 在内」，就先把 X 的页数填进外表的位置。这是这类题最常见的丢分点。

公式总表

六种算法的成本都在这张表里。套公式时，每个除法都要向上取整。

int bnlj   = M + ceil_div(M, B - 2) * N;           // 块嵌套循环
int passes = 1 + ceil_log(B - 1, ceil_div(P, B));  // 外部排序的遍数
int grace  = 3 * (M + N);                          // Grace 哈希连接
// 考点：每个除法和 log 都要向上取整，少一处就落到相邻选项

块嵌套循环像搬家用的推车。推车越大（B 越大），往返内表的趟数就越少。

算法 成本 要点
朴素嵌套循环 M + m · N 外表每条元组把内表整个扫一遍
块嵌套循环 M + ⌈M / (B−2)⌉ · N 外表每装满 B−2 页，就扫一遍内表。别忘了向上取整
索引嵌套循环 M + m · C C 是一次索引探测的代价。只要求内表有索引
外部归并排序（一张 P 页的表） 2P × 遍数，遍数 = 1 + ⌈log_(B−1) ⌈P / B⌉⌉ 每一遍都要把整张表读一遍、写一遍
排序归并连接 排外表 + 排内表 + 归并 归并时，无重复键是 M + N。最坏是连接键全相同，要 M · N
Grace 哈希连接 3 (M + N) 分区时读一遍、写一遍。探测时再读一遍。不计递归分区

排序 R ⌈600 / 22⌉ = 28 个 run。遍数 = 1 + ⌈log₂₁ 28⌉ = 1 + 2 = 3。2 × 600 × 3 3,600
排序 T ⌈1,500 / 22⌉ = 69 个 run。遍数 = 1 + ⌈log₂₁ 69⌉ = 3。2 × 1,500 × 3 9,000
排序 S ⌈200 / 22⌉ = 10 个 run。遍数 = 1 + ⌈log₂₁ 10⌉ = 2。2 × 200 × 2 800
排序归并 T ⋈ R 的归并阶段，最坏 1,500 × 600 900,000
同上，无重复键 1,500 + 600 2,100
(S ⋈ T) 的结果再和 R 归并，无重复键 120 + 600 720
Grace 哈希，S 外 R 内 3 × (200 + 600) 2,400

排序 R 那一行，拆成代码是这样：

runs   = ceil(600 / 22)            # 第 0 遍切出 28 个 run
passes = 1 + ceil(log(runs, 21))   # log₂₁ 28 ≈ 1.09，取整成 2，再加 1 是 3 遍
cost   = 2 * 600 * passes          # 每遍读一次、写一次，共 3,600
# 考点：块嵌套循环 R 外 S 内 = 600 + ⌈600 / 20⌉ × 200 = 600 + 30 × 200 = 6,600
# 考点：S 外 R 内 = 200 + ⌈200 / 20⌉ × 600 = 200 + 6,000 = 6,200
# 考点：B = 102 时排序 T，⌈1,500 / 102⌉ = 15 个 run
#       遍数 = 1 + ⌈log₁₀₁ 15⌉ = 1 + 1 = 2，I/O = 2 × 1,500 × 2 = 6,000

外部排序像整理一大摞卷子。桌上一次只摆得下 22 份，就先分堆排好，再一轮轮合并。

几个值得停下来看的地方：

  • 两种块嵌套循环差了 1,300 次。 小表 S 放外层时，内表只被扫 10 遍。T 放外层，要扫 75 遍。经验是「小表放外层」。但一定要算，外表页数和遍数都在公式里。
  • 排序 R 是 3 遍，不是 2 遍。 log₂₁ 28 ≈ 1.09，向上取整成 2。28 个 run 一次只能归并 21 个。第一轮过后还剩 2 个 run，还得再归并一轮。
  • 归并阶段最坏比最好大了 400 多倍。 最坏的情况是连接键全一样。内表的游标每次都得回溯到开头（#12 §5 回溯的四个要点）。

本节对应下方演示的前三个场景。

易错点

这一题的坑，集中在取整和「谁是 outer」上。先看哈希连接里谁要进内存。

// CMU 课上的叫法：建哈希表的一侧叫 outer（build side）
HashTable ht = Build(outer);            // outer 或它的每个分区，必须放得进内存
for (auto &t : inner) ht.Probe(t);      // inner 一页页流过去探测就行
// 考点：要放进内存的是 outer，inner 多大都行

outer 像摊在桌上的字典，得整本摆得下。inner 像要查的单词，一个个念过来就行。

踩坑：向上取整写在哪？块嵌套循环是 ⌈M / (B−2)⌉。排序有两处要取整，⌈P / B⌉ 和 ⌈log⌉。少一处，答案就落到相邻的选项上。出题人很喜欢把这个"差一点"的数放进选项。

踩坑：排序的第 0 遍用 B 页。之后每遍归并 B − 1 路，因为要留 1 页写输出。见 #11 §6。

踩坑：哈希连接里，到底谁要装进内存？CMU 课上把建哈希表的那一侧叫 outer（build side）。扫过来探测的那一侧叫 inner（probe side）（#12 §6）。所以要能放进内存的是 outer 表，或它的每个分区。inner 多大都行，一页页流过去探测即可。有些教材把 build 侧叫 inner。读题时看定义，别看名字。

判断题里的常见说法

这些判断题考的是公式背后的道理。拿公式推一下，真假就出来了。

int scans = ceil_div(M, B - 2);   // 块嵌套循环里，内表被扫的遍数
// B 变大，scans 变小，I/O 就少
// 考点：两表都放得进内存时，谁在外层都是 M + N
// 考点：两边已按连接键排好序，排序归并不用再排，只要 M + N
说法类型 想清楚这一点
两张表都放不进内存时，按元组处理比按块处理 I/O 少 反了。按块处理（块嵌套循环）每读一页，就把这一页的事做完。I/O 少得多
两张表都能放进内存时，谁在外层无所谓 对。各读一遍就全在内存里了。成本都是 M + N
索引嵌套循环只需要内表有索引 对。外表是顺序扫的，用不到索引
排序归并在任何情况下都比哈希连接快 不对。两边都已按连接键排好序时，它能和哈希连接一样快。两者都是 M + N。但不是"总是更快"
两边都已经排好序时，一定选哈希连接 不对。这时排序归并不用排序，只要 M + N。而且输出还是有序的
排序归并要求输入事先排好序 不对。它自己的第一阶段就是排序
块嵌套循环里加大缓冲池能减少 I/O 对。B 变大 → ⌈M / (B−2)⌉ 变小 → 内表扫描遍数减少

数据倾斜时的哈希连接

某个分区大得装不下，就只对它换一个哈希函数，再分一层。

场景：表太大，放不进内存。而且很多不同的键被 h₁ 分到同一个分区。这个分区大得装不下。

正确做法：仍然用 h₁ 分区。只对那个过大的分区换函数。用一个不同的哈希函数 h₂ 再分一层（递归分区，#12 §8）。

auto parts = Partition(R, h1);                // 第一层照常用 h1
for (auto &p : parts)
  if (TooBig(p)) p = Partition(p, h2);        // 只对过大的分区换 h2 再分
// 考点：B = 22 时 Grace 哈希 S ⋈ R，分 21 个分区，每个约 ⌈200 / 21⌉ = 10 页
// 考点：建哈希表时可用 B - 2 = 20 页，够了，不需要递归分区

这像分快递。一个格子塞爆了，就按另一套规则把这一格再细分。还按老规则分，东西只会原样落回同一格。

踩坑：为什么必须换函数？如果还用 h₁，同一个分区里的键会被分到同一个子分区里。等于什么都没做。

踩坑：递归分区也有救不了的情况。所有键都相同时，怎么分都在一起。注意，这里不只是哈希值相同。这时应该退回块嵌套循环。

3题型二：执行与优化的判断题

难度 ★★★★★必会HW4 Q2 直接考，逐条判断真假

这一题全是判断。先想清楚每种说法错在哪，再去讲义里对一下。拿向量化举例：

Batch b = child->Next();                           // 一次 Next() 吐一批元组
for (int i = 0; i < b.size; i++) Filter(b.rows[i]); // 紧凑循环，能用 SIMD，缓存友好
// 省掉的是每条元组一次的虚函数调用
// 考点：读的页和迭代器模型一样多，好处来自 CPU，不是磁盘 I/O

向量化像超市收银，一次扫一整筐，不用一件一件叫号。货一样多，省的是叫号的功夫（#13 §5）。

说法类型 想清楚这一点 讲义
Zone map 能让某些查询完全不读数据页 对，前提是 zone map 是最新的。比如求某列的 MIN / MAX，直接读每个区的元数据就够了 #13 §8
几个 OR 谓词各自都很有选择性，只命中很少的行。表又极大。这时用多索引扫描比顺序扫描好 对。每个索引各取一个 RecordID 集合。OR 就是求并集，只读命中的那几页 #13 §9
迭代器模型里元组总能一口气流过整棵计划树 不对。那只在一条流水线内成立。遇到流水线阻断算子，必须等孩子全部吐完。比如哈希连接的 build 侧、排序、子查询…… #13 §1 · §3
每个 worker 一个进程，故障隔离和调度控制都更好 只对一半。故障隔离确实更好。但调度上，线程模型给 DBMS 的控制更细 #14 §2
OLAP 查询能从查询内并行受益 对。一条大查询拆给多个 worker 同时跑，延迟下降 #14 §5
向量化模型的收益主要来自减少磁盘 I/O 不对。主要来自 CPU：调用次数少、缓存友好、能用 SIMD #13 §5
代价最低的计划一定最快 不对。代价是估出来的。统计信息可能过期。独立性假设可能不成立。代价模型可能不准 #15 §3 · #16 §10
谓词 / 投影下推总能让查询变快 不对。如果下推的谓词里有一个很贵的函数，比如 UDF。先做完一个很有选择性的连接再算它，调用次数反而少 #15 §6
采样统计只看表的一部分元组 对，这就是采样的定义 #16 §7 采样
等深直方图每个桶的值域宽度相同 不对。等宽是宽度相同。等深是让每个桶里的元组数大致相同，所以宽度不一 #16 §8
直方图 vs 采样 直方图要事先定好桶的边界，数据倾斜时很难定准。采样对任意谓词都能估，直接在样本上算。但它比查直方图慢。这些都与列是整数还是浮点无关 #16 §7–§8

补充：判断题里出现「总是 / 一定 / 保证 / 主要来自」时，先找反例。能找到，就是假的。

踩坑：「选择性高」这个词有两种用法。讲义 #16 §9 把选择性定义成「一条元组满足谓词的概率」。按这个定义，选择性高意味着命中的行多。但口语里常用「高选择性 / highly selective」表示命中的行少。作业这道题自己的括号说明，用的也是口语意思。遇到这个词，以题目给的解释为准。

4题型三：基数估算

难度 ★★★★★必会HW4 Q3 直接考选择性和连接公式

单表：独立性假设会怎样出错

两列相关时，优化器还把选择性直接相乘，行数就会估小。

自编例子：表 Course 有 20,000 行。其中 dept = 'CS' 占 8%，building = 'GHC' 占 2%。

SELECT * FROM Course WHERE dept = 'CS' AND building = 'GHC';

在均匀 + 独立假设下：

估计行数 = 20,000 × 0.08 × 0.02 = 32
考点：独立性假设就是把两个选择性直接相乘

但"计算机系的课在计算机楼上"，两列高度相关。假如 CS 的课有 80% 在 GHC，真实行数约为 20,000 × 0.08 × 0.8 = 1,280（示意）。独立性假设把它低估了 40 倍。

这像估算「既穿雨衣又打伞」的人数。两件事常一起出现，按独立相乘就估少了。

补充：正相关时，两个条件常常一起成立。所以同时成立的概率，比两个概率相乘要大。所以独立性假设通常导致低估。这正是讲义里「Honda Accord」那个例子（#16 §10）。

公式表

基数估算就这六个公式。主键、外键两行不用算，直接写答案。

double eq   = N / V_A;                          // A = c，均匀假设
double neq  = N - N / V_A;                      // A != c
double conj = N * (1 / V_A) * (1 / V_B);        // 合取，独立性假设，可以小于 1
double join = N_R * N_S / max(V_A_R, V_A_S);    // 连接，包含原则
// 考点：A 是主键时等值就是 1，外键连主键就是子表行数

等值估计像平均分蛋糕。N 行分给 V(A) 个不同值，每个值分到一样多。

情形 估计 说明
等值 A = c（A 不是键） N / V(A) 均匀假设：每个不同值出现得一样多
等值，A 是主键 1 主键唯一
不等 A ≠ c N − N / V(A) = N × (1 − 1/V)
合取 A = c AND B = d N × (1/V(A)) × (1/V(B)) 独立性假设。结果可以小于 1
连接 R ⋈ S（按 A） N_R × N_S / max(V(A,R), V(A,S)) 包含原则（#16 §11）
外键 → 主键的连接 = 子表（含外键那张）的行数 每条子表元组恰好连上父表的一条

自编算例：四张表

四张表、七个查询，把公式表的每一行都用上一遍。

表 行数 不同值个数
A(x, y) 6,000 V(x) = 300，V(y) = 600
B(y, z) 12,000 V(y) = 600，V(z) = 800
C(z, w)，w 是指向 D 的外键 12,000 V(z) = 800，V(w) = 700
D(w 主键, v) 3,000 V(w) = 3,000

假设：均匀分布。同名列的不同值集合完全重合。也就是说，V(y, A) 和 V(y, B) 是同一批值。

查询 计算 估计
σ_{w=7}(D) w 是主键 1
C ⋈ D 外键 → 主键：C 的每行恰好连上一行 12,000
σ_{x=5}(A) 6,000 / 300 20
σ_{z≠3}(C) 12,000 − 12,000 / 800 = 12,000 − 15 11,985
σ_{y=2 ∧ z=4}(B) 12,000 / 600 / 800 0.025
A ⋈ B 6,000 × 12,000 / max(600, 600) 120,000
A ⋈ B ⋈ C 120,000 × 12,000 / 800 1,800,000 
neq  = 6000 - 6000 / 300               # σ_{x≠5}(A) = 6,000 − 20 = 5,980
eq   = 3000 / 500                      # σ_{v=1}(D) = 6，这里设 V(v, D) = 500
join = 12000 * 12000 / max(800, 800)   # B ⋈ C（按 z）= 180,000
# 考点：不等就是「总数减等值」，连接的分母取 max(V)

本节对应演示的第 4 个场景。

易错点

基数估算有四个坑：外键连接、多表连接、取整、高估低估。先看多表连接怎么算：

step1 = 6000 * 12000 / max(600, 600)   # A ⋈ B = 120,000
step2 = step1 * 12000 / 800            # 再连 C，分子用上一步的估计 = 1,800,000
# 考点：第二步的分子是第一步的结果，分母是连接列的不同值个数

多表连接像接力跑。第二棒从第一棒交棒的地方起跑，不回起点重跑。

踩坑：不要被 V(w, C) = 700 骗了。外键 → 主键的连接，直接等于子表行数 12,000。如果硬套通用公式，算的是 12,000 × 3,000 / max(700, 3,000) = 12,000。结果碰巧一样，但要知道为什么是 12,000。

踩坑：多表连接的第二步，分子用的是第一步的估计结果。分母用连接列的不同值个数。有的题目会说「假设 C 的不同值个数始终是 800」。这就是告诉你，中间结果里 V(z) 也按 800 算。

踩坑：注意题目要不要取整。有的问题要求对估计值向上取整，有的直接问小数，比如 0.025。

踩坑：低估还是高估，看条件之间的关系。正相关的条件同时出现，会低估。互斥倾向的条件，比如 city = '匹兹堡' AND state = '加州'，真实值接近 0。这时独立性假设反而高估。

2题型一：判断一个调度

难度 ★★★★★必会HW5 Q1 四连问直接考，视图可串行最绕

四连问的顺序

判断一个调度就按这五步走。③ 的答案能直接定下 ⑤。

① 是串行的吗？       只要有两个事务的操作交错，就不是
② 画依赖图           同一对象、不同事务、至少一个是写
                     → 从先发生的连向后发生的
③ 冲突可串行吗？     依赖图无环 ⇔ 冲突可串行
④ 视图可串行吗？     找一个串行顺序，让三件事都一样：
                     读初值、读谁写的、谁写最终值
⑤ 2PL 能产生它吗？   2PL 只产生冲突可串行的调度
                     ③ 是「否」，这里就一定是「否」

这像体检。③ 那一项不过关，⑤ 的结论就已经定了。

自编调度

这个调度不是冲突可串行，却是视图可串行。差别出在盲写上。

四个事务、三个对象 X、Y、Z。时间从左往右：

时刻 t1 t2 t3 t4 t5 t6 t7 t8
T1 R(Y) W(Y)
T2 W(Y) W(X)
T3 R(X) W(Z)
T4 R(X) W(Y)

① 串行吗？ 不是。T1 的两个操作中间，夹着 T2、T3 的操作。

② 依赖图：按对象把操作按时间排好，再两两检查（#17 §10）。

对象 按时间的操作 冲突对 → 边
Y R1(t1) W2(t2) W1(t4) W4(t8) R1→W2：T1→T2 · W2→W1：T2→T1 · R1→W4、W1→W4：T1→T4 · W2→W4：T2→T4
X R3(t3) W2(t5) R4(t7) R3→W2：T3→T2 · W2→R4：T2→T4
Z W3(t6) 只有一个操作，没有冲突

边集合：T1→T2、T2→T1、T1→T4、T2→T4、T3→T2。

换个更短的调度，练一下画边：

R1(A)  W2(A)  R2(B)  W1(B)
A 上：R1 → W2，得到 T1 → T2
B 上：R2 → W1，得到 T2 → T1
考点：两条边成环，所以不是冲突可串行

③ 冲突可串行吗？ T1→T2→T1 是一个环，所以不是。

④ 视图可串行吗？ 写出三件事：

检查项 原调度里 推出的顺序约束
谁读了初值 T1 读 Y 的初值。T3 读 X 的初值 T1 要在所有写 Y 的事务（T2、T4）之前。T3 要在写 X 的 T2 之前
谁读了谁写的 T4 读到的 X 是 T2 写的 T2 在 T4 之前，且中间没有别人写 X
谁写了最终值 Y 是 T4。X 是 T2。Z 是 T3 T4 在 T1、T2 之后，因为它最后写 Y

满足所有约束的串行顺序：T1 → T3 → T2 → T4（T3 → T1 → T2 → T4 也行）。在这个串行顺序下，三件事完全一样。所以它视图可串行。

盲写像在黑板上写了字，没人看过就被擦掉重写。中间写过什么，不影响最后的结果。

补充：为什么依赖图里的环"不碍事"？环出在 Y 上。T2 和 T1 都写了 Y。可这两个值谁都没读过，最后又被 T4 覆盖了。T2 写 Y 之前从没读过 Y，这叫盲写（#17 §11 例 B）。视图可串行只关心"读到什么、最终留下什么"。所以它能接受这种调度。冲突可串行做不到。

⑤ 2PL 能产生它吗？ 不能。2PL 产生的调度都是冲突可串行的，而它不是。

本节对应下方演示的前两个场景。

判断题里的常见说法

这几条判断题，考的是每个协议「管什么、不管什么」。比如冲突可串行，就不管中止：

W1(A)  R2(A)  COMMIT(T2)  ABORT(T1)
依赖图只有 T1 → T2，无环，是冲突可串行的
但 T2 读了 T1 没提交的值，T2 又先提交了
考点：T1 中止后，T2 读到的值等于"从未存在过"
考点：这是脏读，而且不可恢复，冲突可串行管不了中止

冲突可串行像只查排队顺序的保安。有人中途退场，它不管。

说法类型 想清楚这一点 讲义
2PL 是乐观协议 不对。它先拿锁再动手，是悲观的。乐观的是 OCC #19 §1
Strong Strict 2PL 既没有级联中止、也天然没有死锁 只对一半。锁持有到提交，所以没有级联中止。但两个事务照样可以互相等对方的锁。所以死锁照样会发生，仍需检测或预防 #18 §5–§8
普通 2PL 保证冲突可串行 对 #18 §4
视图可串行的调度都冲突等价于某个冲突可串行的调度 不对。视图可串行比冲突可串行范围大。多出来的，就是上面那种带盲写的调度 #17 §11
冲突可串行的调度没有不可重复读和脏读 不对。冲突可串行只管"等价于某个串行顺序"，不管中止。例如 W1(A)、R2(A)、T2 提交、T1 中止。依赖图只有 T1→T2，无环。但 T2 读到了一个后来被撤销的值，这就是脏读 #17 §9

3题型二：层次封锁怎么选锁

难度 ★★★★★必会HW5 Q2 直接考，挑最弱且正确的锁组合

规则

从根往下，每层先挂意向锁。最后在要动的那一层拿真锁。能用弱锁，就不用强锁。

① 从根（数据库）往下走，在每个要经过的节点上先拿意向锁：
     下面要读  → 这里至少 IS
     下面要写  → 这里至少 IX
     这里要整体读、下面还要改一部分 → 这里 SIX
② 在真正要操作的那一层拿显式的 S 或 X
③ 在满足正确性的前提下，选「最弱」的锁
     越弱，和别人越兼容，并发越好

意向锁像大楼门口的登记簿。你要进楼里某间办公室，先在门口登记「楼里有人」。别人想包下整栋楼，一看登记簿就知道不行。

兼容性矩阵见 #18 §10。最常用的几条：IS 和除 X 以外的都兼容。IX 和 IX 兼容。S 和 IX 不兼容。SIX 只和 IS 兼容。

自编例子

读写的范围不同，锁的组合就不同。下面五个操作，用的是同一个数据库。

数据库 D 有两张表：Orders（3,000 页，记作 O1…O3000）和 Users（200 页，U1…U200）。每页 100 条记录。O450.3 表示 Orders 第 450 页第 3 条。没有索引。

操作 该拿的锁 理由
找出 Orders 里金额最大的订单 IS(D), S(Orders) 要扫全表，只读。表上一把 S，顶掉三十万条记录锁。D 上只需"下面有人读"的 IS
把 O450.3 的状态改成已发货 IX(D), IX(Orders), IX(O450), X(O450.3) 只改一条。一路 IX 下来，只在记录上拿 X
删除 Users 里所有 vip = false 的用户 IX(D), X(Users) 没有索引，要扫全表，可能大部分都要删。直接拿表级 X
扫描 O100–O900，并修改 O450.3 IX(D), SIX(Orders), IX(O450), X(O450.3) 既要读一大片，又只改其中一条。SIX 隐含了整表的 S
甲：扫 Orders 全表只读。乙：改 U17.5 甲 IS(D), S(Orders)。乙 IX(D), IX(Users), IX(U17), X(U17.5) D 上 IS 与 IX 兼容。两边动的是不同的表，所以完全并行

再看一个只读一页的操作：

-- 读 Users 第 5 页的全部记录
IS(D)        -- 根上声明「下面有人读」
IS(Users)    -- 表上同样声明
S(U5)        -- 读的是一整页，在页上拿 S 就够
-- 考点：不用一条条记录去锁

易错点

选锁题常错在四处。漏了上层、缺了真锁、SIX 放错层、记录上拿意向锁。

S(Orders)              -- 错：漏了 IS(D)，别人在 D 上拿 X 时看不见你
IS(D), IS(Orders)      -- 错：只声明了要读，没锁住任何记录
IS(D), S(Orders)       -- 对

只拿意向锁，就像只在门口登了记，没去拿房间钥匙。门是打不开的。

踩坑：漏了上层的意向锁。只写 S(Orders) 不写 IS(D)，协议就不成立。别的事务在 D 上拿 X 时，根本看不见你。

踩坑：只拿意向锁，不拿真正的锁。IS(D), IS(Orders) 只是"声明下面有人要读"。它没有锁住任何记录，读不了。

踩坑：SIX 放错层。SIX 的意思是"这一层整个读，下面某处还要写"。只是要改一张表里的记录，就没必要在数据库这一层拿 SIX。那会挡住所有想在别的表上拿 IX 的事务。

踩坑：记录是最底层，只能拿 S 或 X。在叶子层拿 IX 没有意义，因为下面已经没有东西了。

补充：「扫全表、只改其中几条」有两种写法。X(表) 简单，但挡住所有人。另一种是 SIX(表)，再对要改的行拿 IX(页), X(行)。这样别人还能 IS 进来读其他行，并发更好（#18 §10 例 2）。选择题要在给出的选项里挑最合适的那个。

4题型三：OCC 与后向验证

难度 ★★★★★必会HW5 Q3 直接考，要对齐读和写阶段的时刻

规则（作业的设定，与课上一致）

OCC 先在私有工作区里干活，到验证时才分配时间戳。验证只问一件事：我有没有读到旧版本？

读阶段：读写都在私有工作区里做
        读一个对象时，把它连同「写时间戳」一起复制进来
验证阶段：此刻才分配时间戳
          一次只允许一个事务在验证（串行验证）
后向验证：和「在我运行期间已经提交的事务」比
          它写的东西，我是不是读到了旧版本？
          是 → 我中止。否 → 通过
写阶段：把私有工作区的改动装进全局数据库

OCC 像先在草稿本上算题。交卷前才核对一遍：抄完题以后，题目有没有被人改过？改过就作废重来。

（#19 §4 的例子里，读操作会把 A=123, ts=0 一起复制进工作区。这正是后面能判断「读到的是哪个版本」的依据。）

踩坑：只比集合会多杀一个。教科书里有一种最保守的条件。它只看「对方的写集和我的读集有没有交集」。我读到的是哪个版本，它不看。按那种写法，T3 也会被中止。课上和作业是按「有没有读到旧版本」来判的。读的时候连写时间戳一起拷贝，验证时就能比出来。所以 T3 通过。读题时以课上的判法为准。

踩坑：T3 在 t9 读到的 X 是 T1 写的。OCC 的读，是从全局数据库取当时已提交的最新值。T1 在 t7 已经装入，所以 T3 拿到的是新值。

踩坑：时间戳在验证开始时才分配（#19 §4）。T1 物理上第一个开始。但如果 T2 先验证，T2 的时间戳就更小。

判断题里的常见说法

OCC 赌的是冲突少。赌对了，省掉加锁。赌错了，活就白干了。

Read(X)   // 第一次读：从全局数据库拷进私有工作区
Read(X)   // 再读一次：读的是自己那份，所以没有不可重复读
// 考点：验证只查读过、写过的对象，查不出新多出来的行，所以会有幻读
说法类型 想清楚这一点
OCC 在并发事务访问不相交的数据时最好 对。冲突少，几乎不中止，又省掉了加锁开销（#19 §7）
OCC 的中止很浪费，因为发生在事务干完活之后 对。验证在读阶段结束后才做。被中止时，活已经白干了
OCC 下会有不可重复读 不会。读过的对象已经拷贝在私有工作区。再读一次，读的是自己那份
OCC 下会有幻读 会。验证只检查读过、写过的对象。它不检查"满足某个条件的集合"有没有多出新行（#19 §8）
读集里的对象在事务开始时一次性全部读进来 不对。读阶段里用到哪个，读哪个

5题型四：MVCC 判断题

难度 ★★★★★必会HW5 Q4 直接考版本链、存储和 GC 判断

MVCC 判断题全围着版本链转。链怎么排，版本存哪，谁来回收，索引指向哪。

N2O: index -> [newest] -> [older] -> [oldest]   // 链头就是最新版本
O2N: index -> [oldest] -> [older] -> [newest]   // 读最新要一路走到链尾
// 考点：N2O 读最新快，不用沿链往下走
// 考点：但每次更新都换链头，所有指向链头的索引都得改指针

N2O 像把最新一期杂志放在最上面。拿最新的很快。可每来一期新的，所有目录卡都得改（#20 §9 ①）。

说法类型 想清楚这一点 讲义
追加式存储下，用主键索引读最新版本。这时新→旧（N2O）比旧→新（O2N）快 对。索引指向链头。N2O 的链头就是最新版本。O2N 要一路走到链尾 #20 §9 ①
O2N 下用协作式垃圾回收，二级索引必须用逻辑指针 不对。协作式回收是"顺着版本链往下找时顺手清"。它和你从哪个索引、用什么指针走到这条链无关 #20 §10 A-2
增量式存储下，后台 vacuum 只删增量记录、从不碰主表 不对。被删除的元组，在主表里那一份也要回收 #20 §9 ③ · §12 删除
增量式 + N2O 时，所有可回收的版本都在增量区里 不对。一条只有一个版本的元组，只存在于主表里。它被删除后，可回收的那份就在主表里 #20 §9
修改主键时，不管版本链怎么排都要当作「删除 + 插入」 对。主键索引里要同时保留两个条目。一个指向旧键，一个指向新键 #20 §11

2题型一：ARIES 日志分析

难度 ★★★★★必会HW6 Q1 直接考，要同时推日志、ATT、DPT、页

先记住四条推理规则

ARIES 题的每一问，都能从这四条规则推出来。最要紧的是第一条：检查点记的是 BEGIN 那一刻。

<CHECKPOINT-BEGIN>           // 在这一刻给 ATT、DPT 拍快照
<T3, BEGIN>                  // BEGIN 之后才开始，不进这次的 ATT
<CHECKPOINT-END, ATT, DPT>   // 只是把那张快照写出来
// 考点：END 里的两张表看 BEGIN 那一刻，不看 END 那一刻

模糊检查点像拍集体照。按快门那一刻在场的才算。照片洗出来得晚，不改变照片里有谁。

# 规则 来自
① CHECKPOINT-END 里的 ATT、DPT，是 CHECKPOINT-BEGIN 那一刻的快照。BEGIN 之后才开始的事务，不在 ATT 里。BEGIN 之后才变脏的页，不在 DPT 里 #22 §6
② 某页不在 DPT 里，说明 BEGIN 那一刻它是干净的。也就说明，它在 BEGIN 之前的所有修改都已经落盘 #22 §6 DPT
③ 有后台线程随时刷脏页。所以任何一个脏页，随时都可能已被刷掉。因此「一定是脏的」几乎从不成立。问「可能是哪些值」时，要把每一个中间值都算上 题干假设
④ 看到 TXN-END，才把事务从 ATT 里删掉。COMMIT 之后、TXN-END 之前，它仍在 ATT 里 #22 §3

情形 A：LSN 19 刚落盘就崩溃

只有 P 的值是确定的，Q、R、S 各有两种可能。ATT 是 {T1, T2}。

磁盘上每页可能是什么值？

页 推理 可能的值
P 不在 DPT 里 → 规则 ②：12 的修改在 15 之前已落盘。15 之后没人再改 P 只能是 6
Q 在 DPT 里 → 13 的修改可能落盘了，也可能没有 1 或 2
R 17 在 BEGIN 之后才改，DPT 不管它。按规则 ③，后台线程可能刷过，也可能没刷 0 或 1
S 同上（18） 7 或 8

崩溃点往后挪，R 的可能值还会变多：

17   <T3, UPDATE, prev=16, R, 0→1>   // R 第一次变
21   <T3, UPDATE, prev=17, R, 1→2>   // R 第二次变
// 考点：LSN 22 刚落盘就崩溃，R 被改过两次（0→1→2）
// 中间可能被后台线程刷过任意次，所以 0、1、2 都有可能

后台刷盘像随手存档。你知道最后改到了哪，却不知道它存到了哪一步。

LSN 19 里的 ATT 是什么？ 按规则 ①，看 15 那一刻谁还活着。T1 还在跑。T2 已经 COMMIT，但还没 TXN-END（规则 ④）。T3 在 16 才开始，不在里面。所以 ATT = {T1, T2}。

情形 B：LSN 26 刚落盘就崩溃

ATT 是 {T1, T3}。DPT 不唯一，可能是 {Q, R, S} 的任意一个子集。

LSN 26 里的 ATT：看 23 那一刻。T1 在 22 已 COMMIT，27 才 TXN-END，所以还在。T3 在跑。T2 在 20 已经 TXN-END。T4 在 24 才开始。所以 ATT = {T1, T3}。

LSN 26 里的 DPT 可能是什么？

  • P：15 时是干净的，因为它不在第一个检查点的 DPT 里。15–23 之间没人改它。所以 23 时一定干净，不可能在 DPT 里。
  • Q（13 起就脏着）、R（17、21）、S（18）：在 23 之前都被改过。后台线程可能刷了，也可能没刷。

所以 DPT 可能是 {Q, R, S} 的任意一个子集，包括空集，一共 8 种。任何含 P 的都不可能。

for page in ["Q", "R", "S"]:
    in_dpt[page] = "可能在，也可能不在"   # 后台线程刷没刷，谁也说不准
# 每页两种情况，2 × 2 × 2 = 8 种，P 永远不在里面
# 考点：DPT 只记 BEGIN 那一刻还脏着的页

这像猜三盏灯开没开。每盏都可能开着，也可能关着。

情形 C：LSN 31 落盘后崩溃，并假设 LSN 26 里的 DPT 是空的

MasterRecord 指向 23。重做从 25 开始。撤销阶段处理 T3、T4，给 T3 补 3 条 CLR，给 T4 补 1 条。

MasterRecord 指向哪？ 指向最后一个已经写出 END 的检查点的 BEGIN，也就是 23。

分析阶段（从 23 扫到 31，#22 §8）：

LSN 记录 ATT DPT（页 : recLSN）
24 T4 BEGIN T4 空
25 T4 改 Q T4 Q:25
26 CHECKPOINT-END（ATT={T1, T3}，DPT=∅） T1(已提交), T3, T4 Q:25
27 T1 TXN-END T3, T4 Q:25
28 T3 改 R T3, T4 Q:25, R:28
29 T4 改 P T3, T4 Q:25, R:28, P:29
30–31 T4 ABORT、CLR(P) T3, T4（都要撤销） 不变 
22   <T1, COMMIT, prev=18>
27   <T1, TXN-END, prev=22>   // 分析阶段读到这里，就把 T1 从 ATT 里删掉
// 考点：T1 不用撤销，也不用再给它写 TXN-END
// 撤销阶段根本不会碰它

各页在最后一条日志写出时的状态：

问题 答案 理由
一定是干净的页 S 23 时不在 DPT（规则 ②）。之后再没人改它
崩溃时一定是脏的页 没有 规则 ③：后台线程可能把所有页都刷过了
崩溃时可能是脏的页 P、Q、R 23 之后都被改过

重做阶段（#22 §9）：从 DPT 里最小的 recLSN 开始，也就是 25。

记录 结论 理由
12、13、17、18、21 一定不重做 都在 25 之前。而且它们改的页，在 23 时都已干净
25、28、29、31 可能重做 页在 DPT 里，要读进来看 pageLSN 才知道。后台线程可能早已刷过
没有哪条 一定重做 规则 ③ 
// 假如 LSN 26 的 DPT 是 {R}，R 的 recLSN 记为 17
lsn_t redo_start = MinRecLSN(dpt);   // = 17，DPT 里最小的 recLSN
// 考点：这时 17、21 变成「可能重做」，要看 R 页的 pageLSN
// 考点：12、13、18 仍然一定不重做，因为 P、Q、S 在 23 时干净

撤销阶段（#22 §10）：ATT 里剩下的 T3、T4 要撤销。T1、T2 都已提交。

事务 要撤销的修改 新写的 CLR
T1 已提交 0
T2 已提交 0
T3 28、21、17 3
T4 29 已经被 31 那条 CLR 撤过。undoNext = 25，所以只剩 25 1

撤销按 LSN 从大到小、跨事务交替进行：

28  撤销（T3）
25  撤销（T4），随后 T4 写 TXN-END
21  撤销（T3）
17  撤销（T3），随后 T3 写 TXN-END
// 考点：如果 31 那条 CLR 没来得及落盘，日志只到 30
// 那么只有 ABORT、没有 CLR，T4 的 29 和 25 都没撤销，要补 2 条 CLR
// 先撤 29，再撤 25

撤销像倒带。不管是哪个事务录的，都按时间从后往前倒。

恢复完成后：P = 6、Q = 2、R = 0、S = 8。

踩坑：崩溃前已经存在的 CLR，不要重复算。T4 的 31 已经撤销了 29。沿 undoNext 直接跳到 25，所以只补 1 条（#22 §4 CLR）。

踩坑：「一定 / 可能 / 一定不」三个问题的答案要互相补全。每条 UPDATE / CLR 记录，恰好落在其中一类里。做完三问，可以拿来自检。

3题型二：日志与恢复的判断题

难度 ★★★★★必会HW6 Q2 直接考 STEAL / FORCE、提交点

NO-STEAL 就不需要 undo，FORCE 就不需要 redo。其余几条考提交点、TXN-END、检查点和索引日志。

NO-STEAL：未提交的改动从不上盘  →  不需要 undo
FORCE：   提交时改动已全部上盘  →  不需要 redo
// 考点：提交点是 COMMIT 记录落盘的那一刻，数据页可以以后再写

提交点像寄挂号信。回执（COMMIT 记录）落了盘就算数，包裹（数据页）可以晚点送到。

说法类型 想清楚这一点 讲义
STEAL = 未提交事务改过的页可以在提交前写盘 对 #21 §3
NO-STEAL + FORCE 下，恢复时要撤销中止事务的改动 不对。NO-STEAL 下，未提交的改动从不上盘，所以不需要 undo。FORCE 下，提交时改动已全部上盘，所以不需要 redo #21 §3 四种组合
STEAL + NO-FORCE 下，事务改过的数据页都写盘了才算提交 不对。提交点是 COMMIT 记录（连同它之前的日志）落盘的那一刻。数据页可以以后再写 #21 §6
FORCE 下可能要重做已提交事务的改动 不对。提交时所有改动都已（原子地）落盘，没有可重做的 #21 §3
只有提交的事务才有 TXN-END 不对。中止的事务撤销完，也写 TXN-END。这是 #22 §4 里中止流程的最后一步。TXN-END 只是告诉系统"可以从 ATT 里删掉了" #22 §3
模糊检查点不用暂停所有事务 对，这正是它的意义 #22 §6
模糊检查点开始后、结束前不能刷脏页 不对。照常刷。DPT 记录的是 BEGIN 那一刻的状态。之后刷掉的页，只会让恢复少做事 #22 §6
物理日志就不需要给索引另写日志 不对。物理日志记的是「哪一页哪个位置改成了什么」。索引的页也是页。改了索引，同样要有它自己的日志记录 #21 §8 索引也要记日志

4题型三：分布式数据库

难度 ★★★★★必会HW6 Q3 直接考分布式连接、CAP、2PC

分布式连接：谁该动、怎么动

已按连接键分区或全复制的表不动。剩下那张表，小就广播，大就 shuffle。

自编例子：8 个节点的 shared-nothing 集群。Orders(oid, cust, amt) 有 2 亿行，Items(oid, sku, qty) 有 500 万行。Items.oid 是指向 Orders.oid 的外键。查询按 oid 连接。假设从别的节点取数据，比读本地盘慢 10 倍。

配置 Orders 怎么办 Items 怎么办 理由
Orders 按 oid 分区。Items 在每个节点都有完整副本 不动 不动 每个节点用本地的 Orders 分区，和本地的 Items 全量做连接。零传输（#24 §9 情形 ①）
两张表都按 oid 分区 不动 不动 同一个 oid 的数据，本来就在同一个节点（情形 ②）
Orders 按 oid 分区。Items 按 sku 分区 不动 按 oid 重新分区（shuffle），或整个广播 Orders 太大，绝不能动。Items 要么按 oid 发到对应节点，每行发一次。要么复制到每个节点，每行发 7 次
Orders 按 cust 分区。Items 按 sku 分区 不动 广播 Items 两张都没按 oid 分区。一种办法是两张都 shuffle，Orders 的 2 亿行大部分都要过网络。另一种是把小表 Items 广播出去，Orders 原地不动。后者传输少得多

第三种配置下，两种搬法的网络量可以直接算：

shuffle   = 500 万 × 7/8 ≈ 440 万行     // 每一行 Items 只发一次
broadcast = 500 万 × 7   = 3,500 万行   // 每一行都发给另外 7 个节点
// 考点：这里 shuffle 的网络量更小
// 前提：Items 能按 Orders 的分区函数算出该去哪个节点

shuffle 像按门牌号送快递，每件只送一次。广播像给每户都塞一份传单，份数翻了好几倍。

补充：判断顺序分两步。先看哪张表已经按连接键分区，或者全复制。它就不用动。再看剩下那张大不大。小就广播，大就 shuffle（#24 §9 情形 ③）。

其他几个判断题考点

这三条分别考 CAP、原子提交和一致性哈希。

ring: A -> B -> C -> A    // 一致性哈希环，节点名是示意
remove(B)                 // B 挂了
// 原来落在 B 那段弧上的键，交给环上的下一个节点 C
// 考点：别的键原地不动，所以只有一部分键要搬

一致性哈希像圆桌分菜。有人离席，只把那人面前的菜挪给下一位。其他盘子都不动。

说法类型 想清楚这一点 讲义
网络分区时，分布式数据库能立刻提交且不损失一致性 不对。分区时只能在一致性和可用性之间选一个。要一致，就得等或拒绝。要立刻提交，就可能不一致。这就是 CAP #24 §7
可以用 Paxos 或 2PC 来保证分布式事务的强一致 对。两者都能用来让多个节点对「提交还是中止」达成一致。2PC 要全部参与者同意，Paxos 只要多数派。课上讲过，2PC 可以看成 Paxos 的一个退化特例 #24 §2 · §5
一致性哈希下一个节点挂了，只有一部分键要搬 对。原来落在那个节点那一段弧上的键，交给环上的下一个节点。只有这些键要搬，别的键原地不动 #23 §7
