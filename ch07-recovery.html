1问题是什么

难度 ★★★★★重要本讲和 #22 的动机，读懂就行

数据库回复"提交成功"时，改动可能还只在内存里。6:14 一断电，就没了。

T1: R(A) → 从磁盘取页进缓冲池
T1: W(A) → 直接改缓冲池里的页
T1: COMMIT → 告诉应用"你提交成功了"
        ↓
       断电
        ↓
重启：缓冲池全没了，磁盘上根本没有那个改动

考点：对外说提交成功了，数据却没了，这就是本讲要解决的问题

这像写了一下午文档，跟老板说"写完了"。结果没点保存，停电了。

我们对外宣称提交成功了，但数据没了。这就是要解决的问题。

恢复算法有两半：

部分 内容 讲在哪
① 正常运行期间做什么 为将来的恢复做准备 本讲
② 崩溃之后做什么 翻记录、重建状态 #22 ARIES

一个必须澄清的竞态

数据已经落盘，确认消息还没发出去就崩了。9:44 这仍然算正确。

T1 COMMIT → 数据落盘成功
        ↓
     崩溃，确认消息没发出去
        ↓
应用：没收到确认，得自己回头查"我那笔提交了没有"
考点：落盘后、发确认前崩溃，仍是正确行为，回头查是应用的责任

这像网购付款时页面卡住了。钱可能已经扣了，你得自己去订单页查一下。

"数据落盘成功了，但发确认消息之前系统崩了"。这仍然是正确的行为。

应用有责任回头去查"我那笔事务到底提交没有"。（呼应 #17。）

踩坑：现实中没人这么写代码，但理论上就该这样。没收到确认，不代表事务没提交。

硬件前提

硬件只保证 4 KB 的写是原子的。11:34 数据库页却可能是 8 KB。

  • 数据主存储在非易失存储（SSD / HDD / S3）。缓冲池在易失的 DRAM。
  • 磁盘交互的粒度是页（4 KB / 8 KB）。
  • 硬件只保证 4 KB 是原子写的。所以一个 8 KB 的数据库页要写两次 4 KB，可能只成功一半。这叫撕裂写。
// 8 KB 的数据库页，硬件要分两次 4 KB 写
disk.Write(page_id, first_half);    // 前 4 KB
disk.Write(page_id, second_half);   // 后 4 KB
// 两次之间断电：前半页是新的，后半页是旧的
// 考点：硬件只保证 4 KB 原子写，8 KB 的页可能撕裂

这像一封信分两页寄出，结果只到了一页。

2Undo 与 Redo

难度 ★★★★★必会HW6 Q2 考 undo / redo，#22 两阶段都用

Undo 把没完成的事务抹掉，Redo 把已提交的事务补上。12:57

机制 作用 什么时候用
Undo（撤销） 抹掉未完成或已中止事务的影响 事务自己 ROLLBACK。并发协议强制中止。崩溃时正在飞行中的事务
Redo（重做） 重新应用已提交事务的改动 崩溃后，确保已提交的东西真的在 
ROLLBACK，或者被并发协议中止 → undo
崩溃时还在飞的事务           → undo
崩溃前已提交的事务           → redo
考点：undo 抹掉没完成的，redo 补上已提交的

Undo 像 Ctrl+Z，Redo 像 Ctrl+Y。一个往回退，一个往前补。

支不支持 undo / redo，取决于你的缓冲池策略。

3缓冲池的两个策略：Steal 与 Force

难度 ★★★★★必会HW6 Q2 直接考，清单明列四种组合

缓冲池何时能把脏页写回磁盘，决定了恢复要不要 undo 和 redo。14:22 这是本讲最核心的概念。

为什么会有这个问题

一个页里，常常同时装着不同事务的改动。

一个页里同时有 A 和 B：
T1 改了 A（未提交）
T2 改了 B（要提交了）
        ↓
T2 提交要求把这页写盘，但这页里带着 T1 未提交的改动！

这像一个快递箱里装了两个人的东西。一个人急着寄，另一个还没打包好。

两个策略

STEAL 问未提交的改动能不能先上盘。FORCE 问提交前要不要全部上盘。

策略 问题 选项
STEAL（偷取） 允许把未提交事务改脏的页写回磁盘吗？ 这会覆盖已提交的版本 STEAL = 允许。NO-STEAL = 不允许
FORCE（强制） 事务提交前，必须把它改的所有脏页都刷盘吗？ FORCE = 必须。NO-FORCE = 不必 
// 替换算法挑中一个脏页，准备淘汰
if (page->IsDirty() && page->HasUncommittedChanges()) {
  if (policy == NO_STEAL) continue;   // 不许偷，换下一个候选
}
// 考点：STEAL 问未提交的脏页能否写盘，FORCE 问提交前要不要刷完脏页
// 考点：P1 的 LRU-K / ARC 淘汰脏页时，必须知道系统用哪种策略

STEAL 像饭还没吃完，服务员就能先收走盘子。FORCE 像结账之前，必须把桌子收干净。

补充：这直接绑定到你 Project 1 写的那个替换算法。LRU-K / ARC 在淘汰脏页时，必须知道当前系统用的是哪种策略。

踩坑：一个系统只实现其中一种组合，不会按事务切换。

四种组合的含义

允许 STEAL 就得有 undo，允许 NO-FORCE 就得有 redo。

含义
NO-STEAL 不需要 undo。磁盘上只会有已提交的数据
STEAL 必须有 undo。磁盘上可能有未提交的改动
FORCE 不需要 redo。提交了就一定在盘上
NO-FORCE 必须有 redo。提交了，但可能还没落盘 
NO-STEAL + FORCE   →  恢复最简单  运行时最慢  → 影子分页
STEAL   + NO-FORCE →  恢复最复杂  运行时最快  → 预写日志（所有系统的选择）

考点：NO-STEAL 不要 undo，STEAL 要 undo，FORCE 不要 redo，NO-FORCE 要 redo

NO-STEAL + FORCE 的死结

回到开头那个页，FORCE 要求写，NO-STEAL 不许写。20:39 两条规矩直接打架。

FORCE 说：T2 提交了，这页必须写盘
NO-STEAL 说：这页带着 T1 未提交的改动，不许写
        ↓
        冲突

考点：稻草人解法是复制一份页，只放已提交的改动
考点：学生的三个质疑是没空间、内存装不下、让 T2 等多久
考点：Databricks 的 24 小时超时说明，等待没有上限

稻草人解法：复制一份页，只把已提交事务的改动放进副本。然后写那个副本。

课堂上学生当场把它捅穿了：

质疑 回应
"没空间做副本怎么办？" "对，你在戳它的漏洞。我没说这是好主意，这是稻草人。"
"NO-STEAL 下，十亿条更新装不下内存怎么办？" 只能想办法写到别处去
"让 T2 等 T1 呢？" 等多久？ Databricks 讲过一个真事。用户在 notebook 里开了事务，然后起身走了。Databricks 不得不设一个 24 小时自动杀事务的超时。你愿意让 T2 等 24 小时吗？

4NO-STEAL + FORCE：影子分页

难度 ★★★★★必会清单明列影子分页的优劣

影子分页把改动全写在副本上，提交时靠一次原子写切过去。24:09 这是 NO-STEAL + FORCE 的正经实现方式。IBM 1970 年代在 System R 上发明的。

机制

维护两份数据库，用一个主指针决定哪份算数。

维护【两份】数据库：
  · 主副本（master）  ：只含已提交事务的改动
  · 影子副本（shadow）：未提交事务在这里改，需要时也能写盘

┌─ 主指针（Master Pointer）─┐  ← 一条记录，指向当前的页目录
│  单个页，可以【原子写】     │
└───────────────────────────┘

流程：

① T1 开始 → 复制一份页目录当作影子页目录（初始内容完全一样）
② T1 改页 → 不覆盖原页，复制新页，改副本，更新影子页目录的指针
③ 别的只读事务 → 走主指针 → 主页目录 → 完全看不到 T1 的改动
④ T1 提交 → 把影子页目录刷盘 → 【原子地翻转主指针】指向它
⑤ 从此所有人都看到 T1 的改动

考点：主指针是单个页，一次原子写就能让所有改动一起生效

这像网站发版。新版本先在另一个目录里搭好，最后把软链接一切，就上线了。

它怎么保证原子性（课堂追问）

多页写做不到原子，单页写可以。32:47 所以把多页的生效，压成一次单页写。

T1 改了三个页，我没法保证三次页写是原子的。

但我可以保证一次页写是原子的。 所以先把这三个页全部装好。再对主指针做一次原子写，"一键生效"。

WritePages(shadow_dir, {p1, p2, p3});   // 三页先写好，崩了也不影响主副本
Flush(shadow_dir);
AtomicWrite(master_ptr, shadow_dir);    // 只有这一次写，决定生效与否
// 考点：主指针只占一个页，单页写是原子的

回滚更简单：崩溃或中止，就直接忽略影子页。主指针没动过。

为什么被抛弃

影子分页把数据库越写越碎，顺序 I/O 慢慢变成随机 I/O。34:55

问题 说明
复制页目录很贵 大数据库尤其致命
碎片化，导致随机 I/O 这是 System R 遇到的真实问题。数据库文件里到处是空洞，扫描时要跳来跳去。越用越像随机 I/O，越来越慢。还得跑昂贵的垃圾回收。在 1970 年代的硬件下，这是灾难。
只能单写者（通常） 多写者的话，主指针什么时候翻转就成了难题 
刚建好：页 1 2 3 4 5 连续放着，扫描是顺序读（示意）
改几轮：页 1 [洞] 3 [洞] 5 …… 新的 2、4 落在文件别处
再扫描：跳来跳去，变成随机 I/O
考点：System R 被碎片化拖垮，影子分页因此被抛弃
考点：Optane 上影子分页仍输给 WAL，拖慢它的换成了内存拷贝

这像书架上的书被抽走又插回别处。找一套书，得满屋子跑。

补充：在更快的硬件上会不会好一些？（36:19）Andy 说在 Intel Optane 持久内存上测过。这种内存是 DRAM 的速度，再加上持久性。结果影子分页仍然打不过 WAL。

道理很有意思：磁盘慢的时候，是磁盘写拖死你。磁盘变快之后，是那些内存拷贝拖死你。

Optane 已经停产了。但 Andy 认为结论仍然成立。

今天还在用的：

  • LMDB。Andy 说 LMDB 的作者和自己完全相反：既爱 mmap，又爱影子分页。
  • CouchDB。靠追加到文件末尾规避随机 I/O，代价是要做垃圾回收。
  • FastDB、GemStone。
  • SQLite 曾经用，后来换了。

5SQLite 的回滚日志模式

难度 ★★★★★了解单个系统的实现，清单明说这类不考

SQLite 先把改动前的旧页存进日志文件，崩了就拿旧页盖回去。39:07 SQLite 直到 2010 年用的都是这种影子分页变体，叫 rollback mode。

补充：顺带一个冷知识。SQLite 承诺文件格式长期向后兼容。 课上说支持到 2035 年，官方现在写的是支持到 2050 年。因为它跑在卫星上、飞机上，是关键基础设施。所以你近期看不到 SQLite 4。

它没有页目录，用一个独立的日志文件（单写者多读者）：

① 要改内存里的 page 2 → 先把【改动前】的 page 2 复制进日志文件、刷盘
② 然后才改内存里的 page 2
③ page 3 同理
④ 提交时把 page 2、page 3 写回主数据库文件
        写 page 3 时崩溃
        ↓ 恢复
⑤ 打开日志文件 → 里面是【改动前】的 page 2 和 page 3
⑥ 把它们【覆盖】回数据库文件 → 删除日志文件 → 可以跑新事务了

考点：回滚日志存旧数据，恢复时写回去，和影子分页方向相反
考点：SQLite 文件格式官方承诺支持到 2050 年，课上说的是 2035 年

这像改稿之前，先复印一份原稿。改砸了，就拿复印件盖回去。

注意它和影子分页正好相反：

  • 影子分页：影子页里是未提交的新数据，恢复时忽略它们。
  • 回滚日志：日志里是改动前的旧数据，恢复时把它们写回去。

补充：随便翻一个数据库的启动日志，你都会看到它在做恢复。它在查日志、找检查点，想搞清楚上次退出是不是干净的。

6预写日志 WAL

难度 ★★★★★必会HW6 Q2 考提交点，#22 全建在这条规则上

WAL 不再整页写，只把改动顺序追加进日志。44:48 日志先落盘，数据页可以晚点再说。

影子分页的根本问题是：随机 I/O，加上必须整页写。

踩坑：哪怕一页里只改了一个字节，也要把整页写出去。

核心规则（本讲最重要的一句话）

被改过的页写回磁盘之前，它的日志记录必须先落盘。46:10

void FlushPage(Page *p) {
  log_manager->FlushLogFor(p);              // 先把改过这页的日志记录刷盘
  disk_manager->WritePage(p->id, p->data);  // 然后才轮到数据页
}
// 考点：预写 = 先写日志，再写数据库
// 考点：WAL 换来 STEAL + NO-FORCE，前提都是日志先落盘

这像记账。先在账本上写下"要转一笔钱"，再去动钱。钱动到一半出了事，翻账本就知道该怎么补。

脏页从缓冲池写回磁盘之前，它的日志必须先安全落盘。

这就是"预写（write-ahead）"的含义：先写日志，再写数据库。

补充：确实存在"写后日志（Write-Behind Logging）"。它针对一种实验性硬件，先写数据库，再写日志。但那只在研究里，真实系统别这么干。

它换来了 STEAL + NO-FORCE：

条件
STEAL 可以把未提交的脏页写盘。前提是对应日志先落盘
NO-FORCE 提交时不必刷所有脏页。但必须刷完该事务的所有日志记录

补充：改了一千个页，就至少有一千条日志记录。但它们可以顺序写，比一千次随机页写便宜得多。

日志记录的内容

每条日志记下谁改了哪个对象、旧值是什么、新值是什么。50:56

<BEGIN, T1>                              ← 事务开始（#22 恢复时要用它定位起点）
<T1, 对象 A, 旧值(undo), 新值(redo)>      ← 每次修改
<T1, 对象 B, 旧值, 新值>
<COMMIT, T1>                             ← 提交
        ↓ fsync：把这一批全部刷盘
现在才能告诉应用"提交成功"

考点：一条日志记录有事务 ID、对象、旧值、新值
考点：走追加式 MVCC 时从不覆盖，可以不记 undo 值

补充：如果你走 PostgreSQL 那种追加式 MVCC，其实不需要 undo 值（#20）。因为它从不覆盖。但稳妥起见，两个都记。

完整时序：

T1 BEGIN  → 追加 <BEGIN,T1> 到【内存里的日志缓冲区】
T1 W(A)   → ① 先追加日志记录（内存，很快）
            ② 再改缓冲池里的页
T1 W(B)   → 同上
T1 COMMIT → 追加 <COMMIT,T1> → fsync → 硬件确认 → 回复应用

考点：fsync 拿到硬件确认之后，才能回复应用
考点：改动没写回磁盘没关系，恢复所需的一切都在日志里
考点：未提交事务的日志也会写出去，没有 COMMIT 记录，恢复时就 undo

课堂关键问答（53:49）："那些改动一直没写回磁盘也没关系吗？"

"没关系，这正是重点。崩溃后恢复所需的一切都在日志里。"

踩坑：是的，我们会把未提交事务的日志记录也写出去。这没关系，因为它们后面没有 COMMIT 记录。恢复时看到"有改动没提交"，就知道要 undo。

7组提交

难度 ★★★★★重要WAL 的性能优化，作业和清单都没列

每个事务单独 fsync 太慢。54:33 组提交把一批事务的日志攒起来，一次刷盘。

每个事务都单独 fsync 一次，就是灾难：

一次 fsync 在快 SSD 上要 1–5 毫秒
        ↓
最好情况 1 毫秒 → 每秒只能跑 1000 笔事务
        ↓
而网站要的是每秒十万甚至一百万笔

考点：不做组提交，最好情况每秒也只能跑 1000 笔

解法：组提交（Group Commit）

事务想提交 → 不立刻 fsync，先等一个很短的超时（比如 5 毫秒）
        ↓
把这段时间内积攒的所有日志【打包，一次写盘】
        ↓
一次 fsync 服务上万笔事务

考点：50 毫秒经验法则来自广告竞价，高频交易是例外
考点：高频交易靠内存数据库加复制，NonStop SQL 让三台机器算同一笔

这像电梯。不会每来一个人就跑一趟，而是等几秒，凑一批再走。

双缓冲实现（57:19）：日志缓冲区 1 满了，就异步刷盘。同时切到缓冲区 2 继续写。全是顺序写。（呼应 #11 的双缓冲。）

补充："5 毫秒延迟能接受吗？"Andy 的经验法则是：数据库里 50 毫秒以下就算够好。

这个数字来自互联网广告竞价。 你打开一个网页，广告平台向各家发竞价请求。超时通常是 40–50 毫秒。所以你得在 40 毫秒内跑完事务并返回。

例外是高频交易。 Andy 的原话："那帮人嗑着可卡因，要亚毫秒、要微秒级。"

补充：高频交易怎么做？（58:41）用内存数据库加复制。而且跑在高端容错硬件上。还有一类 NonStop SQL，是超容错数据库。

它做的是 NASA 级别的复制。一笔事务在三台机器上并行执行。三边都说"我算出一样的结果"，才算数。

Andy 吐槽："这帮人还会在哈德逊河底下铺光纤。就为了从数据中心到交易总部，少 5 毫秒延迟。这帮人在印钞票，想干嘛干嘛。"

和 LSM 的关系

不是一回事，LSM 树自己也要一个预写日志。59:24 学生问，这跟 #05 日志结构存储 是不是一回事。

写入 → 先追加 WAL → 再进 MemTable（在内存里）
MemTable 落成 SSTable，写到盘上
SSTable 落盘之后 → 对应那段 WAL 才能截断
考点：LSM 也要 WAL，因为 MemTable 不持久
考点：数据库 WAL、文件系统 journaling、SSD 自己的日志，三层冗余

踩坑：不是一回事。LSM 树自己也要一个预写日志，因为 MemTable 在内存里，不持久。等 MemTable 落成 SSTable 写到盘上，那段日志才能截断。

补充：冗余层层叠叠（32:05）。你的数据库在做 WAL。下面的文件系统在做 journaling。再下面的 SSD 自己也在做日志。 除非你控制整个栈，否则这些冗余不可避免。而这一点几乎没人做得到。

这像寄快递。你自己留一张底单，快递站留一份，分拣中心又留一份。

8日志里到底记什么

难度 ★★★★★必会HW6 Q2 考物理日志与索引

绝大多数系统记的是物理逻辑日志。1:01:21 它记的是哪个页的哪个槽，改成了什么。

UPDATE foo SET value = 'XYZ' WHERE id = 1;
-- 物理日志：页 P 偏移 off 处，旧字节 → 新字节，每条元组记一条
-- 逻辑日志：只记这一句 SQL
-- 物理逻辑：页 P 的槽号 S，改成了 'XYZ'
-- 考点：多数系统用物理逻辑日志

物理日志像拍下每一处改动的特写。逻辑日志像只记一句"把这章重写"。物理逻辑日志像记"第几页第几段改成了什么"。

方式 记什么 优点 缺点
物理日志（Physical） 字节级 diff：某页某偏移量，旧值 → 新值 恢复快，确定性强 改十亿条元组，就是十亿条日志记录
逻辑日志（Logical） SQL 语句本身 一条 UPDATE 只记一条，数据量极小 见下
物理逻辑日志（Physiological） 记"哪个页的哪个槽号"改成了什么 折中：页内可以自由重组，恢复照样正确 无

逻辑日志的两个致命问题

逻辑日志重放时，可能算出不同的结果。而且重放和当初一样慢。

UPDATE orders SET created = NOW() WHERE id = 1;
-- 逻辑日志只记了这句 SQL
-- 恢复时重放：NOW() 变成了恢复那一刻的时间，值对不上
-- 考点：逻辑日志的两个问题，非确定性函数和恢复慢
  1. 非确定性函数，比如 NOW()、随机数。恢复时重放，必须拿到和当初一样的值。否则改动就不持久了。
  2. 恢复慢："当初跑了一小时的查询，恢复时还得再跑一小时。没有魔法能让它变快。" 而且不同隔离级别的事务，重放时还得保证真实的执行顺序。元数据负担更重。

踩坑：平时随手写的 NOW()，在逻辑日志眼里是个坑。重放一次，值就变了。

结论：绝大多数系统用物理逻辑日志。

索引也要记日志

索引是数据的第二份拷贝，也要记日志。1:03:29 不记的话，恢复时得整表重扫来重建。

INSERT 一行
  → 日志：表页里插入了一条元组
  → 日志：索引页里插入了一个键
不记索引日志：恢复后只能整表重扫，重建索引
考点：内存数据库常故意不给索引记日志，恢复时顺手重建

索引像书的目录。目录丢了，照着正文能重新编一份，就是费时间。

索引是数据的第二份拷贝。 它也要写日志，否则恢复时得整表重扫来重建索引。

补充：内存数据库常常故意不给索引记日志。反正恢复时整个数据库都要读进内存，顺手重建索引更划算。还省下了大量日志写入。

10检查点

难度 ★★★★★必会清单要比模糊 vs 非模糊，#22 §6 从它改起

检查点把脏页全刷盘，再在日志里打个标记。1:10:47 恢复时，只要往回看到这个标记为止。

WAL 会无限增长。 跑了一年，崩溃后难道要重放一整年的日志？

检查点（Checkpoint）：把缓冲池里所有脏页刷盘。然后在日志里记一条"这里打了检查点"。恢复时只需要往回看到这条记录为止。

这像游戏存档。挂了就从最近的存档点重来，不用从第一关打起。

阻塞式检查点（稻草人）

最笨的做法，是先把整个系统停下来，刷完再继续。1:12:07

① 暂停所有查询，不许新事务开始
② 把内存里的日志记录全部刷盘
③ 把缓冲池里所有脏页刷盘
④ 写一条 <CHECKPOINT> 记录并刷盘
⑤ 恢复执行

考点：阻塞式检查点五步，停、刷日志、刷脏页、写 CHECKPOINT、恢复

恢复时怎么用（1:12:46）：从日志尾部往回扫，扫到 <CHECKPOINT> 为止。

<T1 COMMIT>  <CHECKPOINT>  <T2 COMMIT>  ……  崩溃时 T3 还没提交
             ↑ 从尾部往回扫，扫到这里就停
考点：T1 忽略，T2 redo，T3 undo
事务 情况 动作
T1 检查点之前就提交了 忽略。改动肯定在盘上
T2 检查点之后提交 REDO
T3 崩溃时还没提交 UNDO

三个问题

阻塞式检查点要停掉一切，还不一定省得掉全日志扫描。1:14:53 打的频率也没有标准答案。

问题 说明
必须暂停一切 缓冲池 100 TB 且全脏，最坏要写 100 TB。高端系统这么大并不夸张。期间一条查询都跑不了
还是可能要扫全日志 有些事务在检查点之前就开始了，之后没再动过。你还是得往前找它们
多久打一次？ 打太勤，拖慢查询。打太稀，恢复太久。没有标准答案。

踩坑：检查点不是打得越勤越好。打太勤会拖慢查询，打太稀会让恢复变久。

考点：阻塞式检查点有三个问题。要暂停一切，可能还要扫全日志，频率也没标准答案。100 TB 的例子说明，暂停的代价可以大到不能接受。

实践中的触发条件（1:16:54）：

依据 例子
时间间隔 高频交易那帮人每 5 分钟打一次
日志数据量 MySQL：每写满 512 MB 日志就打一次。系统空闲时不会白打 
按时间：每 5 分钟打一次，系统闲着也照打
按日志量：每写满 512 MB 日志打一次，没有写入就不打
考点：按日志量触发更聪明，空闲时不会白打

WAL 要保留多久？

技术上不用一直留，但监管可能要求留七年。1:17:35

技术上不需要保留。 正确的检查点机制，让你不必回看那么远。

但可能有外部要求。 比如萨班斯-奥克斯利法案等监管审计。金融机构为此要保留七年。

踩坑：技术上能删，不代表业务上能删。

考点：WAL 技术上不必长期保留。金融机构为了监管审计，要留七年。

最后一个"肮脏的秘密"

难度 ★★★★★了解运维层面的提醒，作业和清单都没列

同步提交才是真的等日志落盘。1:18:57 把它关掉，就可能丢已经"提交"的数据。

每个主流数据库都支持"同步提交"（synchronous commit）。 也就是真的等日志落盘，再回复你。

SHOW synchronous_commit;                                 -- PostgreSQL，默认 on
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';    -- MySQL，默认 1
-- 1 表示每次提交都把日志写盘并刷盘
-- 考点：关掉同步提交，崩溃窗口里会丢已经"提交"的数据

这像银行柜员说"钱存好了"，单子其实还压在抽屉里没入账。

踩坑：课上 Andy 说，它在多数系统里默认不开，还点了 PostgreSQL 和 MySQL。原话是"我不觉得默认开着"。

实际这两个系统默认都是开的。PostgreSQL 的 synchronous_commit 默认 on。MySQL InnoDB 的 innodb_flush_log_at_trx_commit 默认 1，也就是每次提交都把日志写盘并刷盘。

踩坑：只有把它关掉，才会出现一个窗口。在这个窗口里崩溃，你会丢已经"提交"的数据。

真在乎不丢数据，就别关它。

1ARIES 是什么

难度 ★★★★★重要三个核心思想是总览；HW6 考点从 §2 算起

ARIES 是崩溃恢复协议的黄金标准。3:22 数据库崩了重启，靠它把数据修回正确的样子。

ARIES = Algorithms for Recovery and Isolation Exploiting Semantics

IBM 研究院为 DB2 开发了它。论文发表于 1992 年，约 70 页。期刊版是第 94–162 页，共 69 页。

"这就是崩溃恢复协议的黄金标准。"它重要到有自己的维基百科条目。

void Recover() {   // 重启后，恢复管理器按固定顺序做三件事
  Analysis();      // 读日志，弄清崩溃时谁还活着、哪些页是脏的
  Redo();          // 把历史原样重放一遍
  Undo();          // 把没提交的事务倒回去
}
// 考点：ARIES 的全称、出处（IBM / DB2）、年份 1992、论文约 70 页

它像飞机的黑匣子。出事以后，只靠黑匣子里的记录，就能把经过还原出来。

三个核心思想

ARIES 只靠三招：先写日志，重放历史，撤销也记日志。5:19

# 思想 说明
① 预写日志（WAL） #21 那条铁律：日志先落盘，脏页才能落盘
② 重放历史（Repeating History） 恢复时，把日志里的所有改动全部重做一遍。哪怕其中一些其实已经落盘了。宁可多做，不能漏做
③ 给撤销操作也记日志（CLR） 撤销一个改动时，为这个撤销动作本身再写一条日志记录 
log:  <T1, A, 30, 40>        -- 正常修改，先写日志（示意）
redo: A = 40                 -- 重放历史：不管 A 落没落盘，都再写一次
log:  <CLR, T1, A, 40, 30>   -- 要撤销？先给这次撤销记一笔
undo: A = 30                 -- 再把值改回去
-- 考点：三个核心思想。重放历史听着浪费，但不知道哪些页落了盘，只能全做

这像记账。花了钱要记一笔，退了钱也要再记一笔。不能直接把原来那行划掉。

ARIES 相比前人的关键差别

ARIES 把恢复顺序钉死了：先分析，再重做，最后撤销。4:41

在它之前，各家系统有的先 redo，有的先 undo。ARIES 极其谨慎，三个阶段依次跑完，才宣布数据库恢复完成。

以前：有的系统 redo → undo，有的 undo → redo
ARIES：分析 → 重做 → 撤销，三步全跑完才算恢复完成
考点：ARIES 相比之前的方案，关键差别是顺序固定、三阶段跑完

这是贯穿本讲的态度。

"我宁愿先做到极度小心，再一点点把它剥薄变快。但首先得保证什么都不丢。"

踩坑：所以本讲会写下大量冗余信息。这是刻意的，不是写错了。

本讲的简化假设

本讲先做了几条简化，把问题收窄。16:48

  • 一条日志记录装得进一页。放不下就分段编号，第一段写"1 of 2"。
  • 磁盘写以 4 KB 为原子单位。
  • 单版本 + Strong Strict 2PL，不操心奇怪的交错。
  • STEAL + NO-FORCE。
  • 用物理 / 物理逻辑日志，不用逻辑日志。
  • 索引页的处理方式和数据页一样，不单独讲。

2日志序列号 LSN 家族

难度 ★★★★★必会HW6 Q1 直接考，后面各阶段都靠它判断

每条日志记录都有一个编号，叫日志序列号（LSN）。它全局唯一、单调递增。8:33 成千上万个事务并发时，全靠它分清操作真实的先后。

lsn_t AppendLogRecord(LogRecord &rec) {
  rec.lsn = next_lsn_++;        // 全局唯一，只增不减
  log_buffer_.push_back(rec);   // 先进内存里的日志缓冲区
  return rec.lsn;
}
// 考点：LSN 表示物理顺序，事务时间戳表示逻辑顺序

LSN 像银行叫号机吐出的号码。号码只会越来越大，谁先谁后一目了然。

踩坑：别把 LSN 和事务时间戳混为一谈。

  • #19 的事务时间戳 表示逻辑顺序。
  • LSN 表示改动真正落到页上的物理顺序。

五个 LSN，各司其职

五个 LSN 分别盯着日志、页、事务和检查点。

名称 存在哪 含义
flushedLSN 内存（全局） 已经刷到磁盘的最大 LSN。它是内存日志和磁盘日志的分界线
pageLSN 每个页的头部 最近一次改这个页的那条日志，它的 LSN
recLSN 内存（脏页表里） 这个页上次刷盘以后，第一条改它的日志的 LSN
lastLSN 内存（活跃事务表里） 某个事务最近一条日志记录的 LSN。中止时从这里开始往回走
MasterRecord 磁盘 最近一次成功完成的检查点，它起点的 LSN 
// 某页上次刷盘后被改了三次，LSN 依次是 10、20、30（示意）
dpt[page_id]  = 10;   // recLSN：刷盘后最早的那次，记在脏页表里
page->pageLSN = 30;   // pageLSN：最新的那次，记在页头里
// 考点：五个 LSN 的名字、存放位置和含义
// 考点：pageLSN 是最新一次修改，recLSN 是刷盘以来最早一次

这像一面墙上的涂鸦。上次刷白以后的第一笔是 recLSN，最新的一笔是 pageLSN。

踩坑：pageLSN 和 recLSN 是一对，最容易记混。pageLSN 是最新的那次修改。recLSN 是自上次刷盘以来最早的那次修改。

缓冲池怎么用它们

缓冲池淘汰脏页前，只查一个条件：pageLSN <= flushedLSN。11:12 这直接把 #21 的 WAL 规则 变成了一行代码。

要淘汰一个脏页时：
    if  page.pageLSN <= flushedLSN:
        可以刷盘（对应日志已在磁盘上）
    else:
        不能刷，那条日志还在内存里
        → 可以主动叫日志缓冲区【提前 flush 一次】（提前触发组提交）
        → 拿到确认后再刷这个页

考点：淘汰脏页的判断条件，以及条件不满足时先提前 flush 日志

这像寄快递要先留底单。底单还没存档，包裹就不许出门。

补充：这就是 Project 1 的缓冲池和 Project 4 的事务系统真正的接缝。

每改一次页，都要按顺序动四样东西。

① 追加日志记录，拿到新 LSN
② 修改页（此时持有该页的【写 latch】）
③ 把页头的 pageLSN 更新成这个 LSN
④ 日志刷盘时，更新全局 flushedLSN

考点：一次修改要更新的四样东西

3正常提交

难度 ★★★★★必会HW6 Q1、Q2 都考 TXN-END

提交的关键一步，是把 COMMIT 记录 fsync 到磁盘。18:36 落盘以后，才能告诉应用提交成功。

<BEGIN, T1>
<T1, 对象A, 旧值, 新值>
<T1, 对象B, 旧值, 新值>
<COMMIT, T1>
      ↓ fsync：必须落盘
      ↓ 更新 flushedLSN
      告诉应用"提交成功"
      ↓
<TXN-END, T1>     ← 新记录类型

这像网购下单。付款成功那一刻就算成交，后面的归档不着急。

TXN-END 是干什么的

TXN-END 表示这个事务彻底完结了。系统再也不需要为它维护任何状态。

它不需要立即刷盘。放在日志缓冲区里，等着被顺路写出去就行。

<COMMIT, T1>    -- 必须 fsync，应用在等
<TXN-END, T1>   -- 不用 fsync，留在缓冲区里顺路写
-- 考点：TXN-END 是干什么的，它需不需要立即刷盘

踩坑：对提交的事务，COMMIT 和 TXN-END 之间什么都没有。中止的事务不一样，见下节。

补充：一个优化。知道了 flushedLSN，内存里已经落盘的那段日志缓冲区就可以裁掉了。

4正常中止与 CLR

难度 ★★★★★必会HW6 Q1 考 prevLSN、CLR 与 undoNext

中止就是恢复时的 undo，只不过发生在正常运行期间。20:36 两边是同一套动作。

void Abort(Txn *t) {
  for (auto lsn = t->lastLSN; log[lsn].type != BEGIN; lsn = log[lsn].prevLSN)
    UndoAndWriteCLR(log[lsn]);   // 是修改记录就撤销，并写一条 CLR
  WriteTxnEnd(t);                // 撤到 BEGIN，写 TXN-END
  ReleaseAllLocks(t);            // 最后才放锁
}

这像按 Ctrl+Z。一步步往回撤，每撤一步都记一笔。

日志记录加一个字段：prevLSN

prevLSN 把同一个事务的所有日志记录，串成一条反向链表。

001  <BEGIN, T1>       prevLSN = null   -- 链表到头了
002  <T1, A, 30, 40>   prevLSN = 001
003  <T1, B, 3, 4>     prevLSN = 002    -- 中止时从这里往回跳
-- 考点：prevLSN 的作用。它是为了性能，不是为了正确性

<BEGIN> 记录的 prevLSN 是 null。

这像一大摞混在一起的快递单。每张都写着"我的上一张是几号"，顺着找就行，不用翻遍整摞。

踩坑：它不是为了正确性，是为了性能。上千个事务的日志交织在一起。你需要快速跳着，找到自己的那些记录。

中止过程中锁不能放

锁要等回滚彻底做完才能放。21:57

应用说 ABORT，我不能立刻释放锁。因为我还要去改那些我之前改过的记录，把它们改回去。

只有等回滚彻底完成，才释放锁。

T1: ABORT，并提前放了 A 的锁    -- 错误示范
T2: 写 A = 50                   -- 别人抢先写了（示意）
T1: 把 A 恢复成 30              -- T2 的写被覆盖掉了
-- 考点：中止过程中为什么不能马上放锁，不这样会发生什么

踩坑：提前放锁，别人就可能抢先写了那个对象。我再把它"恢复原状"，就把人家的写覆盖掉了。这还是 #18 2PL 那一套。

补偿日志记录（CLR）

CLR 就是一条"我把某个改动撤销了"的日志记录。24:01

CLR 的全称是 Compensation Log Record。

它的内容和普通 update 记录一样，只是把 before 和 after 对调。

它多一个字段 undoNext，指向下一条还需要撤销的日志记录。

CLR 像发票冲红。原来那张发票不撕，另开一张金额相反的红字发票。

完整的中止流程：

LSN prevLSN 事务 类型 对象 before after undoNext
001 nil T1 BEGIN
002 001 T1 UPDATE A 30 40
003 002 T1 UPDATE B 3 4
004 003 T1 ABORT
005 004 T1 CLR B 4 3 002
006 005 T1 CLR A 40 30 001
007 006 T1 TXN-END 
看到 ABORT
  → 沿 prevLSN 跳到 003，写 CLR 反转它，undoNext 指到 002
  → 再写 CLR，undoNext 指到 BEGIN
  → 完成，写 TXN-END
考点：CLR 是什么，它比普通 update 记录多了 undoNext 字段
考点：从 ABORT 到 TXN-END 的完整日志序列，含 CLR

踩坑：TXN-END 之后，才释放全部锁。

三条重要规则

关于 CLR，记住三条规则。

  1. CLR 不需要立即刷盘。 应用一说 ABORT，我们立刻回复"已中止"，不必等。
  2. 永远不给 CLR 再写 CLR。 "撤销一个撤销"没有意义。CLR 可以被反复重放，结果一样。
  3. 对比提交和中止。 提交的事务，COMMIT 和 TXN-END 之间是空的。中止的事务，中间塞满了 CLR。
提交：<COMMIT, T1>  <TXN-END, T1>                     -- 中间是空的
中止：<ABORT, T1>  <CLR ...>  <CLR ...>  <TXN-END, T1>  -- 中间塞满 CLR
考点：关于 CLR 的三条规则（刷盘、不给 CLR 写 CLR、和提交事务对比）

6模糊检查点

难度 ★★★★★必会HW6 Q1 考 ATT / DPT，清单明列；快照时刻易错

真实系统用的是模糊检查点。打检查点时，事务照常跑。33:08 #21 那个阻塞式检查点要暂停一切，不可接受。这一节一步步改好它。

阻塞式：暂停一切 → 刷脏页 → 恢复运行     -- 不可接受
中间版：只暂停事务，不等它结束           -- 磁盘上会留下半个事务
模糊式：不暂停，另记下 ATT 和 DPT        -- 大家实际用的

这像给一个热闹的商场盘点。关门盘点最准，但没人受得了。实际做法是边营业边盘，再记下开盘那一刻的账本。

中间方案：只暂停、不等事务结束

只暂停事务、不等它结束，还是不行。35:08

事务改了 page 3 → 检查点暂停它 → 检查点刷出 page 1,2,3 → 事务醒来 → 改 page 1

考点：中间改良版为什么还是不行，用 page 1 / page 3 的例子说明

踩坑：你仍然得回去翻日志。搞清楚检查点期间，那个事务在干什么。

加两张表

模糊检查点靠两张表，记下检查点开始那一刻世界的样子。36:30

① 活跃事务表（ATT, Active Transaction Table）

ATT 记的是：哪些事务还活着，各自走到了哪。

字段 说明
txnId 事务 ID
status Running（运行中）/ Committing（提交中）/ Candidate for Undo（待撤销）
lastLSN 该事务最近一条日志记录的 LSN 
struct ATTEntry {
  txn_id_t txnId;
  Status   status;    // Running / Committing / Candidate for Undo
  lsn_t    lastLSN;   // 这个事务最近一条日志
};
// 考点：ATT 记 txnId、status、lastLSN。恢复时默认所有事务都要回滚

看到 TXN-END，就把这个事务从 ATT 里删掉。 无论提交还是中止，它都不会再有新动作了。

踩坑：恢复时的默认假设是：所有人都要回滚。 直到看到相反的证据，才改判。

这像图书馆清点。没有归还记录的书，一律当作还在外面。

② 脏页表（DPT, Dirty Page Table）

DPT 记的是：哪些页是脏的，从哪条日志开始脏的。

字段 说明
pageId 页号
recLSN 这个页上次刷盘以后，最早改它的那条日志的 LSN

DPT 记录的是：检查点开始那一刻，缓冲池里哪些页是脏的。

std::unordered_map<page_id_t, lsn_t> dpt;   // pageId → recLSN
bool flushed = (dpt.count(7) == 0);         // 页 7 不在表里，说明已经刷盘（示意）
// 考点：DPT 记 pageId、recLSN
// 考点：某页不在 DPT 里，意味着它已刷盘。DPT 是唯一的信息来源

踩坑：课堂上有人问："某个页为什么不在 DPT 里？"答案是：它已经被刷盘了。 而日志里从来不会有"某页已刷盘"这种记录。DPT 是我们唯一的信息来源。

模糊检查点（Fuzzy Checkpoint）

模糊检查点是大家实际用的方案。41:19 它不暂停事务，所以拍下的状态是"模糊"的。

"模糊"体现在两点。

  • 它刷出去的脏页里，可能混进了检查点开始之后的改动。
  • 检查点开始之后才变脏的页，可能压根没被它刷出去。

没关系。ATT 和 DPT 给了足够的线索，能去日志里翻出真相。

这像边走边拍的全景照片。有人被拍了两次，有人没拍到。但只要记下按快门那一刻的名单，就对得上。

检查点在日志里，从一条记录变成了两条。

<CHECKPOINT-BEGIN>     ← LSN 007
   ... 事务照常运行、照常写日志 ...
<CHECKPOINT-END, ATT, DPT>   ← LSN 010，内容是【BEGIN 那一刻】的快照
   ↓
更新磁盘上的 MasterRecord = 007（指向 BEGIN，不是 END）

考点："模糊"体现在哪两点，为什么这样也没关系
考点：BEGIN 和 END 各记什么，MasterRecord 指向 BEGIN

踩坑：ATT 和 DPT 记的是 BEGIN 时刻的状态，却写在 END 记录里。这纯粹是为了以后好找。

8阶段一：分析

扫描规则：

看到什么 做什么
TXN-END 从 ATT 里删掉这个事务
任何记录，事务不在 ATT 里 加进去，状态设为"待撤销（Candidate for Undo）"
COMMIT 把状态改成"允许提交"

  if (r.type == TXN_END) { att.erase(r.txn); continue; }

9阶段二：重做

难度 ★★★★★必会HW6 Q1 考一定 / 可能 / 一定不重做

重做阶段从 DPT 里最小的 recLSN 开始，把历史原样重放一遍。52:42

这个起点是什么？就是"检查点开始时就脏着的那个页，最早的那次修改"。它一定比检查点期间发生的任何改动都早。

对扫到的每一条 UPDATE 或 CLR 记录，按下面三级判断要不要重做。

① 该页不在 DPT 里？
       → 跳过（它在崩溃前已经刷盘了）
② 在 DPT 里，但 recLSN > 当前 LSN？
       → 跳过（这次改动在页上次刷盘之前就发生了，已经在盘上）
③ 都不满足？
       → 必须把页读进内存，看它的 pageLSN：
            pageLSN >= 当前 LSN  → 跳过（已应用）
            pageLSN <  当前 LSN  → 【重做】

考点：重做从哪里开始，为什么是最小的 recLSN
考点："要不要重做"的三级判断，只有第三步必须读磁盘

这像核对快递。先看清单上有没有这个包裹，清单说不清，再拆箱看。

踩坑：前两条只查内存里的 DPT 就够了。第三条必须真的去读磁盘。 因为 DPT 里只有 recLSN，没有 pageLSN。

重做的动作：

重新应用那个改动 + 把 pageLSN 设成这条记录的 LSN
【不写新日志】
【不 fsync】，恢复期间没别的事务在跑，刷盘纯属浪费时间

考点：重做时不写新日志，也不 fsync
考点：CLR 也要重做，体现的是"重放历史"

踩坑：CLR 也照样重做。 这正是"重放历史"的含义。当初发生的一切，包括那些撤销动作，都原样再走一遍。

重做结束后，给已经确定提交的事务写上 TXN-END。

        ↓

        ↓

这像倒带。从磁带末尾往回倒，倒到这个事务开头为止。每倒一段，都在本子上记一笔。

和正常运行时的 ABORT 完全是同一套动作，见第 4 节。

全部做完，数据库就恢复完毕，开始接受新事务。

11恢复过程中又崩了怎么办

难度 ★★★★★重要HW6 考点止于 §10、清单没列；续做逻辑要想透

恢复中途再崩也不怕，重启后再跑一遍就行。1:01:12 这才是 ARIES 真正的考验，也是它设计得这么啰嗦的原因。

崩在哪个阶段 怎么办
分析阶段 什么都不用做。它是只读的，从头再跑一遍
重做阶段 什么都不用做。它是幂等的，同一个改动重复应用，结果一样。重跑即可
撤销阶段 靠 CLR 
void ApplyRedo(Page *p, const LogRecord &r) {
  if (p->pageLSN >= r.lsn) return;   // 已经做过，再来一次也不变
  p->Apply(r);
  p->pageLSN = r.lsn;
}
// 考点：崩在三个阶段分别怎么办。前两个只读、幂等，所以不用特殊处理

幂等像按电梯按钮。按一次和按十次，电梯都只来一趟。

撤销阶段崩溃的完整走法

撤销做到一半崩了，重启后从 CLR 的 undoNext 接着撤。

撤销 T2 和 T3：
  T3 撤销完，写了 TXN-END
  T2 撤销了一半 → 崩溃
        ↓ 重启
① 分析：发现 T3 已 END（忽略），T2 还在 ATT 里（要撤销）
② 重做：把上次那条【CLR 也重新应用一遍】，确保那一步的撤销确实生效了
③ 撤销：看那条 CLR 的 undoNext = 014
        → 我知道该从 014 继续撤，前面撤过的不必再撤
        → 继续写 CLR，直到 BEGIN → TXN-END

考点："撤销到一半又崩了"的恢复过程，undoNext 告诉你从哪接着撤

这像看书夹了书签。中途睡着也不怕，醒来从书签那页接着读。

无论崩多少次，每次重启都会先重做已完成的撤销。然后从 undoNext 接着往下。最终一定能走到 TXN-END。

这就是第 5 节那个问题的最终答案。CLR 存在的意义，是让撤销这件事本身也能恢复、能续做。

两个可选的优化

恢复还能更快，课上给了两个可选的优化。1:04:12

优化 说明
重做阶段不频繁 fsync 原始 ARIES 论文几乎每遇到一个 TXN-END 就刷一次盘。其实不必。 大多数系统都放宽了这一点
延迟撤销 有研究提出，撤销阶段不真的去改页。而是在页上挂一个"待撤销清单"。这很像 #08 B+树 或 MySQL 压缩里的 mod log。这样能立刻开门接客，等有事务碰到那个页时再顺手应用。
改应用 "避免长事务"。说起来容易，做起来难。 
page 7: undo_list = [T2 的待撤销改动]   -- 先挂上，不急着改页（示意）
数据库立刻开门接客
某个事务读到 page 7，再顺手把 undo_list 应用掉
-- 考点：两个可选优化。延迟撤销的思路像 B+ 树或 MySQL 压缩里的 mod log

这像餐馆先开门营业。后厨的碗，等要用的时候再洗。

ClickHouse 是什么

ClickHouse 是一个开源的列式分布式分析数据库。它用 C++ 写成，已经开源十年。GitHub 上约有 4.5 万星。从树莓派到几百节点的集群，它都能跑。

它的存储层为追加做了优化。插入极快。 更新和删除也能用，但慢一些。

INSERT INTO events VALUES (...);   -- 追加：极快
UPDATE events SET ... WHERE ...;   -- 能用，但慢一些
-- 考点：存储层为追加优化，适合事件、日志、时序、金融数据

这像记流水账。只往后写新的一行，很少回头改旧账。

补充：追加型负载是合理的。事件、日志、时序、金融数据都是这样。数据源源不断进来，但极少甚至从不修改。

存储结构：Part 与 Granule

每次 INSERT 都生成一个新的 part，后台再慢慢合并。

每次 INSERT → 生成一个【part】（磁盘上一个文件 + 元数据）
      ↓ 插入时不需要和已有 part 同步、不需要查索引验唯一性
      插入速度只受磁盘速度限制
      ↓
每个 part 内部，行按【用户指定的主键列】排好序
      ↓
后台【compaction】线程持续把多个 part 归并成更大的 part
      因为 part 内部有序，可以用【K 路归并排序】

考点：part 是怎么产生的，插入为什么这么快

这像每次进货都先装一个新箱子，不去翻旧箱子。仓库闲下来，再把小箱子并成大箱子。

和 LSM 树的关键区别

ClickHouse 的所有 part 都是平等的。没有树，也没有层级。 对照 #05 日志结构存储 来看。

这带来两个好处。

  1. 扫描可以在所有 part 上并行。 part 之间没有隐含的时间先后关系，不会限制并发。
  2. 归并不受 LSM 层级约束。 可以自由挑任意 part 来合并。
LSM 树：     L0 → L1 → L2             -- 有层级，新旧有先后
ClickHouse： part1  part2  part3      -- 全部平等，随便扫、随便并
考点：和 LSM 树的关键区别，带来哪两个好处、什么代价

LSM 树像按年级分班的学校。ClickHouse 更像一堆平行的小组，谁跟谁合并都行。

踩坑：代价是更新和删除更麻烦，而且不能用墓碑（#05）。但对 ClickHouse 的场景来说，这无所谓。

三层数据裁剪

ClickHouse 的核心理念是：让 SELECT 尽可能跳过数据。 每一个不用读的字节，都让查询更快。

① 稀疏主键索引（Sparse Primary Index）

稀疏主键索引只给每个 granule 记一条，所以小到能整个放进内存。

part 被切成【granule】，每个 granule 固定 8192 行
        ↓ granule 是扫描算子能从磁盘加载的最小单位
在主键列上建一个小索引：只记录【每个 granule 的第一行】
        ↓
"稀疏"的含义：它每 8192 行才指一次，不是每行都指

考点：granule 是什么，每个固定 8192 行
考点："稀疏"稀疏在哪，为什么不直接在主键列上二分查找

小到什么程度？1000 个条目就能索引 800 多万行。 小到可以整个常驻内存，也就是 pin 住。

查询分四步走。

在稀疏索引上二分查找
  → 定位到相关 granule
  → 只加载这些 granule
  → 再逐行过滤（granule 里仍可能混着不匹配的行）

这像字典侧边的字母标签。先看标签找到大概哪几页，再翻进去一行行找。

踩坑：为什么不直接在主键列上二分？ 二分只要对数次磁盘访问。但在对象存储上，每次访问要几十毫秒。这还是太慢。

② 投影（Projection）

投影就是把整张表按另一个主键重排一份。行完全相同，只是顺序不同。

投影实现在 part 级别。 每个 part 可以有任意多个投影。优化器每来一个查询，就挑最划算的那个。

-- 原表按 user_id 排序，再加一份按 ts 排序的投影（示意）
ALTER TABLE events ADD PROJECTION by_ts (SELECT * ORDER BY ts);
-- 考点：投影是什么。优点是查询快，缺点是存储开销大

这像一本书同时按章节和按关键词各印一份。查得快，但书架占两倍。

踩坑：投影最大的问题是存储开销。 它能轻松让表体积翻倍，甚至变成三倍。

③ 跳过索引（Skipping Index）：客户最喜欢的

跳过索引给每个 granule 附上少量元数据。扫描时先看元数据，这一整块不可能有匹配的行，就整块跳过。

类型：min-max 索引、唯一值集合、Bloom Filter。

granule 42: min = 100, max = 200   -- min-max 索引（示意）
WHERE x = 500                      -- 500 不在 100 到 200 之间
→ 整个 granule 跳过，一行都不读
考点：跳过索引是什么，它对应本课 #13 的 Zone Map 和 #09 的 Bloom Filter

这像快递柜门上贴的标签："本柜只有 A 区包裹"。找 B 区的件，这个柜门都不用开。

补充：这就是 #13 的 Zone Map 和 #09 的 Bloom Filter 在真实系统里的样子。

踩坑：跳过索引比投影轻量得多，但很难调优。因为它对数据分布做了假设。
