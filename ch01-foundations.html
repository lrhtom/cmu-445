1这门课到底教什么

这门课不教你用数据库，教你把数据库拆开，看它内部怎么跑。2:24 Andy 开场就划清了边界。想学写业务 SQL、想当 DBA，去信息系统学院。

2用 CSV 手搓数据库：一个注定失败的方案

难度 ★★★★★重要十二条问题对应后面各讲，读懂动机就行

自己拿文件存数据，就是把数据库的活全压给应用代码。19:33 这是整门课的动机来源。Andy 每年都用同一个例子：做一个 Spotify 克隆，要存"艺人"和"专辑"。

最朴素的做法是两个 CSV 文件。

artist.csv:   Wu-Tang Clan,1992,USA
              GZA,1990,USA

album.csv:    Enter the Wu-Tang,Wu-Tang Clan,1993
              Liquid Swords,GZA,1995

要查"GZA 是哪年单飞的"，就得自己写段解析代码。

def solo_year(name):
    for line in open("artist.csv"):    # 打开文件，按换行切，每次都从头扫
        fields = line.split(",")        # 按逗号切
        if fields[0] == name:           # 考点：第 0 列是名字，这个知识写死在代码里，加一列就崩
            return int(fields[1])       # 考点：CSV 没有类型，年份要手动转，转失败才知道数据脏

这就像把账记在一沓便签纸上。查一笔账，得从第一张翻起。

看着能跑。但 22:23 起，Andy 让学生轮流挑毛病。最后凑出了一张完整的"为什么需要 DBMS"清单。

# 问题 展开
1 只能线性扫描 不解析前一行，就不知道下一行从哪开始。每次查询都是 O(n) 全文件扫
2 没有类型 CSV 里一切都是字符串。年份要手动 int() 转换，转失败了才知道数据脏
3 字段偏移硬编码在代码里 "艺人名在第 0 列"写死在程序里。加一列就全线崩
4 数据完整性无保障 用文本编辑器就能把年份改成 hello。程序随即全挂
5 跨文件一致性无保障 专辑里写的艺人名，艺人文件里可能根本没有
6 同一实体的多种写法 "Wu-Tang Clan" 和 "WuTang Clan" 逻辑上是一个。存的字节不同，就匹配不上
7 建模能力不足 一列只能放一个艺人。合辑、多人 mixtape 都表达不了
8 悬垂引用 删了艺人，没删这个艺人的专辑。等于留了个野指针
9 解析逻辑跨语言重复 Python 写一遍，换 Rust 再写一遍。两边逻辑很难保持同步
10 并发写没有语义 两个线程同时追加记录，谁赢？后写的覆盖，还是第二个失败？没人定义
11 崩溃会丢数据 追加到一半断电，回来看到什么？半条记录吗？
12 无法做副本 想多机冗余，怎么保证副本同步？

26:30 第 11 条，Andy 用银行举例。你把钱存进去，银行却把这笔存款弄丢了，你会疯。所以银行在数据库上下了海量功夫，保证不丢。这就是不该在应用代码里自己攒数据库的原因。 可人们天天在这么干。

现实中的反面教材

有的数据库为了跑分好看，会悄悄关掉安全写入。27:11 Andy 讲了个很新鲜的例子。据 Andy 说，那篇博客是开课前两天发的。

// 示意：开着安全写入，要等数据落盘才返回
Status Put(Key k, Value v) {
  log.Append(k, v);
  if (safe_writes) log.Flush();   // 默认关掉，就省了这一步，跑分好看
  return Status::OK();            // 可一断电，数据就可能丢
}

这就像快递员没把包裹送到门口，就先点了"已签收"。

英国有家公司叫 SurrealDB。它默认关掉了安全写入（safe writes），所以跑分很好看。可数据其实没被安全落盘。一旦崩溃或断电，数据库可能损坏，数据也可能丢。这个开关还藏在文档深处。等用户发现时，已经晚了。

Andy 补了一句：MongoDB 早年也玩过同样的把戏。 这不是新趋势。

补充：这门课的价值之一就在这。一个系统吹嘘自己有多快时，你能判断它是不是在偷工减料。 靠的不是 Andy 说它不行，而是你自己懂原理。

3数据库 ≠ 数据库系统

难度 ★★★★★了解术语区分加选型建议，后面不再依赖

database 是数据本身，DBMS 是管这些数据的软件。17:31 这里有个经典的"钓鱼问题"。Andy 让大家随便说一个 database。学生喊出 PostgreSQL、MySQL、SQLite、SQL Server、ClickHouse、Redis……Andy 说：你们全错了。

CREATE DATABASE roster;   -- roster 里这堆数据，才叫 database
-- 帮你存它、管它的 PostgreSQL，叫 DBMS
-- 考点：一句话说清 database 和 DBMS 的区别，做系统的人必须分清

数据库像一屋子书，DBMS 像管这屋子书的图书管理员。

术语 含义 例子
Database（数据库） 一组相互关联的数据，用来给现实世界建模 这门课的选课学生名单（姓名、邮箱、生日……）
DBMS（数据库管理系统） 用来存储和管理数据库的那个软件 PostgreSQL、MySQL、ClickHouse……

平时在酒吧跟同行说"我在用这个 database"，没人会较真。但做系统的人必须分清。要存的数据是一回事，要造的软件是另一回事。

28:28 通用型 DBMS 是一类软件。任何应用都能把数据存进来，以后还能高效查询和分析。你不用从零造轮子。只要按某种数据模型定义好 schema，剩下的它全包。

29:49 Andy 的选型建议：新应用首选 PostgreSQL，或者更轻的 SQLite。 Andy 说，这门课别的都忘了，也要记住这条。常有人说"没有现成系统满足我的需求，我只能自己造"。99% 的情况下这是假的。

Andy 对 Postgres 的评价很有意思："前端极好，后端很烂"（amazing front end, terrible back end）。SQL 层、类型系统、扩展生态都是一流。存储引擎层却有历史包袱。这个论断在后面讲 MVCC（#20）时会兑现。

4数据模型与模式

难度 ★★★★★重要schema 这类用语全课在用，分清两个词即可

数据模型规定"能存什么"，模式描述"这个库具体存了什么"。29:49 两个概念必须分清，Andy 用建筑打了个比方。

-- 关系模型（数据模型）规定：世界由表、列、类型组成
CREATE TABLE artist (     -- 这份具体的表定义，就是 schema
    name VARCHAR(50),
    year INT
);
概念 定义 建筑类比
Data Model（数据模型） 一套高层抽象。规定能存在哪些东西，它们之间能有什么关系 建筑规范：建筑可以有房间、有门、有窗
Schema（模式） 在某个数据模型下，对一个具体数据库的描述 具体的蓝图：这扇门在这，这个房间多大

一份蓝图能盖出很多栋房子，也就是多个数据库实例。但蓝图能画什么，由建筑规范说了算。

31:59 数据模型全家福：

数据模型 说明 代表
关系模型 Relational 本课主角。今天绝大多数系统都是它 PostgreSQL、MySQL、ClickHouse……
键值 Key/Value 最简单的模型，就是个关联数组 / 哈希表 Redis、各类缓存
文档 Document 嵌套的 JSON/XML 文档 MongoDB
数组 / 矩阵 / 向量 一维向量、二维张量 科学计算、ML 负载。向量数据库做 RAG / 语义搜索
层次 Hierarchical 1960s 的老古董 IBM IMS
网状 Network 同上 CODASYL 系统
图 Graph / 语义 Semantic 显式建模节点与边 Neo4j 等

32:43 说到 NoSQL，Andy 承认自己早年是 NoSQL 的批评者。而且事实证明，批评得对。现在几乎所有 NoSQL 系统，都在往回加关系模型的能力。Andy 也承认 NoSQL 没死。文档、JSON、XML 数据库都还在。

有学生问"键值算不算 NoSQL"。Andy 答得很实在：NoSQL 没有学术上的严格定义。你要说 Redis 是 NoSQL，也行。

34:48 Andy 的定位是：关系模型之于数据库，就像 1+1=2 之于算术。 它是最基础的构件。唯一真正不适合关系模型的场景是矩阵运算。能建模，但不是最佳方式。

5关系模型之前的黑暗时代

难度 ★★★★★了解历史故事，声明式的好处第 6 节会再讲

关系模型出现之前，程序员得亲手告诉数据库每一步怎么走。

最早的系统

最早的数据库系统，出自通用电气和 IBM。35:33

年份 系统 出处 备注
1965 IDS（Integrated Data Store） General Electric 用汇编写的，Charles Bachman 主导
1960s IMS IBM 为阿波罗登月计划造的，用来追踪飞船的所有零件。课上说"那会儿 NASA 还没叫 NASA"。实际 NASA 1958 年就成立了，IMS 到 1960 年代中期才开始开发

34:08 一个反直觉的事实：IMS 到今天还活着。IBM 靠它还在赚大钱，几乎每家银行都还在跑。只不过外面套了一层关系模型的皮，看不出原样了。

"程序员即导航员"

导航式数据库要程序员先摸清数据怎么存，再亲手写遍历。36:18 Charles Bachman 1973 年拿了图灵奖。获奖演讲的论文叫 《The Programmer as Navigator》。

论文的核心思想是这样的。程序员像哥白尼、像航海家，在数据库这片"海洋"里导航。一步步找到想要的数据。

听着很浪漫。37:01 但这是个糟糕的主意。程序员必须精确知道数据在系统里怎么存。然后针对这些数据结构写代码。

37:38 这套东西的标准叫 CODASYL。写查询长这样（伪代码）：

# 想查：今年这张致敬专辑上都有哪些艺人
FOR EACH artist IN artists:            # 嵌套 for 循环手动遍历
    FOR EACH album IN artist.albums:
        IF album.name == "Tribute":
            OUTPUT artist.name
# 先遍历 artist 还是先遍历 album，是你写死的

39:01 致命问题在于：先遍历 artist 还是先遍历 album，得你自己定。 哪个快？取决于两张表各有多少条记录。

  • 你今天可能知道答案。
  • 可一年后数据变了呢？
  • 这个决定已经硬编码在查询代码里了，数据库只能照做。

这就像出门前把路线背死。哪天修路了，你还是只会走老路。

39:44 等价的 SQL 是这样：

SELECT artist.name
FROM artist
JOIN album ON artist.id = album.artist_id
WHERE album.name = 'Tribute';

这里没有一个字在说"怎么做"，只说了"我要什么"。 剩下的由数据库自己想办法。今天看这是常识，当年却是石破天惊的想法。

1974 年的世纪对决

这场辩论，最后是关系模型赢了。40:26 1974 年，在密歇根大学安娜堡，CODASYL 派和关系模型派当面辩论。全程有公开记录。

  • CODASYL 派：关系模型论文（1970）说得漂亮，但根本造不出来。它太复杂，没人能推理明白。
  • 关系模型派：手动导航数据库，会让程序极其脆弱。这等于把执行计划写死在查询里。

42:38 五十年后的判决是：关系模型完胜。证据就是这堂课开头学生喊出的名字，全是关系数据库。没有一个人提 CODASYL。

数据库领域的四位图灵奖得主

数据库领域出了四位图灵奖得主。41:10

人物 贡献
Ted Codd 提出关系模型
Charles Bachman IDS / CODASYL / 导航式模型
Jim Gray 事务与锁，IBM System R
Michael Stonebraker Ingres，之后是 Postgres

6关系模型的三个核心思想

难度 ★★★★★重要后面换存储、换计划的自由都来自这三条

关系模型的底牌就三张：值代替指针，约束，声明式查询。42:38 Codd 的关系模型剥到核心，只有这三条。

① 用高层集合（关系）来定义数据，用值表达关联

记录之间靠存"值"来关联，不靠物理指针。数据被组织成叫 relation（关系） 的高层集合。它本质就是数学里的集合。

导航式：album 记录里存一个内存地址 / 磁盘偏移，指向 artist
关系式：album 记录里存 artist_id = 42，靠这个值去 artist 表里找

导航式像记下朋友家的门牌坐标，朋友一搬家就找不到了。关系式像记下朋友的手机号，人搬到哪都能打通。

这一条是所有好处的根源。没了物理指针，底层怎么存就完全自由了。

② 可以声明约束，保证数据合法

数据库会在写入时把关，不合法的值进不来。43:22 在前面的 CSV 方案里，年份谁都能改。用文本编辑器就能改成一串乱码。关系数据库不让你这么干。一列声明了什么类型，就塞不进违反类型的东西。

CREATE TABLE artist (name VARCHAR(50), year INT);
INSERT INTO artist VALUES ('GZA', 'hello');   -- 按关系模型：year 是 INT，拒绝写入
-- 但有的系统会照单全收，见下面的踩坑

踩坑：这条不总是成立，Andy 补了句实话。有些系统会让你往列里塞各种不该有的东西，Andy 点名了 SQLite。数据模型和具体实现是两回事。

③ 用高层声明式 API 查询

你只说要什么答案，怎么算由数据库自己定。44:03 你不用关心数据库内部是怎么实现的。于是：

  • 数据库可以自己挑最高效的执行计划。
  • 数据分布随时间变了，同一条查询可以换个更快的方式跑。
  • 存储方式变了，查询一个字都不用改。
SELECT name FROM artist WHERE year = 1992;   -- 只说要什么
-- 走索引还是全表扫，由数据库挑
-- 数据变了，它可以换一种跑法，这条 SQL 不用改

这就像打车只报目的地，路线让司机挑。

7三级模式与数据独立性

难度 ★★★★★重要#03 #06 的存储自由靠它，作业不直接考

应用只碰逻辑层，所以底层怎么存可以随便换，应用不会坏。45:24 这一节讲的是关系模型最大的工程价值。

先看反面。在 IBM IMS 里，声明一张表时，必须同时说它底层是树还是哈希表。而且：

  • 选了哈希表，就用不了范围扫描。
  • 选了树，有些查找方式也用不了。
  • 两种选择给你的 API 不一样。

哪天你发现选错了，想从树换成哈希，所有相关代码都得重写。

CREATE INDEX idx_name ON artist (name);   -- 底层结构由数据库这边定
SELECT * FROM artist WHERE name = 'GZA';  -- 应用只写这句，底层换了也不用改
-- 考点：物理数据独立性。IMS 里选树还是选哈希表，直接决定你能用的 API
-- 考点：所以 IMS 换一次底层结构，相关代码全得重写

这就像墙上的插座。墙里电线怎么走你不用管，插头形状不变，电器就能用。

关系模型没有这个问题。你根本不知道底层是什么数据结构。你只在"关系/表"这个逻辑层访问数据。

46:06 分层结构如下：

┌──────────────────────────────────────────┐
│  应用程序                                  │  用 SQL 这类声明式语言访问
├──────────────────────────────────────────┤
│  External Schema  外部模式（视图）          │  ← 逻辑数据独立性
│    暴露给不同应用的不同"版本"的数据          │
├──────────────────────────────────────────┤
│  Logical Schema   逻辑模式                 │  ← 物理数据独立性
│    有哪些表、哪些属性、什么名字、什么类型     │
├──────────────────────────────────────────┤
│  Physical Schema  物理模式                 │
│    文件、页、区段(extent)，字节怎么摆        │
├──────────────────────────────────────────┤
│  Database Storage 存储介质                 │

8关系模型的基本构件

难度 ★★★★★必会HW1 连表靠主外键，UPSERT 靠主键冲突

关系就是一张无序的表。元组是行，属性是列，域是类型。50:26

CREATE TABLE artist (     -- relation：一张表
    name VARCHAR(50),     -- attribute：一列
    year INT              -- domain：year 只能取 INT 范围内的值
);                        -- 插进去的每一行，就是一个 tuple
术语 定义 SQL 里的叫法
Relation 关系 无序的数据集合 Table 表
Tuple 元组 关系里的一条记录。Andy 念 "tuple"，也有人念 "tupple" Row 行
Attribute 属性 元组里的一个字段 Column 列
Domain 域 某个属性允许取的值的范围 数据类型。比如 32 位有符号整数，域是 −2³¹ ~ 2³¹−1

踩坑：关系是无序的。这一点在 #06 列存 讲存储模型时很关键。到那时，"行"和"列"就不一定这么对得上了。

NULL

NULL 表示"不知道"，所以拿它做比较，得不到 true。51:08 每个域都可以额外允许一个特殊值 NULL，表示值未知。

SELECT NULL = NULL;                       -- 结果不是 true，答案是"未知"
SELECT * FROM artist WHERE year = NULL;   -- 所以别指望靠 = 把 NULL 行找出来

它和 C 语言的空指针有点像，但作用在逻辑层。NULL 确实占了一个存储位置。但你没法对它做任何推理，因为答案是"未知"。这就是 NULL = NULL 不返回 true 的原因。

NULL 像一张没填年龄的问卷。两张都没填，你不能说这两个人同岁。

主键 Primary Key

主键是能唯一认出一条元组的那个值。51:52

CREATE TABLE artist (
    id   INT PRIMARY KEY,   -- 合成键：数据库发的编号，没有业务含义
    name VARCHAR(50)        -- 名字会重名，不能当主键
);
-- 考点：艺人名字为什么不适合当主键？自然键和合成键各有什么代价？

名字通常不能当主键，因为乐队重名太常见了。有些乐队会玩花招，比如去掉元音来避免撞名。但你不能指望这个。

类型 说明 例子
自然键 Natural Key 现实世界里本来就唯一的属性 CMU 的 Andrew 邮箱
合成键 / 标识列 Identity Column 数据库生成的唯一编号，没有业务含义 自增计数器

53:18 很多 ORM 框架会自动帮你生成标识列。Andy 认为这样挺好，直接用。

补充：（非视频内容）网页 URL 里的订单号，基本就是自增标识列。所以很多系统改用 UUID 或雪花 ID，因为自增 ID 会泄露业务量。

外键 Foreign Key

外键让数据库替你拦住"人删了，引用还留着"的操作。54:01 它用来表达不同关系之间元组的关联。

CREATE TABLE album (
    name      VARCHAR(50),
    artist_id INT REFERENCES artist (id)   -- 这个值必须在 artist.id 里找得到
);
DELETE FROM artist WHERE id = 1;   -- 还有专辑指着它，数据库会拦住

56:56 Andy 回答学生提问时，给了一个定义。某个属性的值，必须存在于另一个关系的某一列中。

它解决的正是第 2 节清单里的第 8 条，悬垂引用。你想删掉一个艺人。数据库发现还有外键指着这个艺人，就会拦住你。

多对多：交叉引用表

多对多关系，要单独建一张表来存。54:43 这是本讲最实用的建模知识点。

问题：直接在 album 里放一列 artist_id，就默认了"一张专辑只有一个艺人"。可合辑、feat.、mixtape 遍地都是。

解法：引入一张交叉引用表，专门存关系本身。

artist                album              artist_album  ← 交叉引用表
┌────┬─────────┐     ┌────┬────────┐    ┌───────────┬──────────┐
│ id │ name    │     │ id │ name   │    │ artist_id │ album_id │
├────┼─────────┤     ├────┼────────┤    ├───────────┼──────────┤
│ 1  │ GZA     │     │ 1  │ 36 Ch. │    │ 1         │ 1        │
│ 2  │ RZA     │     │ 2  │ Liquid │    │ 2         │ 1        │  ← 同一张专辑两个艺人
└────┴─────────┘     └────┴────────┘    │ 1         │ 2        │
                                         └───────────┴──────────┘
                                          ↑ 主键 = 两列的组合

CREATE TABLE artist_album (
    artist_id INT,
    album_id  INT,
    PRIMARY KEY (artist_id, album_id)   -- 两列组合当主键
);
-- 考点：album 里加一列 artist_id，一张专辑就只能挂一个艺人

这就像学生名单和选课单分开放。谁选了哪门课，单独记在选课单上。

57:37 学生问这张表的主键是什么。答案是两列的组合，也就是图里画下划线的部分。SQL 里当然可以声明多列组成的主键。

这样 album 表里就不用存 artist_id 了。关联被单独拎出来表达。

约束 Constraints

约束是在数据类型之外，再加一道"什么值合法"的规矩。55:27 Andy 因为时间跳过了细节，核心就是这一句。

name  VARCHAR(50) NOT NULL,                      -- 不能为空

9关系代数：七个算子

难度 ★★★★★必会#25 复习清单写明要懂，HW1 按它拆题

关系代数是一组算子，进去是关系，出来还是关系。执行引擎就照着它搭。58:21 定义完关系长什么样，接下来要能查它。这属于 DML（数据操纵语言）。注意，只读的 SELECT 也算 DML。

DML 分两派：

关系代数 Relational Algebra 关系演算 Relational Calculus
风格 过程式：每一步怎么做、按什么顺序做，我来规定 声明式：我只说要什么答案
时间 Codd 一开始定义模型时就给了 后来才有
对应 数据库执行引擎长得很像它 SQL 基本映射到这个

59:45 Andy 说这门课不教关系演算。除非你要写查询优化器，否则现实世界里没人用。但关系代数必须懂，它是理解查询引擎的基础。

1:00:30 Codd 原始定义了七个算子。重要特性是：每个算子输入的是关系，输出的也是关系。 所以它们能像管道一样串起来，用简单算子拼出复杂查询。

π(name)( σ(year = 1992)(artist) )
-- σ 的输出还是关系，直接喂给 π
-- 就像 Linux 的管道：一个命令的输出，接到下一个命令

踩坑：原始七算子里没有排序，也没有聚合，比如求平均值。这些都是后来的扩展。

σ Select（选择）：对应 WHERE

σ 就是 WHERE，按条件把不要的元组过滤掉。1:01:14

σ(a_id = 'a2')(R)                        →  SELECT * FROM R WHERE a_id = 'a2';
σ(a_id = 'a2' ∧ b_id > 102)(R)           →  ... WHERE a_id='a2' AND b_id > 102;
-- 考点：σ 对应 SQL 的 WHERE 子句，不是 SELECT 关键字

σ 像一把筛子，只管挑行，不管挑列。

踩坑：这是最容易混的地方。关系代数里的 "select" 算子，对应的是 SQL 的 WHERE 子句。它不是 SQL 的 SELECT 关键字。1:04:11 有学生当场就被绕晕了。记住：σ = WHERE。

π Projection（投影）：对应 SELECT 后面的列清单

π 决定输出哪些列，以什么样子输出。1:02:42 它能做三件事：

  1. 重排属性顺序。
  2. 删掉不要的属性，比如把密码列藏掉。
  3. 算出新值。
π(b_id − 100, a_id)( σ(a_id='a2')(R) )

→  SELECT b_id - 100, a_id FROM R WHERE a_id = 'a2';
-- σ 只挑行，π 挑列，还能算新列

1:04:53 有学生问，能不能用 σ 代替 π。不能。 σ 的表达式必须能算出布尔真假，而 b_id − 100 是个数值。硬说"b_id − 100 非零就算 true"，语义就完全不是一回事了。

∪ ∩ − Union / Intersection / Difference

并、交、差就是集合论那一套，前提是两边的列要对齐。1:08:42

SELECT * FROM R UNION     SELECT * FROM S;
SELECT * FROM R INTERSECT SELECT * FROM S;
SELECT * FROM R EXCEPT    SELECT * FROM S;
-- R 和 S 的属性个数、类型必须一一对上

踩坑：这是硬性要求。参与运算的两个关系，必须有完全相同的属性。个数、类型都要对上。否则输出关系没法定义。

× Cartesian Product（笛卡尔积）

笛卡尔积就是把 R 的每一行和 S 的每一行都配一遍。1:10:09 这是无脑组合，输出关系包含双方所有属性。

SELECT * FROM R CROSS JOIN S;
SELECT * FROM R, S;              -- 不写 CROSS JOIN 默认就是它

这就像拿每一把钥匙，都去试每一把锁。

1:10:53 但这几乎不是我们想要的。 你要的是"这张专辑上有哪些艺人"。不是"所有艺人 × 所有专辑"的全部组合，那里面绝大部分是垃圾。

⋈ Join（连接）

Join 就是笛卡尔积，再加一个过滤谓词。只留下"一个关系的值 = 另一个关系的值"的那些组合。

1:11:32 再说 NATURAL JOIN（自然连接）。它会自动找出两个关系里同名同类型的属性，拿来匹配。然后去掉重复列。

-- 不推荐
SELECT * FROM artist NATURAL JOIN album;
-- 推荐
SELECT * FROM artist JOIN album ON artist.id = album.artist_id;
-- 考点：Andy 为什么不推荐 NATURAL JOIN？它在隐式地猜按哪些列连接

踩坑：对 NATURAL JOIN，Andy 明确不推荐。它会隐式地去猜该按哪些属性连接。建议显式写出连接谓词。

10算子顺序决定性能

难度 ★★★★★重要#15 谓词下推的引子，具体规则到 #15 才考

同样的结果，先过滤还是先连接，速度能差几个数量级。1:12:58 这是本讲最重要的收尾。 它也是后面整个查询优化部分（#15 #16）的引子。

看这个需求：把 R 和 S 连起来，再过滤出 b_id = 102 的行。有两种写法：

方案 A：  σ(b_id=102)( R ⋈ S )      先连接，再过滤
方案 B：  R ⋈ σ(b_id=102)(S)        先过滤，再连接

考点：两种写法结果相同，为什么性能能差几个数量级？用极端情况去想

结果完全一样，性能可能差几个数量级。

1:13:00 Andy 在这里给了一条贯穿整个学期的方法论：

"Always think of extremes." 永远拿极端情况去想。

拿这个例子套一下：

  • 一张表 5 条记录，另一张表一万亿条。
  • 方案 A：先做一万亿行的连接，产出巨量中间结果。最后发现只有 2 行满足条件，绝大部分工作白干了。
  • 方案 B：先把 S 过滤到 2 行，再去连接。快得多。

这就像在全城找一个人。先按小区筛，再上门敲，比先挨家敲门再筛快得多。

这就是声明式语言存在的全部理由。 你写关系代数，数据库就得严格按你写的顺序执行。你写 SQL，只说"我要这个答案"。数据库就能自己判断，哪种顺序更快。而且这个判断还能随数据变化而变化。

SQL 分三块：查改数据，定义结构，管权限。11:35

一个语言设计八卦

SELECT 写在 FROM 前面，是一次用户研究定下来的。9:34 对 SQL 最大的吐槽之一，就是 SELECT 写在 FROM 前面。逻辑上明明是先有表，再选列。

SELECT name FROM student;   -- 现在的写法：先写列，再写表
-- 逻辑上是先有 student 表，再从里面挑 name 列

真相是：IBM 1970 年代的原始提案里，FROM 确实在前面。 后来在亚利桑那州立大学做了一次用户研究。被测的学生说"我们更喜欢 SELECT 在前"。于是就这么定了五六十年。

2关键认知：SQL 基于「包」不是「集合」

难度 ★★★★★重要HW1 不单独考，但 DISTINCT、扇出都源于它

SQL 默认不去重，因为去重要额外花力气。12:13 这是本讲最容易被忽略、却最重要的一条。

SELECT cid FROM enrolled;            -- 包：一门课被选了几次，就返回几次
SELECT DISTINCT cid FROM enrolled;   -- 集合：得你自己加 DISTINCT，数据库再额外去重
-- 考点：UNION 要去重，所以比 UNION ALL 慢
-- 考点：COUNT(DISTINCT x) 也因为去重，比 COUNT(*) 贵得多

包像购物袋，同样的苹果能装两个。集合像集邮册，同一张邮票只收一次。

概念 有序？ 允许重复？
Set 集合 否，无序 否，不允许
Bag 包（多重集） 否，无序 是，允许
List 列表 是，有序 是，允许

关系模型建立在集合上，上一讲的 ∪ ∩ − 都是集合运算。但 SQL 建立在包上。

为什么？因为去重要额外开销。 SQL 默认让重复留着。你真的在意，就自己加 DISTINCT。

补充：这个设计选择会一路影响到后面。比如 UNION 比 UNION ALL 慢，因为前者要去重。再比如 COUNT(*) 和 COUNT(DISTINCT x) 的代价差那么多。

3聚合与分组

难度 ★★★★★必会HW1 题型二、四直接考，P3 要写聚合算子

聚合是把一堆行压成一个值。分组是先把行分堆，再每堆各压各的。本讲的示例数据库是个简化的大学模型。三张表是 student（学生）、course（课程）、enrolled（选课与成绩）。

聚合函数

聚合就是把多个元组的多个值，压成一个标量值。14:16 基本的有 AVG / MIN / MAX / COUNT / SUM。有些系统还提供标准差、几何平均等。

聚合函数基本上只能出现在投影列表里。嵌套查询里是例外，先不管。

SELECT COUNT(login) FROM student WHERE login LIKE '%@cs';

15:39 这里有个细节。在这条查询里，COUNT(login) 里那个 login 其实无所谓。

COUNT(login)     ┐
COUNT(*)         ├─ 这条查询里结果一样
COUNT(1)         │
COUNT(1+1)       ┘
-- 考点：COUNT(login)、COUNT(*)、COUNT(1) 结果一样吗？只在这条查询里一样

因为 WHERE login LIKE '%@cs' 已经把 login 为 NULL 的行滤掉了。这时 COUNT 干的事，就是数有多少条元组通过了过滤。

-- 示意：student 一共 3 行，其中 1 行的 login 是 NULL
SELECT COUNT(*)     FROM student;   -- 3，数的是行数
SELECT COUNT(login) FROM student;   -- 2，NULL 那行被跳过了

COUNT(*) 像数到场的人头，COUNT(login) 像数交了作业的人。

踩坑：换一条查询就不一定了。COUNT(col) 会跳过 col 为 NULL 的行，COUNT(*) 数的是行数，不管 NULL。列里有 NULL，又没有这样的过滤，COUNT(col) 就会比 COUNT(*) 小。Andy 说的"填什么都一样"，官方 Notes 的"三条等价"，都只针对这个例子。

为什么必须 GROUP BY

聚合把多行压成一行。不分组的话，旁边的普通列不知道该填谁。16:19 下面这条查询是错的：

-- 想求"每门课的平均 GPA"
SELECT AVG(s.gpa), e.cid
FROM enrolled AS e, student AS s
WHERE e.sid = s.sid;
-- 错误：缺了 GROUP BY
-- 考点：AVG 只产出一个值，cid 却有很多个，这一行该配哪个 cid？
-- 考点：SQLite 允许这样写，它会随便挑一个值

错在哪？ AVG(s.gpa) 把所有元组压成了一个值。那这一行该配哪个 cid？没有"标准答案"。

全班平均分只有一个数，你却要在它旁边写一个课号。写哪个都不对。

各系统的态度不一：

系统 行为
大多数系统 直接报错
SQLite 让你这么干，随便挑一个值
MySQL 以前让，现在不让了

正确写法是加 GROUP BY：

SELECT AVG(s.gpa), e.cid
FROM enrolled AS e, student AS s
WHERE e.sid = s.sid
GROUP BY e.cid;

17:47 GROUP BY 的语义是：在扫描过程中把数据切成组。聚合在每组内部计算。

注意这里没规定怎么实现。 数据库可以建哈希表，也可以先排序再分组。这正是声明式的好处。#11 排序与聚合 会讲这两种实现。

GROUPING SETS

扫一遍数据，就能算出好几种粒度的聚合。不用写好几条查询再拼。18:30 想在一条查询里做多种不同粒度的聚合，怎么办？

朴素做法是写多条查询，再 UNION 起来。更好的做法是告诉数据库"我要的是这一组聚合"。让它扫一遍数据，全算出来：

SELECT cid, grade, COUNT(*)
FROM enrolled
GROUP BY GROUPING SETS (
    (cid, grade),   -- 按课程+成绩
    (cid),          -- 按课程
    ()              -- 总计
);

输出里，某一行没参与分组的列，会填 NULL。

19:47 Andy 在这里点出一个贯穿全课的主题：

尽量减少数据库和应用之间的来回往返。 一次给数据库尽可能完整的信息。它能比你分多次往返做得更好。

这就像去超市前把清单列全。一趟买齐，比跑三趟快。

相关的还有 ROLLUP 和 CUBE，课上没展开。

HAVING

要过滤聚合结果得用 HAVING，因为 WHERE 干活的时候，聚合还没算出来。20:31 想对聚合结果再过滤，不能用 WHERE：

-- 错误
SELECT AVG(s.gpa) AS avg_gpa, e.cid
FROM enrolled e, student s
WHERE e.sid = s.sid AND avg_gpa > 3.9      -- ← WHERE 里引用聚合结果
GROUP BY e.cid;
-- 考点：WHERE 在扫描时逐行过滤，那时 avg_gpa 还没算出来，所以只能放进 HAVING

错在哪？ 想象数据库正在扫描数据。此刻 avg_gpa 还没算出来，它怎么判断该不该丢掉这条记录？

这就像考试还没交卷，就要按平均分把人请出考场。

正确写法：

SELECT AVG(s.gpa) AS avg_gpa, e.cid
FROM enrolled e, student s
WHERE e.sid = s.sid
GROUP BY e.cid
HAVING avg_gpa > 3.9;

踩坑：21:53 别名有可移植性问题。有些系统在 HAVING 里不认上面定义的别名，Andy 点名 PostgreSQL 就要求这样。这时你得把聚合表达式重写一遍，见下面的代码。

HAVING AVG(s.gpa) > 3.9

Andy 承认这有点自打脸。SQL 本来不该让你操心执行顺序。这里却把执行顺序暴露出来了。

23:25 学生追问：AVG 写两遍，数据库会不会真算两次？理想情况下不会。 大多数系统够聪明，能认出来，但没有保证。

踩坑：22:37 看上面例子里的连接写法。FROM enrolled AS e, student AS s 加 WHERE e.sid = s.sid，是老式隐式连接写法。Andy 明确说：别学我这么写，永远显式写 JOIN。数据库通常够聪明，会认出这是内连接，不会先做笛卡尔积。

4字符串：标准与现实的第一道裂缝

难度 ★★★★★重要HW1 只用 || 拼接和 NULL，方言差异不考

同一条字符串查询，换个数据库跑，结果就可能不一样。25:23 从这里开始，是本讲最有价值的部分。Andy 现场在六七个数据库上跑同样的 SQL，展示它们有多不一样。

SQL 标准规定：字符串大小写敏感，字面量用单引号。

SELECT * FROM artist WHERE name = 'RZA';
SELECT * FROM artist WHERE name = 'rza';
-- PostgreSQL：第二条查不到
-- MySQL：两条返回一样的结果，因为它不分大小写

这就像两本字典，一本区分大小写，一本不区分。同一个词，查出来的结果不一样。

系统 大小写 双引号
PostgreSQL 敏感 双引号表示标识符转义，比如表名带空格
MySQL 不敏感 能。单双引号都能当字符串
SQLite 敏感 能。允许当字符串
DuckDB 敏感 双引号被当成列名

踩坑：这里的异类是 MySQL。WHERE name = 'RZA' 和 WHERE name = 'rza' 在 MySQL 里返回一样的结果。在 PostgreSQL 里，后者查不到。跨库迁移时，这是颗隐形炸弹。

29:50 再说标识符，也就是表名、列名的大小写。标准怎么规定，Andy 自己也不确定，于是现场试了一下：

  • PostgreSQL 默认把你给的表名自动转成小写。
  • 但建表时加了双引号，大小写就被保留了。之后查询也必须带双引号。
  • 别的系统未必这样。
CREATE TABLE "Foo" (x INT);   -- 加了双引号，大小写被保留
SELECT * FROM Foo;            -- PostgreSQL 会转成 foo，对不上
SELECT * FROM "Foo";          -- 之后查询也得带双引号

通配符与正则

LIKE 各家都支持，正则就各搞各的了。

SELECT * FROM course WHERE cid LIKE '15%';     -- % 匹配任意子串，含空串
SELECT * FROM course WHERE cid LIKE '15-44_';  -- 示意：_ 只匹配一个字符
SELECT * FROM artist WHERE name ILIKE 'rza';   -- PostgreSQL 的大小写不敏感匹配
功能 标准 现实
LIKE '15%' % 匹配任意子串，含空串。_ 匹配单个字符 各家都支持
大小写不敏感匹配 标准里没有 PostgreSQL 有 ILIKE
正则 标准规定用 SIMILAR TO PostgreSQL / DuckDB 支持。很多系统不支持，各自搞了自己的正则语法

字符串拼接：三种写法

拼两个字符串这种小事，三个系统有三种写法。32:09

SELECT 'Wu' || '-Tang';        -- SQL 标准 / PostgreSQL / DuckDB
SELECT 'Wu' + '-Tang';         -- SQL Server
SELECT CONCAT('Wu', '-Tang');  -- MySQL：前两种都没有
系统 语法
SQL 标准 / PostgreSQL / DuckDB a || b
SQL Server a + b
MySQL 两个都没有，必须写 CONCAT(a, b)

内置的 SUBSTRING / LOWER / UPPER 这类函数，各家语义倒是基本一致。

33:37 Andy 的总结很直白。据 Andy 所知，世界上没有一个系统完整实现了 SQL-92 标准。 各家总有偏差。MySQL 曾经是最大的违规者，近十年改好了不少。

34:19 至于 SQL:2023 的属性图查询，目前只有 Oracle 支持。因为是 Oracle 把它推进标准的。

34:55 Andy 还讲了个八卦。上学期，Andy 请 MySQL 的发明人来做讲座。私下问对方："你们当年为什么搞出那么多怪东西？"对方的回答大意是："就是九十年代随手那么做了，我也不知道。" 很多标准之外的差异，就是某个人当年拍脑袋定的。

另一个例子：LATERAL JOIN 本来就在标准里。可微软的人似乎不知道它存在，自己造了个 CROSS APPLY。语义基本一样，名字完全不同。

5日期时间：裂缝变成深渊

难度 ★★★★★了解方言对比演示，作业不考

算两个日期差几天，七个数据库有七种写法。其中一个还会悄悄算错。35:37 这是 Andy 每年最爱演示的环节。

任务简单到不能再简单。算出 2025 年 8 月 27 日距离 2025 年 1 月 1 日有多少天。 正确答案是 238。

这就像一道小学算术题。七个学生交上来七种解法，还有一个答错了。

第一步：怎么拿到「今天」

连"现在是什么时候"，都没有一种写法能通吃所有系统。Andy 试了两轮。先试 NOW()，再试 CURRENT_TIMESTAMP 的函数写法（带括号）和关键字写法（不带括号）。

SELECT NOW();                -- PostgreSQL 能，SQLite 不能
SELECT CURRENT_TIMESTAMP();  -- MySQL 能，PostgreSQL 不能
SELECT CURRENT_TIMESTAMP;    -- SQLite 能，ClickHouse 不能
系统 NOW() CURRENT_TIMESTAMP() 函数 CURRENT_TIMESTAMP 关键字
PostgreSQL 能 不能 能
MySQL 能 能 能
SQLite 不能 不能 能
DuckDB 能 不能 能
ClickHouse 能 能 不能
Firebolt 能 能 不能
SQL Server 不能 不能 能。而且每条语句后面要写 GO

没有哪种写法在所有系统上都能用。

补充：36:20 一个有用的观察：DuckDB 直接复用了 PostgreSQL 的语法。它是字面上拷了 Postgres 的 grammar。所以 Postgres 有的，DuckDB 大概率也有。

第二步：算日期差

PostgreSQL 一系直接相减就对，MySQL 直接相减会得出 726 这种离谱数。

PostgreSQL / DuckDB / Firebolt：直接减

SELECT CAST('2025-08-27' AS DATE) - CAST('2025-01-01' AS DATE);
-- → 238，对的

40:01 PostgreSQL 还有个 Andy 很喜欢的双冒号转型语法：

SELECT '2025-08-27'::DATE - '2025-01-01'::DATE;    -- 更短

MySQL：答案是 726，离谱

SELECT CAST('2025-08-27' AS DATE) - CAST('2025-01-01' AS DATE);
-- → 726，错的
-- 考点：726 是怎么来的？日期被拼成整数，再做整数减法

40:47 一年哪来 726 天？Andy 自己也没想明白。是 YouTube 评论区一位网友给出了解释，而且是对的。

MySQL 把日期转成了无符号整数，也就是把年月日直接拼成数字。然后做整数减法：

20250827 − 20250101 = 726
   ↑ 月份 8−1=7，日 27−1=26  →  "726"

这就像把 8 月 27 日写成 827，1 月 1 日写成 101。再拿小学减法去减。

正确写法要用专门的函数：

SELECT DATEDIFF('2025-08-27', '2025-01-01');   -- → 238

SQL Server

SQL Server 有 DATEDIFF，但参数形式不同。而且要用 GETDATE()，不用 NOW()。GETDATE() 别家都没有。

ClickHouse：大小写陷阱

42:58 ClickHouse 文档说有 TODAY() 函数。但必须写成小写的 today() 才能用。而同一个系统里，NOW() 大小写都行。

SQLite：最惨

43:41 SQLite 没有 DATEDIFF，直接相减得 0。只能绕路，有两种方案：

-- 方案 1：转成儒略日（自公元前 4712 年起的天数）
SELECT CAST((julianday('2025-08-27') - julianday('2025-01-01')) AS INT);  -- → 238

-- 方案 2：转成 Unix 时间戳（自 1970-01-01 起的秒数）再换算成天
SELECT (strftime('%s','2025-08-27') - strftime('%s','2025-01-01')) / 60 / 60 / 24;

结论

45:06 算两个日期差几天，听上去不能再简单。可它在七个主流数据库上有七种写法。其中一个还会默默给你错误答案。

所以这门课的第一次作业（HW1）用 DuckDB。不是为了教 DuckDB 语法，而是它在任何机器上都能跑起来。

Andy 强调：重点是理解 SQL 能做什么，不是背某一家的方言。 懂了本质，换系统很快。「从 MySQL 到 PostgreSQL」远比「从 Python 到 Rust」容易。

补充：（非视频内容）实践上的推论很简单。业务代码里少写日期函数，多在应用层算。真要写，就封装一层。换库时只改一个地方。

6输出控制

难度 ★★★★★必会HW1 题型一直接考，漏次关键字就丢分

SQL 的结果本身没有顺序，想要顺序和条数，必须自己写明白。45:49 因为关系模型和 SQL 本身是无序的。想要顺序，就得显式声明。

-- 排序
SELECT sid, grade FROM enrolled WHERE cid = '15-445' ORDER BY grade DESC, sid ASC;

-- 限制条数（标准写法）
SELECT sid FROM enrolled FETCH FIRST 10 ROWS ONLY OFFSET 20;

-- 简写（不在标准里，但 DuckDB / PostgreSQL / MySQL 都支持）
SELECT sid FROM enrolled LIMIT 10 OFFSET 20;

-- SQL Server 自己的写法
SELECT TOP 10 sid FROM enrolled;

-- 不写 ORDER BY，就别指望结果有顺序

这就像从抽奖箱里往外摸球。摸出来的顺序由不得你，想排好就得自己说。

46:30 还能把查询结果直接写进一张表，同样是为了减少往返：

-- SQL 标准
SELECT DISTINCT cid INTO course_ids FROM enrolled;

-- PostgreSQL 可以指定为临时表，客户端断开就没了
CREATE TEMP TABLE course_ids AS SELECT DISTINCT cid FROM enrolled;

7嵌套查询

难度 ★★★★★必会HW1 题型三、四直接考相关子查询和 EXISTS

子查询写着顺手。可数据库要是不会把它改写成 JOIN，就会一遍遍重跑内层。47:11 有时候一条 SELECT 表达不了想要的东西。这时就得在查询里套查询。

嵌套查询几乎能出现在 SQL 语句的任何位置。 比如 WHERE 子句、投影列表、FROM 子句。有些系统甚至允许放在 GROUP BY / HAVING 里，但这不是好主意。

性能警告：这是嵌套查询最大的坑

最笨的执行方式是两层嵌套循环。外层每扫一行，内层就完整跑一遍。48:32

for (auto &outer : student) {          // 外层每扫一条记录
  auto inner = RunQuery(subquery);     // 内层就完整跑一遍
  if (inner.Contains(outer.sid)) Emit(outer);
}
// 内层答案通常不随外层变，白跑了很多遍

这就像每进来一位客人，就把整本菜单重新印一遍。

MySQL 以前就是这么干的。 大多数系统刚开始支持子查询时，也都这样。这显然极其低效。因为外层换一条记录，内层的答案通常根本不变。

理想做法是把嵌套查询改写成 JOIN。 因为数据库执行 JOIN 非常高效。

踩坑：49:09 不是每个系统都会做这个改写。 Andy 直言：PostgreSQL 在这方面很差。

49:52 谁做得好？

系统 能力
Umbra（德国，Thomas Neumann 团队，商业版叫 CedarDB） 基本上任何嵌套查询都能改写。今年还有新论文
DuckDB 实现了 Umbra 早期版本的方法，照着论文抄的
SQL Server 也不错
PostgreSQL 差

有意思的是，Andy 的一个博士生构造出了能打爆 DuckDB 的嵌套查询。不是结果错，而是中间结果爆炸，把内存耗尽了。最新版的 Umbra 能处理。

49:52 也有学生指出，子查询有时更快。比如内层算一个 MAX(id)，跑一次就缓存住，反复用。Andy 认可这种情形。但 Andy 强调，你永远不会想让内层查询被反复执行。

写嵌套查询的方法论

先写外层，再用大白话描述内层，最后翻成 SQL。51:11 这是 Andy 给做 HW1 的实用建议：

先写外层查询，确定最终输出长什么样。然后用自然语言描述内层要什么。最后再把它翻译成 SQL，塞进去。

这就像写作文先列提纲，再往每一段里填内容。

例：找出选了 15-445 的学生姓名

-- 第 1 步：外层骨架
SELECT name FROM student WHERE <这些人选了 15-445>;

-- 第 2 步：内层
SELECT sid FROM enrolled WHERE cid = '15-445';

-- 第 3 步：用 IN 缝起来（集合成员判断）
SELECT name FROM student
WHERE sid IN (SELECT sid FROM enrolled WHERE cid = '15-445');

连接内外层的操作符

内外层靠 IN、ANY、ALL、EXISTS 这几个词接起来。52:32

操作符 含义
IN 集合成员，等价于 = ANY
ANY / SOME 至少一个匹配
ALL 全部匹配
EXISTS 内层有结果就为真
NOT EXISTS 内层没结果才为真

例：在选了至少一门课的学生里，找 ID 最大的那个

SELECT sid, name FROM student
WHERE sid IN (SELECT MAX(sid) FROM enrolled);

53:53 Andy 强调，同一个答案有很多种写法。比如排序后取第一行，或者把聚合放进 JOIN 子句。Andy 不认为哪种一定更好，要看具体系统能不能优化。理论上 SQL 是声明式的，不该有差别。实际上经常有。

相关子查询 Correlated Subquery

内层引用了外层的列，就叫相关子查询，它最难被改写成 JOIN。54:32 例：找出没有任何学生选的课

SELECT * FROM course
WHERE NOT EXISTS (
    SELECT * FROM enrolled
    WHERE course.cid = enrolled.cid    -- ← 内层引用了外层的列
);
-- 考点：什么是相关子查询？为什么它比普通子查询更难改写成 JOIN？

内层的 course.cid，绑定到外层当前那条元组。这就叫相关子查询。

普通子查询像一份提前印好的名单，查一次就够。相关子查询像每来一个人都得现场问一句，答案跟着人变。

踩坑：相关子查询最难被改写成 JOIN。能做好的只有 SQL Server、DuckDB、Umbra/CedarDB 这几个。

8LATERAL JOIN

难度 ★★★★★必会HW1 题型五直接考「每组取一个」

LATERAL 让后面的子查询，能引用前面子查询的结果。代价是你得操心执行顺序。55:16 两个子查询在同一层级，不是嵌套层级。后一个可以引用它前面那个子查询的数据。

可以把它理解成两层 for 循环。前面已经执行的查询，能被后面的查询引用。

这就像一条流水线。后一道工序，能拿前一道工序的半成品接着干。

踩坑：有意思的是，Andy 指出这违背了 SQL 的声明式精神。用 LATERAL 时，你必须关心执行顺序。因为这个必须先算出来，那个才能算。

最小例子：

SELECT * FROM (SELECT 1 AS x) AS t1,
       LATERAL (SELECT t1.x + 1 AS y) AS t2;
-- 考点：LATERAL 违背了 SQL 的哪条设计原则？为什么它仍然有用？

实用例子：算每门课的选课人数和平均 GPA，按人数降序。

SELECT * FROM course AS c,
  LATERAL (SELECT COUNT(*) AS cnt FROM enrolled
           WHERE enrolled.cid = c.cid) AS t1,
  LATERAL (SELECT AVG(gpa) AS avg_gpa FROM student AS s
           JOIN enrolled AS e ON s.sid = e.sid
           WHERE e.cid = c.cid) AS t2
ORDER BY cnt DESC;

58:03 注意第二个 LATERAL 里的 c.cid。它既可以来自最外层，也可以来自中间那个。两种写法语义等价，结果一样。

支持情况：DuckDB、MySQL、PostgreSQL、Firebolt 都能给出相同结果。有些系统要求显式写成 JOIN LATERAL。SQL Server 叫它 CROSS APPLY，见上文那个八卦。

9CTE 公用表表达式

难度 ★★★★★必会HW1 通用流程第 ③ 步，每题都靠它拆子问题

CTE 就是查询内部的一张临时表，查询结束就扔掉。58:45 也就是 WITH 子句。有了它，你不用真写两条语句，一条建临时表，一条再查它。

WITH max_enrolled (max_sid) AS (
    SELECT MAX(sid) FROM enrolled
)
SELECT name FROM student, max_enrolled
WHERE student.sid = max_enrolled.max_sid;

这就像做菜前，先把配料切好摆在一边。下锅时直接拿。

要点：

  • 不用写列的类型。数据库从 AS (...) 里的查询自动推导。
  • 下面可以像引用真表一样引用它。
  • 数据库可以只算一次，后面重复使用。

1:00:56 CTE 和嵌套查询比，Andy 认为 CTE 的语法更好。嵌套查询是"埋"在语句里的，会让 SQL 又长又难读。CTE 是先在开头声明，后面再引用。

有学生问 CTE 能不能参数化，Andy 说不能。但 Andy 提到一个有意思的研究方向。把 PL/SQL 这类过程式存储过程，自动转换成 CTE。 做法是用一张状态表来模拟循环状态。

补充：（非视频内容）WITH RECURSIVE 可以写递归 CTE。它是查组织架构树、分类树、图遍历的标准手段。本讲没展开，SQL 笔记 里有例子。

10窗口函数

难度 ★★★★★必会HW1 题型五的另一解法，P3 要实现

窗口函数像聚合，但不把行压掉。每一行都能拿到自己的聚合结果。1:01:37 前面所有聚合都有个共同问题。它们没法表达和"顺序"有关的计算，因为 SQL 是无序的。

但很多需求就是要顺序：

  • 时间序列的移动平均，比如每个时刻的温度均值。
  • 股价走势。
  • 组内排名。

窗口函数就是来解决这个的。

SELECT cid, COUNT(*) FROM enrolled GROUP BY cid;    -- 每门课压成一行
SELECT cid, sid, COUNT(*) OVER (PARTITION BY cid)   -- 每个学生那一行都还在
FROM enrolled;
-- 考点：窗口函数和 GROUP BY 最本质的区别是，行不会被折叠掉
-- 考点：PARTITION BY 对应 GROUP BY 的分组，OVER 负责说明怎么切

GROUP BY 像把全班成绩汇成一张总表。窗口函数像在每个人的成绩单上，加一栏"本课平均"。

语法

OVER 子句负责说明怎么把数据切片。

SELECT ..., <函数>(...) OVER (<怎么切分>)
FROM ...

可用的函数

窗口里既能用普通聚合，也有几个窗口专用的函数。

类别 函数
普通聚合 AVG MIN MAX COUNT SUM，用来算移动平均等
窗口专用 ROW_NUMBER()（在组内是第几行）、RANK()（按排序的名次）

三个递进的例子

从全表编号，到分组编号，再到组内排序，一步步加条件。

1:03:03 ① 全表行号

SELECT *, ROW_NUMBER() OVER () AS row_num
FROM enrolled;

② 按课程分组后各自编号。 PARTITION BY 就是窗口函数版的 GROUP BY。

SELECT cid, sid, ROW_NUMBER() OVER (PARTITION BY cid) AS row_num
FROM enrolled;

每进入一个新分区，行号重新从 1 开始。

③ 组内排序

SELECT cid, sid, ROW_NUMBER() OVER (PARTITION BY cid ORDER BY sid) AS row_num
FROM enrolled;

踩坑：OVER 里的 ORDER BY 和查询末尾的 ORDER BY 是两回事。前者决定窗口内怎么排，影响 ROW_NUMBER / RANK 的结果。后者决定最终输出怎么排。

补充：（非视频内容）ROW_NUMBER / RANK / DENSE_RANK 处理并列的方式不同。分数是 100,100,90 时，结果分别是 1,2,3 / 1,1,3 / 1,1,2。"每组取 Top N" 是窗口函数最经典的用法。

11客串环节：dbt

难度 ★★★★★了解客座内容，#25 清单写明不考

dbt 本质上就是 SQL 加模板，用软件工程的办法管数据转换。1:05:56 本讲后半段有个客座分享。讲者是 dbt Labs 联合创始人 Drew Banin。

Andy 评价说，dbt 是当今数据领域用得最广的工具之一。做数据分析，基本绕不开它。而它本质上就是 SQL 加模板。

它解决什么问题

公司里成百上千张表没人管，dbt 就是来收拾这个烂摊子的。Drew 描述了一个典型的混乱现场。

公司把各处数据抽取、加载进数据仓库。来源有 Postgres、MySQL、广告、支付、财务、遥测、销售、客服等。结果是成百上千张表，由不同团队建出来。有的重复，有的过期。下游的 BI 报表、ML、运营脚本，又各自去查这些表。

这就像一个大厨房，每个厨师都自己囤调料。没人知道哪瓶过期了，也没人知道哪道菜用了哪瓶。

结果是：

  • 没有数据血缘。不知道这张报表的数据从哪来，只能祈祷它是对的。
  • 没有文档。找不到已有资产，只能重复造。
  • 没有发布流程。直接在生产环境上改。
  • 没有 QA。所以经常是坏的。
  • 业务逻辑重复。"什么算一个客户"被重新实现了一百遍，口径互相打架。

dbt 的做法

在数据仓库中间画一条线。左边放原始数据，右边放派生数据集。 dbt 负责中间这些转换管道。

关键在于，用软件工程的方式管数据转换：

  • 业务逻辑就是 SQL 代码，进版本控制（GitHub）。
  • 数据血缘可视化。
  • 走真正的 CI 流程。在开发环境改，不在生产环境改。
  • 资产可以复用。

模型代码本身就是普通 SQL，也就是 SELECT ... FROM ...。Drew 演示的那个，还用了窗口函数去重。唯一的区别是，dbt 内置了 Jinja 模板语言。它用来表达节点之间的依赖边，也能写循环，批量 union 多张表。

-- 示意：一个 dbt 模型文件
SELECT customer_id, name
FROM {{ ref('raw_customers') }}   -- Jinja 写法，表示依赖上游的 raw_customers
-- dbt 会把这条 SELECT 包进 CREATE TABLE AS，交给数据仓库执行

1:15:48 执行方式是这样的。dbt 把你的 SELECT 语句包进 CREATE TABLE AS ...，下推到底层数据仓库去执行。

一个关键问答

dbt 自己不跑查询，查询都下推给客户自己的数据仓库。1:13:36 有学生提了个问题。"你们有高效的执行引擎，来跑这些大数据量的管道吗？"

Drew 的回答很妙：

有啊，它叫 Snowflake、Databricks、BigQuery 或者 Redshift。

dbt 本身不是数据仓库，它只在客户自己的仓库上跑查询。Drew 还补充：Snowflake、BigQuery 上相当大比例的查询，都来自 dbt。

1:16:29 最后 Andy 帮学生翻译了一下这件事的意义：

你们现在体会不到 dbt 的重要性，因为你们还没有数据。等哪天你有了一堆 Python 脚本，在那儿互相拼接。你就会意识到，这东西根本没法维护。dbt 解决的就是这个问题。 它把数据管道声明出来。不再是一堆随手写的脚本，散落在 GitHub 各处。
