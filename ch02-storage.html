磁盘导向架构（Disk-Oriented DBMS）

数据库的主存储位置在磁盘上，可数据只能在内存里读写。5:21 这是整门课的核心架构假设。

这里的磁盘指非易失存储，SSD、机械盘、网络存储都算。冯·诺依曼架构决定了，你不能直接操作磁盘上的数据。必须先把页从磁盘搬进内存（DRAM），在内存里读写。之后再由系统负责，把改动写回磁盘。

auto guard = bpm->ReadPage(page_id);   // 1. 先把页从磁盘搬进内存
auto *data = guard.GetDataMut();       // 2. 在内存里读写这些字节
// 3. 改完的页，由系统找时机写回磁盘

这就像做菜。食材放在冰箱里，可切菜得拿到案板上。切完剩下的，再放回冰箱。

后面讲的所有组件，都建立在这个假设上。

2存储层次与两条分界线

难度 ★★★★★重要块可寻址解释了为什么按页组织，不直接考

存储越往上越快、越贵、越小。6:05 下面就是经典的存储金字塔。

        ┌───────────────────┐
   快   │  CPU 寄存器        │  ┐
   贵   ├───────────────────┤  │ CPU storage
   小   │  CPU 缓存 L1/L2/L3 │  ┘  ← 本学期【忽略】，进阶课再讲
        ├───────────────────┤
        │  DRAM             │  ← 本学期统称 "memory"
   ═════╪═══════════════════╪═════ 易失 / 非易失 分界线
        │  SSD              │  ┐
        │  机械硬盘          │  │ 本学期统称 "disk"
   慢   │  网络存储 (S3/GCS) │  │
   便宜 │  磁带（归档）       │  ┘  Amazon Glacier 之类
   大   └───────────────────┘

分界线一：易失 vs 非易失

分界线以上断电就丢数据，以下断电不丢。更要命的区别在访问粒度：磁盘只能整块读。

易失（分界线以上） 非易失（分界线以下）
断电 数据全没 数据还在。前提是已经发过 flush 命令
访问粒度 字节可寻址（byte-addressable）。可以直接跳到任意字节偏移 块可寻址（block-addressable）。最小访问单位是块，通常 4 KB

块可寻址的代价很大。 哪怕只想读一个字节，也得把它所在的整个块（页）读进来。别的数据你根本用不上，也照样得读。数据库设计里的所有权衡，都从这里开始。

char buf[4096];                      // 一个块，4 KB（示意）
pread(fd, buf, 4096, block_start);   // 只想要 1 个字节，也得读整块
char c = buf[byte_in_block];         // 读进内存以后，再从里面挑
// 考点：磁盘按块寻址，不能按字节寻址，所以数据库只能按"页"组织数据

这就像买鸡蛋。你只要一个，超市也只整盒卖。

补充：Andy 补了一句严谨的说明。DRAM 有 CPU cache line，严格说也不算纯字节寻址。不过本学期忽略这个细节。

分界线二：本课的简化命名

全学期只关心两个地方：disk 和 memory。8:53 统一了叫法，就不用纠缠硬件细节。

  • 分界线以下的一切，一律叫 disk。SSD、HDD、网络存储都算。
  • DRAM 叫 memory。
  • CPU 芯片上的 cache 和寄存器，叫 CPU storage。本学期不管。
enum class Where { DISK, MEMORY };   // 本学期只关心这两个地方
// SSD、HDD、网络存储都算 DISK，DRAM 算 MEMORY
// CPU 缓存和寄存器叫 CPU storage，不在讨论范围内

这门课的核心问题只有一个。东西在内存里，还是在磁盘上？又该怎么在两者之间搬？

3延迟数字：把纳秒换成秒

难度 ★★★★★重要具体数字不考，记住差几个数量级即可

同一份数据放在不同层，读取耗时能差好几个数量级。10:18 本讲在这里和普通算法课分道扬镳。

算法课假设访问任何数据都一样快，真实硬件不是这样。下面这张表源自 Jeff Dean 的经典延迟表。更早可以追溯到 Jim Gray 1990 年代初的版本。

层级 实际耗时 换算成"秒"之后
L1 缓存 ~1 ns 1 秒
L2 缓存 ~4 ns 4 秒
DRAM ~100 ns 100 秒 ≈ 1.5 分钟
SSD ~16,000–50,000 ns 约 4–14 小时
机械硬盘 ~2,000,000 ns 约 1 个月
磁带 未列出 31 年

11:40 Jim Gray 有个换算技巧。 人脑对纳秒没概念，那就把"纳秒"直接换成"秒"。这样一下就有了画面：

读 L1 缓存，好比走到旁边椅子上看一页书，花 1 秒。

读磁带，好比飞到冥王星再飞回来，只为看一页书，花 31 年。

结论：SSD 比 DRAM 慢两个数量级。所以系统设计的第一原则是：尽可能少读磁盘，读了就别浪费。

// 按 Jim Gray 的换算，1 纳秒当 1 秒
ReadL1(addr);        // 约 1 秒
ReadDram(addr);      // 约 100 秒
ReadSsd(page_id);    // 约 4 到 14 小时
// 考点：少读一次 SSD，值得多花很多 CPU 周期去换

4顺序 I/O vs 随机 I/O

难度 ★★★★★必会HW2 Q1 判断题直接问随机读写，#05 #08 都用

连续读一大段，比跳来跳去读快得多。12:58 这是第二个必须建立的直觉。

含义 快速 SSD 上的量级
随机 I/O 跳来跳去，读不同位置 80–100 微秒
顺序 I/O 读一段连续的数据。查找一次，拿到很多字节 可低至 10–100 纳秒级别。具体看读多少、用几个线程

两者差距巨大。在机械硬盘上尤其恐怖，因为磁头要物理移动。

for (page_id_t id : {7, 2, 9, 4}) ReadPage(id);    // 随机：每页都要重新定位（页号示意）
for (page_id_t id = 0; id < 4; id++) ReadPage(id);  // 顺序：定位一次，接着往下读

这就像去图书馆借书。照着书单东一本西一本，每本都得重新找。整排连着拿，走一趟就够了。

所以数据库会做一些"看着很奇怪"的设计。 目的都一样：把随机写换成顺序写。

14:21 MySQL 的 double write buffer 就是一例。刷脏页时，先把所有脏页顺序写进一个专门的缓冲区。这只是一次顺序写。然后在后台慢慢做真正的随机写。这样前台就不用卡着等随机写完成。

这个思路就是"用一次顺序写，换掉一堆随机写"。#05 日志结构存储 和 #21 WAL 会把它推到极致。

5系统全景：一次读页发生了什么

难度 ★★★★★重要#04 会完全展开，这里先建立整体流程

本学期要造的系统，要用 8 GB 内存管好远大于 8 GB 的数据库。15:03 说白了，就是制造"内存够用"的假象。

手段有三个：

  • 允许多个查询并发跑。等 I/O 的时候，CPU 不空转。
  • 复用已经读进内存的数据。
  • 聪明地决定什么时候写回。

踩坑：这套机制也有极限。所有并发查询的工作集加起来超过物理内存，那就没救了。不过一般情况下够用。

18:37 下面走一遍完整流程。假设一开始，内存里什么都没有。

磁盘                              内存
┌──────────────┐                 ┌─────────────────┐
│ page directory│ ──── ① ────►   │ Buffer Pool     │
├──────────────┤                 │  ┌───┬───┬───┐  │
│ page 1       │                 │  │fr1│fr2│fr3│  │  frames
│ page 2       │ ──── ③ ────►   │  └───┴───┴───┘  │
│ page 3       │                 └─────────────────┘
└──────────────┘                          │ ④ 返回指针
                                          ▼
                                   ┌─────────────┐
                                   │ 执行引擎      │  "我要 page 2"
                                   └─────────────┘
  1. 执行引擎说："给我 page 2。"
  2. 先把 page directory 读进内存。它记着有哪些页，各自去哪儿找。
  3. 查目录，算出偏移量。把 page 2 读进 buffer pool 的一个 frame。
  4. 返回一个指针，指向内存里的这一页。 执行引擎说"我用完了"之前，buffer pool 保证这页不会被换出去。这就是 pin 的语义，#04 详讲。
  5. 执行引擎解释页里的字节，做修改。
  6. 之后某个时刻，buffer pool 把这个脏页安全地写回磁盘。
char *data = bpm->FetchPage(2);   // 第 1 到 4 步：查目录、读盘、占 frame、给指针
Modify(data);                     // 第 5 步：执行引擎自己解释字节
bpm->UnpinPage(2, true);          // 说"我用完了"，脏页由缓冲池择机写回

这就像在图书馆借书。你报出书号，管理员先查目录，再去书库把书拿到阅览桌上。你没说还，书就不会被收走。

补充：19:57 这里有一条关键的抽象边界。到这一层为止，没人关心页里装的是什么。字节是什么意思，由上层来解释。这就是分层的价值。

问题 在哪讲
① 数据库文件在磁盘上怎么表示 本讲

6文件与存储管理器

难度 ★★★★★了解背景和产品做法，不考也不用写

数据库就是磁盘上的文件

数据库在磁盘上就是一堆普通文件。17:12 就这么简单。

  • DuckDB 和 SQLite 的卖点是"整个数据库就是一个文件"。
  • 大多数系统把数据库拆成多个文件。
  • 对操作系统来说，这些文件毫无特别之处。它们就是用 fopen/fwrite 建出来的普通文件。魔法全在数据库怎么解释这些字节。
FILE *f = fopen("db.data", "r+");   // 对 OS 来说，这就是个普通文件（文件名示意）
fseek(f, offset, SEEK_SET);
fread(buf, 1, page_size, f);        // 读出来的只是一串字节
// 这串字节是元组还是索引，只有数据库自己知道

这就像一本用暗语写的日记。谁都能翻开，可只有写的人看得懂。

21:56 文件格式历来是私有的。 拿 PostgreSQL 的数据文件到 MySQL 里，是打不开的。那些字节对 MySQL 没有意义。

补充：新趋势是可移植文件格式，比如 Parquet。它是开放规范，任何系统都能读写。#06 列存 会讲。

要不要自己写文件系统

一般不用自己写，现成的文件系统够用。23:23 数据库通常直接跑在 ext4、NTFS 这类文件系统上。

不过 1980 年代，有些系统会在裸块设备上自建文件系统。今天还这么干的，只剩高端商业系统：

  • Oracle ASM：数据库自己接管卷管理和文件系统。对外仍然提供标准 POSIX API。内部布局则完全按数据库的需要来。
  • Teradata 也类似。

收益：约 15% 性能提升。 代价：工程量巨大。所以开源系统基本没人做。

这就像不租房，自己盖房。住着能舒服一点，可得搭进去大把工夫。

存储管理器 Storage Manager

存储管理器负责读写磁盘、管理页、追踪空闲空间。24:06 它也叫 disk manager。

class DiskManager {
  void ReadPage(page_id_t id, char *out);        // 从磁盘读一页
  void WritePage(page_id_t id, const char *in);  // 把一页写回磁盘
  page_id_t AllocatePage();                      // 找块空地，分配新页
};

它就像仓库管理员。东西放在哪、哪里还有空位，都记在它那儿。

踩坑：Andy 的态度很明确，呼应了 #01 那句吐槽。更好的系统会自己做 I/O 调度，自己决定数据放哪。别让 OS 替你拿主意，因为 OS 总会做得很烂。

26:15 存储管理器不负责多副本。 同一个页在磁盘上只有一份。冗余要么放在它下面，比如 RAID、存储设备、S3 副本。要么放在它上面，比如跨节点的逻辑副本。

7页：三种含义与大小选择

难度 ★★★★★重要torn page 到 #22 才用到，作业不考页大小

页里放什么

数据库里的一切都按页来存。27:34 元组数据、元数据、系统目录（catalog）都是页。页目录本身和索引记录，也是页。

有两条常见规则：

  • 不混合页类型：一个文件里的页，通常只归一张表或一个索引。X 表和 Y 表不会混在同一页里。
  • 自包含页（self-contained）：页里带齐解释自己所需的全部信息。有些系统这样要求，比如把表的 schema 直接写进页头。这是为了崩溃恢复。Andy 说，这基本只在 Oracle 这类系统里见到。这类系统"对丢数据极度偏执"，而且这种偏执是对的。

28:17 Page ID：每个页都有唯一的标识。它可能是文件内的偏移量。也可能是个逻辑编号，再通过页目录查到真实位置。

page_id_t id = 42;                          // 逻辑编号（示意）
Location loc = page_directory.Lookup(id);   // 通过页目录查到真实位置
// 也有系统直接拿文件内的偏移量当 Page ID

Page ID 就像快递单号。拿着单号去系统里一查，就知道包裹在哪个仓。

三种「页」千万别搞混

"页"有三种意思，最要命的是硬件页。28:57 这是本讲的高频考点。

层级 大小 关键性质
硬件页 Hardware Page 通常 4 KB 硬件能保证原子写入的最小单位
操作系统页 OS Page Linux 默认 4 KB。大页可到 2 MB–1 GB OS 自己的页表映射
数据库页 Database Page 各系统自定，512 B – 16 KB 数据库自己组织的单位

为什么硬件页这条至关重要？ 看个例子：

假设数据库页是 8 KB，硬件只保证 4 KB 原子写。写这一页时，硬件只能保证其中一半写成功。也就是前 4 KB 或后 4 KB 中的某一个。它没法保证"要么两个都写，要么都不写"。

// 数据库页 8 KB，硬件只保证 4 KB 原子写
WriteFirstHalf(page);    // 前 4 KB 写成功了
// 偏偏这时候断电
WriteSecondHalf(page);   // 后 4 KB 没写上，这一页就撕裂了
// 考点：分清三种页，硬件只保证 4 KB 原子写，坑的是 8 KB 的数据库页

这就像寄两箱货。快递只保证每一箱完好送到，不保证两箱一起到。路上出了事，你可能只收到一箱。

断电正好卡在中间，页就损坏了，这叫 torn page。 所以数据库必须额外做很多事来保证安全。比如校验和、double write buffer、WAL，这些在 #21 WAL 展开。

怎么选页大小

读得多用大页，写得多用小页。31:55 具体还要看硬件环境和数据形态。是宽表还是窄表？是大 blob 还是小整数？最关键的是工作负载：

负载类型 建议 原因

写密集，频繁 update、delete、insert 4–16 KB 小页 块可寻址，改 1 个字节也得写回整页。 页越大，小改动的写放大越严重 
UPDATE t SET flag = 1 WHERE id = 7;   -- 只改了 1 个字节（示意）
-- 页是 4 KB，写回 4 KB
-- 页是 64 KB，就得写回整整 64 KB（示意）
-- 考点：读密集用大页，写密集用 4~16 KB 的小页

这就像改作业本上的一个错字，却得把整本重抄一遍。本子越厚，越亏。

堆文件

怎么定位一个页

情况 A：单文件，纯算术就行。

偏移量 = 文件起始位置 + 页号 × 页大小

前提是所有页大小相同。

这就像一排编号连续、宽度一样的储物柜。柜号乘柜宽，就是位置。

struct DirEntry {
  page_id_t id;          // 哪一页
  Location  where;       // 在哪个文件的哪个位置

};

它就像商场的楼层导览图。哪家店在几楼，看一眼就知道。

难点在同步。38:13 页目录必须和数据页保持同步。崩溃后目录丢了，就再也找不到任何东西了。

不过 Andy 指出了一个务实的权衡：

其实不必 100% 严格同步。 页里的元数据够多，崩溃后就可以重建页目录。只是恢复会慢很多。

这是「运行时速度」和「恢复时长」之间的权衡。 内存里的目录一定要准，磁盘上的可以宽松一点。

页头就像快递箱上的面单。不用拆箱，就知道里面大概装了啥、有没有被拆过。

三种页布局

页里怎么摆数据有三种布局，本讲讲元组导向。42:54

布局 存什么 讲次
Tuple-Oriented 元组导向 完整元组连续存在页内 本讲
Log-Structured 日志结构 不存元组本身，存变更（delta）。同一元组可能有多份 #05
Index-Organized 索引组织 数据直接存在树结构里 #08

本讲假设：每个元组只有一份，完整、连续地存在一个页里。

朴素方案为什么不行

只记条数、往后追加的朴素方案，一删除就崩。44:19

最直觉的做法是：页头只记"有几条元组"。 新元组一条条往后追加，找第 N 条算一下就行。

void Append(Page *p, const Tuple &t) {
  memcpy(p->data + p->count * TUPLE_SIZE, &t, TUPLE_SIZE);  // 按条数算位置
  p->count++;   // 中间删掉一条，这个算法就错了
}
// 考点：朴素方案在删除和变长数据下都会崩，slotted page 靠槽数组解决

这就像电影院按人数排座。中间走了一个人，新来的按人数一算，就坐到别人腿上了。

然后你删掉中间一条，麻烦就来了：

问题 说明
计数器失效 元组数从 3 变成 2。再按计数往末尾追加，会覆盖第 3 条
找空位要扫描 每次插入都得扫一遍找空槽，很贵
不能压实（compaction） 把第 3 条挪到第 2 条的位置，它的物理地址就变了。所有指向它的索引都得更新
变长数据彻底崩 空出来的洞大小不一。新元组可能哪个洞都塞不进

Slotted Pages：标准答案

所有行存系统实际用的都是 slotted page。45:44 各家细节不同，思路一致。

┌──────────┬──────────────┬─────────────────────────┬────────────┐
│  Header  │  Slot Array  │       Free Space        │ Tuple Data │
│          │  ──────────► │                       ◄─│──────────  │
│          │ ┌──┬──┬──┐   │                         │ ┌────┬───┐ │
│          │ │s0│s1│s2│   │                         │ │ T2 │T1 │ │
│          │ └──┴──┴──┘   │                         │ └────┴───┘ │
└──────────┴──────────────┴─────────────────────────┴────────────┘
             槽数组从前往后长                    元组数据从后往前长
                        两者在中间相遇 → 页满
  • Slot Array（槽数组）：一个定长数组。每项记着"第 i 号元组在页内的偏移量"。
  • 元组数据从页尾往前长。
  • 两边相遇，页就满了。
struct SlottedPage {
  Header   header;
  uint16_t slots[];   // slots[i]：第 i 号元组在页内的偏移
};
char *GetTuple(SlottedPage *p, int i) { return (char *)p + p->slots[i]; }

槽数组就像书的目录。正文怎么挪都行，改一下目录上的页码就好。读者永远先查目录。

补充：4 KB 的页，偏移量最多 12 位，所以槽项非常小。

47:09 注意，页不保证 100% 填满。 变长数据不一定正好对齐。但够用。

间接层带来的自由

槽数组是个间接层，元组在页里随便挪，索引都不用改。47:54 这是 slotted page 最核心的价值。

删掉第 3 条元组后，可以把第 4 条在页内挪个位置，做压实。只需要改槽数组里的偏移量。

memmove(new_pos, old_pos, len);   // 第 4 条元组在页内挪了位置
page->slots[4] = new_offset;      // 只改槽数组里的这一格
// 索引里记的还是"哪一页、第 4 号槽"，一个字都不用改
// 考点：槽数组这层间接，让页内压实几乎免费

元组的物理位置变了，"槽号"没变。 所以索引不需要更新。改动的爆炸半径，被限制在这一个页里。

48:38 为什么敢随便挪？因为页已经在内存里了。比起从磁盘读进来的代价，在内存里搬字节几乎免费。

各系统策略不同：

系统 是否压实
PostgreSQL 不做。这是它需要 VACUUM 的原因之一
SQL Server 做。每次更新元组都做

10Record ID

难度 ★★★★★必会P2 叶子存 RID，P3 索引扫描靠它回表

Record ID 就是一条逻辑元组的物理位置标识。49:20 它别名很多，Record ID、Tuple ID、Row ID 说的都是它。

典型构成：

Record ID = 文件 ID + 页 ID + 槽号

各系统的实现：

系统 名称 大小 是否真的存下来

PostgreSQL ctid 6 字节，页 ID 加槽号 否，运行时推导

SQLite 比较特别。 不管你声明什么主键，内部都用 rowid 当主键。rowid 单调递增，所以就算你不给主键，也能靠它唯一定位一行。

-- 数据库在后台压实、搬移数据以后

Record ID 就像酒店的房间号。今晚住这间，明天一换房，号就变了。

踩坑：51:31 这是条重要警告。Record ID 通常能用 SQL 查到，但绝对不要在应用里依赖它。数据库做压实、搬移数据时，同一条逻辑元组的 Record ID 会变。

这么做是合法的。关系模型本来就无序。改变元组的物理顺序，不影响逻辑上的正确性。

元组结构

元组本质上就是一个带 header 的字节数组。52:15

┌─────────────┬───────┬───────┬───────┬───────┐
│   Header    │ attr1 │ attr2 │ attr3 │ attr4 │
│ NULL bitmap │       │       │       │       │
│ 可见性信息   │       │       │       │       │
└─────────────┴───────┴───────┴───────┴───────┘

52:58 元组的 header 里不存 schema。

schema 存在页这一级，或者系统 catalog 里。每个元组都重复存一遍 schema，太浪费了。这也正是同一页里不混放不同表数据的原因。

数据库维护一个 catalog，记着每张表的 schema。读页时，靠它来解释字节数组的含义。

const Schema &s = catalog->GetTable("foo")->schema;               // schema 从 catalog 拿
int32_t id = *reinterpret_cast<int32_t *>(tuple + s.Offset(0));   // 再按它切字节
// 考点：元组 header 不存 schema，所以一页里只放一张表的数据

这就像一行没写表头的 Excel。光看数字分不清哪列是啥，得回去翻表头。

属性顺序与对齐

属性按 CREATE TABLE 里声明的顺序存，大小不齐时就补零对齐。53:42

问题出在大小不一。 各种数据类型大小不同，会跨越 64 位字边界。

CREATE TABLE foo (
  id        INT,        -- 32 位
  cdate     TIMESTAMP,  -- 64 位  ← 跨越两个字！
  color     CHAR(2),    -- 16 位
  zipcode   INT         -- 32 位
);

不对齐:  │ id(32) │ cdate(64) ────────┤ color │ zip │
         └─── 64位字 ───┴─── 64位字 ───┴─── ...
                    ↑ cdate 横跨两个字，读它要取两个 64 位字

跨字读取会拖慢速度，某些架构上编译器甚至会报错。有两种解法。

① 填充（Padding）：各系统实际用的就是它。

│ id(32) │ 000000(32) │ cdate(64) │ color(16) │ 000(16) │ zip(32) │
└──── 64 位字 ────────┴── 64位字 ─┴───── 64 位字 ─────────────────┘

浪费点空间，但保证每个属性都落在正确的边界上。数据库知道只读前 32 位，后面的填充忽略就行。

这就像停车。小车也占一整个车位，绝不骑线占两个。

② 重排列（Reordering）：57:22

把列的物理顺序打乱，正好塞满字边界。逻辑上仍按 CREATE TABLE 的顺序，物理上重排。

踩坑：Andy 说，这个方案只在研究文献里见过。Andy 不知道有哪个真实系统这么做。

12数据类型的真实表示

难度 ★★★★★了解后面各讲和作业都不再用，知道定点数即可

整数和浮点数直接用硬件格式，定点数得数据库自己实现。58:44

CREATE TABLE t (
  a INTEGER,       -- 跟 C/C++ 的整数一模一样
  b REAL,          -- IEEE-754，CPU 直接能算
  c NUMERIC,       -- 数据库自己实现的定点数
  d VARCHAR(64)    -- 长度加字节，太长就放溢出页（64 是示意）
);
类型 表示方式
INTEGER / BIGINT / SMALLINT 和 C/C++ 一模一样，硬件原生
FLOAT / REAL IEEE-754 标准，硬件原生
NUMERIC / DECIMAL 各系统自己实现的定点数，见下文
VARCHAR / VARBINARY / TEXT / BLOB 要么内联，存长度加字节。要么存指针，指向溢出页
TIME / DATE / TIMESTAMP 通常是自 Unix 纪元起的微秒数或毫秒数。也有系统用自定义格式

大小端（endianness）：本课假设 x86，不管这个问题。

补充：59:27 SQLite 的做法很特别。 它把所有东西都存成字符串，运行时再解释。好处是不管机器大端还是小端，结果都一样。大多数系统不这么干。它们会额外记下字节序，方便数据库文件跨机器拷贝。

补充：1:00:51 排序规则（collation）是个真问题。不同语言的字典序不一样。但这属于排序阶段的事，#11 再说。

浮点数为什么不能存钱

浮点数存不准小数，所以不能拿来存钱。1:02:14 这一段是本讲最实用的知识点。

float x = 0.1, y = 0.2;
printf("%f\n", x + y);      // → 0.300000   看着没问题
printf("%f\n", 0.3);        // → 0.300000

printf("%.20f\n", x + y);   // → 0.30000001192092895508  ！
printf("%.20f\n", 0.3);     // → 0.29999999999999998890  ！

这两个数在硬件里的比特位根本不同。 x + y 是 float，字面量 0.3 是 double。double 精度更高，但也不是精确的 0.3。打印精度低时看不出来。可一旦写盘再读回、参与计算，就会得到意外的结果。

这就像用尺子量三分之一米。刻度再细，也只能量个大概。

定点数：数据库自己扛下来

数据库用 NUMERIC / DECIMAL 自己管小数点，换来精确，代价是慢。1:04:24

数据库自己管理小数点位置和标度（scale）。值存成一个字节数组，外加一堆元数据。这些字节是什么意思，全靠元数据来解释。

PostgreSQL 的 numeric 大致长这样：

typedef struct {
    int    ndigits;    // 数字位数
    int    weight;     // 第一个数字的权重
    int    scale;      // 标度
    int    sign;       // 正/负/NaN
    digit *digits;     // 实际的数字数组
} numeric;

代价是什么？ 光是两个 numeric 相加，PostgreSQL 源码里就是一大串 if/else。判断正负，判断是不是无穷，判断是不是 NaN……

对比一下。普通整数加法就是一条 CPU 指令。定点数加法要跑一整段代码。慢得多，但保证结果精确。

CREATE TABLE account (balance NUMERIC(12, 2));   -- 存钱用定点数（精度是示意）
SELECT 0.1::NUMERIC + 0.2::NUMERIC;              -- 精确得到 0.3
-- 考点：float 算 0.1 + 0.2 不精确，存钱必须用 NUMERIC，代价是慢

浮点数像目测，定点数像一枚枚数硬币。数硬币慢，但一分不差。

什么时候必须用？ 银行、计息、科学仪器。凡是不能有舍入误差的场合都得用。Andy 举了个例子：往月球发火箭时，你可不想要舍入误差。

13NULL 的三种存法

难度 ★★★★★重要#06 列存会回头对比，作业不单独考

行存用 NULL 位图，列存用特殊值，给每个属性配标志位最差。1:06:28

// 一行 4 列，下标为 2 的那列是 NULL（示意）
uint8_t null_bitmap = 0b0100;   // 一列占一位
bool IsNull(int col) { return (null_bitmap >> col) & 1; }
// 考点：三种存法各配什么场景，为什么每属性一个标志位是坏主意

这就像点名册。没来的在名字后面打个记号，不用每人单独交一张请假条。

① NULL 位图（在元组 header 里）：行存的标准做法

每个元组的 header 里放一个位图，标出哪些列是 NULL。

补充：位图大小通常等于列数。哪怕某些列根本不允许 NULL，也照样留一位。省那点空间，不值得多一道判断的开销。

② 特殊值：列存 / 内存数据库常用

从值域里牺牲一个值，专门表示 NULL。比如 32 位有符号整数，用 INT32_MIN 表示 NULL，并禁止用户插入这个值。

const int32_t kNull = INT32_MIN;   // 这个值被征用了，专门表示 NULL
bool IsNull(int32_t v) { return v == kNull; }
// 用户想插入 INT32_MIN？数据库直接拒绝

好处：不用为每个元组存 header 位图。 代价：值域少了一个能用的值。

③ 每个属性配一个标志位：千万别这么做

给每个属性前面加一个 1 位的 NULL 标志，看着省事，其实很浪费。1:08:40

坏就坏在对齐。 你没法只存 1 位，实际得占整整 1 字节。于是一个 32 位整数变成了 40 位。

不加标志：│ value(32) │                 共 32 位
加了标志：│ null(8) │ value(32) │       共 40 位

14大对象：溢出页与外部存储

难度 ★★★★★了解仅 #06 提一句，作业和 Project 不用

值太大就往外挪。放不进一页的进溢出页，大到不想进库的放外部存储。

溢出页 Overflow Page

一个属性比整页还大，就把它挪到单独的溢出页里。1:09:18 前面假设过"元组必须放进一页"。可一个属性比整页还大，怎么办？

原元组里只留一个指针，外加数据长度。这个指针本质上就是个 Record ID。

数据页                              溢出页
┌──────────────────────┐          ┌──────────────────┐
│ id │ name │ ptr ─────┼─────────►│ 一大坨 TEXT 数据   │
│    │      │ size     │          │                  │──► 还放不下就再链一个
└──────────────────────┘          └──────────────────┘

struct OverflowRef {
  RecordId ptr;    // 指向溢出页，本质就是个 Record ID
  uint32_t size;   // 大值有多长
};                 // 元组里只放这一小截，大值本体在别处

这就像行李太大就托运，手里只留一张行李牌。

系统 阈值

MySQL / SQL Server / Oracle 超过半个页或整页

两个优化

溢出页可以压缩，元组里还能多存一段前缀。1:11:22

① 压缩：溢出页用 Snappy 或 gzip 压。#06 详讲。

② German Strings（德式字符串）：名字的来源，就是德国人搞出来的。

除了长度和指针，在原元组里再存一小段值的前缀。

SELECT * FROM doc WHERE contents LIKE 'andy%';
-- 1. 先拿元组里存的前缀比一下
-- 2. 前缀对不上，直接跳过，根本不读溢出页
-- 考点：German Strings 体现的原则是花一点存储，换掉一次磁盘 I/O

好处：查 WHERE contents LIKE 'andy%' 时，先比对前缀。不匹配，就完全不用去读溢出页。

这正是本讲开头那条原则：花一点存储，换掉一次磁盘 I/O。

这就像书脊上印着书名。不是要找的书，就不用抽出来翻。

外部存储 External Value Storage

特别大的文件干脆不进库，元组里只存一个外部地址。1:12:44 比如一个 20 GB 的电影文件。你不想把它塞进数据库，又希望数据库知道它存在。

做法是在元组里存一个 URI 或指针。它指向数据库管辖范围之外的存储。

CREATE TABLE movie (
  id   INT,
  film BFILE    -- Oracle：只存外部文件的地址，不存内容
);
系统 名称
Oracle BFILE
Microsoft SQL Server FILESTREAM

这就像图书馆不收胶片，只在卡片上写"片子在某仓库"。片子丢了，图书馆不负责。

踩坑：代价很明确。这部分数据，数据库不提供任何事务安全或持久性保证。它只能在你需要时，把数据流式读进来。

放库里还是库外？1:13:28 Jim Gray 二十多年前有篇论文专门研究过。结论大致是：大于 ~128 KB 放外部，小于就放内部。

1两个贯穿全课的概念

难度 ★★★★★重要评价存储设计的框架，读懂就行，不直接考

数据库摆数据只盯两件事：放在哪，什么时候搬。5:47 决定数据怎么摆、何时进内存，都得想着这两个维度。挑处理算法时也一样。

概念 含义 目标
空间控制 Spatial Control 数据写到磁盘的哪个位置 常一起用的数据放在一起，最大化顺序 I/O
时间控制 Temporal Control 什么时候把数据搬进内存，什么时候放走 页既然读进来了，放走前就把能做的活全做完。尽量少重复读盘

时间控制的反面教材：要读 A、B 两块，其中 A 要用两次。

错：读A → 干活 → 扔掉 → 读B → 干活 → 扔掉 → 再读A     （3 次磁盘 I/O）
对：读A → 干完两次活 → 读B → 干活                    （2 次磁盘 I/O）
考点：空间控制管"放在哪"，时间控制管"什么时候搬、什么时候放"

这就像去超市。一次把清单买齐，别买完酱油回家，又跑一趟买醋。

补充：#06 列存 会把空间控制推到极致。连用不到的列都不读进来。

2缓冲池的结构

难度 ★★★★★必会P1 要实现；HW2 Q2 按缓冲池命中算页数

缓冲池就是数据库启动时申请的一大块内存。9:07 它被切成一个个帧（frame），每帧正好放一个页。

                     内存
        ┌───────────────────────────────┐
        │        Buffer Pool             │
        │  ┌──────┬──────┬──────┬──────┐│
        │  │frame0│frame1│frame2│frame3││
        │  │page1 │page3 │      │      ││
        │  └──────┴──────┴──────┴──────┘│
        └───────────────────────────────┘
                     ▲   copy
        ┌────────────┴──────────────────┐
        │  page1 │ page2 │ page3 │page4 │  磁盘上的数据库文件
        └───────────────────────────────┘

char *pool = new char[num_frames * PAGE_SIZE];   // 启动时一次要够
char *frame_i = pool + i * PAGE_SIZE;            // 第 i 帧就是第 i 段
// 页从磁盘读进来，就拷进某一帧

这就像停车场划好的车位。车位一样大，一个车位停一辆车。页是车，帧是车位。

补充：9:47 为什么叫 "frame"（帧）？ Andy 的解释很直白：词不够用了。 "page" 已经被占了，整体又叫 "buffer/cache"，每个槽位只好叫 frame。

13:05 帧和页必须一一对应，大小相同。 高级系统允许配多个缓冲池实例，比如 IBM DB2。每个实例的页大小可以不同，替换策略甚至也能不同。 实例再按表或索引绑定。

缓冲池管理器的契约

缓冲池交出的指针，对方说"我用完了"之前一定有效。10:23 这里的对方就是执行引擎。

反过来，页在内存里的位置可以随便变。同一个页第二次读进来，完全可以落在另一个帧里。上层无所谓，反正拿到的就是个内存地址。

char *p1 = bpm->FetchPage(7);   // 第一次读进来，落在 frame 2（示意）
bpm->UnpinPage(7, false);       // 用完了，这页之后可能被换出
char *p2 = bpm->FetchPage(7);   // 再读一次，可能落在 frame 0，p2 != p1

这就像寄存行李。取回来的还是那件行李，可柜子号可能变了。

不只是数据页

理想做法：启动时一次性 malloc 够所有内存，之后再不找 OS 要。13:48

为什么？最糟的情况是，查询跑到一半临时申请内存，OS 却说"没了"。这种事你希望越早知道越好。

int main() {
  auto *bpm = new BufferPoolManager(num_frames);   // 启动时就把内存要够
  // 之后查询跑到一半，不会再因为要不到内存而崩
}

这就像出远门前先把钱取够。别走到半路，才发现取款机里没钱。

所以数据库里几乎所有堆内存，都来自某个缓冲池：

  • 数据页缓冲池，本讲的主角。
  • 排序、连接用的中间结果缓冲区，见 #11 #12。内存不够时，可以溢写到磁盘。
  • 日志缓冲区，见 #21。

3Page Table、Pin 计数与 Latch

难度 ★★★★★必会P1 的页表和 pin 计数要自己写，#10 也用到

Page Table ≠ Page Directory

页目录管页在磁盘的哪儿，页表管页在内存的哪一帧。21:36 这两个东西极易混淆，务必分清。

Page Directory（页目录） Page Table（页表）
作用 page id → 磁盘上的位置 page id → 内存中的帧
位置 在磁盘上，内存里也有副本 纯内存
是否需要持久化 需要 不需要。崩溃了，内存本来就没了 
std::unordered_map<page_id_t, frame_id_t> page_table;   // 页表：纯内存，崩了就没了
std::unordered_map<page_id_t, Location> directory;       // 页目录：要落盘
auto it = page_table.find(pid);                          // 命中就直接拿到帧号
// 考点：页目录要持久化，页表不用，因为崩溃后内存本来就没了

页目录像仓库总账，记着货在哪个货架。页表像柜台上的便签，记着货现在摆在哪个窗口。便签丢了，重写一张就是。

页表本身通常就是个哈希表。拿 page id 去查，命中就返回帧的位置。

补充：22:17 有些系统会把页表内容写出来，尤其是 serverless 场景。这样崩溃重启后，能直接预取回原来那批热页。不用再重新一点点"学"。但这是优化，不是必须。

Pin 计数

pin 计数大于 0，这一帧就绝对不能换出去。17:39 这是 Project 1 最容易写错的地方。

页表的每个条目，除了帧位置，还带一组元数据：

字段 大小 作用
Pin / Reference Counter ~1 字节 有几个上层组件正拿着这个页的指针
Dirty Flag 1 字节 这个页被改过没有
访问追踪信息 未列出 哪个线程或事务持有它

Pin 的语义：pin 计数 > 0，说明有人正拿着指向这块内存的指针。这时绝对不能把这一帧换出去。否则对方会读到另一个毫不相干的页，拿到一堆垃圾数据。

bool CanEvict(frame_id_t f) {
  return pin_count_[f] == 0;   // 还有人拿着指针，就不能换
}
// 考点：pin 保证用着的页不被换走，忘了 unpin，这一帧就永远换不出去

pin 就像图书馆的借书记录。书没还，管理员就不能把它下架。

踩坑：页表条目本身很小，远小于 1 KB。真正占内存的是那些帧。

Latch vs Lock：数据库领域的专有术语

latch 保护内部数据结构，lock 保护逻辑实体。19:40 这是每年必考的概念区分。

在页表里查找、修改条目时，要保护临界区。这时用的就是 latch。

std::lock_guard<std::mutex> g(latch_);   // latch：只护住页表这一小段（示意用 std::mutex）
auto it = page_table_.find(pid);
// 出了这个作用域马上放，持有时间极短
// 考点：latch 死锁没人兜底，也没法回滚，只能靠开发者自己避免
Latch（闩） Lock（锁）
保护什么 数据结构内部的临界区 逻辑实体：元组、页、表、索引
相当于 互斥量 mutex。OS 世界里就叫 lock 事务级别的并发控制
持有时间 极短 可能很长，长达整个事务
谁在用 我们自己，也就是数据库开发者 外部用户的事务
死锁谁负责 自己。没人会来救你，也没法回滚 有 lock manager 检测，会杀掉事务并清理

这就像餐馆后厨。抢菜刀是几秒钟的事，厨师自己商量好。订座可能一占一晚上，得有经理来管。

Andy 给这个区分的理由很有意思：

Lock 要应付外面的傻瓜。 有人开了个事务，然后跑去喝咖啡，事务一直开着。数据库必须自己处理死锁、活锁这些烂摊子。

Latch 是我们自己用的。 我们是拿高薪写数据库的人，理论上不会犯傻。所以出了死锁没人管，必须自己保证正确。

补充：你可以用 pthread mutex，但不该用。数据库自己实现的总能更快。#10 Latching 会详细讲。

4为什么不能用 mmap

难度 ★★★★★重要作业和 Project 不考，#11 #14 #25 反复呼应

OS 不懂数据库，却要替数据库决定何时读写，所以不能用 mmap。22:54 这是 Andy 的招牌话题，Andy 自称"我的私人执念"。

问题的诱惑

mmap 看起来正好能干缓冲池的活。我们想"制造内存比实际更大的假象"，这听着就是虚拟内存。

OS 正好提供了 mmap。它把磁盘文件映射进进程的地址空间。访问某个偏移，OS 就自动去取对应的页。

char *db = (char *)mmap(nullptr, file_size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
char c = db[offset];   // 页不在内存里？OS 自动去读
db[offset] = 'x';      // 改完以后，OS 自己挑时候写回
// 省事是省事，可什么时候写回，数据库说了不算

流程看起来完全就是我们想要的：

访问未加载的地址 → 主缺页中断（major page fault）
    → OS 挂起你的线程 → 把页读进物理内存 → 接上页表 → 恢复你的线程

物理内存满了 → 挑一个页换出（脏页先写回）→ 再读入新页

这就像把家门钥匙交给物业。省心是省心，可物业什么时候进门，你管不着。

那为什么不直接用？

五条致命问题

根本原因只有一个：OS 不懂 SQL，不懂查询，也不懂事务。25:40 所以 OS 没资格替你做决定。

# 问题 后果
1 脏页会被随时刷盘 最致命。 OS 的后台写线程，随时可能把脏页写出去。可数据库有严格的顺序要求。改一个页之前，必须先把描述这次改动的日志记录写出去。 这就是 WAL，见 #21。OS 完全不知道这层依赖。mlock 只能防换出，防不住写出
2 无法预知的停顿 数据库不知道哪些页在内存里。一碰到不在的页，工作线程就被阻塞，什么活也干不了。想绕开，就得另搞个线程去预热页。为了配合 OS，反倒把系统搞复杂了
3 错误处理散落各处 访问任何一处内存，都可能出错，比如硬件问题、文件被删。而且你拿到的不是异常，是信号或中断。于是整个系统到处都得写中断处理代码。自己管 I/O 的话，错误只会出在 read() 这一个地方
4 更慢 OS 内部也要维护页表，还要有保护页表的锁。这和我们要做的事一模一样。 而数据库总能做得更好
5 统计口径混乱 36:03 想知道"我的数据库用了多少内存"，都变得困难。因为还得算上 page cache 
page[0] = 'x';             // 1. 改了页，它成了脏页
// OS 后台线程：这页脏了，先替你写回磁盘
log_mgr->Append(record);   // 2. 日志这时才写，顺序已经反了
// 考点：mmap 至少有三条硬伤，跟 WAL 冲突的"脏页随时刷盘"最致命

这就像请一个不识字的人替你寄合同。先寄附件还是先寄正文，对方根本分不清。

真实世界的验证

连 MongoDB 都没能让 mmap 跑通。31:02

MongoDB 早期没有自己的缓冲池，直接用 mmap。后来全砍了。

Andy 的论证很有说服力。MongoDB 已经 IPO 了，有的是钱和顶尖工程师。连 MongoDB 都没能让 mmap 跑通，别人还能指望什么？（课上说 2018 年 IPO，实际是 2017 年 10 月。）

踩坑：结论就一句。这辈子都别在数据库里用 mmap。

更普适的原则

数据库永远比 OS 更有资格做决策。32:21 这条经验整个学期会反复出现。

因为我们知道查询是什么，过去执行过什么，将来要执行什么。我们也知道数据长什么样，页之间有什么依赖。

所以我们的预取更好，替换策略更好，调度也更好。能不跟 OS 打交道就不打交道。OS 从来不是我们的朋友，只会想方设法坑我们。

这就像让外包替你管公司的账。再勤快，也不懂你的业务。

5替换策略：从 LRU 到 ARC

难度 ★★★★★必会P1 要实现 ARC，课上没细讲，要自己补

内存满了必须腾地方，替换策略决定踢走哪一页。36:44 这就是缓冲区替换策略。

好的替换策略看三条：

标准 说明
正确性 尽量换出"将来最不可能用到"的页
速度 一次磁盘 I/O 要 1 ms，你的算法跑一次却要 10 ms。那还不如直接读盘
元数据开销 元数据占的内存越多，能存数据的内存就越少 
frame_id_t victim;
if (replacer->Evict(&victim)) {   // 选一帧踢出去
  // 踢得准不准，选得快不快，记账占多少内存，三条都要看
}

这就像冰箱满了要扔东西。扔错了，明天还得再买一趟。

补充：46:31 有学生按算法课的思路问："复杂度是不是一样？"Andy 的回应值得记住：

"这不是算法课。常数项非常重要。1 毫秒和 10 毫秒差一个数量级。"

LRU（1965）

LRU 换出最久没被访问的页，这是最经典的做法。每个页记一个最后访问时间戳，换出时挑最久没碰过的。

可以用链表实现。访问就移到队首，换出就取队尾。

void Access(frame_id_t f) {
  lru_.remove(f);       // 从原来的位置拿出来
  lru_.push_front(f);   // 放到队首，表示刚用过
}
frame_id_t Victim() { return lru_.back(); }   // 队尾就是最久没用的

这就像衣柜。刚穿过的挂最前面，最里面那件就是最久没穿的。

CLOCK（1969）：近似 LRU

CLOCK 用 1 个 bit 近似 LRU，不要精确顺序，只要个大概。40:12

每个页只留 1 个 bit，叫引用位或访问位：

        ┌───┐
   ┌───►│ 1 │───┐
   │    └───┘   │
┌──┴─┐       ┌──▼─┐
│ 0  │◄──时钟指针──►│ 1 │
└────┘       └────┘

扫描规则：指针转到某页时，看它的引用位。

  • 引用位是 1：清成 0，继续往下走。
  • 引用位是 0：说明上次扫过以后没人碰过它，换出它。
while (ref_bit[hand] == 1) {      // 被碰过：清成 0，放它一马
  ref_bit[hand] = 0;  hand = (hand + 1) % n;
}
return hand;                      // 上次扫过以后没人碰：换它
// 考点：访问时置 1，要腾帧时才转，从上次停的地方接着转

这就像保安夜里巡楼。屋里有人动过，就擦掉记号接着走。转一圈回来还是没记号，这间就收回。

三个关键细节，都是学生现场问出来的：

问题 答案
时钟什么时候转？ 45:06 只在需要腾帧时才转。平时访问只是把位设成 1
每次从头开始吗？ 46:31 不，从上次停的地方接着转。不然会一直捶开头那几个页
那个"引用计数"到底是什么？ 43:40 就是一个 bit。叫"访问位"更准确，意思是上次检查以后这页被碰过没有

Linux 内核用的就是这个思路，是多指针版本的 CLOCK。

致命缺陷：顺序泛洪 Sequential Flooding

一次全表扫描，就能把 LRU 和 CLOCK 的缓冲池整个冲掉。47:09 这是两者共同的要命问题。

全表扫描从头读到尾。它会把缓冲池里所有页全部冲掉，塞进一堆只用一次的页。之前攒下的"最近性"信息，也全毁了。

具体场景：

① 点查 WHERE id=1，落在 page0，读进缓冲池        [page0]
② 聚合扫描 SELECT AVG(...) 从头扫到尾
   扫到 page3 时缓冲池满了，LRU 挑最久未用的 → 正好是 page0（换错了）
③ 又来一次 WHERE id=1 → page0 已经被换出，只能重读磁盘
考点：顺序泛洪就是一次大扫描冲掉热页，LRU 就这样被击溃

这就像旅游团涌进小饭馆。常客的座位全被占了，团客吃一顿就走，再也不来。

49:48 Andy 打了个比方：真实负载极度倾斜。 Taylor Swift 的 Instagram，和某人晒猫的账号，访问量差着天量级。我们当然想让 Taylor Swift 那页常驻内存，可朴素 LRU 做不到。

补充：48:32 OLAP 分析型负载里，情况甚至反过来。MRU（Most Recently Used，最近使用）才对。反复做全表扫描时，可以这次从头扫到尾，下次从尾扫到头。这样刚读进来的页，正好能被复用。

LFU（1971）：也不行

LFU 改记访问频率，换出访问次数最少的页，可它照样不行。

两个问题：

  1. 维护频率信息是对数复杂度，比 LRU 贵。
  2. 没有时间概念。 某人半夜把猫的账号刷了十亿次，之后再没人看过。可它的计数永远最高，永远不会被换出。
count_[cat_page] = 1000000000;   // 半夜被刷了十亿次（示意）
// 之后再没人访问，计数却一直最高
Victim();                        // LFU 永远挑不到它，这就是"老热点"
// 考点：LFU 的老热点问题，LRU-K 用第 K 次最近访问的时间来解决

这就像过气网红。当年粉丝多，现在没人看了，排行榜上却一直挂着。

LRU-K（1990s）：实用方案

LRU-K 看最近 K 次访问，能分清"来一次就走"和"一直在用"。51:10 它记的是最近 K 次访问的时间戳，不只是最后一次。

换出规则：算一个差值，当前时间 − 第 K 次最近访问的时间戳。差值最大的换出。 不足 K 次访问的，记为无穷大，优先换出。并列时，挑最后访问时间最老的。

size_t KDistance(frame_id_t f, size_t now) {
  auto &h = history_[f];                // 这页最近几次访问的时间戳
  if (h.size() < K) return INF;         // 不足 K 次，记为无穷大，先踢
  return now - h[h.size() - K];         // 跟第 K 次最近访问比
}
// 考点：Ghost Cache 留着被换出页的时间戳，再读进来时恢复历史

这样就能区分"访问一次就再没来"和"反复在访问"。

这就像评先进。不看今天来没来，看最近 K 次打卡。只来过一次的，先淘汰。

Ghost Cache（幽灵列表）52:37：页被换出后，它的访问时间戳还留着。下次再读进来，就能恢复历史，不用从零重新学。

实际使用：SQL Server 用它。PostgreSQL 早期版本用的也是它，由 Tom Lane 实现。Tom Lane 也是 CMU 博士。

MySQL 的近似 LRU-K

MySQL 把一条链表切成 young 区和 old 区，新页只能先进 old 区。58:14 链表上有两个入口指针。

     young 区（受保护）              old 区（易被淘汰）
  ┌────┬────┬────┬────┐        ┌────┬────┬────┬────┐
  │    │    │    │    │        │    │    │    │  8 │ → 被挤出去
  └────┴────┴────┴────┘        └────┴────┴────┴────┘
       ▲                            ▲
    young 入口                   old 入口
                                  ↑ 新页先放这
  • 新页先进 old 区。 要是再也没人访问，它很快就被挤出去，不会污染 young 区。
  • 再次被访问，才提升到 young 区头部。 这证明它确实重要。
void OnAccess(Page *p) {
  if (!InPool(p))    old_.push_front(p);   // 新来的：先进 old 区
  else if (InOld(p)) MoveToYoungHead(p);   // 二次访问：才升进 young 区
}
// 考点：全表扫描的页只在 old 区打转，碰不到 young 区的热页

这就像公司的试用期。新人先进试用区，干得好才转正。临时工干完就走，碰不到正式编制。

这个简单设计，直接解决了顺序泛洪。 全表扫描的页全在 old 区打转，碰不到 young 区的热数据。

ARC：Project 1 要实现的算法

ARC 兼顾最近性和频率，还能用参数 P 自动调两边的比重。59:37

它全名 Adaptive Replacement Cache（自适应替换缓存），被认为是缓冲区替换的 state-of-the-art。

核心思想：LRU 的好处（最近性）要，LFU 的好处（频率）也要。但两者的权重不用手动调。 系统用一个自适应参数 P，按实际访问模式自动调整。调的是两个列表的大小。

   访问模式偏"重复访问同样的东西"
        → frequent 列表变大，recent 列表变小
   访问模式偏"总是新数据"
        → recent 列表变大，frequent 列表变小
   考点：ARC 比 LRU-K 多了自适应，P 决定两个列表各占多大

再配合 ghost list，记下最近被换出的页。重新读入时，就能恢复历史。它是动态的，负载模式变了也能跟上。

这就像饭馆按客流调菜单。熟客多，就多备招牌菜。新客多，就多上新品。

独立的扫描缓冲区（Ring Buffer）

全表扫描读进来的页，别往全局缓冲池里塞。前提是你知道两件事。这个查询在做全表扫描。这张表别的查询多半用不上。

PostgreSQL 的做法：从缓冲池里拿出一小块，做成环形缓冲区。扫描的页只在这个环里循环覆盖。

Page *ring[RING_SIZE];   // 扫描专用的一个小环
size_t pos = 0;
void OnScanRead(Page *p) { ring[pos] = p; pos = (pos + 1) % RING_SIZE; }   // 满了就绕回开头覆盖

实现极其简单，就是不断追加，然后绕回来。却能直接消掉顺序泛洪对整个系统的影响。

这就像饭馆给旅游团单开一个包间。团客再多，也挤不到大厅常客的座位。

优先级提示 Priority Hints

上层可以直接告诉缓冲池，哪些页特别重要。1:03:41

最典型的例子：B+ 树的根节点。

INSERT INTO t VALUES (counter++);   -- 递增插入
-- 每次插入都从根节点走下来，根页绝不能被换出去

如果索引按 min→max 排序，每次插入都要从根节点走下来。所以根页极其重要，无论如何都不该被换出去。

频率统计也能反映这一点。但直接给个"这页是根，钉住"的提示，更可靠。

这就像公司前台。每个访客都得先经过它，前台绝不能撤。

合并同一事务的重复访问

同一个事务连着碰一个页两下，热度上只该算一次。1:04:56

一个事务先读某条记录，紧接着更新它。这是两次访问同一个页。

可从"热度"看，这不该算两次。并不是很多人都在抢这个页，只是同一个事务碰了两下。SQL Server 支持这类提示，让访问计数只加一次。

BEGIN;
SELECT * FROM account WHERE id = 1;              -- 第一次碰这页
UPDATE account SET bal = bal - 1 WHERE id = 1;   -- 第二次碰同一页
COMMIT;   -- 热度只该加一次，并没有两个人在抢

这就像同一个顾客一天进店两次。客流统计只该记一个人。

补充：1:05:34 Andy 指出，商业和开源系统就是在这拉开差距的。昂贵的商业系统有 Oracle、DB2、Teradata。开源系统有 PostgreSQL、MySQL、SQLite。商业系统在替换算法上砸的时间和钱，远比开源系统多。DB2 内部的 ARC 版本，比公开论文里的复杂得多。

情况 处理
干净页 直接丢弃，零成本
脏页 必须先写回磁盘，才能复用这一帧 
if (frames_[f].is_dirty) {
  log_mgr_->FlushFor(frames_[f].page_id);                  // 先刷描述这次修改的日志

而且脏页写回还有顺序依赖。往往要先刷描述这次修改的日志记录，再刷数据页。#21 WAL 会详讲。这一整套下来很慢。

这就像还租来的车。车干净，直接还。车脏了得先洗，洗之前还得先把单子填好。

后台写线程 Background Writer

后台线程提前把脏页写出去，替换时候选就全是干净页。1:06:57 这是理想状态。

做法和 OS 的后台写一样，只不过这次由我们自己控制。后台线程遍历页表，把脏页提前写出去，清掉脏标记。这也叫 page cleaning 或 buffer flushing。

void BackgroundWriter() {
  for (auto &[pid, f] : page_table_)
    if (frames_[f].is_dirty) { Flush(f); frames_[f].is_dirty = false; }
}
// 考点：刷得太猛，I/O 带宽全被占了，正经查询反而没资源

权衡在哪？

如果一直在后台刷脏页，I/O 带宽全被占了。正经查询反而没资源了。

这就像服务员趁空收碗。收得勤，翻台就快。可光顾着收碗，就没人点菜了。

各系统的策略：

系统 策略
PostgreSQL 简单阈值。脏页数到了一定量就触发
高端商业系统 多级阈值，加上各种兜底机制。激进程度可以精细控制

8磁盘 I/O 调度与 Direct I/O

难度 ★★★★★重要P1 调度器只要队列加后台线程，其余不用写

自己排队

OS 分不清哪个 I/O 请求更要紧，所以数据库自己排队。1:08:19

磁盘越来越快，比如 NVMe，但仍是瓶颈。OS 和硬件会尽力做并行和重排。

可 OS 不知道优先级。 同一个数据库里，两个线程要读盘。一个是关键业务查询，一个是无所谓的后台任务。Linux 完全区分不了。 而且 Linux 的 I/O 优先级只能设到进程级别。

所以数据库自己维护 I/O 请求队列。再按自己掌握的信息重排：

优化 做法
随机变顺序 多个线程的随机页请求，按 page id 或磁盘位置排序。再合并成顺序 I/O
按重要性排优先级 关键查询和事务，优先于后台任务
保证持久性顺序 日志数据必须先写，然后才轮到普通脏页 
std::sort(reqs.begin(), reqs.end(), [](const IoReq &a, const IoReq &b) {
  if (a.is_log != b.is_log) return a.is_log;                      // 日志永远排最前
  if (a.priority != b.priority) return a.priority > b.priority;   // 再看谁更要紧
  return a.page_id < b.page_id;                                   // 最后按位置排，随机变顺序
});

这就像医院分诊台。急诊先看，普通号按顺序排。挂号机只认号码，分不出谁急。

补充：很多数据库的部署文档写得很直白。Linux 的 I/O 调度器，设成最简单的那种就行。 因为数据库自己做得更好。

双份拷贝问题与 Direct I/O

普通 read() 会让同一页在内存里存两份，Direct I/O 能省掉一份。1:11:38 这个浪费很隐蔽，但很严重。

普通 read() 的路径：

磁盘 → OS page cache（第 1 份拷贝）→ 用户态缓冲区 → 我们的 buffer pool（第 2 份拷贝）

同一个页在内存里存了两遍。 一份在 OS 页缓存，一份在数据库缓冲池。

解法：Direct I/O

磁盘 ──────────────────────────────► 我们的 buffer pool
       告诉文件系统：别放你的 page cache，直接给我

省掉一次拷贝，快很多。

int fd = open("db.data", O_RDWR | O_DIRECT);   // 告诉 OS：别经过你的 page cache（文件名示意）
pread(fd, frame, PAGE_SIZE, offset);            // 直接读进缓冲池的帧
// 考点：Direct I/O 省掉的是 OS page cache 那一份拷贝

这就像快递先送到驿站，你再去驿站搬回家。Direct I/O 就是让快递直接送上门。

补充：更极端的还有 DPDK / SPDK 这类技术。它们让数据库直接和硬件对话，完全绕过文件系统。这属于进阶课（15-721）的内容。

1缓冲池的三个优化

难度 ★★★★★重要HW3 只考 1.1 多缓冲池，预取和扫描共享不考

这三招都是数据库能做、操作系统做不到的事。因为 SQL 是声明式的，数据库提前知道查询计划长什么样。这部分是上一讲因为时间没讲完的内容。

多缓冲池 Multiple Buffer Pools

缓冲池可以切成好几个子池，各管各的。6:14 它不必是一整块内存。每个子池有自己的 page table，也有自己的替换策略。

struct BufferPool {
  PageTable page_table;   // 每个子池有自己的页表
  Replacer *replacer;     // 也有自己的替换策略
};
BufferPool pools[N];      // 不再是一整块内存
// 考点：除了策略可定制，多缓冲池还能减少 latch 竞争

这像超市多开几个收银台。顾客不用挤一条队，每个台子还能定自己的规矩。

切法很多。可以每个数据库一个池，也可以每张表一个。还可以按页类型分，索引页和数据页各进各的池。

两个好处：

好处 说明
策略可定制 知道某个池装的是什么，就能挑合适的替换算法
减少 latch 竞争 多个工作线程不再挤在同一个数据结构上

一个页该去哪个池，有两种定法：

方案 A（对象映射）：拆开 record ID，取出 object id → 查表决定去哪个池
方案 B（哈希，MySQL 用这个）：hash(record_id) % 缓冲池数量
考点：一个物理页只能待在一个池里，否则两份没法同步

踩坑：这是铁律。任何一个物理页，在任意时刻只能存在于一个缓冲池里。否则两处各写一份，怎么保持同步？

各家实现差别很大。IBM DB2 分得最细。每张表、每个索引都能有一个缓冲池，甚至每种 blob 类型一个。MySQL 就是简单的哈希取模。

预取 Prefetching

预取就是提前把后面要用的页读进来。9:26 数据库先识别出访问模式，再动手读。查询处理完当前页，下一页已经就位，不用停下来等 I/O。

// B+ 树范围扫描：顺着叶子的兄弟指针预取
page_id_t next = leaf->GetNextPageId();   // 下一个叶子是 page3
bpm->Prefetch(next);                      // 现在就发 I/O，不等扫到那里
// 考点：OS 只会顺序猜 page3、page4，数据库知道该要 page3、page5

这像看网剧。这一集还在播，下一集已经在后台缓冲好了。

OS 也能预取，你可以给它传 hint。但它只会顺序预取。它不知道页里装的是什么，也不知道页和页之间什么关系。

数据库能做得更好。最典型的例子是 B+ 树范围扫描：

                  [根 page0]
                   /      \
          [内部 page1]   [内部 page4]
             /                  \
    叶子 page2 ──► 叶子 page3 ──► 叶子 page5
                （磁盘上不连续！）
  • OS 的判断：你刚读了 page1、page2，那我给你预取 page3、page4。
  • 数据库的判断：我知道要沿着叶子节点扫。下一个是 page3，再下一个是 page5。 page4 根本不需要。

扫描共享 Scan Sharing

后来的查询可以搭先来查询的顺风车，共用读进来的页。12:43 这招也叫同步扫描（synchronized scans）。

场景：查询 Q1 正在全表扫描。扫到一半，查询 Q2 也要扫同一张表。

SELECT SUM(salary) FROM employees;   -- Q1：已经扫到一半
SELECT AVG(age) FROM employees;      -- Q2：从 Q1 当前的位置搭车
-- 考点：两个查询共享的是页读取，算的东西可以完全不同

        page0   page1   page2   page3
Q1:  ────►──────►──────►──────►         已扫完
Q2:              └─ 从这里搭车 ─►──►     然后回头补扫 page0~1

做法：让 Q2 搭 Q1 的顺风车。两者共用同一个游标读到的页，各自算各自的聚合。Q1 扫完退出后，Q2 再回头，把开头漏掉的部分补上。

这像坐环线公交。你在半路上车，坐到终点后，再绕回来坐完前面那几站。

踩坑：别把它和结果缓存搞混。

  • 结果缓存：同一条查询跑过，直接复用输出结果。
  • 扫描共享：在最底层的页读取这一级共享。两个查询可以算完全不同的东西。

支持情况：

系统 支持
DB2 / SQL Server / Teradata / PostgreSQL 支持
Oracle 有类似机制，但要求查询字符串完全一致

Oracle 那个限制很好笑。它把查询字符串哈希之后再比对。所以下面几条语义明明一样，却匹配不上：

SELECT * FROM employees;
SELECT * FROM Employees;    -- 只差一个大写 E，就匹配不上
SELECT *  FROM employees;   -- 中间多一个空格，也匹配不上
-- 考点：Oracle 按字符串哈希比对，所以特别容易失效

补充：16:10 有学生问，Q2 能不能更聪明一点？先去缓冲池看看 page0/page1 还在不在。还在的话，先读完再搭车。Andy 说理论上可以。不过 Andy 不认为 PostgreSQL 这么做。商业系统闭源，不清楚。

2回顾：元组导向存储的代价

难度 ★★★★★必会HW2 Q1 直接考碎片、随机 I/O 这些代价

元组导向存储读和插都顺，偏偏更新很贵。23:55 先把三条路径过一遍。

读取路径很顺畅：

索引查找 → 拿到 Record ID → 查 page directory 定位页
        → 页读进内存 → 用 Record ID 里的槽号在 slot array 里找到偏移 → 拿到元组

插入也还行。查 page directory，找一个空闲空间够用的页。读进来，在 slot array 里找个空槽写进去。没空间就分配新页。

补充：这里能提前知道要占多少空间，因为 SQL 是声明式的。你已经告诉数据库要存什么了。

更新才是痛点（28:50）：

定位到页 → 新值比旧值大吗？
    ├─ 不大 → 直接覆盖，完事
    ├─ 大，但页内重组后能塞下 → 重组，完事
    └─ 页内怎么都塞不下 → 【删除旧元组 + 插入新元组】← 很贵

UPDATE users SET bio = 'a much longer bio' WHERE id = ?;
-- 新值变长，这页塞不下了
-- 只能删掉旧元组，再找地方插入新元组

这像在笔记本上改一句话。改短了，涂掉重写就行。改长了这页写不下，只能撕掉换一页。

元组导向存储的四个问题

元组导向存储有四个硬伤。30:16 第 2 条和第 4 条最关键。

# 问题 说明
1 碎片化 页不可能刚好填满。slot array 和元组数据之间，总有一小块空隙用不上
2 无效磁盘 I/O 要改 8 个字节，得把整个 16 KB 的页读进来。改完还得整页写回
3 批量更新代价高 要更新 10 条元组。如果它们散在 10 个页里，就得把 10 个页全读进内存
4 有些存储压根不支持原地更新 见下 
auto guard = bpm->WritePage(page_id);   // 先把整个 16 KB 的页读进来
guard.AsMut<Tuple>(slot)->SetAge(v);    // 只改其中 8 个字节
// guard 释放后页变脏，以后还得整页写回

这像为了改一个错别字，把整本书借回家。改完，再整本还回去。

第 4 条：只能追加的存储

有些存储系统根本不让你原地改。31:41 你不能跳到某个偏移量，覆盖几个字节。只能追加，只能创建新文件。想删旧的，只能整个删掉，再重新追加。

append(file, new_record)        // 能做：往末尾追加
create(new_file)                // 能做：建一个新文件
overwrite(file, offset, bytes)  // 不能做：跳到偏移量原地覆盖
// 考点：四个问题里，第 4 条在 S3、HDFS 上是致命的

这像用圆珠笔记账。写错了不能擦，只能在后面再记一笔。

系统
HDFS（Hadoop 文件系统） 最早这么干的之一
Colossus Google 内部文件系统
Amazon S3 等对象存储 部分提供这种语义

在这类存储上，元组导向的 slotted page 架构根本没法用。

3索引组织存储

难度 ★★★★★重要#08 叶子存元组的方案，#20 讲 MySQL 时用

索引组织存储就是让索引本身充当表。25:19 B+ 树的叶子里不存 Record ID，直接存元组。在讲 LSM 之前，先看这个中间方案。

动机：元组导向存储的读取要走两步。先查索引拿 Record ID，再去堆文件里取元组。能不能合成一步？

-- MySQL InnoDB：主键索引的叶子里就是整行数据
CREATE TABLE users (id INT PRIMARY KEY, name TEXT);
SELECT * FROM users WHERE id = ?;   -- 走到叶子，直接拿到元组
-- 考点：省掉了拿 Record ID、再去堆文件取元组这一步
-- 考点：SQLite 和 MySQL InnoDB 默认就是索引组织

这像一本按字母排好的字典。查到词条，释义就在旁边，不用再翻到书后面的附录。

索引组织存储的叶子节点
┌──────────┬────────────────────┬─────────────────┐
│  Header  │ key→offset 数组     │   元组数据        │
│          │ （按 key 排好序）    │                 │
│          │ ──────────►        │      ◄────────  │
└──────────┴────────────────────┴─────────────────┘

叶子节点内部长得很像 slotted page。区别在前面那个数组。它存的是 key → offset，而且按 key 排好序，可以二分查找。

查找流程：从根往下走，落到叶子。在 key/offset 数组里二分，直接拿到元组。不需要再查 page directory。

系统 默认
SQLite 索引组织
MySQL (InnoDB) 索引组织，这就是"聚簇索引"
Oracle / SQL Server 默认 slotted page。建表时可以指定用索引组织

4为什么需要日志结构存储

难度 ★★★★★重要引出 LSM 的动机，读懂就行，不直接考

日志结构存储只追加变更记录，从不原地改。32:22 把上面的问题总结一下，就是这一句：

如果我们只能追加，不能原地改，数据库该怎么造？

核心思路：不再存元组的当前状态，也不再原地修改。只往数据文件末尾追加变更记录。

PUT(k1, "a")    // 追加一条
PUT(k1, "b")    // 再追加一条，旧的 "a" 原样不动
DELETE(k1)      // 删除也是追加一条
// 文件里躺着三条记录，读的时候以最新那条为准

这像银行流水。余额不是改出来的，是把每笔交易从头加出来的。所以记一笔很快，查余额就得翻流水。

代价与收益：
好处：写入极快 插入、更新都只是追加，全部是顺序 I/O
好处：适配只能追加的存储 HDFS、S3 都能用
坏处：读取变慢 一个 key 的最新值可能藏在很多层里，得逐层找

这正是 #03 那条原则的极致应用。用更多顺序 I/O，换掉随机 I/O。

出身

LSM 论文发表于 1996 年。33:50 有意思的是，LSM 的发明人，就是上一讲 LRU-K 的发明人。

更早的源头，是 1980 年代末、90 年代初的日志结构文件系统。LSM 把这套思路搬进了数据库。

踩坑： Andy 特意提醒，本讲的东西看起来很像多版本并发控制（MVCC）。但它们不是同一回事。MVCC 在 #20 讲。

5LSM 的两个核心结构

难度 ★★★★★必会HW2 Q1 要比 MemTable、SSTable 的写路径

LSM 只靠两样东西：内存里的 MemTable，磁盘上的 SSTable。34:34 MemTable 能改，SSTable 一旦写下就不能改。

                内存
        ┌────────────────────┐
        │     MemTable        │  树结构（B+树 / 跳表 / 字典树）
        │  可以原地更新         │  写满了就落盘
        └────────────────────┘
   ═══════════│════════════════════ 内存 / 磁盘分界线
              ▼ flush
        ┌────────────────────┐
Level 0 │ SSTable │ SSTable   │  不可变，按 key 排序
        ├────────────────────┤
Level 1 │  SSTable（更大）      │
        ├────────────────────┤
Level 2 │  SSTable（更大）      │
        └────────────────────┘

void Put(Key k, Value v) {
  memtable.Insert(k, v);                  // 在内存里，可以原地覆盖
  if (memtable.Full()) Flush();           // 写满了，整体落盘成 SSTable
}
// SSTable 写出来以后，再也不改

MemTable 像草稿纸，随便涂改。SSTable 像交上去的考卷，交了就不能再动。

结构 位置 可变性
MemTable 内存 可以原地更新，因为在内存里
SSTable（Sorted String Table） 磁盘 不可变

只有两种操作

LSM 只认 PUT 和 DELETE。没有 update，也没有 upsert。

PUT(k1, row_v1)    // 第一次写：逻辑上是插入
PUT(k1, row_v2)    // 再写一次：逻辑上就是更新
DELETE(k1)         // 删除：写一条墓碑
// 考点：更新用 PUT 表达，删除用 DELETE 墓碑表达

补充：PUT 在物理上是插入一条新记录。在逻辑上，它可能是更新一个已有的值。

持久性

MemTable 在内存里，崩了就没了。所以旁边还有一个单独的日志文件。36:43 PUT 操作会追加进这个日志。事务提交前，必须先 flush 这个日志。

log.Append(k, v);        // PUT 追加到单独的日志文件
memtable.Insert(k, v);   // 内存里的 MemTable 照常更新
log.Flush();             // 事务提交前，日志必须先落盘
// 考点：MemTable 在内存里，崩溃不丢数据靠的是这个日志

这像餐厅点单。服务员脑子里记着，每单也写在小票上。服务员忘了，小票还在。

这一讲不展开，#21 WAL 会详讲。现在只要知道，MemTable 是有持久性保障的。

落盘流程

MemTable 写满了，就排好序整个倒到磁盘上，变成一个 SSTable。37:25

  1. MemTable 写满，比如几百 MB。
  2. 扫描它的叶子节点，把条目按 key 从小到大排序。再写成一个 SSTable。
  3. flush 到磁盘。
  4. 新建一个空的 MemTable，继续。
memtable.Put("k1", "v1");
memtable.Put("k1", "v2");
memtable.Put("k1", "v3");   // 内存里原地覆盖，只剩 v3
Flush();                    // SSTable 里只有 ("k1", "v3") 这一条

补充：这是关键。同一个 key 在 MemTable 里被改了很多次也没关系。MemTable 支持原地更新，落盘时只会写出最新的那一个版本。

这像把草稿誊到正式本上。草稿涂改了十遍，誊的时候只抄最后一遍。

排序规则：

  • 单个 SSTable 内部：按 key 从小到大。
  • 多个 SSTable 之间：按时间戳，从新到旧。

6读、写、删

难度 ★★★★★必会HW2 Q1 考读路径和墓碑，HW3 Q4 用到过滤器

读

读一个 key，就是从新到旧一层层找。40:13 先碰到的那个就是最新版本。

① 先查 MemTable：它有最新的改动，命中就直接返回
② 没有 → 从 Level 0 开始逐层往下查 SSTable
③ 同一个 key 在多层都出现 → 【永远取层级更靠上/时间更新的那个】
考点：必须从新到旧查，先碰到的就是最新版本，可以直接停

这像找一份文件的最新版。先翻桌上的，再从最新的档案盒往旧的翻。

这就是 LSM 的代价：读要在一堆文件里大海捞针。

用过滤器加速读

内存里多存一张 summary table，就能跳过不相干的文件。41:39 这张表记着每个 SSTable 的额外元信息。

过滤器类型 回答什么问题
范围过滤器 这个 key 范围在这个 SSTable 里存在吗？它支持范围扫描
Bloom Filter 这个 key 在这一层存在吗？ 
for (auto &level : levels) {
  if (!level.bloom.MayContain(k)) continue;   // 说"不存在"，就一定不存在
  if (auto v = level.Get(k)) return v;        // 说"可能存在"，还得真去查
}

这像门口的访客登记簿。簿上没有名字，人一定不在。簿上有名字，人也可能已经走了。

踩坑： Bloom Filter 会有假阳性。它说"可能存在"，你还得真的去查。它说"不存在"，那就一定不存在。#09 详讲。

删除：墓碑

删除不用去找原数据，追加一条墓碑记录就完事。45:15 墓碑就是写进 MemTable 的一条 DELETE key 记录。

DELETE(k1)   // 往 MemTable 追加一条墓碑，原数据一个字节都不碰
GET(k1)      // 从新到旧查，先碰到墓碑，直接返回"不存在"
// 旧值物理上还在，逻辑上已经不存在了

墓碑这个名字很形象。人不在了，就立块碑，告诉后来的人。

之后有人读这个 key，会先看到这条删除记录。这就说明它在逻辑上已经不存在了。它的旧值其实还在，物理上散落在一堆 SSTable 里。

补充：对比一下元组导向存储。那边删除要先取到页，再标记删除，可能还要重组。这边一条追加就搞定。

值里存什么

SSTable 里存的是整条元组，不是改动的那个字段。43:52 学生问了个好问题：只更新一个字段时，存的是什么？

答案是整条元组。 RocksDB 和大多数系统都存完整元组，用序列化的形式。所以更新分两种：

UPDATE t SET a=1, b=2, c=3;      -- 盲写（blind write）：字段全给了，不用读旧值，直接 PUT
UPDATE t SET age = age + 1;      -- 读-改-写：先读出当前值，算完再整条 PUT 回去

这像改简历。哪怕只改了电话号码，交上去的也是一整份新简历。

不会出现"一条记录的不同字段，散在不同 SSTable 里"的情况。

7压实 Compaction

难度 ★★★★★必会HW2 Q1 直接考，合并过程要手动走一遍

压实就是后台把一堆 SSTable 合并，每个 key 只留最新版本。46:40 一个 key 被更新一千次再删除，会留下 1001 条记录。我们只需要最后一条。

PUT(k1, v1) ... PUT(k1, v1000)   // 一千次更新
DELETE(k1)                       // 再删掉
// 磁盘上一共 1001 条，真正有用的只有最后那条

这像清理手机相册。同一个场景连拍了一千张，只留最后一张。

触发条件各系统不同。比如 SSTable 的总大小、重叠 key 范围的数量……RocksDB 有一堆策略可配。

踩坑：这和后台刷脏页是一模一样的权衡。压实做得太狠，I/O 全被占，查询变慢。做得太少，SSTable 越堆越多，读越来越慢。没有一刀切的答案。

合并算法

合并就是归并排序的合并步骤。47:56 它和 #12 排序归并连接 是同一个算法。

两个游标从两个 SSTable 的开头出发。实际会同时合并多个。

SSTable A (新)            SSTable B (旧)            输出
─────────────             ─────────────             ────────────
DEL (key100)              PUT (key101,a2)           DEL (key100)     ① 100<101，B 没有 100，墓碑也照样输出
PUT (key101,a3)           PUT (key102,b1)           PUT (key101,a3)  ② key 相同 → 只保留新的（A）
PUT (key102,b2)           DEL (key103)              PUT (key102,b2)  ③ 同上
PUT (key103,c1)           PUT (key104,d2)           PUT (key103,c1)  ④ 同上，A 的 PUT 盖掉 B 的 DEL
（A 结束）                                           PUT (key104,d2)  ⑤ A 走完，B 剩下的直接抄过去

B 一共 4 条记录，A 也是 4 条。两个游标各自从第一行开始往下走。

if (a.key < b.key)      out.Append(*a++);    // 小的先输出，墓碑也照样输出
else if (b.key < a.key) out.Append(*b++);
else { out.Append(*a++); ++b; }              // key 相同：只留新的 A，丢掉旧的 B
// 考点：压实就是归并排序的合并步骤

这像两队按身高排好的学生，合成一队。每次比两个队头，矮的先出列。

规则很简单：key 相同时，永远只保留最新那个版本。不管它是 PUT 还是 DELETE。

8两种压实策略

难度 ★★★★★必会HW2 Q1 的写放大判断直接出自这里

分层压实 Level Compaction

分层压实让 Level 1 往下的每一层，key 范围都不重叠。50:04 换来的是读得快，代价是写放大。它是 RocksDB 的默认策略。

核心规则：

层 key 范围
Level 0 允许重叠。它是 MemTable 直接落盘来的，管不了
Level 1 及以下 保证不重叠 
Level 0:  [A~R]  [E~T]  [B~Q]     ← 三个范围互相重叠
                  │ compaction
                  ▼
Level 1:  [A~K]        [L~T]      ← 不重叠

为什么这样读更快：

查 key = Q
在 Level 0：Q 落在 [A~R] ∩ [E~T] ∩ [B~Q]，三个都可能有，最坏要全查
在 Level 1：Q 只可能在 [L~T]，只查一个 SSTable
考点：Level 0 允许重叠，Level 1 往下不允许，所以下层一查就准

这像图书馆按编号分区的书架。每个区只放一段编号，找书很快。可新到一批书，整片书架都得挪一遍。

补充：55:50 Level 0 是按时间从新到旧排的。在第一个里找到了，就不用看后面。但最坏情况仍然要全扫。summary table 和过滤器能帮忙跳过一部分。

层数不固定，可以一直加下去。实践中用 RocksDB 默认配置，最底层会积累一堆很大的文件。

代价：写放大（Write Amplification） 52:53

Level 1 必须保证不重叠。从 Level 0 合并下来时，上层的 key 可能落进下层任何一个文件。所以往往要把整层读进来，再全部写回去。

Level 1 有 10 GB，一次压实就可能要读 10 GB、写 10 GB。

Level 0 新来一个 [A~Z] 的 SSTable
  → 和 Level 1 的 [A~K]、[L~T] 全都重叠
  → 两个文件都得读出来、合并、再整体写回
考点：分层压实读得快，代价是写放大

通用压实 Universal Compaction

通用压实只有一层。59:28 它不维护多层结构，只做有针对性的局部合并。挑几个相邻的 SSTable，合成一个更大的。

[SST1] [SST2] [SST3]   [SST4] [SST5]
   └──── 合并 ────┘        └── 合并 ──┘
        [大 SST]           [大 SST]

适合什么：

  • 写入非常快、更新非常多的负载。
  • 只关心最新数据的场景，典型是时序数据。

比如记录房间温度。你只关心最近 5 分钟、10 分钟的，一年前的温度根本不查。这时最新数据就在最新的 SSTable 里，查得飞快。

SELECT AVG(temp) FROM room_temp
WHERE ts > now() - INTERVAL '10 minutes';   -- 只碰最新的那几个 SSTable
-- 考点：写多、只查最新数据的时序负载，适合通用压实

这像收快递。新件堆在门口最上面，你也只拆新到的，老箱子不用动。

对比

一句话：分层压实偏向读，通用压实偏向写。

Level Compaction Universal Compaction
层数 多层 一层
key 范围 Level 1+ 保证不重叠 不保证
读 快，只查一个 SSTable 慢一些
写放大 严重 小
适合 读多 写多、只查最新数据（时序）

补充：这是计算机科学里最经典的权衡之一。花力气把写做重一点，读就快。写做轻一点，读就慢。

1三类工作负载：OLTP / OLAP / HTAP

难度 ★★★★★必会#13 #14 按它选执行模型

数据库的工作负载分三类：OLTP、OLAP、HTAP。7:25 理解列存之前，必须先分清它们。

OLTP 像超市收银台，一单一单地扫。OLAP 像月底盘点，把全年的账翻一遍。HTAP 想两件事一起干。

OLTP（联机事务处理）

新应用一开始建的都是 OLTP。它不断从外部世界接收新数据。但每次操作涉及的数据量很小。

INSERT INTO comments (user_name, created_at, body)
VALUES (?, now(), ?);   -- 一条评论就这么点数据
-- 数据量很小，但这种操作数量极大，必须极快

Andy 的例子很具体：

  • 在 Reddit 发一条评论。存的就是用户名、时间戳和一段文本，没多少数据。
  • 在亚马逊把商品加入购物车。存的是账号信息、时间戳、商品和数量。

但这种操作数量极大，而且必须极快。

OLAP（联机分析处理）

OLAP 是攒够了大量数据之后，再回头做分析。目标是从聚合里提取新知识。

还是亚马逊的例子。单个人买一件商品，数据量很小。但所有人的所有订单加起来，就非常大。于是可以问：

"九月某天气温高于某度时，匹兹堡市卖得最好的商品是什么？"

SELECT o.item, COUNT(*) AS cnt
FROM orders o JOIN weather w ON o.day = w.day
WHERE w.city = 'Pittsburgh' AND w.temp > ?
GROUP BY o.item ORDER BY cnt DESC LIMIT 1;   -- LIMIT 1 只是示意

这类查询要跨越大量记录，而且复杂得多。里面会有多表连接、窗口函数和聚合。

HTAP（混合事务分析处理）

HTAP 想在同一份数据上，既快速写入，又直接分析。9:24 这是系统设计的圣杯。而且两边还不能拖慢彼此。

代表是 SingleStore 和 PingCAP TiDB。

INSERT INTO orders VALUES (?, ?, ?);               -- 前台还在不停下单
SELECT item, SUM(qty) FROM orders GROUP BY item;   -- 同时直接在这份数据上分析
-- 考点：HTAP 想同时做好 OLTP 和 OLAP，结果常常两头不讨好

这像一家店，既想当便利店，又想当仓储超市。两样都能做，但哪样都不是最好。

踩坑： Andy 的评价很坦率。这条路经常两头不讨好。它既不是最好的 OLTP 系统，也不是最好的 OLAP 系统。大公司里，在乎 OLTP 的人会选专门的 OLTP。在乎 OLAP 的人会选专门的 OLAP。但这个细分市场确实存在。

OLTP 在左下角，OLAP 在右上角，HTAP 夹在中间。10:46

-- 考点：OLTP 只是"相对"写得多，大多数操作其实还是读

补充： "复杂度"不是科学指标。大致就看这几样：连了几张表，有没有聚合。还有几个 GROUP BY，嵌套了几层查询。

踩坑：有个反直觉的点。即使在 OLTP 系统里，大多数操作其实也是读。OLTP 只是相对 OLAP 写得更多。

2存储模型的自由来自哪里

难度 ★★★★★重要回顾物理数据独立性，读懂就行，不直接考

数据库敢把一张表拆开存，靠的是物理数据独立性。15:59 这要回到 #01 讲的内容。

关系模型只规定了数据在逻辑层长什么样。物理上怎么摆字节，它完全没有规定。

所以有一件事，没有任何东西要求。那就是一张表的各个属性，必须在磁盘页上连续存放。

CREATE TABLE t (a INT, b TEXT, c TIMESTAMP);
-- 逻辑上：一行三个属性
-- 物理上：可以按行连着存，也可以按列分开存，查询写法不变
-- 考点：这份自由来自物理数据独立性，#03 的溢出页第一次用到它

这像点外卖。你只管菜单上点了什么。后厨把菜放在哪个冰箱，你不用知道。

其实这个假设我们已经破过一次了，就是 #03 的溢出页。PostgreSQL 把超过 2 KB 的大文本扔到 TOAST 表里，元组里只留指针。查询时数据库自己把它拼回来，应用完全察觉不到。

于是可以走得更远。对某些负载，尤其是 OLAP，连续存放根本不是最优解。

而这带来的收益，不是一点点：

6:50 Andy 讲了个故事。早期列存系统 Vertica 的一个朋友告诉 Andy 一件事。某澳大利亚电话公司，有些查询原本要跑好几天。换成列存后，变成了几分钟。

3NSM 行存

难度 ★★★★★必会HW2 Q2 直接考行存下读几页

行存把一个元组的所有属性，连续放在同一个页里。19:59 写完这个元组，才开始写下一个。

它的学术叫法是 N-Ary Storage Model（N 元存储模型）。日常说 row store（行存），大家都懂。它就是 #03 讲的 slotted page。

struct Tuple { int userID; char userName[32]; Timestamp lastLogin; };  // 32 只是示意
Tuple page[N];   // 行存：一页里一条元组接一条元组

这像把 Excel 表一行一行抄进本子。每行从左抄到右，抄完再换行。

OLTP 查询在行存上有多顺

行存跑 OLTP 很顺，一次 I/O 就拿到整条元组。

以 Wikipedia 的 schema 为例。有 useracct 用户表、pages 页面表、revisions 修订表。

-- 用户登录
SELECT * FROM useracct WHERE userName = ? AND userPass = ?;

索引查 userName → Record ID(1234)
    → page directory 说 1234 在 page5
    → page5 读进内存 → slot array 跳到偏移 → 拿到整条元组

一次 I/O，拿到需要的全部数据。插入也一样简单。找个有空闲空间的页，写进去就行。

这像查字典里的一个词。翻到那一页，读音、释义、例句全在一起。

补充： Andy 在这里顺带插了句安全提醒。永远不要在数据库里存明文密码。加密在应用层做，数据库只存密文。每次数据泄露的新闻说"密码被泄露了"，就是因为存了明文。

OLAP 查询在行存上有多惨

行存跑 OLAP 很惨，按这个例子，超过一半的 I/O 是白读的。

-- 统计 .gov 域名的用户每月登录次数
SELECT EXTRACT(month FROM lastLogin) AS month, COUNT(*)
FROM useracct
WHERE hostname LIKE '%.gov'
GROUP BY month;

补充：这条查询有真实背景。十五年前有一桩丑闻。一批国会议员让拿政府工资的助理登录 Wikipedia，美化自己的词条。Joe Biden、Mike Pence 都被抓到过。大致就是靠这类查询查出来的。

问题在哪：

没有可用的主键谓词 → 必须扫描【所有页】
每个页读进来 → 只用了 hostname 和 lastLogin 两列
             → userID / userName / userPass 三列【完全没用上，但被迫读进来了】
考点：hostname LIKE '%.gov' 只用两列，行存却得整页读，过半 I/O 白费

24:44 按这个例子算，超过一半的 I/O 是白费的。数据都在页里，你没法只读其中几列。

这像只想统计全班身高，却得把每人的整份档案都搬出来。

行存的适用面

一句话：行存擅长少量元组、整条拿，不擅长海量数据、只看几列。

擅长 不擅长
快速插入、更新、删除 分析型查询
需要整条元组的查询 只用少数几列的查询
只涉及少量元组 扫描海量数据
配合索引组织存储、聚簇，可以做到只读一个页 会给缓冲池带来巨大压力，塞满用不上的数据

补充：顺带一提，SELECT * 在分析型负载里几乎见不到。也不该写。

4DSM 列存

难度 ★★★★★必会HW2 Q2 直接考列存下读几页

列存把每个元组拆开，同一个属性的所有值连续存放。26:05 一个页里只放一列的数据。

它的学术叫法是 Decomposition Storage Model（分解存储模型），也就是 column store（列存）。它是行存的完全对立面。

int         userID[N];      // 列存：每一列是一个独立的数组
std::string hostname[N];
Timestamp   lastLogin[N];
// 考点：查 hostname 和 lastLogin，只读这两个数组，别的列碰都不碰

这像把全班成绩单按科目拆开。数学老师只拿数学那一张，不用翻每个人的整份档案。

行存 (NSM)                     列存 (DSM)
┌─────────────────────┐       ┌──────────┐ ┌──────────┐ ┌──────────┐
│ id1 name1 host1 t1  │       │ id1      │ │ name1    │ │ host1    │
│ id2 name2 host2 t2  │       │ id2      │ │ name2    │ │ host2    │
│ id3 name3 host3 t3  │       │ id3      │ │ name3    │ │ host3    │
└─────────────────────┘       └──────────┘ └──────────┘ └──────────┘
   一个页装完整的行              每个页只装一列

同样那条 OLAP 查询在列存上：

① WHERE hostname LIKE '%.gov'  → 只读 hostname 那些页
② EXTRACT(month FROM lastLogin) → 只读 lastLogin 那些页
   userID / userName / userPass 的页【从头到尾没碰过】

页头的简化

列存省掉了每条元组各自的 header。28:12 这个好处容易被忽略，但很实在。

行存里，每个元组都有自己的 header，里面有自己的 NULL 位图。

列存里，一个列的页只需要一个 header。一个 NULL 位图，就覆盖整列所有值。

struct RowTuple   { Header hdr; /* 各个属性 */ };              // 行存：每条元组一个 header
struct ColumnPage { Header hdr; Bitmap nulls; int values[N]; }; // 列存：整页一个 header

这正好呼应 #03 第 13 节。列存适合用"特殊值"表示 NULL。

列存的四大收益

列存有四大收益，最关键的是对 CPU 友好和压缩率高。35:04

# 收益 说明
1 避免无效 I/O 只读查询真正需要的列
2 对 CPU 友好 数据在内存里是连续的跨步（stride）。现代超标量 CPU 最讨厌分支和跳转。没有 if、没有跳跃，流水线就不停顿
3 压缩率高得多 见下
4 页头开销小 见上 
int64_t sum = 0;
for (size_t i = 0; i < n; i++) sum += price[i];   // 连续内存，循环里没有分支
// 考点：对 CPU 友好，指同类型数据连续摆放，没有 if 和跳转
// 考点：没有分支，流水线就不用停下来等

第 3 点为什么成立？36:28 Andy 的类比很好懂：

页里混着整数、字符串、浮点数，还有一堆杂七杂八的东西。这时压缩它，就像拿 gzip 去压 JPEG。压不动，因为数据已经很"随机"了。

如果一个页里全是同一个值域的数据，比如全是温度读数。那就像拿 gzip 去压一个全是 0 的文本文件。压缩率爆表。

代价

列存的代价是点查和写入都慢，因为一条元组被拆散了。

问题 原因
点查很慢 要从多个页把一条元组拼回来
插入、更新、删除很慢 每次都要拆开，再分发到 N 个页 
INSERT INTO wide_table VALUES (v1, v2, /* ... */ vn);
-- 一千列的表：这一条要拆成一千份，写进一千个不同的页

5怎么把元组拼回去

难度 ★★★★★必会HW2 Q2 的隐式偏移就是这里的方案 A

拼回元组的正确做法，是让所有列都定长。31:40 这样第 N 个元组，在每一列里都是同一个下标。

这是列存最核心的实现问题。WHERE 在 hostname 列上匹配到了第 2、5、6 个位置。怎么在 lastLogin 列里找到对应的值？

方案 A：固定长度偏移 正确答案

所有列都用定长值，存成简单数组。于是"第 N 个元组"在任何一列里，都是同一个下标。

hostname 列    lastLogin 列
[0] x.com      [0] ...
[1] y.com      [1] ...
[2] a.gov 命中 [2] ← 简单算术直接跳过来
[3] z.com      [3] ...

for (size_t i : matches)          // hostname 列命中的下标，比如 2、5、6
  out.push_back(lastLogin[i]);    // 同一个 i，直接去 lastLogin 列取值
// 定长时，第 i 个值的地址 = base + i * width，纯算术
// 考点：拼回元组靠固定长度偏移，不用额外存任何东西

这像几栋一模一样的楼。知道房号，在哪栋楼都能直接走到同一个位置。

纯算术，零额外存储。

方案 B：内嵌元组 ID 别这么做

内嵌元组 ID 是个坏主意，既费空间又慢。32:24 做法是每个值旁边存一个元组 ID。再维护一个索引来定位。

struct Entry { uint32_t tuple_id; Value v; };   // 每个值都背着一个元组 ID
Entry hostname_col[N];
// 拼回元组时，得先查索引找到 tuple_id 在哪，没法按下标直接跳
// 考点：内嵌元组 ID 多占空间，还得靠索引定位

为什么是坏主意：每个值都要多存一个数字。而且值可以变长，所以还得额外维护索引，才能跳到指定偏移。

6PAX 混合模型：真实系统用的那个

难度 ★★★★★重要真实系统都用它，但 HW2 只考纯 NSM / DSM

真实系统说的"列存"，几乎都是 PAX：先按行切块，块内再按列存。37:46 这是本讲最重要的实践知识点。

纯列存的问题

纯列存的问题是，元组迟早要拼回来，拼一次就要跑很多页。

最理想的 OLAP 查询只碰一列。但这种查询其实不常见，迟早要把元组拼回来。

如果彻底按列拆开，会怎样？十亿条元组过滤后只剩一千条。可为了拼出这一千条，每条都要去一千个不同的页里取数据。

for (auto rid : survivors)                  // 过滤后只剩一千条
  for (auto &col : columns)                 // 每条都要跑遍所有列
    row.push_back(col.PageOf(rid).Get(rid)); // 每列都在不同的页里
// 考点：纯列存拼元组太贵，这正是 PAX 要解决的问题

PAX 的折中

PAX = Partition Attributes Across（跨属性分区）。它的做法是：先按行水平切块，块内再按列组织。

思路是两头都要。一头是列存的好处：不读无关列，同列数据挨着，所以压得好。另一头是同一条元组的各个属性，别离得太远。

┌─────────────────────────────────────┐
│  Row Group 1                        │
│  ┌────────┬────────┬────────┐       │
│  │ A 列块  │ B 列块  │ C 列块  │       │  ← column chunk
│  └────────┴────────┴────────┘       │
│  Row Group 元数据（压缩方式、字典……）  │
├─────────────────────────────────────┤
│  Row Group 2                        │
│  ┌────────┬────────┬────────┐       │
│  │ A 列块  │ B 列块  │ C 列块  │       │
│  └────────┴────────┴────────┘       │
├─────────────────────────────────────┤
│  Footer（全局元数据）                 │ ← 最后才写
└─────────────────────────────────────┘

struct RowGroup {                 // 先按行切：一批元组一组
  ColumnChunk chunks[NUM_COLS];   // 组内再按列：每列一个 column chunk
  Metadata meta;                  // 本组的压缩方式、字典等
};
// 考点：row group 是水平分块，column chunk 是组内某一列的数据
// 考点：PAX 既不读无关列、压得好，又让同一条元组的属性离得不远

这像按班级分教室，每个教室里再按科目放作业本。找一个人的全部作业，只用进一个教室。

术语用的是 Parquet 的叫法，它已经成了事实标准：

术语 含义 典型大小
Row Group 一批元组组成的水平分块 Parquet 默认约 100 万行。ORC 默认按数据量算，约 100 MB
Column Chunk Row Group 里某一列的数据 无
Footer 全局元数据 写在文件末尾

这像写书的目录。正文写完了，才知道每章在第几页。

谁在用

系统说"我们是列存"，99% 的情况下指的是 PAX，不是纯 DSM。39:56 这是最关键的一句话。纯列存的系统，Andy 说自己只能想到一两个。

7压缩：目标与约束

难度 ★★★★★重要HW2 Q3 的背景，三条要求不单独考

压缩就是拿 CPU 换存储和 I/O。46:44 本课始终假设 I/O 是主要瓶颈。在云上尤其如此，磁盘可能还隔着网络。

压缩的逻辑很直白：

一个未压缩的页能放 10 条元组，压缩后能放 100 条。同样一次 I/O，拿到的有用数据变成 10 倍。

Page *p = disk.Read(page_id);   // 一次 I/O
auto tuples = Decompress(p);    // 多花一点 CPU
// 未压缩：一页 10 条元组。压缩后：一页 100 条

这像用真空压缩袋装衣服。打包费点劲，可一个箱子能多装好几倍。

核心权衡：CPU 换存储和 I/O。多花计算去压缩、解压，换来更小的存储和更少的 I/O。

三条硬性要求

数据库对压缩有三条硬性要求：定长、晚解压、无损。48:07

# 要求 为什么
1 压缩后必须是定长值 否则 第 5 节 的偏移量定位就崩了。32 位整数压完，有的 16 位，有的 24 位，就没法算偏移了
2 尽可能推迟解压 最好能直接在压缩数据上跑查询
3 必须无损 
uint16_t v = codes[i];   // 定长：地址 = base + i * 2，一算就有（2 字节只是示意）
// 变长：有的 16 位有的 24 位，第 i 个在哪，只能从头数
// 考点：定长排第一条，因为拼元组全靠偏移量

补充：变长数据可以单独放到别的页或存储池里。那里随便用什么压缩都行。

无损 vs 有损

数据库只做无损压缩。49:31

  • 无损：压了再解，比特级完全一致。
  • 有损：MP3、MP4 那种。人眼人耳察觉不到，但数据确实变了。

无损像 zip 打包文件，解开一字不差。有损像把照片存成小图，看着差不多，像素其实丢了。

INSERT INTO temp_10min                     -- 按 10 分钟聚合
SELECT bucket_10min(ts), AVG(temp) FROM temp_by_sec GROUP BY bucket_10min(ts);
DELETE FROM temp_by_sec;                   -- 删掉秒级原始数据，这就是有损
-- 数据库不会自己这么干，必须由人明确要求

补充：有损也不是完全不能用，前提是人明确要求。Andy 举了个例子。按秒记录房间温度，记了一整年。一年后，你可能不需要精确到秒了。那就按 10 分钟聚合，删掉秒级原始数据。这就是有损，但对你的场景够用。

还有一类叫近似查询执行（approximate query execution）。原始数据保留，但用有损算法来算查询。结果是带误差界的估计值。

四个压缩粒度

压缩可以按四种粒度做，收益最大的是按列压。50:54

粒度 说明 谁在用
块/页级 整页压缩 MySQL InnoDB，见下节
元组级 整条元组压缩 极罕见。中国的 Terark 做过，后被字节跳动收购
属性级 单个属性值压缩 PostgreSQL 的 TOAST 表，大文本单独压
列式 按列压缩 所有列存系统。收益最大

这像搬家打包。可以整箱封，可以一件件裹，也可以把同类东西放一起压。同类放一起，最省地方。

8块级压缩与 MySQL 的 mod log

难度 ★★★★★了解MySQL 实现细节，HW2 只考列式压缩

块级压缩就是拿现成的通用算法，把整个数据块压一遍。51:33 常用的有 gzip、zstd、LZ4、Snappy。

补充： Oracle 有自己的专利算法 OZIP，别人不能用。

MySQL InnoDB 的做法

InnoDB 的压缩页不解压也能接受写入，靠的是 mod log。53:33 这个设计值得单独看。

一个压缩页：
┌──────────────────────────────┐
│ Header │  Mod Log  │ 压缩数据  │
└──────────────────────────────┘
              ↑
        像 WAL 一样记录"改了什么"
  • InnoDB 默认页是 16 KB。压缩页只有 1 / 2 / 4 / 8 KB 这几档，压完向上取整到其中一档。压出 900 字节，就补到 1 KB。课上口误说成了"8 的倍数"。
  • 页读进内存时，保持压缩状态。

写入时：

如果是【盲写】（不需要知道旧值），比如"把 lastLogin 改成当前时间"
    → 【不用解压】，只在 mod log 里追加一条变更记录
mod log 写满了
    → 才解压、应用所有变更、清空 mod log
考点：mod log 让盲写不用解压，代价是写满时会阻塞写入

读取时：

如果需要的数据 mod log 里就有 → 直接读
否则 → 解压（回到 16 KB）+ 应用 mod log 的变更
       同时【保留压缩版本】。如果没有待应用的变更，可以随时丢掉解压版省内存

这像在打印好的合同边上贴便利贴。小改动先贴上去，贴满了再重新打印一份。

补充：55:34 先把变更快速记在一边，后台再整理。这个模式在数据库里到处都是。LSM 的 MemTable、后面会讲的 delta store，本质都是同一招。

踩坑： mod log 写满时，确实会阻塞写入。天下没有免费的午餐。

踩坑： PostgreSQL 做不了页级压缩。它只能压 TOAST 表里的大属性。

通用压缩的根本局限

gzip、Snappy、zstd 对数据库来说是黑盒。59:00

数据库拿到一堆压缩字节，完全不知道它们是什么意思。唯一的办法就是整个解压。压缩算法也不懂数据的语义，不知道哪些页应该放在一起压。

这像把文件锁进保险箱。想看一行字，也得先把整个箱子打开。

我们真正想要的是这样：

SELECT * FROM users WHERE name = 'Andy';

把常量 'Andy' 也转成压缩形式（比如整数 10）
    → 扫描压缩数据时，比较的是【整数 vs 整数】而不是【字符串 vs 字符串】
    → CPU 有专门指令，快得多
考点：通用压缩是黑盒，我们想要的是直接在压缩数据上比较

通用压缩算法给不了这个能力。它们内部其实也在做字典编码，只是不把字典暴露给你。

9列式压缩五招

难度 ★★★★★必会HW2 Q3 直接考保序字典和各编码适用场合

同一列的数据值域相同、重复值多、彼此接近。1:01:35 这正是下面这些算法的用武之地。

游程编码 RLE（Run-Length Encoding）

RLE 把连续重复的值只存一次，再记下它出现了几次。

存成三元组：(值, 起始偏移, 长度)。

原始 is_dead 列:  N N N Y Y N N N N          （9 个值）
排序前 RLE:       (N,0,3) (Y,3,2) (N,5,4)     （3 个三元组，还行）

--- 先按该列排序 ---
排序后:           Y Y N N N N N N N
排序后 RLE:       (Y,0,2) (N,2,7)             （2 个三元组，好得多）

这像记考勤。连着请了一周假，记一句"请假七天"就行，不用一天一天写。

能直接在压缩数据上算。下面这条查询，直接读三元组就出答案了：

SELECT is_dead, COUNT(*) FROM people GROUP BY is_dead;
-- 读 (Y,0,2) (N,2,7) 就知道：Y 有 2 个，N 有 7 个，一个值都不用解压
-- 考点：RLE 必须先排序，交替出现的值压完反而更大
-- 考点：选最优排序方案是 NP 困难的

踩坑： 最坏情况会变大。N Y N Y N Y ... 这样交替出现，每个 run 长度都是 1。这时压缩后比原始数据还大。

所以必须排序。但排序也有代价。1:05:07 排序要求所有其他列同步重排，否则偏移对不上。而且按 A 列排好了，B 列可能就压不动了。

怎么选最优排序方案？Andy 的回答是：NP 困难。

位打包 Bit Packing

人们声明的类型，总是比实际需要的大。1:05:51 位打包就是只用够用的位数来存。

age INT    -- 32 位。但年龄根本用不到 32 位

原始（8 个 32 位整数）:   256 位，其中高 24 位全是 0，纯浪费
位打包后（8 位就够）:      64 位  无精度损失，且仍是定长

这像用一整张 A4 纸记一个电话号码。纸再大，号码也就占一行。

补丁 Patching / Mostly Encoding

补丁是给位打包兜底的。1:07:19 位打包的问题是，万一有个离群值放不下怎么办？

解法：绝大多数值按小位宽存。离群值用一个哨兵值标记，真实值放进单独的补丁表。

值:  20  25  31  999999  27
     ↓   ↓   ↓    ↓      ↓
存:  20  25  31  [哨兵]   27      ← 全部 8 位
                   ↓
          补丁表: {偏移 3 → 999999}

这像统一订做校服。绝大多数人穿标准码，个别特别高的单独登记、单独做。

Amazon Redshift 管这个叫 mostly8、mostly16 之类的编码。

哨兵怎么选：用全 1 的位模式，然后禁止真实数据取这个值。真要有这个值，就也放进补丁表。

补充：一个小优化。哨兵值重复出现时，补丁表里只存一份，多个偏移共用。

位图编码 Bitmap Encoding

位图编码给值域里每个不同的值配一个位图。1:08:50 位图第 i 位为 1，表示第 i 个元组取这个值。

is_dead 列:   Y  N  N  Y  N  N  Y  N
位图 Y:       1  0  0  1  0  0  1  0
位图 N:       0  1  1  0  1  1  0  1

只在基数很低时有用。基数就是不同值的个数。

int dead = 0;
for (size_t w = 0; w < nwords; w++)
  dead += std::popcount(bitmap_Y[w]);   // 一条指令数完一整个字里的 1
// 考点：位图适合低基数，高基数（比如邮政编码）就是灾难
// 考点：位运算一次处理一整个位向量，比逐个比较整数快

这像签到表。每个选项一张表，来了就打勾。选项少时一目了然，选项上万就成了一堆废纸。

课上有学生连续追问："这比直接存个小整数好在哪？"1:12:30 Andy 的回答是关键：

因为现代 CPU 有位运算指令。一条指令就能处理一整个位向量，找出所有匹配。扫整数要慢得多。聚合场景尤其明显。

踩坑： 基数高就是灾难。给邮政编码建位图，就是几万个位图，存储直接爆炸。

补充：稀疏位图有专门的压缩方法，叫 Roaring Bitmap，很多系统在用。课上没时间展开。

增量编码 Delta Encoding

值彼此接近时，存差值，不存绝对值。1:13:54 典型场景是时序数据。

原始:   time      temp
        12:00     99.5
        12:01     99.4
        12:02     99.5
        12:03     99.6

Delta:  12:00     99.5      ← 基准值放在页首
        +1        -0.1
        +1        +0.1
        +1        +0.1

auto t = base;                                    // 页首放基准值
for (auto d : deltas) out.push_back(t += d);      // 每次加上差值，还原出原值

这像记体重。第一天记下准确数字。之后每天只记比昨天胖了多少、瘦了多少。

还可以叠加：time 那一列全是 +1，再套一层 RLE：

原始:              320 位
只做 Delta:        128 位
Delta + RLE:        96 位

补充： 压缩方案是可组合的（multiplicative）。这是列存能把压缩率做到极致的关键。

补充： Frame of Reference 是个变体。它用一个跨多页的全局最小值做基准，思路一样。

字典编码 Dictionary Encoding 最常用

字典编码把频繁出现的值，换成定长的小整数。1:15:59 另建一个字典做双向映射。它是最常用的一招。

原始 name 列          压缩后        字典（按值排序！）
┌──────────┐        ┌────┐        ┌───────┬──────┐
│ Andrea   │        │ 10 │        │ 值     │ 编码 │
│ Prashanth│   →    │ 30 │        ├───────┼──────┤
│ Andy     │        │ 20 │        │ Andrea│  10  │
│ Andy     │        │ 20 │        │ Andy  │  20  │
└──────────┘        └────┘        │Prashan│  30  │
                                   └───────┴──────┘

这像公司给员工发工号。平时系统里只传工号，要看名字再去花名册查。

字典必须支持双向查询：值到编码，编码到值。

关键设计：保序（order-preserving）

字典按原始值排序。于是编码的大小关系，就等于原值的大小关系。这样就能直接在压缩数据上做比较和范围查询：

SELECT * FROM users WHERE name LIKE 'And%';

① 在【字典】上跑 LIKE 'And%'  ← 字典比原始数据小得多
② 得到编码范围 [10, 20]
③ 改写成：WHERE name_code BETWEEN 10 AND 20
④ 扫描列时【只做整数比较】
考点：字典保序，LIKE 'And%' 才能改写成编码上的 BETWEEN

补充：1:19:27 还有更极端的情况。SELECT DISTINCT name FROM users WHERE name LIKE 'And%'，连原始列都不用扫，查字典就够了。

增删改

字典删除容易，插入麻烦。1:19:27

操作 难度
删除 简单，从字典删掉就行
插入 麻烦。要在编码 10 和 11 之间插一个新值，可中间没有空位。只能重新压缩 
字典：Andrea → 10，Andy → 11（这里的编码只是示意）
新来一个 "Andrew"，按顺序要排在两者之间
10 和 11 之间没有整数，只能重新压缩

补充： OLAP 数据基本是不可变的，所以这在实践中不是大问题。

补充

  • 大多数实现是一个值一个编码。理论上可以做得更细，比如哈夫曼编码。但 Andy 说没有生产系统这么做。
  • 一个 1 MB 的文本块，也可以整体映射成一个 32 位整数。
  • ORC 格式对所有东西都做字典编码。
  • 平时"说字典压缩"，默认就是保序的。不过非保序的实现也确实存在。
