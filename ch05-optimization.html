1从 SQL 到物理计划的完整路径

难度 ★★★★★重要全链路地图，帮助定位，作业不考

一条 SQL 要过好几道工序，才变成能跑的物理计划。4:13

SELECT * FROM foo;
-- 解析器：切成 AST，这时 foo 还只是个字符串
-- 绑定器：查目录，把 foo 换成内部对象 ID
-- 优化器：问成本模型，挑出物理计划，交给执行引擎

这像寄快递。先看地址格式对不对，这是解析。再查这个地址真的存在，这是绑定。最后挑一条最省的路线，这是优化。

  应用（PHP / Java / Rust …）
        │  SQL 字符串
        ↓
  ① 解析器 Parser ──────────→ 抽象语法树 AST
        │                      （只有字符串，"扫描一张叫 foo 的表"）
        ↓
  ② 绑定器 Binder ←──── 目录 Catalog
        │              把表名/列名/函数名 → 内部对象 ID（PostgreSQL 里叫 oid）
        │              找不到就在这里报错
        ↓
    逻辑计划 Logical Plan
        │              （"我要访问 foo、做聚合、按某列排序"，不说怎么做）
        ↓
  ③ 优化器 Optimizer ←──── 成本模型 Cost Model ←──── 统计信息 Statistics
        │
        ↓
    物理计划 Physical Plan
        │              （"对 A 和 B 做哈希连接、走这个索引扫描"）
        ↓
  ④ 执行引擎（#13 #14）

考点：能画出从 SQL 字符串到物理计划的整条路径，说清每一步做什么

每一步都在做什么：

步骤 做什么 难度
解析器 编译原理课那套，词法加语法分析 纯工程活
绑定器 字符串 → 对象 ID，顺便拿到类型和 schema 比想的难得多。SELECT * FROM foo 很简单。但嵌套查询、重名、自连接，能把它折磨得很惨
优化器 本讲主题 难
成本模型 判断"这个计划比那个好" 难，见 #16 
SELECT * FROM foo f1 JOIN foo f2 ON f1.id = f2.parent_id;
-- 自连接：同一张 foo 出现两次，绑定器得分清 f1 和 f2
-- 考点：绑定器把名字换成对象 ID，嵌套查询、重名、自连接让它很难写

补充： Andy 说，解析器和绑定器"就是一堆工程活"。很痛苦，尤其是绑定器。但现成的库可以直接拿来用。

补充：本讲聚焦 SQL。但所有技术对任何查询语言都成立。

2优化能有多大威力：2,000,000 → 37

难度 ★★★★★重要动机算例，串起 #12 #13，作业不考

同一条查询，换个计划，I/O 能从 200 万次降到 37 次。7:30 这个例子是本讲最有说服力的部分。

SELECT DISTINCT e.name
  FROM employee AS e, department AS d
 WHERE e.dept_id = d.id
   AND d.name = 'Toy';

这像从家去机场。走错路要绕城大半天，走对了一脚油门就到。目的地一样，差的全是路线。

目录里的统计信息：

表 元组数 页数 索引
employee 10,000 1,000 主键上的聚簇索引。外加 name、dept_id 上的非聚簇索引
department 500 50 主键 id 上的聚簇索引。外加 name 上的非聚簇索引

五步优化，I/O 从 200 万降到 37

每一步只换一个决策，I/O 就一路往下掉。

-- 第 0 步的字面翻译，等于先做笛卡尔积，再过滤
SELECT DISTINCT e.name FROM employee e CROSS JOIN department d
 WHERE e.dept_id = d.id AND d.name = 'Toy';
-- 考点：五步依次是去笛卡尔积、换排序归并、换向量化、下推加换边加索引
# 做了什么 I/O 次数
0 SQL 的字面翻译。笛卡尔积加过滤加投影，每个算子都把结果写成临时文件 2,000,000
1 消掉笛卡尔积，换成块嵌套循环内连接。边扫边匹配，不再物化全部组合 54,000
2 换成排序归并连接（B = 50 缓冲页） 7,000
3 从物化模型换成向量化模型。不再写临时文件，全程流水线（#13） 3,000
4 谓词下推，交换连接两侧，再用索引嵌套循环连接 37

最后一步最狠，它把 3,000 砍到了 37。最后一步做了什么，见 12:55：

把 d.name = 'Toy' 这个过滤【推到 join 下面】、直接压在 department 的扫描上
        ↓
用 department.name 上的索引，一下子只取出极少数行
    → 3 次读 + 1 次写 = 4
        ↓
再拿这几行去 employee 的 dept_id 索引上做【索引嵌套循环连接】
    → 1 + 3（查索引）+ 20（回表，每个部门约 20 人）次读 + 4 次写 = 28
        ↓
投影去重：读临时结果
    → 4 次读 + 1 次写 = 5
        ↓
合计 4 + 28 + 5 = 37 次 I/O

考点：department 放外层，是因为 name 上有索引，而且这个谓词选择性高

补充：课上 Andy 口头只说了第一步的"3 读 1 写"。这三段的账来自官方幻灯片。

踩坑：怎么知道该把 department 放外层？这是 13:38 的课堂提问。department.name 上有索引。统计信息还说："500 条记录、约 100 个部门，分布不是一家独大"。所以这个谓词选择性很高。这个选择性怎么算，是 #16 的内容。

补充：取统计信息本身要不要 I/O？14:20 要。统计信息在实现上通常就是另一张表。所以真有 I/O 和锁的开销。但它比真实数据小得多，一般常驻内存。本讲忽略这部分。

补充： 15:41 有一点很迷人。你在终端敲下回车的那一瞬间，DuckDB、SQLite、PostgreSQL 就开始干活了。它们在实时跑上面这一整套搜索。一条简单查询可能跑 10 毫秒，优化本身只占 1 毫秒。人感觉是瞬间的。

3优化器的三大组件

难度 ★★★★★必会HW4 Q2 判断题引到 §3 理想 vs 现实

优化器由三块拼成。变换负责出候选，搜索负责挑路，成本模型负责打分。23:16

Plan Optimize(Plan p) {
  for (auto &cand : Search(ApplyRules(p)))    // 变换出候选，搜索决定看哪些
    best = Cheaper(best, cand, cost_model);   // 成本模型来打分
  return best;
}
// 考点：三大组件是变换、搜索、成本模型。前两个在本讲，成本模型在下一讲

这像装修选方案。设计师画出几套图，这是变换。你决定看哪几套、看到什么时候为止，这是搜索。预算表告诉你哪套最省，这是成本模型。

组件 职责 讲在哪
① 变换（Transformation） 逻辑算子换成别的逻辑算子，或者换成物理算子。用来枚举候选计划 本讲
② 搜索算法（Search） 看哪些候选，下一步用哪条规则，什么时候停 本讲
③ 成本模型（Cost Model） 判断 A 计划是不是比 B 计划好 #16

铁律：变换必须保持等价

怎么变都行，结果必须和原来一模一样。17:33

SELECT * FROM t WHERE a = 1 AND b = 2;
SELECT * FROM t WHERE b = 2 AND a = 1;   -- 等价，可以互换
-- 考点：变换的铁律是语义等价。又快又错的计划，毫无意义

无论怎么变，新计划必须和原计划语义等价。

Andy 的原话大意：产出一个飞快但结果错误的计划，毫无意义。那我干脆直接返回 1 或者 null 好了。

这像翻译。译得再快，意思错了，就是废稿。

搜索空间有多大

连接顺序的搜索空间是天文数字。

  • 连接顺序选择已被证明是 NP-hard 的。
  • N 路二元连接的顺序数量是天文数字，卡塔兰数级别。

这像给一桌客人排座位。人一多，排法就多到数不过来。

现实中的分布（18:49）：

最多的查询：没有连接
第二多：    两表连接
然后是：    一条很长的尾巴，什么奇怪的东西都有
考点：连接顺序选择是 NP-hard，可现实中的查询大多连接很少

踩坑： Andy 见过的最极端案例，一条查询连接了 1500 张表。显然不是人写的。是某个仪表盘，用户点了一堆按钮生成的。

理想 vs 现实

理想的优化器，不管 SQL 写得多离谱，都能给出好计划。19:27 现实做不到。

-- 大模型吐出来的 SQL，常常绕得很远
SELECT * FROM (SELECT * FROM (SELECT * FROM t) x) y WHERE y.a = 1;
-- 理想情况下，优化器应该把它当成 SELECT * FROM t WHERE a = 1 来处理
-- 考点：LLM 时代到处是机器写的 SQL，优化器的鲁棒性格外重要

理想：用户把 SQL 写得再离谱，优化器也应该产出一个好计划。

补充：这件事在 LLM 时代格外重要。现在到处都是大模型吐出来的 SQL。

踩坑：现实是，有些事在人眼里"显而易见"，优化器就是做不到。第 11 节的演示会让你看到。

只做单查询优化

优化器一次只看一条查询，把它当成孤岛。21:24 本讲是这样，几乎所有真实系统也是这样。

SELECT sum(x) FROM t WHERE d = 'mon';   -- 查询 A
SELECT avg(x) FROM t WHERE d = 'mon';   -- 查询 B，扫的是同一批行
-- 优化器各算各的，不会想到两条共用一次扫描
-- 考点：多查询优化几乎没人做。例外是 dbt，它的查询本来就是一张 DAG

这像外卖平台一单一单派。同一栋楼的两单，也不会合成一趟。

多查询优化要识别多条查询之间的重叠，共享中间结果。除了研究界，基本没人做。因为大家写程序时，不会一次性把所有查询交出来。

补充：唯一的例外是 dbt，#02 提过。它的查询本来就组织成一张 DAG，天然适合做多查询优化。

4逻辑计划 vs 物理计划

难度 ★★★★★重要#16 物理属性由此而来，作业不考

逻辑计划说要做什么，物理计划说怎么做。20:05

逻辑：Join(A, B)              我要连接 A 和 B
物理：HashJoin(A, B)          对 A 和 B 做哈希连接
物理：SortMergeJoin(A, B)     也可以换成排序归并连接
考点：逻辑算子和物理算子不是一一对应的

逻辑计划像点菜，只说要一条鱼。物理计划是后厨决定红烧还是清蒸。

说什么 例子
逻辑算子 要做什么 "我要连接 A 和 B"
物理算子 怎么做 "对 A 和 B 做哈希连接"

踩坑：两者不是一一对应的。一个逻辑连接算子，未必只对应一个物理连接算子。有时会拆开，有时会合并。优化器有权随意重排。

还要跟踪"物理属性"

优化器还得一路记着，每个算子的输出带着什么物理属性。21:24 最典型的是排序顺序。

SELECT * FROM A JOIN B ON A.id = B.id ORDER BY A.id;
-- 选排序归并连接：输出天然按 id 有序，ORDER BY 等于白送
-- 选哈希连接：顺序全乱，上面还得再排一次
-- 考点：物理属性的典型例子是排序顺序，必须在变换中一路跟踪

查询要求输出有序。优化器就得知道，哪个算子会产出有序数据。可能是排序归并连接，可能是 ORDER BY 算子。也可能数据本来就从索引里有序地出来。

这类物理属性必须在变换过程中一路跟踪。否则你会拼出一个"逻辑正确，但满足不了 ORDER BY"的计划。#16 的 Cascades 框架，会把这件事做成一等公民。

5变换规则的基石：关系代数等价性

难度 ★★★★★重要§6 的合法性依据，直接用的是 §6

优化器敢乱改计划，是因为关系代数是被严格定义的。它比 SQL 严格得多。26:37 两个式子等价，换掉就不会错。

这像解方程。移项、合并同类项都有定理撑腰，怎么变都不会把答案变错。

选择（σ）的规则

选择算子能拆开、能重排，还能和几乎所有算子交换位置。

① 合取分解：

σ_{p1 ∧ p2 ∧ p3}(R)   ≡   σ_{p1}( σ_{p2}( σ_{p3}(R) ) )
考点：合取分解让每个谓词能独立移动。交换性的唯一例外是外连接

拆开之后，每个谓词就能独立移动了。这是后面所有下推优化的前提。

还能重排顺序。p2 更便宜、选择性更高，就先做 p2。

② 交换性：选择算子和几乎所有算子都可交换。

SELECT * FROM A LEFT JOIN B ON A.id = B.id WHERE B.x = 1;
-- 这个过滤不能随手推到 B 的扫描下面
-- 没匹配上的 A 行会补 NULL，推下去之后结果就变了

踩坑： 28:50 唯一的例外是外连接。因为 NULL 语义太微妙。一边没匹配上时，NULL 是谁产生的？

补充：顺带澄清一个概念。关系代数里根本没有外连接。它是 SQL 后来扩展出来的，所以语义才这么麻烦。本课不涉及。

表达式层面的优化

表达式也能在执行前先化简，省得每条元组都重算一遍。29:33 这和 #13 的表达式树优化 是一脉的。

WHERE x = 1 + 1          -- 常量折叠后变成 x = 2
WHERE x = 3 AND y = x    -- 传递性替换后变成 x = 3 AND y = 3
-- 每条元组都要算一遍，十亿条就是十亿遍，所以先化简

这像炒菜前先把调料兑好一碗。炒的时候直接倒，不用每盘都现配。

规则 例子 为什么值
传递性替换 x = 3 AND y = x → x = 3 AND y = 3 不再需要引用另一个变量。比较的值可以直接待在寄存器里
常量折叠 x = 1 + 1 → x = 2 别把 1+1 算十亿遍
函数提升 WHERE YEAR(col) = 2025 里的常量部分 十亿条元组，就调十亿次函数。能提前算，就提前算

连接（⋈）的规则

内连接可以随便换左右、换结合顺序。这就是调连接顺序的合法性来源。

交换律：  R ⋈ S  ≡  S ⋈ R
结合律：  (R ⋈ S) ⋈ T  ≡  R ⋈ (S ⋈ T)
考点：交换律和结合律，让"小表放外层"的调换成为合法操作

踩坑：这两条只对内连接和等值连接成立。外连接照例除外。

正是这两条，让 #12 里"小表放外层"的调换，成了合法操作。

笛卡尔积

除非查询明确写了 CROSS JOIN，否则永远不要产生笛卡尔积。

SELECT * FROM a, b WHERE a.id = b.id;   -- 写成逗号，其实是连接
SELECT * FROM a CROSS JOIN b;           -- 只有明确这么写，才真做笛卡尔积

这是一条不需要成本模型就能确定的规则。

6逻辑到逻辑的变换

难度 ★★★★★必会P3 要写优化规则，HW4 Q2 考谓词下推

逻辑到逻辑的变换"永远该做"，根本不用问成本模型。32:50

因为我们作为造数据库的人，知道这些事一定更好。

plan = SplitConjuncts(plan);        // ① 拆分合取子句
plan = PushDownPredicates(plan);    // ② 谓词下推
plan = CrossToInnerJoin(plan);      // ③ 笛卡尔积加连接谓词，变成内连接
plan = PushDownProjections(plan);   // ④ 投影下推
// 考点：必须先拆开，谓词才能各自往下推。这些变换一定更好，所以不问成本模型

这像搬家前先扔垃圾。扔了一定更省力，不用算。

完整的四步演进

例子是"找出所有出现在某张致敬专辑上的艺人"。也就是 artist ⋈ appears ⋈ album。

起点：绑定器给出的朴素计划

        [ 投影 artist.name ]
                ↑
        [ 过滤 p1 ∧ p2 ∧ p3 ]     ← 所有条件挤在一个算子里
                ↑
             [ × ]                ← 笛卡尔积
             ↗   ↖
          [ × ]   [ album ]
         ↗    ↖
   [ artist ] [ appears ]

① 拆分合取子句。按 AND 拆开，变成三个独立的过滤算子。沿着树遍历一遍就行，很容易。

② 谓词下推（Predicate Pushdown）。这就是要先拆开的原因。

把 artist.id = appears.artist_id  推到 artist × appears 的正上方
把 album.name = 'Mooshoo Tribute' 推到 album 的扫描正上方

// 考点：X 该设多少取决于硬件和数据，写死就是在猜

怎么判断索引扫描比顺序扫描好？

  • WHERE id = 123，且 id 是主键。那就走索引扫描，没悬念。
  • 但范围谓词呢？你得知道数据分布。还得知道访问索引和扫全表的相对成本。

结论：

  • 简单查询够用。也就是没有连接、只做下推的那种。
  • 一旦连接超过两张表，就崩了。你没法推理各种依赖关系。数据在计划里怎么传播，你也推不出来。

9基于成本的搜索：何时停下来

难度 ★★★★★重要成本搜索主线，HW4 和 P3 都没用到

成本优化器每走一步都问成本模型，再决定剪枝还是继续。49:34 这是两大流派的第二种。

for (auto &cand : Enumerate(ApplyRules(plan))) {
  if (Cost(cand) < Cost(best)) best = cand;   // 更好就留下
  else if (!AllowUphill()) Prune(cand);       // 更差就剪掉，也可以暂时爬坡
  if (ShouldStop()) break;                    // 什么时候停，见下一小节
}

这像在山里找最低的山谷。眼前先往上爬一段，翻过去可能是更深的谷。

踩坑：两个流派不互斥。完全可以先用规则做一遍逻辑变换。剩下的决策，再交给成本搜索。

流程：应用规则，枚举候选，每一步都问成本模型。比目前最好的差，就剪枝。也可以像梯度下降那样，允许暂时爬坡。因为翻过这个小山头，后面可能有更低的谷。

有些系统分阶段做。先优化单表子计划，再优化连接，再优化嵌套查询。有些系统一次性整体优化。

四种停止条件

搜索总得停下，停法有四种。51:34

bool ShouldStop() {
  return elapsed_ms > 500          // ① 超时
      || found_10pct_better        // ② 找到比上次好 10% 的计划
      || frontier.empty()          // ③ 穷尽，搜完了
      || rules_applied > budget;   // ④ SQL Server 的做法：数规则
}
// 考点：四种停止条件是超时、成本阈值、穷尽、数变换规则
条件 说明
① 超时 跑够 500 毫秒就停，交出目前最好的计划
② 成本阈值 "找到比上次好 10% 的计划就停"
③ 穷尽 简单查询能真的搜完。SELECT * FROM foo 秒出
④ 变换规则计数 SQL Server 的做法。数应用了多少条规则，用完就停

为什么"数规则"比"数时间"好

数规则次数，换来的是确定性。52:49 Andy 让全班猜，答案很漂亮。

CPU 空闲时：1 秒能应用 1000 条规则    → 计划 A（数字是示意）
CPU 打满时：1 秒只能应用 200 条规则   → 计划 B
改成数规则：每次都应用 500 条再停     → 永远是同一个计划
考点：数规则不受系统忙闲影响，所以更好。SQL Server 就这么做

确定性。

墙钟时间取决于硬件，也取决于系统当前有多忙。同一台机器上，CPU 可能空闲，也可能打满。两种情况下，1 秒能跑完的规则数完全不同。同一条查询会得到不同的计划。

改成数规则次数就不一样了。无论系统多忙，只要查询和输入约束一样，计划就永远一样。

这像考试按题量收卷，不按时间收卷。不管今天手快手慢，大家都答完同样多的题。

各系统的做法：

系统 停止条件
PostgreSQL / MySQL ① 超时。PostgreSQL 里压根没有"变换规则"这个概念可数。它就是一串 if-else，从头跑到尾
SQL Server ④ 数规则。配合自顶向下搜索，天然能增量计数

踩坑：无论如何，都必须保证第 ③ 条的底线。至少要走到搜索树底部一次。否则你连一个能跑的计划都没有。

什么叫"好"计划？

"好"一般指快。但优化器算的不是毫秒，而是一个合成的成本值。47:32

double Cost(Plan p) {                 // 不是毫秒，是个合成出来的分数
  return p.disk_io * w_disk + p.net_io * w_net + p.cpu * w_cpu;
}
// 想优化"云上要花多少钱"，换个目标函数就行
  • 绝大多数系统优化的是性能。人感知的性能是墙钟时间。但"这么多次 I/O 等于多少毫秒"极难建模。所以实践中用的是合成的成本值（#16）。
  • 少数系统优化的是"在云上跑这条查询要花多少钱"。换个目标函数而已。不常见，但完全可行。
  • 优化什么指标？ I/O 通常是大头。但 I/O 也分磁盘 I/O 和网络 I/O。而且磁盘和网络越来越快，CPU 常常才是瓶颈。

10访问方法的选择与 Sargable

"扫描 foo"是个逻辑算子。优化器要把它落成一种具体的物理访问方法。54:51 也就是 #13 第 7、9 节 讲的那些。

     [ 逻辑：扫描 foo ]
              │ 查目录 + 统计信息，应用变换规则

[顺序扫描] [索引扫描] [多索引扫描]

这像找东西。有目录就翻目录。没目录，就从头翻到尾，反正总能找到。

顺序扫描永远是兜底。就算没索引可用，它也总能跑。比如谓词不匹配。又比如索引是哈希索引，查询却要范围。

Sargable

谓词能被索引用上，就叫 sargable。56:10

11现场演示：+ 0 就能让优化器变傻

难度 ★★★★★了解PG 与 DuckDB 现场对比，产品细节

PostgreSQL 匹配索引时只看字面。ORDER BY 里多一个 + 0，它就认不出索引了。56:51 这是本讲最有教育意义的一段。

准备：PostgreSQL，一张 1000 万行的表。id 是主键，value 是随机整数。value 上建了 B+ 树索引。

这像门卫只认工牌上的名字。你在名字后面多写了个"+0"，人还是那个人，门卫就是不放行。

正常情况：优化器很聪明

条件和排序直接写列名时，PostgreSQL 都会用上索引。

EXPLAIN SELECT id FROM xxx WHERE value >= 123 AND value < 456;
-- → 用了 value 上的索引

EXPLAIN SELECT * FROM xxx ORDER BY value LIMIT 20;
-- → 也用了索引（数据本来就按需要的顺序排好）

加一个 + 0，全线崩溃

多一个 + 0，PostgreSQL 就放弃索引，改做全表扫描。

EXPLAIN SELECT * FROM xxx ORDER BY value + 0 LIMIT 20;
--                                       ↑
--                     value 是整数列，加 0 完全不改变任何东西
-- → PostgreSQL 放弃索引，改做全表扫描
-- 考点：PostgreSQL 对列名做字面匹配，ORDER BY 里一出现表达式就认不出索引

Andy 排除了各种可能的借口：

  • 会不会是因为列可空？Andy 重建了表，加上 NOT NULL，重新灌数据、重建索引。结果还是不用索引。
  • 跑了 ANALYZE，收集完整的统计信息（#16 讲）。结果依然不用。

真正的原因在 1:01:55：

PostgreSQL 是在对列名做字符串式的精确匹配。 ORDER BY 里一出现任何表达式，哪怕是 + 0，匹配就失败。它直接判定"这个索引用不上"。

Andy："优化器说'不是精确匹配，我做不了'。" 学生追问："用有原则的方式处理啊！"Andy 回答：对，可 PostgreSQL 就是没这么做。

但也有站得住脚的顾虑，这是 1:03:19 的课堂讨论。

ORDER BY value + 1   -- value 接近整数上限时会溢出，不能无脑改写成 ORDER BY value
ORDER BY value + 0   -- 永远不会溢出，改写一定安全

+ 1 可能整数溢出。所以严格来说，不能无脑重写。

但要是统计信息表明"没有任何值接近上限"，重写就是安全的。只是统计可能出错，所以系统选择了保守。而 + 0 根本不存在这个问题。

补充： SQL Server 处理这个毫无问题。

DuckDB 的选择更出人意料

DuckDB 既不走索引，也不只扫一遍。它做了两次顺序扫描。1:07:37 同样的表，同样的 ORDER BY value LIMIT 20。Andy 让全班投票：用索引，还是全表扫？

"你们全错了。它做了两次顺序扫描。"

DuckDB 的计划：

顺序扫描 ─→ 取 Top-20 ─┐
                       ├─→ 哈希连接（自连接找回完整行）─→ 结果
顺序扫描 ──────────────┘

考点：DuckDB 选了两次顺序扫描加一次自连接，加不加 + 0 都一样

这像去超市找一样东西。大家都以为该看货架指示牌。结果有人把两排货架飞快扫一遍，反而更快。

按 DuckDB 的成本模型，这就是更快。而且无论你加不加 + 0，它都选同一个计划。

实测：DuckDB 约 10 毫秒，PostgreSQL 接近 1 秒。

12自底向上 vs 自顶向下

难度 ★★★★★必会#25 清单列出，高层对比即可

成本搜索有两个方向。一是从表往上搭，二是从结果往下拆。1:10:41 在经典优化理论里，这就是前向链接 vs 后向链接。

1自底向上搜索：System R 的动态规划

自底向上就是从"每张表怎么读"开始，一层层往上拼连接。5:21 这部分接着 #15 第 13 节 讲完。

best[{R}]     = cheapest_scan(R)                       # 第 1 层：每张表怎么读
best[{R,S}]   = min(hash_join(R, S), merge_join(R, S)) # 第 2 层：只留最便宜的

# 考点：自顶向下从最终结果开始，代表是 Cascades

3自顶向下搜索：Cascades

难度 ★★★★★必会#25 清单列自顶向下，高层即可

Cascades 从想要的最终结果往下搜，半路发现太贵就砍掉。16:38 这叫分支限界（branch and bound）搜索。

核心机制：

一路记住"目前见过的最优完整计划的成本"
        ↓
沿某条路径往下走时，若【当前累计成本】已经 > 那个最优值
        ↓
直接砍掉这条分支，不必走到底

if (cost_so_far > best_full_plan_cost) return;  // 半路就比最优贵，直接砍
if (memo.contains(group)) return memo[group];   // 算过的子问题，直接查表
// 考点：Cascades 靠分支限界剪枝，重复子问题靠 memo 表兜底

这像网购比价。你已经见过一家很便宜的。另一家光运费就更贵，商品不用看了，直接关页面。

踩坑：代价是会重复访问同一批子问题。所以所有 Cascades 实现都依赖一张 memo 表（记忆化表）。算过成本的节点记下来，下次直接查表。

物理属性是一等公民

自顶向下一开始就把"我要按 artist_id 排序"写进搜索目标。20:59 这是它相比 System R 的关键进步。

于是搜索时可以直接判断：

考虑哈希连接？ → 不行：它不保证排序 → 【连看都不用看】，直接跳过
考虑排序归并？ → 行：满足要求，继续往下
考虑"排序算子 + 哈希连接"？
    → 排序算子能把数据变成需要的形状（这叫【强制器 Enforcer 节点】）
    → 但一算成本：排序 + 哈希 > 单个排序归并
    → 剪掉

考点：Enforcer 节点专门补上物理属性，比如排序
考点：自顶向下从一开始就带着物理属性搜，System R 只能事后补

强制器（Enforcer）节点是专门插进计划里的算子。它保证上层拿到的数据，满足某个物理属性。有了它，变换规则就能先问一句：产出的数据满足要求吗？不满足的直接跳过，不用盲目地全面展开。

强制器像快递的"加急"服务。东西本来不保证明天到，多加一道工序就能保证。值不值，还得比价。

规则优先级

变换规则可以排优先级。20:21 比如先看哈希连接，再看排序归并。这样万一搜索超时，手上至少有一个"全是哈希连接"的计划。它不一定最优，但够用。

rules = [hash_join_rule, merge_join_rule]   # 排在前面的先试
while not timed_out(): apply_next(rules)
return best_so_far     # 超时也能交卷：至少有个全是哈希连接的计划
# 考点：设优先级，是为了超时时手上也有一个能用的计划

-- 考点：成本数字不能跨系统比较，它只回答"A 计划是不是比 B 计划好"

这像两家店各自的会员积分。积分只在自己店里比大小，拿到别家去一文不值。

踩坑：它不是要预测"这条查询要跑 15 秒"。它算出的只是一个内部的相对数值。用途只有一个：回答"A 计划是不是比 B 计划好"。

MySQL 吐出的成本数字，拿到 PostgreSQL 或 Oracle 里毫无意义。两边完全是两套体系。

两类成本

物理成本算资源消耗，逻辑成本算输出大小。

物理成本 Physical Cost 逻辑成本 Logical Cost
是什么 算子消耗的资源 算子的输出大小
包含 磁盘 I/O 次数、网络包数、CPU 周期、缓存未命中、内存占用 产出多少条元组
依赖什么 依赖硬件。比如有多少 L3 缓存、CPU 多快 与物理算子无关

逻辑成本的妙处在这里（27:35）：

R ⋈ S 产出多少条元组，跟用哪种连接算法无关。排序归并、嵌套循环、哈希连接，产出的元组数完全一样。

所以逻辑成本在还没比较物理算子之前，就能拿来剪枝。

rows(R_join_S) = f(rows(R), rows(S))   # 逻辑成本：只关心吐出多少条
rows(R) = f(rows(child_of_R))          # 要知道输出，先得知道输入
# 考点：物理成本依赖硬件，逻辑成本和物理算子无关，所以能提前剪枝
# 考点：逻辑成本的难题是递归，下面估错，上面全错

逻辑成本像估一道菜能出几盘。不管用炒锅还是电饭煲，出菜量都一样。

踩坑：问题也出在这。要预测输出多少，先得知道输入进来多少。于是变成一个递归问题。第 11、12 节的灾难就从这来。

数据不是静态的

数据一直在变，今天的成本估计，一个月后可能就不准了。25:33

比如你在跑 Reddit 这种网站，插入和更新源源不断。值的分布会漂移。今天算出来的成本估计，一个月后可能面目全非。

内存里的东西    ≈  比读磁盘快 400 倍
顺序 I/O        ≈  比随机 I/O 快 4 倍

对应的参数：seq_page_cost、random_page_cost、cpu_tuple_cost …

SHOW seq_page_cost;      -- 顺序读一页的权重

SHOW cpu_tuple_cost;     -- 处理一条元组的 CPU 权重
-- 考点：默认假设内存比磁盘快 400 倍，顺序 I/O 比随机 I/O 快 4 倍
-- 考点：文档挂警告，是因为这些值因硬件而异，只是猜测

这像出厂就写死的油耗表。不管你开山路还是高速，它都按同一个数算。

踩坑：PostgreSQL 文档自己就挂着一大段警告。这些值没有好办法精确确定，因硬件而异，只是"合理的猜测"。改多了会选出糟糕的计划。

高端系统怎么做：跑微基准测试

DB2 启动时会先跑一堆微基准测试，把实测值填进成本模型。30:15

它实测这些东西：从磁盘读一个块要多久？发一个网络包要多久？CPU 多快？测完就把真实测量值填进成本模型。配置文件里的魔法常数，就用不着了。

好处：数据库搬到另一台机器，成本模型会自动跟着更新。

double disk_us = Benchmark(ReadOneBlock);    // 读一个块要多久
double net_us  = Benchmark(SendOnePacket);   // 发一个网络包要多久
cost_model.Calibrate(disk_us, net_us);       // 用实测值代替魔法常数
// 考点：DB2 和 Linux 的 BogoMIPS 是同一个思路，都是开机先跑微基准

这像搬进新家先试试厨房的火力。火大火小心里有数，再决定炖多久。

补充：有个精彩的类比（31:04）。Linux 启动时会在 /proc/cpuinfo 里算一个 BogoMIPS。它也是个微基准，给调度器估时用。同一个思路。

为什么 PostgreSQL 不改进？

一句话：PostgreSQL 的优化器太脆，没人愿意碰。学生当场问了，Andy 的回答很实在。

"难。而且在 PostgreSQL 里，没人愿意碰查询优化器。它太脆了。"

不过 Andy 也补充了一句。加 DB2 那种微基准测试，比重写整个优化器容易得多。这是个可行的改进方向。

补充：还有一层原因。DB2 和 Oracle 是分布式并行系统，必须知道网络传输要多久。它们还要感知存储分层，比如本地快盘和远程存储。PostgreSQL 根本没有这些概念，它只有表空间。

相关列统计（Correlated Statistics）

CREATE STATISTICS zip_city ON zip, city FROM address;

-- 考点：相关列统计解决"把相关列当独立"的问题
-- 考点：SQL Server 看到两列进了同一个索引，就自动建相关统计

8直方图的三种压缩方式

直方图必须压缩，否则光一列的统计就能撑爆。41:34 压缩办法有三种。

朴素直方图：为每个不同值存一个计数

朴素直方图给每个不同值存一个计数。问题是太大了。

num_values = 1_000_000_000    # 一列有十亿个值
bytes_per_count = 4           # 用 32 位整数存计数
# 光这一列的直方图，就要 4 GB 多
# 考点：朴素直方图不可行，一列就要 4 GB 多，表有一百列呢

这像给每位顾客单独记一行账。账本本身，就比仓库还大。

一列有十亿个值，用 32 位整数存计数。仅这一列的直方图，就要 4 GB 多。

而这还只是一列。表有一百列呢？

① 等宽直方图（Equi-Width）

等宽直方图让每个桶的"宽度"（值域范围）相同。

桶1: [1-3]   计数 9
桶2: [4-6]   计数 4
桶3: [7-9]   计数 15
桶4: [10-12] 计数 3
桶5: [13-15] 计数 14

幻灯片上桶 1 的柱子标 9，下面却写 Count=8。总数是 45，按 9 才对得上。

估算 age = 9：落在桶3，算 15 / 3，因为桶里有 3 个值。

等宽像按年龄段分组。每组都跨三岁，人多人少不管。

② 等深直方图（Equi-Depth）

等深直方图让每个桶的"高度"（计数）相同，宽度自适应。

桶1: [1-5]   计数 12
桶2: [6-8]   计数 12
桶3: [9-13]  计数 9
桶4: [14-15] 计数 12

估算 age = 9：落在桶3，算 9 / 5，因为桶里有 5 个值。

它被证明比等宽更好。热点值不会被一堆低频值淹没在噪声里。桶内元素少，估计更准。

est_width = 15 / 3    # 等宽：age = 9 落在 [7-9]
est_depth = 9 / 5     # 等深：age = 9 落在 [9-13]
# 考点：等宽按值域切，等深按计数切，N 偏单独照顾重击者
# 考点：等深比等宽好，因为热点值不会被低频值淹没

等深像按人数分班。每班人数一样，年龄跨度随便。

③ N 偏直方图（N-Biased / MCV + 直方图）

N 偏直方图专门照顾"重击者（heavy hitters）"。45:08 最热门的几个值单独记精确数，其余的打包粗算。

用 N−1 个桶，为【最频繁的键】各自存【精确计数】
剩下所有值统统扔进最后一个桶 R，只有粗略计数

SELECT most_common_vals, most_common_freqs, histogram_bounds
  FROM pg_stats WHERE tablename = 'enrolled';
-- 前两列是重击者的精确值和频率，最后一列管剩下的值
-- 考点：N 偏直方图解决重击者估不准的问题，PostgreSQL 的 MCV 就是它

这像排行榜。前几名单独列出票数，后面的统称"其他"。

补充：理由是：不频繁的值本来就很少被查到，估不准影响小。这就是 PostgreSQL 里 most_common_vals / most_common_freqs 的由来。

分布变了怎么办？

分布一变，就得整个重建。45:52 学生问："如果出现了新的最频繁值，是不是要整个重建？"

Andy：是的。ANALYZE 就是把直方图整个抹掉重算。

PostgreSQL 会聪明一点。它记录哪些页自上次分析以来没被改过，跳过它们，增量更新。但这会引入误差。 Andy 的说法是："不过反正本来就是近似，本来就会出错。"

补充：PostgreSQL 的直方图怎么实现的？ 就是一个数组。没什么花哨的。

9选择性估算：单谓词

难度 ★★★★★必会HW4 Q3 直接考，#25 清单要求会算

选择性估算的目标，是预测每个算子会吐出多少条元组。50:43 这个数叫基数（cardinality）。

三个基本积木：

  1. 选择条件：谓词能匹配多少条？
  2. 连接：两表连接产出多少条？
  3. 不同值估算：GROUP BY 会有多少组？

有了这三个，才能处理多连接、分组加排序的复杂计划。

SELECT * FROM people WHERE age = 9;   -- 优化器先问：这会吐出多少行？
-- 行数估错，后面选的连接算法就可能跟着错
-- 考点：age = 9、age >= 7、age != 2、AND、OR 五种选择性都要会算

这像点外卖前估人数。人数估错，点多少菜、拿几副碗筷全都跟着错。

记号

符号 含义
n_R 关系 R 的元组数
V(A, R) 属性 A 在 R 里的不同值个数
SC(A, R) 选择基数，也就是给定 A 的某个值，平均匹配多少条

选择性（selectivity）就是概率：一条元组满足这个谓词的概率。

情形 ①：等值谓词 age = 9

等值谓词的选择性，就是这个值占总数的比例。

精确直方图：

选择性 = 该值的出现次数 / 总元组数 = 4 / 45 = 0.088

等深直方图（age = 9 落在桶 [9-13]，计数 9，桶宽 5）：

选择性 ≈ 9 / 5 / 总元组数 = 1.8 / 45 ≈ 0.04
         ↑   ↑
      桶计数 桶内值的个数

考点：等值谓词要会用精确直方图和分桶直方图各算一遍

情形 ②：范围谓词 age >= 7

范围谓词就是把命中的桶加起来，切到一半的桶按比例分。56:09

桶 [1-5] 计数 12      ← 完全不要
桶 [6-8] 计数 12      ← 部分命中：7 和 8 → 12 / 3 × 2
桶 [9-13] 计数 9      ← 全要
桶 [14-15] 计数 12    ← 全要
                       ─────────
估计 = 9 + 12 + (12/3 × 2) = 29，选择性 ≈ 29 / 45 ≈ 0.64

这像按比例分披萨。一块切到一半，就默认里面每一口都一样大。

踩坑：注意那个"部分命中"的桶。只有假设桶内值均匀分布，才能这么切。

情形 ③：否定 age != 2

否定就是用 1 减去等值的选择性。

选择性(age != 2) = 1 − 选择性(age = 2)

情形 ④：多个谓词

多个谓词就回到概率论。58:14 AND 直接相乘，OR 加起来再减去重叠。

合取（AND）：sel(P1 ∧ P2) = sel(P1) × sel(P2)        ← 假设【独立】
析取（OR） ：sel(P1 ∨ P2) = sel(P1) + sel(P2) − sel(P1) × sel(P2)

考点：AND 直接相乘的前提是谓词独立，这一条马上就会出事

10三个致命假设

难度 ★★★★★必会HW4 Q3 考独立性假设会怎样出错

成本模型只能靠三个明知是错的假设撑着：均匀、连续、独立。

54:12 Andy："成本模型里有个肮脏秘密。我们没有准确的统计，也没有数据的完整视图。所以不得不做一大堆假设，否则这问题根本不可解。"

sel = bucket.count / bucket.width        # 假设 1：桶内均匀分布
rows = sum(b.count for b in hit_buckets) # 假设 2：值域连续，没有空洞
sel_and = sel_p1 * sel_p2                # 假设 3：谓词独立，最要命
# 考点：三个假设是均匀、连续、独立，各自什么时候垮掉要说得出

这像天气预报默认明天和今天差不多。大多数日子没事，碰上寒潮就全错。

# 假设 什么时候垮掉
① 均匀分布：桶内每个值出现概率相同 数据倾斜时就垮。N 偏直方图能缓解重击者，其他值只能这么假设
② 值连续：桶的值域里没有空洞 大数值范围里很可能有大段空洞。你会数进根本不存在的元组
③ 谓词独立：可以直接相乘 最要命的一个，见下

独立性假设怎么崩的：Honda Accord 的例子

独立性假设一碰到相关的列就崩。1:01:00 这是一个 IBM 研究员多年前举的经典例子。

SELECT * FROM cars WHERE make = 'Honda' AND model = 'Accord';

按假设计算：

10 个厂商   → sel(make = 'Honda')   = 1/10
100 个车型  → sel(model = 'Accord') = 1/100
假设独立     → 1/10 × 1/100 = 0.001

但人类都知道，Accord 只有 Honda 做。

真实选择性 = 1/100 = 0.01

考点：独立假设算出 0.001，真实是 0.01，差一个数量级

这像算"会说中文"和"住在北京"同时成立的概率。两件事明显相关，直接相乘就严重低估。

踩坑：差了整整一个数量级。小数字看着无所谓？放到十亿条元组的表上，你以为有 100 万条，实际有 1000 万条。这足以让优化器选错算法。

SQL Server 的补丁：指数退避

SQL Server 从 2014 年起，给后面的谓词一个比一个打折。59:42

多个 AND 谓词进来

按【各自独立的选择性】排序，最有选择性的排最前
        ↓
第 1 个谓词：全额计入
第 2 个谓词：打个折
第 3 个谓词：折得更狠（指数衰减）
        ↓
结果不会是 0.001，但也不会离谱到差一个数量级

preds.sort(key=selectivity)            # 最有选择性的排最前
est = selectivity(preds[0])            # 第 1 个：全额计入
for i, p in enumerate(preds[1:], 1):
    est *= discount(selectivity(p), i) # 越往后折得越狠
# 考点：SQL Server 用指数退避缓解独立性假设，Andy 不确定它有没有统计学保证

又一个假设：包含原则（Containment Principle）

为了能写出公式，只好再加一个假设。

假设：内表的键【总能】在外表的键里找到匹配。

考点：必须这么假设，否则公式写不出来
考点：N 对 M 的连接会让它彻底失效

踩坑：为什么必须这么假设？一旦考虑"可能匹配不上"，公式就写不出来了。又一次拿准确度换可解性。

公式

先算笛卡尔积，再除以两边不同值个数的较大者。

                    n_R × n_S
estSize(R ⋈ S) = ─────────────────────
                  max( V(A,R), V(A,S) )

def est_join_size(n_R, n_S, V_A_R, V_A_S):
    return n_R * n_S / max(V_A_R, V_A_S)   # PostgreSQL 用的基本就是这个
# 考点：分子是笛卡尔积的大小，分母取两边不同值个数的较大者
# 考点：能真正解决连接基数估算的只有采样

这像算两个班里有几对同一天生日的。先把人数相乘，再除以生日的种类数。

踩坑：学生追问（1:05:57）："N 对 M 时，包含原则怎么处理？"Andy：它处理不了。它的价值只是让公式能写出来。

能真正解决这个问题的只有采样。因为你可以直接在样本上把连接跑一遍。基于直方图或 sketch，就只能到这一步。PostgreSQL 用的基本就是这个公式。

研究文献的一致结论

所有系统都在低估连接的输出，而且连接越多，低估越狠。

由于这些假设，所有数据库系统都在【低估】连接的输出大小。而且连接越多，低估得越厉害。

为什么低估比高估更糟（1:09:59）：

以为只有 10 条元组上来  →  选【嵌套循环连接】（内存里超快，见 #12）
实际上来了 100 万条      →  用最慢的算法处理最大的数据

考点：低估更要命，因为会用最慢的算法处理最大的数据

反过来高估呢？（1:13:26）

  • 该用嵌套循环时，选了哈希连接。
  • 哈希表分配得比实际需要大得多，浪费内存。

低估像派一辆小轿车去接一个旅行团。高估像开大巴去接一个人，浪费，但人能接到。

踩坑：低估还有个额外后果。哈希表建小了，跑到一半得停下来整个搬家。 PostgreSQL 就有这问题。

13自适应查询处理

难度 ★★★★★了解讲义说是进阶课内容，高层了解即可

自适应查询处理，就是跑到一半发现估错了，就换计划。1:09:59 学生自然会问：为什么不能跑到一半，发现不对就换？

}
// 考点：AQP 分两层，细粒度中途换算子，粗粒度整个重新规划

这像导航发现前面堵车，中途给你改路线。

① 细粒度：中途换算子

细粒度就是在计划里埋钩子，行数一超阈值，就当场换算子。

优化器在计划里埋钩子：
  "我预期这里上来 10 条元组，所以选了嵌套循环连接"
        ↓ 运行时
  实际上来超过阈值 → 停下，丢掉已做的工作，切换成哈希连接

考点：细粒度只换一个算子，SQL Server 和 Snowflake 能做

谁能做：SQL Server、Snowflake，后者用在 GROUP BY 之类。只有高端系统才有，而且很罕见。

② 粗粒度：整个重新规划

粗粒度是整条查询作废，带着真实情况回优化器重来。

钩子发现"我的估计错得离谱"
        ↓
中止查询，扔掉全部结果
        ↓
回到优化器："你估错了，这是我看到的真实情况"
        ↓
重新生成计划，重跑

考点：粗粒度要在底部就发现问题，阈值必须是动态的
考点：Andy 觉得粗粒度版本没人真做

合理性：假设当前计划要跑一小时。再花 20 秒重新优化，换来一半的时间，那就划算。

这像做菜做到一半发现菜谱错了，干脆倒掉重做。越早发现，损失越小。

踩坑：两个关键前提。

  1. 要在【底部】就发现问题，不能等到顶上。跑了 59 分钟才放弃，就毫无意义了。
  2. 阈值必须是动态的。它取决于你在计划树的哪一层、算子是什么、数据规模多大。

"100 MB 的表谁在乎。PB 级别就要命了。"
