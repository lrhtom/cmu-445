2遗留问题一：MVCC + 2PL

难度 ★★★★★重要补 #20 §7，作业和清单都没列

MVCC + 2PL 里读不加锁，排他锁只管一件事。17:39 这是 Piazza 上的提问，Andy 重新讲了一遍。

T1(ts=1)  R(A) → 读 A₀
T1        W(A) → 拿 A 的【排他锁】，建 A₁，A₀.end = 1
T2(ts=2)  R(A) → 读 A₀，【不需要共享锁】，读者不阻塞写者
T2        W(A) → 拿不到排他锁 → 阻塞
T1        R(A) → 读到自己写的 A₁
T1        COMMIT → 事务表状态改为 committed，释放锁
T2        建 A₂

考点：元组上不取共享锁，排他锁只保证同一时刻只有一个事务建新版本

这像图书馆里的书。旧版谁都能随便翻，新版的稿子同一时间只许一个人改。

要点：

  • 元组上不取共享锁。 否则就没法"读者不阻塞写者"了。
  • 排他锁的作用只有一个。它保证同一时刻，只有一个事务能创建新版本。

这个调度其实有写偏斜

这个调度里有写偏斜，所以它不是可串行化的。20:27 Andy 当场确认了这一点。

// 要真正可串行化，还得多这一步（示意）
if (txn->WritesTo(A) && txn->ReadOldVersionOf(A))   // 要写的东西，读到的是旧版本
  Abort(txn);                                        // 杀掉这个事务
// 考点：要做到可串行化得维护依赖图，PostgreSQL 的 SSI 就这么做

T2 读到的是过去的版本，却被允许覆盖它。这就是写偏斜。

只要出现了写偏斜异常，就说明它不是可串行化的。

要做到真正可串行化，还得多一步。 先识别出"我要写的东西，我在过去读过的是另一个版本"。然后杀掉那个事务。这需要维护一张依赖图。PostgreSQL 就是这么做的，叫 SSI，也就是可串行化快照隔离。

Andy 说教材写错了

Andy 认为，教材那句"MVCC + 2PL 总是用 strict 2PL"是错的。23:20

教材：                MVCC + 2PL  =>  总是 strict 2PL
Gray 和 Reuter 的定义：并不要求 strict
PostgreSQL：          不是 strict 2PL（Andy 很确定）
SQL Server：          大概是 strong strict
// 考点：Andy 说教材错了，依据是 Jim Gray 和 Reuter 那本事务教材

教材说"MVCC + 2PL 总是用 strict 2PL"。我认为教材是错的。

我参照的是 Jim Gray 和 Reuter 那本讲事务的经典教材。 Reuter 就是造出"ACID"这个缩写的人。按这两位的定义，并不要求是 strict 的。

PostgreSQL 做 MVCC + 2PL，我很确定它不是 strict 2PL。SQL Server 大概是 strong strict。

补充：考试里会把协议、版本策略、版本链顺序全部写明。不会有歧义。

MVCC 的开销值不值？

值。因为旧版本你本来就要存。21:56 当时有学生问，维护版本的开销和收益怎么比。

// 单版本系统的 Update（示意）
undo_buffer.Save(tuple.old_value);   // 覆盖前先存旧值，不然没法回滚
tuple.value = new_value;
// 考点：单版本系统也得存旧值，所以旧版本本来就要维护

这像改文档前先另存一份。就算不用多版本，这份备份你也得留。

Andy 的关键观察：你本来就要维护旧版本。

单版本系统里，覆盖数据之前，也得把旧值存到某个 undo 缓冲区。 不然没法回滚。

踩坑：你当然可以只把旧值写进 WAL。但那样一来，它一旦被刷到磁盘，内存里就没有了。回滚时就得回去读日志再重放。 天下没有免费的午餐。

3遗留问题二：Paxos 与完整性约束

难度 ★★★★★重要补 #24 §5 的边界情况，作业和清单没列

在 Paxos 里，完整性约束必须在开始提交之前就查完。27:37 这是补上 #24 那个没讲透的问题。

// Paxos 下，领导者发起提交前就得查完约束
if (!CheckConstraints(txn)) return Abort(txn);   // 先查，确定能提交
PaxosAgreeOnOrder(txn);                           // 之后大家只对提交顺序达成一致
// 考点：2PC 每个节点独立判断，Paxos 只看多数派，所以约束要提前查完

这像先过安检再排队登机。进了队伍，就只剩谁先谁后的问题。

2PC Paxos / Raft
谁来判断"能不能提交" 每个节点独立判断。所以完整性约束可以在这里检查 只要多数派同意
后果 必须在开始提交流程之前，就把完整性约束检查完

在 Paxos 里，"能不能提交"必须是一个确定性的、已经定好的结论。

提议者或领导者发起提交时，已经确定它没违反任何约束。 剩下的事，只是让大家对提交顺序达成一致。

为什么不能事后反悔（29:43）：

这是个状态机，你在给提交排序。 如果发生脑裂，两边会各自排序。恢复后一边说"先 T1 后 T2"，另一边说"先 T2 后 T1"。不能允许这种事。所以决定必须是确定性的。

分布式系统的"肮脏秘密"

分布式系统往往根本没有单机那么全的约束，外键最先被砍。30:27

学生问："复杂约束不还是要各节点协调吗？那开销不就一样了？"

"肮脏的秘密是：分布式系统的约束，往往根本没有单机全。完整性约束和引用约束都是这样。"

外键约束通常是第一个被砍掉的。 因为检查它太贵了。

Spanner 的情况：主键、唯一键、基本的 CHECK 都有。外键大概也有。但取决于分区方式：

如果 students(id=123) 和 enrolled(student_id=123) 被分到【同一个节点】→ 检查很便宜
如果要广播出去 → 就麻烦了

考点：分布式系统的肮脏秘密是约束不全，外键最先被砍
考点：Spanner 的外键取决于分区方式
考点：全局 ASSERTION 没人支持，因为每笔事务都要向所有节点广播查询

这像连锁店查会员。档案就在本店，一查就有。要打电话问全国分店，就没人愿意查了。

补充：有些系统的做法很直接。"你要是不把分区键设成和外键一样，我就不帮你检查。"

踩坑：全局 ASSERTION 是说，每次提交都跑一遍某个查询。返回非空，就算违规。SQL 标准里有它。但在分布式环境下，没有任何系统支持。 那等于每笔事务都要向所有节点广播一次查询。

4无分支代码

难度 ★★★★★了解进阶课内容，讲义开头明说不考

无分支代码先无条件拷贝，再用算术决定留不留。36:07 这样 CPU 就不用猜分支。从这里开始是进阶课内容。

SELECT * FROM t WHERE key >= low AND key <= high;

你在 BusTub 里会写的版本

带 if 的循环会让 CPU 猜分支，猜错了就得重来。

for (auto& tuple : table) {
    if (tuple.key >= low && tuple.key <= high) {   // 分支
        out[n++] = tuple;
    }
}

这像开车到路口先猜左转还是右转。猜错了，就得倒回来重走。

问题在哪：现代超标量 CPU 遇到分支会预测，并投机执行。预测错了，就要冲刷流水线、回滚、重来。 十亿条元组，代价巨大。

无分支版本

每条都先拷进去，不满足条件就让下一条覆盖掉。

for (auto& tuple : table) {
    out[n] = tuple;                                        // 先【无条件】拷贝
    n += (tuple.key >= low ? 1 : 0) & (tuple.key <= high ? 1 : 0);
    //   不满足条件时 n 不增加 → 下一轮直接覆盖掉
}
// 考点：对人类反直觉，对 CPU 最优，因为完全没有跳转

这像流水线装盒。每个零件都先放进盒子。不合格的，下一个零件来了直接压在上面。

踩坑：这对人类极其反直觉。 "我每次都拷贝，然后再检查刚才那次该不该拷。不该的话，下一轮就把它覆盖掉。"

但对 CPU 是最优的，完全没有跳转。 循环结束时，要单独判断最后一条留不留。

实测曲线

无分支版本是一条水平线，分支版本只在选择性很低时占优。39:34 横轴是谓词的选择性。

选择性 < 5%   → 分支版本更快（分支预测器猜得准：几乎都不进 if）
选择性升高    → 分支版本急剧变差（预测频繁失败）
无分支版本    → 【一条水平线】，固定成本，与选择性无关

考点：选择性低于 5% 时分支版更快，因为预测器几乎总猜对"不进 if"

踩坑：编译器不会替你做这个变换，得你自己写。所有现代 OLAP 系统都这么写。

5SIMD 向量化

难度 ★★★★★了解进阶课内容不考；掩码流程要走一遍

SIMD 一条指令同时比一批 key。40:59 这是在无分支的基础上再上一层。

// 一次比 16 个 32 位 key（示意）
__m512i keys = _mm512_loadu_si512(col + i);
__mmask16 m = _mm512_cmpge_epi32_mask(keys, lo) & _mm512_cmple_epi32_mask(keys, hi);
// 考点：vectorized 有两层意思，SIMD 指令和批处理执行模型，两者天生一对

这像阅卷老师一眼扫过一整排答题卡，而不是一张张翻。

谓词求值

两次 SIMD 比较加一次 AND 得到掩码，再用 compress 挑出命中位置。

① 把一批 key 装进 SIMD 寄存器（AVX-512 = 512 位）
② SIMD 比较 key >= low     → 得到掩码向量 M1
③ SIMD 比较 key <= high    → 得到掩码向量 M2
④ SIMD AND：M1 & M2        → 得到最终掩码 M3
⑤ SIMD compress 指令：
     用 M3 从"偏移量数组 [0..7]"里【压缩出】所有为 1 的位置
     → 得到一个紧凑的"命中偏移量"数组
⑥ 按这些偏移量取数据，飞快

考点：compress 指令用掩码，从偏移量数组里压出命中位置
考点：这套东西出自 Marcin Żukowski 在 CWI 做的 VectorWise

补充：这正是要用向量化执行模型的原因。 有了一批元组，才能用向量化指令。

踩坑：命名确实很糟。 "用向量化指令（SIMD）"和"向量化查询处理模型（批模型）"是两件事。但它们天生一对。

补充：这套东西的出处，是 Snowflake 联合创始人 Marcin Żukowski。这是 Żukowski 在 CWI 做 VectorWise 时的核心贡献之一。VectorWise 被 Ingres 以很低的价格买走。 Żukowski 离开后，和两位来自 Oracle 的人一起创办了 Snowflake。今天所有人都这么做了。

SIMD 探测哈希表

每个槽打包 4 个 key，再配 8 位指纹，一条指令就能比完。45:07 这叫横向向量化（Horizontal Vectorization）。

哈希表的每一"行"里打包放 4 个 key + 4 个 value
        ↓ 还额外存一列【哈希指纹】
   完整哈希是 32/64 位，只留 8 位当指纹
        ↓ 探测时
① hash(key) → 落到某个槽
② 一次性拿回 4 个指纹 → SIMD 比较 8 位指纹（一条指令）
③ 指纹不匹配 → 完整 key 必然也不匹配，直接跳过
④ 指纹匹配 → 再比完整 key

考点：用指纹不直接比 key，是因为 key 可能变长，指纹永远定长
考点：更快是因为整条 64 字节缓存行反正要拉，多塞点一起比

指纹像快递单号的后几位。先对后几位，对不上就不用拆包。

踩坑：为什么用指纹，不直接比 key？因为 key 可能是变长的。 长度不齐，就没法向量化。指纹永远定长。

补充：为什么这样更快？这是课堂追问。探测哈希表本来就要拉一整条 64 字节的缓存行。 既然那 64 字节都拉过来了，就往里多塞点东西。用一条 SIMD 指令比完，比 for 循环一个个比快得多。

补充：再说 GPU（50:12）。上个十年有一批 GPU 数据库，没成气候。因为整个数据库得塞进显存。但 NVLink 和新版 PCIe 正在改变这一点。 Andy 说："我不能多讲，但明年会有一批新的 GPU 数据库出来。"原理和 SIMD 是一样的。

6选择向量与位图

难度 ★★★★★了解进阶课内容不考，只有两种表示的对比

算子之间得告诉下游"这一批里哪些还活着"。48:46 办法有选择向量和位图两种。

// 一批 8 条，第 1、4、6 条通过（示意）
uint16_t sel[] = {1, 4, 6};       // 选择向量：只记通过的位置
uint8_t  bitmap = 0b01010010;     // 位图：每条元组一位
// 考点：选择向量传定长偏移量，位图每条元组一个 0 或 1

选择向量像点名册上只写到场的学号。位图像每人名字后面打个勾或叉。

方案 做什么
选择向量（Selection Vector） 传一组定长偏移量，指向输入向量里通过了的那些位置
位图（Bitmap） 每条元组一个 0 或 1

稀疏问题

一批里只活下来一条，是直接往上传，还是攒满再传？各系统选法不同。

收到 1024 条，只有 1 条通过
        ↓ 两种选择
① 直接往上传一个稀疏批（1024 个槽只有 1 个有效）
② 攒一个暂存缓冲区，等下面再送上来，攒满了再传一个【密集】批

考点：稀疏批要么直接传，要么攒满成密集批再传

这像公交车只坐了一个人。是直接发车，还是等坐满再走。

各系统做法不同，各有取舍。 这呼应了 #13 那个没细讲的设计难题。

7代码生成与 JIT 编译

8预编译原语：现在的正确答案

现在的正确答案，是把所有操作提前编译成原语。运行时再把它们串起来。56:28 这条路 VectorWise 提出、Snowflake 发扬、Photon 采用。

// 运行时按查询挑原语，用函数指针串起来，不需要 JIT
// 考点：预编译原语的核心是提前编译好，运行时串起来

这像乐高积木。积木块出厂就做好了，拼法现场再定。

核心思路：把所有可能的操作提前编译好，放进二进制里。运行时把它们串起来。

在源码里用模板自动生成一大堆原语：
   int 列 == int 常量
   int 列 <  int 常量
   string 列 == string 常量
   两个 int 列相等
   ……
        ↓ 编译进二进制
运行时：根据查询把这些积木【用函数指针串起来】
        不需要 JIT

组合方式

前一个原语输出位置向量，后一个原语只处理这些位置。

WHERE str_col = 'ABC' AND int_col = 4

[原语：string 列 == 常量]  →  输出【位置向量】
              ↓ 位置向量作为输入传给下一个
[原语：int 列 == 常量]     →  只处理位置向量里的那些行
              ↓
           最终结果

考点：组合是有限的，因为数据类型和操作就那么几种
考点：跳转开销被一批元组摊薄了，一次一条元组就不成立
考点：最大好处是可调试，Andy 的结论是这才是正确方式，而不是 JIT

踩坑："组合的排列不是无穷多吗？"实际上是有限的。 数据类型就那么几种。操作也就那么几种，比如等于、小于、列比列。

踩坑："函数跳转的开销呢？"这是课堂追问。Andy 答："因为你处理的是一批元组，跳转开销被摊薄了。"如果一次只处理一条元组，这招就不成立。 这也是 Snowflake 那位联合创始人想通的关键点。

补充：最大的好处是可调试。 某个原语有 bug 崩了，你可以直接上 GDB 走一遍，复现它。 JIT 就不行。

Andy 的结论："当前的研究结论是：这才是造系统的正确方式。而不是 JIT 编译。"

问题一：三种"等价"写法，结果不同

③ SELECT a FROM R WHERE NOT EXISTS (SELECT * FROM S WHERE S.a = R.a);
-- 考点：S 里有 NULL 时，三种写法给出三个不同的答案

问题三：NULL 造成的"假阳性"

NULL 会让 SQL 言之凿凿地给出一个已知为假的答案。这叫假阳性。

-- 订单表 orders，付款表 payments
-- 查：哪些订单还没付款？
SELECT * FROM orders o
 WHERE NOT EXISTS (SELECT * FROM payments p WHERE p.order_id = o.id);
-- 考点：这类我们已知为假的答案，叫假阳性

这像收据上的单号糊了。你不知道是哪单付的，就硬说两单都没付。

数据库里明明有两笔付款。SQL 却告诉你，"订单 2 和订单 3 都没付款"。

我们凭直觉知道这是错的。 其中至少有一个很可能已经付了，只是我们不知道是哪个。

SQL 却言之凿凿地说，两个都没付。

"于是你跑去追客户：'你没付款。'客户说：'我付了。'然后这个客户再也不回来了。"

这叫假阳性，也就是我们已知为假的答案。

一个著名的都市传说：主角是一位姓 Null 的人。在那个世界里，什么都要进数据库，字段都设成 NOT NULL。这位几乎寸步难行。

而且后果可以很严重。 讲者引用了一则 BBC 报道的标题。报道讲的是，数据不完整导致儿童心脏手术被叫停。

问题四：标准到底有多"标准"

哪怕只用最基础的 SQL，各系统也有约 2% 的查询行为不一致。

有些只是无伤大雅的语法差异，但有些是严重问题。

1成本公式速查

难度 ★★★★★必会#25 清单要求会算成本，HW4 Q1 Q3 直接套公式

统一记号：

  • M = 表 R 的页数，m = R 的元组数。
  • N = 表 S 的页数，n = S 的元组数。
  • B = 可用缓冲页数。

排序（#11）

外部归并排序的总 I/O，就是遍数乘以 2N。每一遍都要把 N 页完整读一遍，再写一遍。

遍数   = 1 + ⌈ log_(B−1) ⌈N / B⌉ ⌉
总 I/O = 2N × 遍数

多给内存，减少的是【遍数】，不是每趟的 I/O 量。

验算：N=108、B=5。

第 0 遍：⌈108 / 5⌉ = 22 个 run
遍数   = 1 + ⌈log₄ 22⌉ = 4 趟
总 I/O = 2 × 108 × 4 = 864 次 I/O
// 考点：B 越大，对数的底越大，遍数就越少

连接（#12）

Grace 哈希是默认最优。朴素嵌套循环要跑 1.3 小时，别用。

算法 成本 算例（M=1000, m=100k, N=500, n=40k, B=102, 0.1ms/IO）
朴素嵌套循环 M + (m × N) 50,001,000 → 1.3 小时，别用
块嵌套循环 M + (⌈M/(B−2)⌉ × N) 6,000 → 600 ms
块嵌套循环（全内存） M + N 1,500 → 150 ms
索引嵌套循环 M + (m × C) C 写不出来
排序归并 排序R + 排序S + (M + N) 7,500 → 750 ms
Grace 哈希 3 × (M + N) 4,500 → 450 ms，默认最优 
块嵌套循环：1000 + ⌈1000 / 100⌉ × 500 = 6000
Grace 哈希：3 × (1000 + 500) = 4500
// 考点：B−2 页装外表，剩下 1 页读内表，1 页写输出
// 考点：全内存版要求缓冲池装得下整张外表
// 考点：C 取决于用的是什么索引，所以写不出具体值

选择性估算（#16）

选择性就是一个谓词能留下几成元组。

等值（精确直方图）：sel = 该值出现次数 / 总元组数
等值（等宽直方图）：sel ≈ (桶计数 / 桶内值个数) / 总元组数
否定：            sel(A ≠ v) = 1 − sel(A = v)
合取：            sel(P1 ∧ P2) = sel(P1) × sel(P2)        假设独立
析取：            sel(P1 ∨ P2) = sel(P1) + sel(P2) − 两者乘积

连接基数：estSize(R ⋈ S) = (n_R × n_S) / max( V(A,R), V(A,S) )

踩坑：这里有三个明知是错的假设：均匀分布、值连续、谓词独立。所以所有系统都在【低估】。连接越多，错得越离谱。

SELECT * FROM cars WHERE make = 'Honda' AND model = 'Accord';
-- #16 的例子：按独立假设，1/10 × 1/100 = 0.001
-- 可 Accord 只有 Honda 做，真实选择性是 1/100
-- 考点：独立假设一相乘，基数就被估小了

2易混淆概念对照

难度 ★★★★★必会#25 清单列的 Steal / Force、2PL 等都在这

① Lock vs Latch（#10 / #18）

Lock 护的是数据库里的逻辑内容，Latch 护的是内存里的数据结构。

Lock（锁） Latch（闩）
保护 逻辑内容（元组/表/库） 内存数据结构
正确性 逻辑正确性 物理正确性
持有 整个事务 纳秒/微秒
模式 S / X / IS / IX / SIX Read / Write
死锁 系统检测，系统解除 系统不管，靠编码纪律（no-wait 自杀重试）
元数据 集中式锁管理器 分散嵌在结构里
回滚 系统自动 worker 自己 
latch.lock();                 // Latch：护住内存里的结构
node->Insert(key, value);     // 纳秒到微秒，干完就放
latch.unlock();
lock_mgr.Lock(txn, rid, X);   // Lock：护住一条元组，持到事务结束
// 考点：Lock 的死锁系统会查，Latch 的死锁只能靠自己写对

踩坑：操作系统圈的人，把 latch 叫作 lock。看 OS 资料时别搞混。

② Pin vs Latch（P1）

Pin 管这页能不能被换出去，Latch 管这页能不能被同时读写。

Pin Latch
"别把这页换出去" "别在我读写时改它"
计数器，可多人持有 读写互斥 
auto guard = bpm->ReadPage(page_id);  // pin 计数加一，再加读 latch
// 别的线程也能同时 pin 这一页，计数接着往上加
// 考点：pin 是计数器，latch 是读写互斥

踩坑：改 dirty flag 需要 pin，不需要写 latch。

③ 页表 vs 页目录（#03 / #04）

页表告诉你页在内存哪一帧，页目录告诉你页在磁盘哪里。

页表 Page Table 页目录 Page Directory
page_id → frame_id page_id → 磁盘位置
内存，不持久化 磁盘，必须持久化

页表像手边的便利贴，重启就扔。页目录像档案柜里的总账，必须存在磁盘上。

④ 逻辑正确 vs 物理正确（#10）

逻辑正确看数据对不对，物理正确看指针对不对。

逻辑正确性 物理正确性
"我该看到的数据看到了吗" "指针指向的是我期望的地方吗，会不会 segfault"
#17–#20 用 Lock #10 用 Latch

⑤ 物理成本 vs 逻辑成本（#16）

逻辑成本只数输出多少条元组，跟选哪个物理算子无关。

物理成本 逻辑成本
I/O、CPU、网络、内存 输出多少条元组
依赖硬件 与物理算子无关，所以可以提前剪枝

⑥ 早期物化 vs 晚期物化（#11 / #12）

早期物化一路传完整元组，晚期物化只传 RecordID 和必要的列。

早期物化 晚期物化
传完整元组 传 RecordID + 必要列
行存 列存
不用回表 要回表，但不搬要扔掉的列 
SELECT r.name FROM r JOIN s ON r.id = s.id;
-- 早期物化：连接时就带着 r 的整行往上传
-- 晚期物化：只带 RecordID 和 id，最后按 RecordID 回表取 name
-- 考点：行存配早期物化，列存配晚期物化

⑦ 冲突可串行化 vs 视图可串行化（#17）

真实系统只做冲突可串行化。视图可串行化，没有系统能做。

冲突可串行化 视图可串行化
只看读写冲突（依赖图无环） 要懂应用语义
所有真实系统用这个 没有系统能做 
所有调度 ⊃ 视图可串行化 ⊃ 冲突可串行化 ⊃ Strong Strict 2PL ⊃ 串行调度

左边的集合包含右边的。越往右，允许的调度越少。

⑧ 2PL 的三个变体（#18）

三个变体只差在收缩期怎么放锁。真实系统用的是 Strong Strict 2PL。

收缩期 级联中止
2PL 可逐步释放 有
Strict 2PL 只放 S 锁，X 锁持到事务结束 没有
Strong Strict 2PL 全部持到提交 没有 
T1: X-LOCK(A)  W(A)  UNLOCK(A)  ...  ABORT
T2:                         R(A)     // 读到了 T1 没提交的值
// 考点：普通 2PL 提前放锁，T1 一中止，T2 也得跟着中止

⑨ 悲观 vs 乐观（#18 / #19）

2PL 申请锁那一刻就发现冲突，OCC 要到提交时才发现。

悲观像先订会议室再开会。乐观像直接进去开，散会时发现撞了就重开。

2PL（悲观） OCC（乐观）
假设一定冲突 假设很少冲突
申请锁那一刻就发现冲突 提交时才发现，前面全白干
中高竞争更好 低竞争、只读为主时更好
IBM System R, 1976 CMU, 1981

⑩ STEAL / FORCE（#21）

选 STEAL 就要 undo，选 NO-FORCE 就要 redo。

问什么 后果
STEAL 能不能把未提交的脏页写盘 选 STEAL，就需要 undo
FORCE 提交前必须刷完所有脏页吗 选 NO-FORCE，就需要 redo 
NO-STEAL + FORCE   → 影子分页：恢复最快，运行最慢
STEAL + NO-FORCE   → WAL：运行最快，恢复最慢（所有系统的选择）

STEAL 让没提交的改动先上了盘。事务一中止，就得 undo 改回去。NO-FORCE 让提交了的改动还留在内存。一崩溃，就得 redo 补回来。

⑪ 五个 LSN（#22）

刷脏页之前，先比两个 LSN。

名字 位置 含义
flushedLSN 内存（全局） 已刷盘的最大 LSN
pageLSN 页头 最后一次改这页的 LSN
recLSN 内存（DPT） 自上次刷盘以来第一次改这页的 LSN
lastLSN 内存（ATT） 某事务最近一条记录
MasterRecord 磁盘 最后一次成功检查点的起点

淘汰判据：pageLSN <= flushedLSN 才能刷盘。

bool CanFlush(Page *page) {
  return page->pageLSN <= flushedLSN;  // 改这页的日志都已落盘
}
// 考点：先写日志，再写数据页，这就是预写日志

⑫ Shared-Nothing vs Shared-Disk（#23）

云时代的主流是 Shared-Disk。扩容只改目录，不用搬数据。

Shared-Nothing Shared-Disk
磁盘也是本地的 磁盘全局共享（S3）
性能最好 要走网络取数据
扩容要搬数据 扩容只改目录
1980s–2010s 主流 云时代主流

⑬ 2PC vs Paxos（#24）

2PC 要全票通过，Paxos 和 Raft 只要多数派。

2PC 像全班一致同意才出游，一个人请假就卡住。

2PC Paxos / Raft

隔离级别（#19）

你设的隔离级别，不一定是数据库真给你的。

级别 脏读 不可重复读 幻读
SERIALIZABLE 不会 不会 不会
REPEATABLE READ 不会 不会 可能
READ COMMITTED 不会 可能 可能
READ UNCOMMITTED 可能 可能 可能

表里"不会"指这种异常不会出现，"可能"指可能出现。

默认级别：SQL Server / Oracle / PostgreSQL 都是 READ COMMITTED。MySQL 是 REPEATABLE READ，四者中最高。

SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;      -- Oracle：给你更低的级别
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;  -- PostgreSQL：给你 READ COMMITTED
-- 考点：Oracle 往下撒谎，PostgreSQL 往上撒谎

踩坑：Oracle 会往下撒谎。你要 SERIALIZABLE，它给你更低的。PostgreSQL 会往上撒谎。你要 READ UNCOMMITTED，它给你 READ COMMITTED。

系统的"招牌做法"

每个系统只记最有辨识度的几条。

系统 特征
PostgreSQL 进程模型。追加式 MVCC（Andy 公开批评）。优化器里 if-else 一大堆。13 表以上改用遗传算法。ORDER BY value+0 就放弃索引
MySQL 默认 REPEATABLE READ（四大里最高）。增量式 MVCC + 二级索引存主键。2019 年才有哈希连接，至今没有排序归并。不做查询内并行
Oracle 要 SERIALIZABLE，给你更低的。1980s 有个"语义优化器"营销故事。2014 起支持多线程，但 Linux / UNIX 上默认仍是进程
SQL Server 最好的自顶向下优化器（Cascades）。约 500 条变换规则。唯一用采样的。数变换规则次数，不看时间
DuckDB 列存 + 向量化 + 推模型。批大小 1024。优化器抄的是 HyPer，不是 Umbra。CAST(4.8 AS INT) = 5
HyPer / Umbra / CedarDB 最好的自底向上优化器。两段式 JIT：汇编先跑，后台 LLVM 编好再热替换。唯一用精确封锁的
Snowflake 战略性选择 shared-disk：工程投在计算上，存储交给 S3。预编译原语
ClickHouse 24 种哈希表实现。part 之间平级，不是 LSM 那种层级。稀疏主键索引 + granule（8192 行）。优化器较弱
Yellowbrick 自写内核驱动，自研 UDP 协议，DPDK 内核旁路。启动后再也不和 OS 说话
Photon (Databricks) C++ 运行时，用 JNI 接进 JVM。预编译原语战胜了 JIT
Spanner 少数支持严格可串行化 / 外部一致性的系统。用原子钟
SQLite 单写者多读者。2010 前用回滚日志（影子分页变体）。官方承诺支持到 2050（课上说 2035）
LMDB 和 Andy 完全相反：既爱 mmap，又爱影子分页

PostgreSQL 放弃索引那条，是 #15 的现场演示：

EXPLAIN SELECT * FROM xxx ORDER BY value LIMIT 20;      -- 走索引
EXPLAIN SELECT * FROM xxx ORDER BY value + 0 LIMIT 20;  -- 放弃索引，全表扫

三个"肮脏的秘密"

  1. "所有人的查询优化器都很烂。问题只在于你比别人烂多少。"（#16）

    技术含义：优化器靠三个明知是错的假设（均匀、连续、独立）。所以所有系统都在低估连接基数。连接越多，错得越离谱。

  2. "绝大多数数据库默认根本不给你可串行化。"（#19）

    原因：开了会很慢。用户会觉得"这数据库真烂"，然后换掉。

  3. "同步提交在多数系统里默认是关的。"（#21。这句是课上口误，PostgreSQL、MySQL 实际默认都开）

    后果：一旦关掉它，哪怕用着 WAL，也会出现一个窗口。窗口内会丢已"提交"的数据。
