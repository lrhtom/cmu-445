1我们造的数据库还差什么

难度 ★★★★★重要引出事务这条主线，读懂就行

到这里，你造的数据库已经能端到端跑 SQL 了，但还不能上生产。2:03 因为它不安全，还差两样东西。

  1. 崩溃之后，怎么保证不丢数据？
  2. 两条查询同时更新同一个东西，怎么办？
UPDATE account SET balance = balance - 25 WHERE id = 'A';
-- 问题 1：这条写到一半机器崩了，回来以后数据还对吗？
-- 问题 2：室友同一时刻也在跑这条，谁的结果算数？
-- 考点：还差的两样是崩溃恢复和并发控制

这像一辆车已经能开了，但还没装刹车和安全带。平时开着没事，一出事就要命。

为什么这两讲不出现在那张分层图里

因为并发控制和恢复不是某一层，它们横穿所有层。2:43

if (frame->is_dirty_) {
  disk_->WritePage(frame->page_id_, frame->data_);  // 缓冲池只管脏不脏
}  // 它不知道这页上的改动属于哪个事务，那个事务提交了没有
// 考点：并发控制和恢复横穿所有层，所以不在分层图里

这像大楼的消防系统。它不属于哪一层，每一层都得有。

补充：举个立刻能懂的例子。你在 Project 1 写的缓冲池，完全不知道事务的存在。淘汰算法只看"这页脏不脏"，脏了就写回磁盘。

踩坑：接下来你会发现，还有另一种"安全"。这一页现在到底能不能写回去？一次更新如果跨了两页，只写了一页就崩了。你回来时，手里就是撕裂的写（torn write）。

2两个要命的场景

难度 ★★★★★重要转账例子只是动机，ACID 各节都回到它

转账这种多步操作，最怕中途崩溃和两个人同时改。5:08 用一个银行转账应用来看。应用代码用 Python、Java 或随便什么写：

① 读 A 的余额       → 得到 $100
② 检查够不够 $25    → 够
③ 把 $25 转给别人
④ 算出新余额 $75
⑤ 把 $75 写回数据库

这像两个人拿同一张银行卡，在两台 ATM 上同时取钱。

场景一：写回之前崩了

钱已经转出去了，余额却没扣，这就是写回之前崩溃。

①②③④ 做完：钱已经转出去了
        【崩溃】
⑤ 没做：A 的账户还是 $100

A 的账户里现在应该是多少？对方账户里应该是多少？

场景二：你和室友同时转账（共享账户）

两个人同时读到 $100，各自写回 $75，一笔扣款就丢了。

你：  读 $100 → 够 → 转 $25 → 算出 $75 → 写 $75
室友：读 $100 → 够 → 转 $25 → 算出 $75 → 写 $75
                                   ↓
                        数据库里是 $75
                        但一共转出去了 $50，应该是 $50！

考点：两个失败场景是写回前崩溃、两人同时转账互相覆盖

互相覆盖，钱凭空多出来了。

踩坑：重要澄清（14:23）。事务执行中途，数据库处于不一致状态是可以的。上面第 ③ 步到第 ⑤ 步之间，系统里确实凭空多了 $25。只要它不在提交或中止之后残留下来，就没问题。我们没法把一切压成一条原子指令。

考点：中途不一致可以。提交或中止之后还残留，就不可以。

数据库管不了的东西

数据库只能回滚自己管辖范围内的读写。15:48

db.execute("UPDATE account SET balance = balance - 25 WHERE id = 'A'")
send_email("transfer done")  # 这封邮件已经发出去了
db.rollback()            # 数据库能撤回 UPDATE，撤不回邮件
# 考点：数据库只能回滚自己管辖范围内的读写，发出去的邮件收不回

这像撤回聊天消息。对方已经截图了，你撤回也没用。

我们只能回滚我们管辖范围内的读写操作。

事务中途可能发了确认邮件，甚至发射了导弹。事务回滚时，这些收不回来。现实世界会不一致，但数据库不知道，也不关心。

3一个"能用但很慢"的方案：影子分页

难度 ★★★★★重要这里只是稻草人，清单要的优劣在 #21 §4

影子分页就是先改副本，提交时一把翻指针。8:35 它安全也正确，但完全没有并发。

Andy 先抛出这个稻草人方案，让全班投票：

① 只有一个 worker，同一时刻只跑一个事务
② 事务要改数据时，不覆盖原页，而是【复制一份】
③ 所有修改都写在副本上
④ 提交时：原子地翻转页目录指针，指向新版本
⑤ 崩溃 / 失败：直接忽略并清理那些未提交的副本

Page *copy = CopyOf(page);              // 不覆盖原页，先复制一份
copy->Apply(changes);                   // 所有修改都写在副本上
page_directory.AtomicSwap(page_id, copy); // 提交：原子地翻转指针
// 考点：影子分页安全又正确，致命缺陷是完全没有并发

这像改合同。不在原件上涂改，先复印一份改好。签字那一刻，把复印件换成正本。

投票结果：全班认为它既安全又正确。确实如此。

但它性能怎么样？有两个致命问题：

问题 说明
要复制 可以只复制被改的那几页，不必整库。但仍然有开销
完全没有并发 最后那步"原子翻转"，同一时刻只能有一个事务做。所以整个数据库退化成单事务串行

这就是影子分页（Shadow Paging）

这套方案叫影子分页，IBM 发明事务时用的就是它。

IBM 在 1970 年代发明事务概念时，用的就是它。也就是 Jim Gray 那批人。Jim Gray 在 1990 年代因这套事务工作拿到了图灵奖。

IBM 后来因为性能原因抛弃了它（见第 6 节）。

补充：SQLite 有一个模式就是走影子分页的。

所以接下来两讲要解决的问题是：

怎么让多个事务同时跑，还保证正确？

4事务的形式化定义

难度 ★★★★★重要三个简化是后面的前提，不单独考

本讲把事务简化成一串对抽象对象的读和写。16:24 为了能讲清楚，做了三个简化。

简化 说明
① 抽象对象 不谈元组、页、索引，只有抽象对象 A、B、C、D。它可以是一条元组、一张表、整个库。协议照样成立
② 数据库大小固定 所有对象在事务开始前就存在，结束后还在。不考虑插入和删除，那会引出幻读
③ 只有读和写 事务就是一串对数据库对象的读写操作

这像下棋只看落子。棋子是木头的还是塑料的，规则都一样。

事务的生命周期：

BEGIN;              -- 开始（有些系统也支持 START）
   ...              -- 一串 READ / WRITE
COMMIT;             -- 保存全部修改
-- 或者
ROLLBACK / ABORT;   -- 撤销全部修改（两个词是一回事）
-- 考点：三个简化是抽象对象、大小固定、只有读写
-- 考点：大小固定这一条，把幻读排除在外了

每条 SQL 其实都是一个事务

单条 SQL 也是事务，数据库偷偷在外面包了 BEGIN 和 COMMIT。23:12 学生问"单条语句也算事务吗"：

算。你在 PostgreSQL 里敲一条查询，它隐式地在外面包了 BEGIN / COMMIT。这叫 autocommit。

你可以关掉它。那样连着写好几条 UPDATE 都不用 BEGIN，但最后必须自己 COMMIT 或 ROLLBACK。

UPDATE account SET balance = 75 WHERE id = 'A';
-- 实际执行的是：BEGIN; UPDATE ...; COMMIT;
-- 考点：每条单独的 SQL 都是事务，这个机制叫 autocommit

这像寄信总要装信封。你没看见，邮局替你装好了。

5ACID

难度 ★★★★★必会复习清单明列四个字母的含义

ACID 是事务的四条保证，本讲的重点是 I。18:23

字母 名称 含义 难度
A 原子性 Atomicity 事务的操作要么全做，要么全不做。不允许"半个事务" 好懂
C 一致性 Consistency 数据库本来是一致的，事务做的事也是一致的。那提交后仍然一致 有点怪
I 隔离性 Isolation 事务执行时，看起来像是系统里只有它一个 本讲重点
D 持久性 Durability 提交之后，机器崩了、OS 挂了，改动也还在 好懂 
BEGIN;
UPDATE account SET balance = balance - 25 WHERE id = 'A';  -- A：两条要么都成，要么都不成
UPDATE account SET balance = balance + 25 WHERE id = 'B';  -- I：别人看不到这半截状态
COMMIT;                                                    -- D：提交后崩了也还在
-- 考点：C 是被硬塞进缩写的，为了读起来像 ACID 而不是 AID

ACID 像银行柜台的四条规矩。要么办完，要么不办，账不能做错。看起来一次只接待一位，办完的单子要存档。

"ACID"这个词是怎么来的

C 是被硬塞进缩写里的，只为读起来像 ACID 而不是 AID。21:12 Andy 讲了个段子：

1980 年代造出这个缩写的，是德国人 Theo Härder。Härder 和 Andreas Reuter 合写了那篇经典论文。Härder 其实是硬把 Consistency 塞进去的。只为让它读起来像 "ACID"，而不是 "AID"。

据说 Härder 这么做，还为了跟自己太太开个玩笑。太太不爱吃甜食，所以 Härder 管太太叫"acid woman（酸性女士）"。

Andy 补充："我没见过本人，故事听来的。"

6A：原子性：日志 vs 影子分页

难度 ★★★★★重要#21 #22 的预告，这里先知道两种实现

原子性就是事务只有两种结局：全部生效，或者全部撤销。21:49 提交就是全部生效。中止 / 回滚就是全部撤销，像没跑过一样。

BEGIN;
UPDATE account SET balance = 75 WHERE id = 'A';
ROLLBACK;   -- A 的余额回到原样，就像这条 UPDATE 从没跑过
-- 考点：要么全做，要么全不做，不存在半个事务

这像游戏存档。要么打通这关存下来，要么读档回到关卡开头。

谁能发起回滚？

应用和数据库两方都可以发起回滚。

  1. 应用主动："我不喜欢现在的结果，中止。"
  2. 数据库强制："我不喜欢你在干什么，我把你中止并回滚。"
try:
    run_transfer(db)
except TransactionAborted:    # 数据库可能主动把你踢掉
    retry_or_give_up()        # 重不重试，是应用自己的事
# 考点：回滚可以由应用或数据库发起，应用代码必须能接住中止

踩坑：你的应用代码必须能处理"事务被中止"这个异常。要不要重试，是你自己的事。

实现方式一：日志（Logging） 主流

日志就是一本账，按顺序记下事务对数据库做的每一个操作。24:34

踩坑："log"这个词在数据库里被用滥了。调试日志、#05 的 LSM……都叫 log。这里说的是账本。

日志里记什么：

用途
Redo 信息 怎么重新应用这个改动
Undo 信息 怎么撤销这个改动

两者都需要。 Undo 日志要在内存里边跑边维护。

struct LogRecord {
  txn_id_t txn_id;  page_id_t page_id;
  Bytes undo;   // 改之前的样子，回滚时用
  Bytes redo;   // 改之后的样子，重放时用
};  // 考点：redo 重新应用改动，undo 撤销改动，两者都要

日志像记账本。每笔都写清"原来多少、改成多少"。想往前翻、往后翻都行。

预写日志（Write-Ahead Logging）的核心排序规则

脏页刷盘之前，让它变脏的那条日志必须【先】落盘。25:52 就这一条简单的排序规则，保证了崩溃后能正确恢复。

void FlushPage(Page *page) {
  log->FlushRecordsThatDirtied(page);  // 先刷让这页变脏的日志
  disk->WritePage(page);               // 再刷数据页，顺序不能反
}  // 考点：WAL 的核心规则就是日志先落盘，数据页后落盘

补充：Andy 的比喻：日志就是飞机上的黑匣子。它记录了坠毁前发生的一切。崩溃回来之后翻开它，就知道当时在干什么。然后把数据库放回正确状态。

日志里记"什么"？物理 vs 逻辑

日志可以记字节级的改动，也可以记查询本身。26:24 学生问是记快照还是记改动，Andy：都可以。

方式 记什么 恢复时 权衡
物理日志 / 物理逻辑日志 字节级的 diff，像 git 的 diff 重放 diff 恢复快
逻辑日志 查询本身 重新执行这条查询 原来跑一小时，恢复时再跑一小时。但对很快的操作反而更省 
physical: page=7 offset=120 old=100 new=75            -- 示意：直接记字节怎么改
logical:  UPDATE account SET balance = 75 WHERE id = 'A'  -- 记查询本身
-- 考点：物理日志恢复快，逻辑日志要把查询重跑一遍

物理日志像记下"哪一页哪个字改成了什么"。逻辑日志像只记"把这段改通顺"，恢复时得重新改一遍。

补充：关键洞察：日志是有序的。只要按原样重放同一顺序，就保证回到正确的数据库状态。

补充：日志还有另一个用途。金融机构要把每笔交易的日志保留七年，以备监管审计。

实现方式二：影子分页：已被淘汰

就是第 3 节那个方案，现在已经被淘汰了。29:53

两者的性能对比（很重要）

日志平时快、恢复慢，影子分页平时慢、恢复快。30:37 要分清这两种性能。

日常运行时 崩溃恢复时
预写日志 快。只是往日志尾部顺序追加 慢。要重放日志，最坏可能几小时甚至几天
影子分页 慢。要复制页、更新指针 极快。忽略所有影子页，瞬间就是正确状态 
# 总代价 = 日常开销 × 很多次 + 恢复开销 × 很少几次
wal_cost    = cheap  * many + slow  * few     # 预写日志
shadow_cost = costly * many + instant * few   # 影子分页
# 考点：数据库不会经常崩，日常快的预写日志赢

这像买保险。天天交高额保费，只为偶尔出事时少等一会儿。多数人算下来不划算。

补充：绝大多数场景选预写日志。因为"数据库不会经常崩"，日常性能才是主要矛盾。

那个选了影子分页的奇葩案例

天天崩溃的系统，反而该选影子分页。31:20 Andy 讲了个故事：

1970 年代，波多黎各的电力公司造了一个数据库。它用来记录用户用电量。

当地电力基础设施太差，一天要停电好几次。数据库天天崩。

电力公司承受不起"每次停电后等一小时恢复"。何况可能刚起来又崩。

所以电力公司选了影子分页：牺牲日常性能，换取瞬间恢复。

if crashes_per_day > 1:      # 波多黎各：一天停电好几次
    use(SHADOW_PAGING)       # 牺牲日常性能，换瞬间恢复
else:
    use(WAL)                 # 绝大多数系统走这条

7C：一致性

难度 ★★★★★重要§5 已够答清单；最终一致性 #23 再展开

一致性就是不准出现违反现实的状态。37:26 规则得由应用提前告诉数据库。

数据库要建模真实世界，所以不能允许违反现实的状态。 例子：年龄用整数存，没人能是负 100 岁。

但数据库自己推不出这一点，它只看到整数。所以这类完整性约束（integrity constraint），必须由应用提前告诉它：

CREATE TABLE person (
    age INT NOT NULL CHECK (age >= 0)   -- ← 这就是完整性约束
);
-- 考点：数据库推不出"年龄不能为负"，约束必须由应用提前声明

然后由数据库负责强制执行。任何事务都不许把库改成非法状态。

这像给表格加数据校验。你不设规则，表格就让你在年龄栏填负数。

最终一致性（Eventual Consistency）

最终一致性就是允许你暂时读到旧版本，过一阵才同步上。38:48 这个概念到多机场景才真正有意义。

含义
（强）一致性 我在节点 1 上提交，立刻去节点 2 读同一条记录。我就该看到我自己的写
最终一致性 有个时间窗口，改动还没传播过去。你会读到旧版本 
node1.write("A", 75)   # 在节点 1 上提交

# 考点：最终一致性让普通程序员去推理不一致的数据，后来大家承认这是个错误

这像朋友圈发了新状态，别人刷新之前看到的还是旧的。

补充：历史：这是 2000 年代 Google 带火的东西。

踩坑：但后来大家承认，这是个错误。这等于让一群普通应用程序员，去推理不一致的数据。这从来不会有好结果。

8I：隔离性与调度

难度 ★★★★★必会可串行化定义在此，#18–#20 都靠它判对错

隔离性就是让每个事务都觉得，系统里只有自己在跑。40:57 这是本讲的核心。

隔离性 = 让应用觉得"系统里只有我这一个事务在跑"。

为什么这是好事：这是对普通应用开发者最友好的编程模型。开发者不用去想"要是别人同时改了同一个东西怎么办"。

但我们又想真的并发执行，拿到多核的性能。所以：

必须交错执行，但结果必须像是一个接一个跑出来的。

# 物理上：T1 和 T2 的操作在多核上交错着跑
# 逻辑上：结果必须等于先 T1 后 T2，或者先 T2 后 T1
assert final_state in {run(T1, T2), run(T2, T1)}
# 考点：隔离性要求交错执行的结果，等价于某个串行顺序

这像餐厅后厨同时做好几桌的菜。厨师们来回穿插，但每桌上菜时都像是专门为它做的。

两大流派

并发控制分悲观和乐观两派，区别在于假设冲突多还是少。42:08

悲观（Pessimistic） 乐观（Optimistic）
假设 一定会冲突 冲突很罕见
做法 提前阻止你做危险的事 随你做，提交时再检查、再清理
讲在哪 #18 两阶段封锁 #19 OCC 
// 悲观：先上锁，再动手（#18 两阶段封锁）
lock_manager->LockExclusive(txn, rid);
// 乐观：先动手，提交时再检查（#19 OCC）
if (!Validate(txn)) Abort(txn);
// 考点：悲观假设一定会冲突，乐观假设冲突很罕见

悲观像进门先敲门。乐观像直接推门，撞上了再道歉。

补充：这个"乐观 vs 悲观"的对立，你在 #10 Latch Crabbing 里已经见过一次了。同一个思想，不同层次。

什么叫"正确的交错"

不管怎么交错，最后的总额都必须跟串行跑一样。43:20 经典例子：A、B 两个账户各有 $1000。

T1：从 A 转 $100 到 B
T2：给 A 和 B 各计 6% 利息

不管怎么跑，最后 A + B 必须等于：(1000 + 1000) × 1.06 = $2120

两个关键前提

数据库可以不按到达顺序执行。只要等价于某个串行顺序就行。

① 到达顺序不重要（44:45）

应用先提交 T1，再提交 T2。数据库仍然可以按任意顺序执行它们。

补充：如果你真的在乎到达顺序，该怎么办？那叫严格一致性 / 外部一致性（external consistency）。极少有系统支持。 Google Spanner 是最有名的一个，它保证先提交的事务先生效。

② 只有两个"串行顺序"是合法的：T1→T2 或 T2→T1。

两者会让 A、B 各自的余额不同，但总和都是 $2120。两个都是正确的。

# 先 T1 后 T2：A = 954，B = 1166（按上面的数算出来的）
# 先 T2 后 T1：A = 960，B = 1160
assert 954 + 1166 == 960 + 1160 == 2120   # 余额不同，总和一样，两个都对
# 考点：到达顺序不重要，在乎到达顺序的叫外部一致性，Spanner 支持

好的交错

交错没问题，只要每个对象上都是 T1 先于 T2。49:45

为什么会发生交错？事务要取的页不在缓冲池，就得去磁盘。这一停顿，数据库就趁机让别人跑。

T1: 读A, A-=100, 写A   ─┐停顿（去磁盘）
T2:                     └→ 读A, A*=1.06, 写A ─┐停顿
T1: 读B, B+=100, 写B, COMMIT ←───────────────┘
T2: 读B, B*=1.06, 写B, COMMIT

它等价于 T1 → T2。关键在于：对 A 和对 B 的操作，都是 T1 先于 T2。

坏的交错

T2 在 T1 转账转到一半时计息，总额就少了 $6。51:04

T1: 读A, A-=100, 写A   ─┐停顿
T2:                     └→ 读A, A*=1.06, 写A
T2:                        读B, B*=1.06, 写B, COMMIT
T1: 读B, B+=100, 写B, COMMIT

考点：坏在给 A 计利息时，那 $100 已经离开 A，却还没进 B

总和少了 $6。因为给 A 计利息时，那 $100 已经离开 A，却还没进 B。

这像银行盘点时，正好有一笔钱在路上。两边账上都没有它，利息就漏算了。

数据库其实看不到"高层含义"

数据库只看得见读和写，看不懂你在转账。52:24 上面写成 A = A - 100，是为了人类好懂。数据库看到的只有：

T1: R(A) W(A) R(B) W(B)
T2: R(A) W(A) R(B) W(B)

考点：数据库只知道你在读还是写哪个对象，不知道你在转账

这像快递员只认箱子编号。箱子里是礼物还是砖头，快递员不知道。

踩坑：它完全不知道你想干什么。只知道你在读还是在写某个对象。

所以问题变成：怎么只靠这串读写序列，判断一个调度对不对？

术语

可串行化调度就是：有交错，但等价于某个串行调度。52:57

术语 定义
串行调度（Serial Schedule） 事务一个接一个跑，没有交错
等价调度（Equivalent Schedules） 两个调度让数据库进入同样的最终状态
可串行化调度（Serializable Schedule） 有交错，但等价于某个串行调度 
def is_serializable(schedule):
    return any(same_final_state(schedule, s) for s in serial_orders(schedule))
# 只要等价于任意一个串行顺序就算对，不在乎是哪一个
# 考点：串行、等价、可串行化三个定义要分清

补充：为什么定得这么宽松？（53:53）因为它给了数据库更大的自由，去发掘并行机会。要是只能严格按提交顺序一个个跑，就退回单线程队列了。

踩坑：注意"任意一个串行顺序都行"。我们不在乎最后等价于哪一个，只要至少等价于一个。

9三种冲突（异常）

难度 ★★★★★必会HW5 Q1 直接考；依赖图的边由它定

两个不同事务碰同一个对象，只要有一个是写，就算冲突。55:17

冲突的定义：两个不同事务的操作，作用在同一个对象上。而且至少有一个是写。

def conflicts(op1, op2):
    return (op1.txn != op2.txn and op1.obj == op2.obj
            and "W" in (op1.kind, op2.kind))   # 至少一个是写
# 考点：两个都是读，谁在乎呢，所以没有读-读冲突

这像两个人看同一本书，没事。只要有一个人要在书上涂改，就得排队。

为什么没有"读-读冲突"？两个人都只是读，谁在乎呢。

① 读-写冲突（R-W）= 不可重复读

读-写冲突会让同一个事务两次读到不同的值。57:16 这就是不可重复读。

T1: R(A) → $10
T2:              R(A) → $10, W(A) = $19, COMMIT
T1: R(A) → $19   同一个事务里读两次，值不一样了！

如果真的串行执行，第二次读必然还是 $10。

② 写-读冲突（W-R）= 脏读

写-读冲突会让事务读到别人还没提交的值，这叫脏读。57:59

T1: R(A), W(A) = $12
T2:                    R(A) → $12  读到了 T1【尚未提交】的值
T2:                    W(A) = $14, COMMIT
T1: ABORT（回滚）

T1 撤销了，但 T2 已经基于它的中间值提交了。

踩坑：提交的含义是：你在告诉外部世界"我做的一切都已生效"。串行执行下，T2 根本不可能看到 T1 未提交的值。

③ 写-写冲突（W-W）= 丢失更新

写-写冲突会让两个事务的写被撕开，这叫丢失更新。1:00:51

T1: W(A) = $10
T2:              W(A) = $19       ← 【盲写】：不读就直接覆盖
T2:              W(B) = "Bob"
T1: W(B) = "Alice"
        ↓
最终：A = $19，B = "Alice"

考点：三种冲突分别是不可重复读、脏读、丢失更新

任何串行顺序都得不到这个结果。要么是 ($10, "Alice")，要么是 ($19, "Bob")。两个事务的写被撕开了。

还有两个本讲不讲的异常

还有幻读和写偏斜两种异常，后面几讲再讲。56:39

异常 什么时候讲 简述
幻读（Phantom Read） #18 本讲假设了数据库大小固定，所以没有它。真实系统有插入和删除。我扫描一个范围，别人往里插了一条。我再扫一遍，就多出来一行
写偏斜（Write Skew） #20 MVCC 两个事务读到同样的库状态，各自做了写。合起来看，这些写是冲突的 
SELECT * FROM account WHERE balance > 0;   -- 第一次扫：3 行（示意）
-- 别的事务插进来一条 balance > 0 的新行
SELECT * FROM account WHERE balance > 0;   -- 第二次扫：多出一行，这就是幻读
-- 考点：本讲没讲的两个异常是幻读（#18）和写偏斜（#20）

10冲突可串行化与依赖图

难度 ★★★★★必会HW5 Q1 直接考，清单明列依赖图

判断一个调度对不对，就画一张依赖图，看有没有环。1:01:36 这是机械的判法。

g = build_dependency_graph(schedule)
print("serializable" if not g.has_cycle() else "not serializable")  # 有环就不行
# 考点：所有真实系统用的都是冲突可串行化

这像排课表。谁必须在谁前面，就画一个箭头。箭头绕成了圈，课就排不出来了。

两种可串行化的定义：

冲突可串行化（Conflict Serializability） 视图可串行化（View Serializability）
判据 只看读写冲突 还要懂应用的高层语义
现实 所有真实系统用的都是这个，尽管不一定这么叫 没有系统能做（见第 11 节）

定义

冲突可串行化的意思是：跟某个串行调度冲突等价。

  • 冲突等价：两个调度涉及相同事务的相同操作。而且每一对冲突操作的相对顺序都一样。
  • 冲突可串行化：这个调度冲突等价于某个串行调度。

依赖图（Dependency Graph / 优先图）

依赖图就是每个事务一个点，冲突就连一条边，有环就不行。1:04:13

① 每个事务画一个节点
② 若 Ti 的某操作与 Tj 的某操作【冲突】，且 Tj 的那个操作在调度中【更晚】
   → 画一条边 Ti → Tj
③ 判定：
   无环 → 冲突可串行化（等价于某个串行顺序）
   有环 → 不可串行化

考点：依赖图怎么画、怎么判，有环就不是冲突可串行化

例 1：两个事务，有环

A 上 T1 在前，B 上 T2 在前，两条边方向相反，就成环了。

T1: R(A) W(A)                     R(B) W(B)
T2:           R(A) W(A) R(B) W(B)

T1 的 W(A) 早于 T2 的 R(A)  →  边 T1 → T2
T2 的 W(B) 早于 T1 的 R(B)  →  边 T2 → T1（B 上方向相反）
                    ↓
              T1 ⇄ T2  有环，不可串行化

补充：W(A) 与 W(A) 也是冲突。但那只会画出一条重复的边，不影响判定。

例 2：三个事务，无环

图里没有环，就能读出一个等价的串行顺序。1:05:36 把所有冲突边画出来后：

T2 ──→ T1 ──→ T3        （无环）

考点：BEGIN 的先后、提交的先后都不重要，只看最终状态是否等价

结论：等价于串行顺序 T2 → T1 → T3。

这像比赛排名。谁先进场、谁先离场都不算数，只看成绩单。

踩坑：这里有两件反直觉的事，值得单独记。

  1. T1 先调用了 BEGIN，但等价的串行顺序里 T2 在前。 没关系。
  2. T3 实际上比 T1 更早提交。但在这个逻辑顺序里，T3 排在 T1 之后。也没关系。我们只关心最终状态等价，不关心物理上谁先谁后。

补充：这就是那个"新的正确性概念"。它和你在系统课里学的严格内存序，完全不是一回事。数据库有权重排，只要结果看起来像串行的。

11视图可串行化

难度 ★★★★★必会HW5 Q1 直接考，清单明列；盲写的判断易错

视图可串行化是一个更宽松的定义。1:07:02 只要懂应用真正想要什么，有些"冲突"其实无所谓。

例 A：求和 vs 计数

同一个交错，T2 求和就错，T2 计数就对。

T1: R(A) W(A) R(B) W(B)     -- 从 A 转 $10 到 B
T2:      R(A)      R(B)     -- 读 A 和 B

依赖图有环，所以不是冲突可串行化。

但对不对，取决于 T2 到底想干什么：

T2 做的事 这个交错正确吗
SUM(A, B)，求总额 不正确。会看到转账中间态，少 $10
COUNT(余额 >= 0)，数有几个账户 正确！转账不影响这个计数

例 B：盲写

如果只在乎 A 最后被谁写，盲写的乱序就无所谓。1:09:50

T1: R(A)      W(A)
T2:      W(A)                  ← 盲写
T3:                W(A)        ← 盲写

考点：视图可串行化比冲突可串行化宽松，例子是求和 vs 计数、盲写

依赖图有环，所以不是冲突可串行化。

但假设我唯一在乎的，是"A 最后被 T3 写"。那这个调度就等价于 T1 → T2 → T3。它是视图可串行化的。

为什么没人实现它

没人实现，是因为得先知道应用到底想要什么。1:09:11

要做视图可串行化，你得知道应用到底想要什么。要么去分析应用代码，那是噩梦。要么去问人。

"而问人是最糟糕的，因为人根本不知道自己在说什么。"

# 视图可串行化：还得知道 T2 是在 SUM 还是在 COUNT
def is_view_serializable(schedule, what_app_wants): ...  # 第二个参数没人给得出
# 考点：没有系统实现视图可串行化，因为得问人，而人根本不知道自己在说什么

这像让快递员判断哪些包裹可以晚送。不拆箱就不知道，拆箱又太累。

1锁与闩的完整对照

难度 ★★★★★重要六项对比要记；#19 §10 还会用，不直接考

锁管的是数据库里的逻辑对象，闩管的是内存里的数据结构。3:31 回到 #10 那张 Goetz Graefe 的表。当时只看了右半边的 Latch，现在补上左半边的 Lock。

-- 考点：Lock 和 Latch 有六项差别。lock 要集中管，因为应用发来的查询不可控

锁像酒店的房卡，退房之前一直归你。闩像公共厕所的门闩，用完马上打开。

2锁管理器

难度 ★★★★★重要死锁检测的数据来源，不考也不写代码

锁管理器就是一个中心化的哈希表。它记着谁拿了什么锁，谁在排队。5:28

锁管理器（哈希表）
  ├─ 对象 A → { 持有者：T1（X 模式） ; 等待队列：[T2, T5] }
  ├─ 对象 B → { 持有者：T3、T4（S 模式） ; 等待队列：[] }
  └─ ...

它像图书馆前台的借书登记簿。谁借走了哪本，谁在排队预约，全记在这一本上。

它有全局视野。它知道每个事务持有什么锁、在等什么锁。这正是它能做死锁检测的原因。

std::unordered_map<RID, LockRequestQueue> lock_table_;  // 对象 → 持有者和等待队列
std::mutex latch_;                                      // 锁表自己也是共享结构，要用 latch 护着
// 考点：锁管理器存的是"谁持有什么、谁在等什么"
// 考点：它贵在每秒要处理百万事务，自己还得拿 latch

基本流程：

T1 → 「我要 A 的锁」 → 锁管理器 → 没人占 → 授予
T2 → 「我要 A 的锁」 → 锁管理器 → T1 占着 → 拒绝 → T2 阻塞等待
T1 → 「还 A 的锁」   → 锁管理器 → 从等待队列唤醒 T2 → 授予

支持锁升级（upgrade）。持有 S 锁的事务，可以申请升级成 X 锁。锁管理器看还有没有别人持着 S 锁，再决定批准还是拒绝。

补充：崩溃后不用恢复锁表（11:21）。因为当时在跑的事务全都死了，直接全部清空就行。页目录和数据本身才需要持久化。

踩坑：锁管理器很贵。你在终端里只能看到两三个事务。可高端事务系统一秒钟要跑十万甚至百万笔事务。维护这堆元数据，成本非常可观。而且锁管理器本身是共享数据结构，还得用 latch 保护。这呼应 #04 page table 是热点。

别人要 S 别人要 X

3光有锁不等于可串行化

难度 ★★★★★重要引出 2PL 的反例，看懂即可

锁放得太早，加了锁照样出错。11:21 这是本讲最重要的一个反例。

T1: X-LOCK(A), R(A), W(A), UNLOCK(A)
T2:                              X-LOCK(A), W(A), UNLOCK(A)
T1:                                                      S-LOCK(A), R(A) ← 读到了 T2 的值！
考点：光加锁不等于可串行化。这里出现的异常是不可重复读

T1 第二次读 A，得到的值和第一次不一样。这就是 #17 的不可重复读。

这像你在超市先看了一眼价签，转身去推购物车。回来时价签已经被人换了。锁拿过，也放了，只是放得太早。

踩坑：加了锁不会自动变正确。关键在于什么时候发锁、什么时候放锁。这正是两阶段封锁要规定的东西。

4两阶段封锁协议

难度 ★★★★★必会HW5 Q1 直接考，清单明列增长 / 收缩期

2PL 只立一条规矩：放过一次锁，就再也不准拿新锁。13:28 它由 Jim Gray 在 1970 年代提出。它是第一个被证明能产生可串行化调度的并发控制协议。

它专门为动态环境设计。所谓动态，就是不知道事务未来要干什么。

void Lock(Txn *t, Obj o)   { assert(t->phase == GROWING); lm.Acquire(t, o); }
void Unlock(Txn *t, Obj o) { t->phase = SHRINKING; lm.Release(t, o); }
// 第一次 Unlock 之后，phase 就永远停在 SHRINKING
// 考点：增长期只拿不放，收缩期只放不拿。核心禁令是放过锁就不能再拿

这像爬山。上山时一路捡装备。一过山顶就只能往下丢，不准再捡。

阶段 规则
① 增长期（Growing） 可以向锁管理器申请任意锁。被拒就阻塞等待，或者因死锁被中止
② 收缩期（Shrinking） 一旦释放了任何一个锁，立刻进入此阶段。从此不能再申请新锁，只能继续归还

踩坑：核心禁令是不允许先放掉一些锁，然后又去申请新锁。

它是怎么修好第 3 节那个 bug 的

2PL 逼着 T1 一直攥着 A 的锁，所以 T2 插不进来。

T1: X-LOCK(A), R(A), W(A)          ← 【不释放】A 的锁！因为后面还要读它
T2:            X-LOCK(A) 阻塞……
T1: R(A)  读到自己写的值
T1: UNLOCK(A) → COMMIT
T2:            现在拿到锁，W(A), COMMIT

道理很简单。一进收缩期，就永远不能再拿锁。T1 后面还要读 A，只能一直持有 A 到最后。

几个容易混淆的点

阶段按事务各算各的，SQL 里也基本没法手动放锁。24:04

BEGIN;
SELECT * FROM t WHERE id = :id;            -- 系统自动加 S 锁，你不用写 LOCK
UPDATE t SET v = v + 1 WHERE id = :id;     -- 系统自动加 X 锁
COMMIT;                                    -- 锁在这里一起放。SQL 里没有 UNLOCK
-- 考点：收缩期还能读写手里有锁的对象。阶段是每个事务各有一套
-- 考点：SQL 基本不能手动加锁解锁，解锁实际发生在 COMMIT
问题 答案
进了收缩期还能做读写吗？ 能。你还持有锁的对象，随便读写。只是不能申请新锁。
阶段是全局的还是每事务的？ 每个事务各有各的阶段，不是全系统统一
SQL 里能手动 LOCK / UNLOCK 吗？ 基本不能。 SQL 是声明式的。你跑一条查询，系统自动帮你加锁。解锁尤其没法手动做，见第 5 节

2PL 的代价：过于悲观

2PL 会把一些本来可串行化的调度也拒绝掉。24:47 因为它是悲观协议，假定一定会冲突。我们因此损失了一些本可获得的并行度。

UPDATE account SET balance = balance - :amt WHERE id = :id;  -- 原地改余额
INSERT INTO ledger VALUES (:id, -:amt);                      -- 真实银行：只往流水账里追加
SELECT SUM(amount) FROM ledger WHERE account_id = :id;       -- 余额靠求和算出来
-- 考点：2PL 的代价是丢掉一些并行度，换来不丢钱。银行其实用的是流水账

悲观协议像出门必带伞。十天里九天用不上，可一次也淋不着。

但这是值得的：

"如果是你的银行账户呢？数据库很快，却会弄丢你的钱。你不会在乎它快。"

踩坑：大多数系统的默认隔离级别并不是 SERIALIZABLE，而是更低的级别。更低的级别允许出现某些异常。很多时候这是可以接受的。

5级联中止与三种加强版

难度 ★★★★★必会HW5 Q1 直接考，清单明列 strict 变体

基本 2PL 能保证正确，但一个事务中止，会连累一串事务陪葬。17:35 基本 2PL 保证冲突可串行化，也就是依赖图无环。它剩下的问题不是正确性问题，是性能问题。

级联中止（Cascading Aborts）

T2 读了 T1 没提交的值。T1 一中止，T2 只能跟着中止。

T1: LOCK(A), LOCK(B), R(A), W(A), UNLOCK(A) ─────────┐
T2:                              LOCK(A), R(A) ← 读到 T1 未提交的值
T2:                                       W(A)
T1: R(B), W(B), ABORT ←──────────────────────────────┘
T2: 被迫也要 ABORT
考点：级联中止怎么发生。T2 必须跟着死，因为它读了未提交的值

这像抄作业。你抄的那份后来被判作废，你的也得跟着重写。

T2 读到的是 T1 还没提交的值，这叫脏读。T1 定局之前，T2 不能提交。因为绝不能把未提交事务的信息泄露给外部世界。T1 一中止，T2 只能跟着中止。

踩坑：两个事务还不算什么。真实系统里，可能有成千上万个事务依赖同一个事务。它一死，全部要回滚。大量的 I/O 和 CPU 全白烧了。

补充：系统怎么知道 T2 依赖 T1？靠额外维护的元数据，幻灯片上没画。

三个变体

加强版的思路只有一个：锁攥得更久，别人就读不到脏数据。27:31

Strong Strict 2PL 像装修完再揭幕。揭幕之前，谁也看不到半成品。

协议 收缩期怎么做 有级联中止吗

7选谁当牺牲品、回滚到哪

难度 ★★★★★重要几条判据记一下，作业和清单都没列

检测到死锁后，要中止一个事务。挑代价最小的那个下手。40:20

Txn *PickVictim(std::vector<Txn *> &cycle) {
  return *std::min_element(cycle.begin(), cycle.end(),
      [](Txn *a, Txn *b) { return a->work_done < b->work_done; });   // 杀干活最少的
}
// 考点：四个判据是年龄、工作量、持锁数、连带回滚数
// 考点：改了十亿条的事务不该杀，撤销代价太大

这像船要减重。先扔最轻、最不值钱的箱子，别把整船货扔了。

判据

依据 说明
年龄 通常杀最新的。它待得还不够久，杀它不算饿死它
已完成的工作量 一个改了十亿条记录，一个只改了一条，就杀那个改一条的。 别浪费掉巨大的撤销代价
持有的锁数量 同理。拿锁本身就很贵，要进锁管理器，要 latch 保护。不像 latch 那样翻个 64 位整数就完事
会连带回滚多少事务 针对级联中止场景。Strong Strict 2PL 没这问题

补充：又是高端和平价的差别。贵的系统维护全套统计来做这个决策。MySQL 基本就是"杀最新的"。

中止之后

被中止的事务，要么由系统重启，要么把异常甩给应用。

释放全部锁 + 撤销全部改动（保证原子性）
        ↓
① 系统自己重启它（如果是存储过程，相当于重新调一次 RPC）
② 或者抛异常给应用，由应用决定要不要重试

catch (TxnAbortException &e) { Retry(); }   // 很多应用压根没写这一段
// 考点：中止后有两条路。第二条的风险是应用未必写了异常处理

踩坑：注意第 ② 条。应用代码未必写了异常处理。

保存点（Savepoint）：不用全部回滚

保存点让你只回滚半截，不用整个事务重来。43:38

BEGIN;
   UPDATE ... ;        -- 改了 5 条
   SAVEPOINT sp1;      -- ← 事务内部的检查点
   UPDATE ... ;        -- 第 6 条卡住了，死锁
   ROLLBACK TO sp1;    -- 只回退到这里，不用整个事务重来
COMMIT;
-- 考点：保存点由应用显式创建。单条 UPDATE 卡住时，系统能隐式做到类似效果

这像打游戏存档。死了就从存档点读档，不用从第一关重打。

好处是打破死锁的同时，保留大部分工作。甚至不用告诉应用发生过死锁。

踩坑：保存点得由应用代码显式创建。不过有些情况，系统能隐式处理。比如一条 UPDATE 要改两条记录，第二条拿不到锁。系统可以只撤销第一条的改动，解开死锁。然后重新执行这条语句，全程不惊动应用。

8死锁预防：Wait-Die 与 Wound-Wait

难度 ★★★★★必会清单点名 wound-wait / wait-die

预防就是根本不让死锁发生。锁被占的那一刻，就按年龄当场拍板。46:28

做法：申请锁被占用的那一刻就做决定。

不需要等待图。只需要每个事务的开始时间戳，越早优先级越高。

void OnConflict(Txn *req, Txn *holder) {             // 时间戳越小越老
  bool older = req->ts < holder->ts;
  if (WAIT_DIE) older ? Wait(req) : Abort(req);      // 老的等，年轻的自杀
  else          older ? Abort(holder) : Wait(req);   // Wound-Wait：老的抢，年轻的等
}
// 考点：Wait-Die 和 Wound-Wait 的规则，用下面两个例子对一遍

Wait-Die 像老人排队可以慢慢等，年轻人被挡就自己走开。Wound-Wait 像老人直接把占位的年轻人请走，年轻人遇到老人只能等。

协议 口诀 规则
Wait-Die 老的等年轻的 申请者更老 → 允许等待
申请者更年轻 → 自杀
Wound-Wait 年轻的等老的 申请者更老 → 抢锁，杀掉持有者
申请者更年轻 → 允许等待

两个例子

例 ①：T2 先拿到锁，T1（更老）来申请

协议 结果
Wait-Die T1 更老 → 允许等待
Wound-Wait T1 更老 → 抢锁，T2 被中止

例 ②：T1 先拿到锁，T2（更年轻）来申请

协议 结果
Wait-Die T2 更年轻 → T2 自杀
Wound-Wait T2 更年轻 → 允许等待

为什么这就不会死锁

因为所有的等待都朝同一个方向发生。49:18

Wait-Die 下只剩"老的等年轻的"这一种边
边的方向一路从老指向年轻，绕不回起点，环就成不了
考点：单向等待保证无死锁。Andy 拿 #10 的 crabbing 作类比

Andy 拿 #10 的 B+ 树 crabbing 作类比。所有 worker 都从上往下走，没人反方向走，所以不可能死锁。

踩坑：两种协议只能选一个用，不能同时开。

重启时时间戳怎么办

重启的事务要沿用它最初那个时间戳。

void Restart(Txn *t) {
  t->ts = t->original_ts;   // 不换新号，沿用最初的时间戳
  Run(t);                   // 越等越老，迟早轮到它
}
// 考点：重启用旧时间戳，这样不会被饿死

这像医院挂号。你中途去拍了个片子，回来还用原来的号，不用重新排。

这保证它最终会变成"最老的那个"。到那时想要什么就有什么，不会被饿死。

补充：哪个更好？看负载。高端系统让你切换。

10意向锁

难度 ★★★★★必会HW5 Q2 直接考；兼容矩阵和 SIX 易错

意向锁是挂在上层的一块提示牌，告诉别人"我在下面干活"。54:59 只有 S / X 两种模式的话，层次封锁根本用不起来。

问题出在这里。2PL 要求"动手前必须先拿锁"，所以你必须先检查上层。可你不想为此把整棵树遍历一遍。

意向锁（Intention Lock）就是给其他事务的一个"提示"。 提示的内容是：我在下面干什么，你不用下去看。

lm.LockTable(txn, INTENTION_EXCLUSIVE, table_oid);   // 先在表上挂 IX
lm.LockRow(txn, EXCLUSIVE, table_oid, rid);           // 再在元组上拿 X
// 考点：意向锁解决"要查上层，又不想遍历整棵树"。IS / IX / SIX 各管一种意图

这像楼道口贴的一张告示："本层有房间在装修。"想整层大扫除的人一看就知道要等，不用挨个敲门。

锁 含义
IS（Intention-Shared） "我下面某处会拿共享锁"
IX（Intention-Exclusive） "我下面某处会拿排他锁"
SIX（Shared + Intention-Exclusive） "这一层及以下我全部拿共享锁。下面某一处我会升级成排他锁"

兼容性矩阵

X 挡住一切，IS 几乎和什么都兼容。

IS IX S SIX X
IS 兼容 兼容 兼容 兼容 冲突
IX 兼容 兼容 冲突 冲突 冲突
S 兼容 冲突 兼容 冲突 冲突
SIX 兼容 冲突 冲突 冲突 冲突
X 冲突 冲突 冲突 冲突 冲突

补充：规律是 X 挡住一切，IS 几乎和什么都兼容。IS 只是个"我在下面干活"的提示，跟当前这一层没冲突。

加锁协议

从上往下拿锁：上层拿意向锁，目标层拿真锁。

① 从根往下走，在【上层】拿【意向锁】
② 在【真正要操作的层级】拿【显式的 S 或 X 锁】
考点：能默写五种锁的兼容矩阵。规律是 X 挡一切，IS 几乎都兼容

例 1：两个事务并行（读一条 + 改一条）

IS 和 IX 兼容，所以一个读、一个改，可以完全并行。57:44

T1（读一条元组）              T2（改一条元组）
     表: IS                        表: IX      ← IS 与 IX 兼容！
      │                             │
   元组1: S                     元组2: X

两个事务完全并行，互不干扰
考点：IS 和 IX 让读一条、改一条并行。T2 不在表上拿 X

踩坑：T2 为什么不在表上拿 X 锁？因为那会挡住表上所有读写。而且 T1 已经持有 IS，X 锁根本申请不到。

例 2：三个事务，看 SIX 怎么用

要读全表、只改一条，就在表上拿 SIX。59:47

T1：扫描 R 的所有元组，并【更新其中一条】
T2：读 R 的单条元组
T3：读 R 的所有元组

lm.LockTable(t1, SHARED_INTENTION_EXCLUSIVE, r);   // T1：读全表，改一条
lm.LockRow(t1, EXCLUSIVE, r, rid);
lm.LockTable(t3, SHARED, r);                       // T3：读全表，被 SIX 挡住
// 考点：T1 为什么用 SIX，T3 为什么用 S 而不是 IS，T3 什么时候才能跑

SIX 像管理员在盘点一整排书架。整排都在看，只抽出一本来修。旁人借别的书没问题。想给整排拍照存档的人得等，因为有一本正在修。

事务 表级锁 元组级锁 结果
T1 SIX 一条元组上 X 获准。SIX 隐含了所有元组的 S 锁，只有那一条显式取 X
T2 IS 一条元组上 S 获准。IS 与 SIX 兼容
T3 S（整表） 无 阻塞。S 与 SIX 不兼容

后续：T2 提交，释放 IS，T3 仍然被挡。只有 T1 提交后，T3 才拿到表级 S 锁。

学生问：T3 为什么在表级拿 S，而不是 IS？（1:02:37 课堂提问）

因为 T3 知道下面有十亿条元组。与其拿十亿把元组锁，不如在表级拿一把 S 锁。

T1 为什么用 SIX？ 因为 T1 要读全部、只改一条。SIX 隐含把下面全部置于读模式，然后只对那一条取显式 X 锁。

如果 T1 要改全部呢？ 那就直接在表上拿 X 锁。

补充：典型场景是改表结构，比如加列、删列。这时就取整表 X 锁，最省事。

锁升级（Lock Escalation）

细锁拿得太多，可以换成上层的一把粗锁。1:02:37

已拿：表上 IS，加一千把元组 S 锁
发现：表里其实有十亿条
升级：表上 IS → S，一把顶掉下面所有细锁
考点：锁升级用在事务低估了数据量的场景

这像超市结账。一件件扫码太慢，干脆整箱按箱结。

事务以为只有一千条元组，于是老实拿了一千把元组锁。跑着跑着，发现有十亿条。这时可以回到层次树上，把表级的 IS 升级成 S。一把锁顶掉下面所有细锁。

11SQL 里的锁提示

难度 ★★★★★了解实用语法，作业和清单都没有

平时你不用手动加锁，但有几个提示很有用。1:04:08 正常情况下，SQL 是声明式的，系统自动判断该加什么锁。

① FOR UPDATE：最常用的一个

FOR UPDATE 让读操作直接拿 X 锁。

SELECT * FROM accounts WHERE id = 42 FOR UPDATE;
--                                    ^^^^^^^^^^
-- 考点：FOR UPDATE 读的时候就拿 X 锁，省掉了回头再升级的那一趟

没有 FOR UPDATE：系统给你 S 锁。 加上 FOR UPDATE：直接给 X 锁。

它的用处在 read-modify-write 场景，比如先读余额，再扣钱。

不加：读时拿 S 锁（进一次锁管理器）→ 下一条要改 → 回去申请升级 X 锁 → 可能失败 → 白读了、还要回滚
加了：读的时候就直接拿 X 锁 → 拿不到就立刻失败，没做无用功

这像去银行窗口办业务。一开口就说要取钱，柜员直接把账户锁好。别先说看看余额，回头再排一次队。

补充：PostgreSQL 有一整族变体：FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE。文档里有完整的兼容性矩阵。MySQL 的语法是 LOCK IN SHARE MODE 等。

② SKIP LOCKED：拿不到就跳过

SKIP LOCKED 遇到拿不到锁的行，直接跳过。

SELECT * FROM job_queue WHERE status = 'pending'
 ORDER BY created_at LIMIT 1
 FOR UPDATE SKIP LOCKED;
-- 考点：拿不到锁的行直接跳过。跑两次结果可能不同，最适合当工作队列

语义：扫描时遇到拿不到锁的行，就跳过它。这些行不出现在结果里。

这像食堂打饭。哪个窗口有人在打，你就去下一个窗口，不在后面干排。

踩坑：这很怪。同一条查询跑两次，可能得到不同结果。

但它对某些场景恰好合适。最典型的就是用数据库当工作队列。一堆 worker 在轮询队列抢任务。别人正在抢的那条，我干脆跳过，去拿下一条，不用干等。

补充：对比一下。FOR UPDATE 是强制你读的时候就拿排他锁。SKIP LOCKED 是拿不到就当没看见。

踩坑：普通业务查询绝对不要用它。它会给出不完整的结果。

1换个假设：乐观协议

乐观协议赌的是冲突很少。先随便干，提交时再查有没有撞车。3:31 #18 的 2PL 是悲观的。它假设一定冲突，所以动手前必须先拿锁。

void Run(Txn *t) {

  t->Install();                                // 没冲突，就装进数据库

// 考点：乐观协议的两条假设是冲突少、事务短。加载一个网页就是一个短事务

这像几个人在各自的草稿纸上改同一份合同。最后交稿时对一遍，没撞车就合并。

换一组假设：

假设 依据
① 事务之间很少冲突 大部分负载确实如此
② 事务都很短 加载一个网页就是一个事务。几条查询，少量数据，毫秒级。现代系统里，事务超过一秒都很罕见

补充：长事务能跑几分钟、几小时，甚至几天、几周。这在老时代更常见。今天主要出现在批量更新场景。

两条都成立的话，干脆别让它们拿锁。想干什么就干什么，提交的时候再检查有没有真的冲突。

这就是本讲的主题：时间戳排序（Timestamp Ordering）类协议。其中最主流的是 OCC（Optimistic Concurrency Control，乐观并发控制）。

踩坑：命名很绕。"OCC"既是一大类协议的名字，也是其中那个具体协议的名字。 不过你说 OCC，大家都知道你指哪个。

核心思路是不用锁来强制顺序，改用时间戳。只要生成的时间戳序列等价于某个串行顺序，就算正确。

要维护两类时间戳。一类是事务的，一类是数据库里每个对象的。对象的时间戳存在元组或页的头部，也就是 #03 讲的那个 header。

// 考点：PostgreSQL 的时间戳是 32 位整数，会回绕

3OCC 的三个阶段

难度 ★★★★★必会HW5 Q3 直接考，清单明列三个阶段

OCC 把每个事务关进私有工作区。跑完先验证，过了再一次性装回去。11:20

补充：说说身世。2PL 是 IBM 1976 年在 System R 上搞的。OCC 是 1981 年在 CMU 发明的。

有趣的是，发明人 H. T. Kung 不是数据库领域的人，是做网络的。这也解释了三个阶段的命名为什么有点怪。

Andy 的评价："不过说到底，你要网络干嘛？跟数据库通信啊。所以做网络的人研究这个，也说得通。"

核心机制：给每个事务开一块私有工作区（private workspace）。所有改动都关在里面，别的事务看不见。

struct Workspace { std::map<Key, Version> reads, writes; };   // 私有工作区
txn->ws.writes[A] = {new_val, INF};   // 读阶段：写只落在自己的工作区
// 别的事务这时去读 A，看到的还是全局数据库里的旧值

这像在自己的草稿本上做题。做完先交给老师检查，过了才誊到黑板上。

┌── ① 读阶段 Read Phase ──────────────────────────────┐
│  名字叫"读"，但读写都在这里发生                       │
│  · 创建私有工作区                                     │
│  · 【写】：改动写进私有工作区                          │
│  · 【读】：想要【可重复读】的话，也把读到的复制进来     │
└─────────────────────────────────────────────────────┘
                       ↓ 调用 COMMIT
┌── ② 验证阶段 Validation Phase ──────────────────────┐
│  此刻才分配时间戳                                     │
│  · 检查：我的改动会不会破坏"等价于某串行顺序"这件事？   │
│  · 不通过 → 中止重试                                  │
└─────────────────────────────────────────────────────┘
                       ↓ 通过
┌── ③ 写阶段 Write Phase ─────────────────────────────┐
│  · 给改动的对象打上验证阶段拿到的时间戳                 │
│  · 把私有工作区的内容【原子地】装进全局数据库           │
└─────────────────────────────────────────────────────┘
考点：三个阶段是读、验证、写。"读阶段"名不副实，读和写都在这里

踩坑：写阶段怎么保证原子？1981 年那个原始协议简单粗暴，整个数据库一把全局锁。那时候 CPU 就一个核，无所谓。 真实系统当然不能这么干。

4完整走一遍

T1 先开始，却后提交，所以 T1 拿到的时间戳反而更大。16:01

数据库：A = 123，写时间戳 = 0（由某个 T0 写入）

T1：R(A), W(A), R(A)
T2：R(A)
考点：T1 先开始，T2 先提交，所以 T2 的时间戳比 T1 小

这像考试交卷。先进考场的不一定先交卷，交卷顺序才决定谁排在前面。

步 发生了什么
1 T1 BEGIN → 创建空的私有工作区
2 T1 R(A) → 把 A=123, ts=0 复制进 T1 的工作区。为的是可重复读
3 上下文切换 → T2 BEGIN → 创建工作区
4 T2 R(A) → 同样复制一份进 T2 的工作区
5 T2 COMMIT → 进验证阶段 → 分配时间戳 = 1
6 验证：T2 只读了 A，T1 还没写过 → 无冲突，通过
7 写阶段：工作区里没有改动 → 直接丢弃，完事
8 切回 T1 W(A) → 在工作区里改值。写时间戳设为 ∞，因为还没拿到号
9 T1 R(A) → 从自己的工作区读 → 读到自己写的值，这就是可重复读
10 T1 COMMIT → 分配时间戳 = 2 → 验证通过
11 写阶段：把工作区里的 ∞ 改成 2，推进全局数据库

为什么时间戳要等到验证阶段才发？

因为所有事务跑完之前，谁也不知道正确的逻辑顺序。19:16 这是本讲最关键的一个观念。

void Commit(Txn *t) {
  t->ts = global_ts++;   // 到验证这一刻才发号，BEGIN 时不发
  Validate(t);
}
// 考点：时间戳在验证阶段分配。开始时就发，会把并行度限制死

T1 物理上先开始，但 T2 逻辑上先提交，所以 T2 的时间戳更小。

踩坑：要是一开始就发时间戳，就等于强行规定了顺序。操作顺序必须匹配到达顺序。这会限制并行度。

这样做是对的，呼应 #17。我们只要求"等价于某个串行顺序"，不要求等价于到达顺序。

5前向验证的三个条件

难度 ★★★★★重要HW5 用后向验证；清单只要 §6 的区别

前向验证拿自己去比所有还活着的事务。三个条件满足一个就能过。27:21

正在验证的事务是 T1。它要逐一检查所有仍在活跃的事务 T2。没分配时间戳的算 ∞，所以 T1 的时间戳一定更小。满足下列之一即可通过。

bool ForwardValidate(Txn *t1) {
  for (Txn *t2 : active_txns)                                      // 只看还在跑的
    if (!(NotStarted(t2) || Cond2(t1, t2) || Cond3(t1, t2))) return false;
  return true;
}
// 考点：三个条件满足其一即可。条件 ② 防的是"未来的事务读到旧版本"

这像交稿前挨个问还在写的同事。"我改的段落，你们有没有照旧稿抄过？"

条件 ①：T2 还没开始

T2 还没开始，就什么都没读过，显然安全。

T1: ├─── 读阶段 ───┤ 验证 │
T2:                       ├─ 开始 ─

T2 什么都还没读。我装进去的改动，T2 自然会看到。

条件 ②：T1 的写阶段在 T2 的写阶段之前完成，且 T1 的写集 ∩ T2 的读集 = ∅

两个集合交集为空，就没有冲突。

它防的是：一个"未来的"事务，读到了我改动之前的旧版本。

反例（30:07）：

T1: BEGIN, R(A), W(A) ────────────── 验证 失败
T2:                  BEGIN, R(A)   ← 读的是 ts=0 的旧版本
考点：中止的是 T1，不是 T2。并行验证时让自己死，协调最简单

T2 逻辑上应该在 T1 之后，那 T2 就该读到 T1 写的新值。可 T2 读的是旧值，所以 T1 必须中止。

这像你改了菜单，可已经有客人照旧菜单点完了菜。客人没做错，是改菜单的人来晚了。

踩坑：注意，是 T1 死，不是 T2 死。T2 什么都没做错，是你的问题。

学生问：T1 干了一堆活，T2 才刚开始，杀 T2 不是更划算吗？

31:35

串行验证时，你可以这么玩。但一旦并行验证，就要协调"谁去死"这件事。自杀简单得多。

这呼应 #10 latch 的自杀重试。

条件 ③：T1 的读阶段在 T2 的读阶段之前完成，且 T1 写集 ∩ T2 写集 = ∅ 且 T1 写集 ∩ T2 读集 = ∅

这个条件处理的是写-写冲突和写-读冲突。

例子（37:25）：

T1: R(A), W(A) ─ 验证（ts=1）通过，装进数据库
T2: R(B) ────────────────────── R(A) ← 读到 T1 写的新版本
                                验证（ts=2）通过

T1 验证时，T2 只读过 B，还没读 A。写集 {A} 与读集 {B} 无交集，所以通过。之后 T2 读到的自然是新版本，完全等价于串行执行。

补充：再看一个改好的调度（35:59）。同样的操作，只要让 T2 先验证，两个都能提交。T2 逻辑上在过去，读旧版本合法。T1 逻辑上在之后，装新版本也合法。

比较两个 64 位整数，是一条 CPU 指令。33:17 如果是大字符串，你得做 diff，贵太多了。

bool changed = (obj->wts != seen_wts);          // 一条指令比完
// bool changed = (obj->value != seen_value);   大字符串得逐字节 diff
// 考点：比时间戳是一条 CPU 指令，比值要做 diff

6前向验证 vs 后向验证

难度 ★★★★★必会清单明列两者区别，HW5 Q3 用后向验证

后向验证只看已经提交的事务，好写得多，所以是主流。25:19

bool BackwardValidate(Txn *t) {
  for (Txn *c : CommittedSince(t->start))                      // 只看我开始后提交的
    if (Intersects(c->write_set, t->read_set)) return false;   // 我漏读了它的改动
  return true;
}
// 考点：前向看活跃事务，后向看已提交事务。后向是主流，因为好实现

前向像考试中途去核对邻座的卷子，人家还在改。后向像考完对答案，对的是已经交上来的卷子。

前向验证（Forward） 后向验证（Backward），主流
看谁 还在跑的活跃事务的读写集 已经提交的事务
在问什么 "我改的东西，有没有别人正在读？" "别人提交的改动，我是不是漏读了？"
干扰 要去读别人正在变化的读写集 对方已经结束了，互不干扰
实现 复杂 简单得多
谁在用 没提到 Amazon DSQL 等几乎所有 OCC 系统

补充：Andy 认为两者性能上差不多。但后向在工程上容易得多，所以是主流。Andy 讲前向，只是因为它更能说明"物理顺序 ≠ 逻辑顺序"。

验证阶段要不要"停止世界"？

串行验证本质上就是停止世界，靠的是事务足够短。40:08

串行验证：一次只放一个事务进验证区，等于停止世界
精细做法：全局挂个牌子"我在验证 A、B"，要碰 A、B 的人先等
考点：停止世界可行的前提是事务短、读写集小，检查不到一毫秒

这像收银台一次只结一个顾客。每人只买一瓶水，队伍照样走得飞快。

学生的提问很尖锐。"我检查到列表末尾时，列表开头的人又开始读了，怎么办？"

Andy 的回答：

  • 串行验证，也就是一次只有一个事务验证。这本质上就是停止世界。这是原始协议的做法。
  • 更精细的做法：在全局某处挂个牌子。牌子上写着"我正在验证这些对象"。别人要碰这些对象，就先等一下。
  • 学生自己补了一句很到位的观察。 "其实事务开始时，也在做一点后向验证。"要检查的是，这东西是不是正在被提交。Andy 认可。

踩坑：真正的前提是：只有事务很短、读写集很小，这才可行。这时检查全在内存里，窗口不到一毫秒。如果事务跑几小时，就等于把整个系统变成单线程。这无法避免。

for (auto &k : keys) CheckAndMark(k);    // 人人都 A → B → C，没人反着走
// 考点：字典序检查防交叉死锁。和 #18 Wound-Wait 的单向思想是一脉的

我改了 A、B、C，你也改了 A、B、C。大家都按 A→B→C 的顺序检查。这样就不会出现"我在查 A、你在查 B"的交叉死锁。 这又是一次单向思想，同 #18 的 Wound-Wait。

为什么要维护"事务状态表"而不是直接查元组？

// 直接查元组：读过的元组可能已被换出，验证时还要再读一遍盘
// 考点：维护事务状态表，比直接查元组快

学生问得很好。Andy 承认两种做法都是正确的，但是：

  • 查一张集中的事务状态表快得多，因为它在内存里。
  • 而你读过但没写的那些元组，可能早就被换出到磁盘了。为了验证，还得再读一遍盘。

"听起来很疯狂：我得读两遍。有些系统真的这么做。"

8幻读：一切协议的裂缝

难度 ★★★★★必会HW5 判断题考 OCC 的幻读，清单要异常

幻读专钻"表的大小会变"这个空子，前面的协议全都挡不住。48:42 到目前为止，包括 #17#18，我们都假设数据库大小固定。一旦允许 INSERT / DELETE，前面讲的一切都会破。

-- T1
SELECT COUNT(*) FROM people WHERE status = 'paid';   -- → 99
--                                    ↓ 上下文切换
-- T2
INSERT INTO people VALUES (..., 'DJ Cash', 'paid');
COMMIT;
--                                    ↓ 切回
-- T1
SELECT COUNT(*) FROM people WHERE status = 'paid';   -- → 100
-- 考点：幻读是同一事务内、一个范围上的不可重复读

这像清点教室里的人数。点完一遍是 99，转身又进来一个人，再点就成了 100。

这是不可重复读。但它不是单个对象上的，而是一个范围上的。

这叫幻读（Phantom Read）。元组像幽灵一样，凭空出现或消失。

为什么 2PL 挡不住

你没法给一个还不存在的东西加锁。50:44

lm.LockRow(t1, SHARED, people, rid);   // 只能锁已经存在的 rid
// DJ Cash 那行还没插进来，没有 rid，也就没法锁
// 考点：2PL 挡不住幻读，因为没法给不存在的东西加锁

T1 第一次查询时，DJ Cash 那条记录根本不在表里。T1 拿不到那条记录的共享锁，所以 T2 可以插进去。

OCC 同样有这个问题。

踩坑：课堂澄清（52:13）。我查一次得到 99，你查一次得到 100，这是完全正常的。插入发生在两次查询之间，等价于串行。幻读是指：在同一个事务内部，东西凭空出现或消失。

9四种应对幻读的办法

难度 ★★★★★重要记四种思路即可，作业和清单都没列

四种办法里，索引封锁最常见。52:54

① 粗粒度锁：整栋楼封掉，谁也进不来
② 重跑扫描：散会前再点一次人头，对不上就重来
③ 谓词封锁：把"所有付费用户"这块区域圈起来
④ 索引封锁：在索引上锁住那一段空位
考点：四种办法里，最常见的是索引封锁，NP-hard 的是谓词封锁

这四种办法，像四种防止有人偷偷往会议室加座位的手段。

方案 做法 常见度
① 加粗粒度锁 锁整表、整库或整页 简单粗暴。在乎可串行化的系统有时真这么干
② 提交时重跑扫描 记住所有 WHERE 子句。提交时再跑一遍，看结果是否一致 主要在内存数据库里用
③ 谓词封锁 在"谓词空间"里加锁 罕见。IBM 1970s 提出，NP-hard
④ 索引封锁 用索引本身当锁的载体 最常见

② 重跑扫描的细节

只需要记录基表上看到了什么数据。55:03 不用记聚合结果，也不用记连接结果。提交时重跑一遍 WHERE，比对即可。

scan_set.push_back({pred, seen_rids});              // 只记基表上看到了哪些行
for (auto &[pred, rids] : scan_set)                 // 提交时逐个重跑
  if (Rescan(pred) != rids) return Abort(txn);      // 多一行或少一行，就是幻读
// 考点：重跑扫描只记基表数据。DynamoDB / Fauna 反过来，先跑侦察事务
系统 做法
Hekaton（微软的内存引擎） 就是这个做法
DynamoDB / Fauna 反过来做。先跑一遍"侦察事务（reconnaissance transaction）"，不改任何数据，只记下扫描集。真正提交时再跑一遍真的，结果一致才放行

③ 谓词封锁

谓词封锁不给元组加锁。它在一个高维空间里，给"谓词定义的区域"加锁。58:48 两个区域相交，就是冲突。

维度：status × name
T1 的 WHERE status='paid'        → 一个条带
T2 的 INSERT (name='DJ Cash', status='paid') → 一个点
                ↓
            两者相交 → 冲突

二维还行。一万列的表，就完全不可维护了。

-- 精确封锁：把读写集当成另一张表，用自己的 WHERE 去查它
SELECT * FROM write_set WHERE status = 'paid';   -- 查到有人写过 paid，就算冲突

补充：一个精彩的学术八卦（1:00:08）。谓词封锁的可行近似，叫精确封锁（Precision Locking）。做法是看读写集是否重叠。

10索引封锁：间隙锁与键范围锁

难度 ★★★★★重要作业和清单没列；键范围锁要走例子

最主流的方案，就是把索引当作锁的组织结构。1:02:09

为什么用索引？索引本来就把数据按序组织好了。它正好能表达"范围"这个概念，还能锁住尚不存在的值。

auto [lo, hi] = index.Neighbors(15);   // 插入 15 前，先找它落在哪个间隙：14 和 16 之间
lm.LockGap(txn, EXCLUSIVE, lo, hi);    // (14, 16) 被别人锁着，就得等
// 考点：间隙锁解决的根本问题，是锁住还不存在的值

这像停车场的车位线。车还没来，你也能先把一段车位圈起来。

四个层次，逐步搭建

从锁一个键，到锁一段空隙，再叠上意向锁，一层层搭起来。

① 键值锁（Key-Value Lock）：锁一个确定存在的键。

索引：… 10, 12, 14, 16, 18 …
              ↑ 锁住 12

踩坑：这些锁不存在 B+ 树节点里，而是存在锁管理器里，同 #18。上下界用虚拟键（±∞）表示。

② 间隙锁（Gap Lock）：锁住"两个已有键之间的空隙"。 这样就锁住了还不存在的值。

索引：… 14 ─(gap)─ 16 …
           ↑ 给 (14, 16) 这个开区间加锁

想插入 15 的事务会被挡住。 如果是浮点数，15.1 / 15.2 / 15.3 全被这一把锁覆盖。如果是字符串，aa 和 abc 之间的一切也是。

③ 键范围锁（Key-Range Lock）：把键和它后面的间隙合并成一把锁。

[14, 16)  ← 一把锁搞定"键 14"和"14 到 16 之间的空隙"

回到开头那个查询。WHERE status='paid' 取一把 [paid, 下一个键) 的键范围锁就行。这样就没人能往这个范围里插东西了。

方向要统一。系统只会选一个方向，向前或向后，不会两边都来。

④ 层次索引封锁：把 #18 的意向锁 叠上去。

B+ 树页面：取 IX 锁（意向排他）
    ├─ 键范围 [14, 16)：取 X 锁   ← 事务 A
    └─ 键 12：           取 X 锁   ← 事务 B
                ↓
    两个事务并行改同一页的不同范围
考点：键值锁、间隙锁、键范围锁、层次索引封锁，一层比一层管得多

Lock 和 Latch 在这里同时出现（本讲最容易混的一点）

锁管逻辑内容，闩管页面字节，两者在这里同时上场。1:09:51

lm.LockKeyRange(txn, EXCLUSIVE, 14, 16);       // Lock：管"这段范围里有哪些键"
auto guard = bpm->WritePage(leaf_page_id);     // Latch：管"这一页的字节"
leaf->Insert(15);                              // 分裂也在 latch 保护下做
// 考点：插入导致节点分裂时，lock 管逻辑内容，latch 管物理正确性

这像搬家时的两份手续。房产证写着这套房归谁，那是锁。搬家具时把门锁好别让人进，那是闩。

学生问：插入 15 导致节点分裂，怎么办？

Andy 的回答值得抄下来：

锁（Lock）保护数据库的逻辑内容，也就是某个范围内存着哪些键。我只是借用索引这个结构，来高效地表达那个范围。

而要真正修改页面里的字节，我还是得拿那一页的写闩（write latch）。

物理正确性照样由 latch 保证。 这正是 #10 和 #18 那条分界线。

没有索引怎么办？

没有合适的索引，就只能退回去锁整张表。1:10:35

SELECT * FROM t WHERE note = 'x';   -- note 上没有索引
-- 没法用间隙锁圈出范围，只能锁整张表
-- 考点：没有合适索引时，可串行化的代价是锁整表

学生问：要跑可串行化事务，查询范围上却没索引。是不是就很贵？

"是。天下没有免费的午餐。"

这像餐馆菜单上写着"现做"，端上来的其实是预制菜。你不细查，根本吃不出来。

我们花了三节课讲可串行化多重要。肮脏的秘密是：绝大多数数据库默认根本不给你可串行化。

踩坑：有些系统还会骗你，Oracle 就很有名。你说要 SERIALIZABLE，它说"好的没问题"。然后给你一个更低的级别。

为什么？一个非常现实的理由

默认可串行化会很慢，慢了就丢客户。1:12:47

前排同学一直在问"没索引怎么办？"。答案是只能走慢路径，全表扫描。

如果这是默认行为，那这个数据库就会很慢。人们会说"这数据库真烂"，然后换一个。你就丢客户了。

所以默认级别都比可串行化低。

隔离级别（SQL-92 标准，假定 2PL 实现）

级别越低，放进来的异常越多。

SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT bal FROM acct WHERE id = :id;   -- 第一次读
SELECT bal FROM acct WHERE id = :id;   -- 第二次可能不一样，也可能一样
-- 考点：四个级别对三种异常的表。Andy 强调用词是 may，不是 will
级别 脏读 不可重复读 幻读
SERIALIZABLE 不会 不会 不会
REPEATABLE READ 不会 不会 可能
READ COMMITTED 不会 可能 可能
READ UNCOMMITTED 可能 可能 可能

踩坑：Andy 特意强调用词。是"可能（may）"发生，不是"一定"。 因为只有一个事务在跑的调度，天然就是串行的。那永远是可串行化的。异常只在别的事务同时读写你碰的数据时，才可能出现。

用 2PL 怎么实现这些级别：就是把前面讲的东西一层层关掉

从 SERIALIZABLE 往下，每降一级就关掉一层保护。1:16:05

void ReadRow(Txn *t, RID rid) {
  if (t->iso == READ_UNCOMMITTED) { Read(rid); return; }   // 根本不拿 S 锁
  lm.LockRow(t, SHARED, rid); Read(rid);
  if (t->iso == READ_COMMITTED) lm.UnlockRow(t, rid);     // 读完立刻放 S 锁
}
// 考点：用 2PL 实现四个级别，每降一级关掉一样东西。X 锁永远持到提交

这像安检一道道撤岗。撤一道快一点，漏网的东西也多一点。

级别 实现
SERIALIZABLE Strong Strict 2PL，加上幻读保护。比如索引锁、谓词锁、重跑扫描
REPEATABLE READ Strong Strict 2PL，去掉幻读保护
READ COMMITTED 2PL，读完立刻释放共享锁。这违反 2PL 的顺序，但换来并行度。排他锁仍持到提交
READ UNCOMMITTED 完全不取共享锁。排他锁仍持到提交，防丢失更新

补充：为什么排他锁总是持到最后？因为几乎所有系统都不允许你手动解锁，所以只能等 COMMIT。

1核心思想与两个关键性质

难度 ★★★★★必会P4 全建在多版本上，本讲各节都要用

数据库从不原地改一条记录。4:51 每次更新都新建一个物理版本。读的时候，再挑一个给你看。

UPDATE users SET name = 'Bob' WHERE id = 1;  -- 不覆盖旧值，新建一个物理版本
SELECT name FROM users WHERE id = 1;         -- 查版本元数据，挑一个我能看的
-- 考点：逻辑元组是应用眼里那条记录，由主键标识
-- 考点：物理版本是底层的一份份拷贝，一个事务同一时刻只看到其中一个

这很像 Git 的提交历史。每次改动都留下一个新提交，旧的还在。你站在哪个提交上，就看到哪个版本。

数据库为每个逻辑元组维护多个物理版本。

  • 逻辑元组：应用眼里那条记录，由主键标识。
  • 从不原地覆盖：每次更新都创建新的物理版本。
  • 读的时候查版本元数据，判断哪个物理版本对我可见。
  • 任一时刻，一个事务只能看到一个物理版本。

踩坑：UPDATE 不是原地改，所以版本会越堆越多。这就需要垃圾回收，见第 10 节。

两个关键性质

读和写各走各的版本，所以谁也不挡谁。8:07

  1. 写者不阻塞读者：有人正在创建新版本，读者照样读旧版本。
  2. 读者不阻塞写者：有人在读，写者照样能装新版本。
2PL ：T1 读 A 拿共享锁，T2 写 A 要排他锁，T2 只能干等
MVCC：T1 去读旧版本 A₀，T2 直接建新版本 A₁，两边都不等
考点：2PL 的共享锁和排他锁不兼容，读写必然互相挡
考点：MVCC 让读者去读旧版本，这个冲突从根上就没了
考点：MVCC 不是协议，它叠在 2PL 或 OCC 之上

这就像图书馆里的书。有人在修订新版，你照样能借旧版来看。

对比 2PL：读要共享锁，写要排他锁，两者不兼容。读写必然互相挡。MVCC 从根上消除了这个冲突。

踩坑："MVCC"这个名字有误导性。名字里有"并发控制"，但它不是 2PL 或时间戳排序那样的协议。你仍然要在它之上跑 2PL 或 OCC。

MVCC 是一个【存储 + 可见性】的维度，叠加在并发协议之上。

补充：你在 BusTub 里做的一切（Project 1–3）都是单版本的。Project 4 才把它变成多版本。

3版本可见性怎么判断

难度 ★★★★★必会P4 的地基；物理可见 ≠ 逻辑可见易错

每个物理版本的头上贴着一个时间区间。11:57 事务拿自己的时间戳去比，落在区间里就能看。

┌───────┬────────┬──────────┬──────────┐
│ 对象  │  值    │ begin-ts │  end-ts  │
├───────┼────────┼──────────┼──────────┤
│  A₀   │  123   │    0     │    ∞     │  ← ∞ 表示"这是最新版本"
└───────┴────────┴──────────┴──────────┘

[begin-ts, end-ts) 就是这个版本可见的时间区间。

bool Visible(const Version &v, ts_t my_ts) {
  return v.begin_ts <= my_ts && my_ts < v.end_ts;   // 左闭右开
}
// 考点：begin-ts 是版本生效的时刻，end-ts 是它被新版本取代的时刻

版本像一张写着有效期的通行证。你的时间戳落在有效期里，这张证才对你有效。

事务在 BEGIN 时拿到时间戳，然后拿它去和这个区间比对。

走一遍

步 发生了什么 数据库状态
1 T1 BEGIN（ts=1），R(A) A₀: [0, ∞)。1 落在区间内，读 A₀
2 T2 BEGIN（ts=2），W(A) 不改 A₀，新建 A₁: [2, ∞)。同时把 A₀ 的 end-ts 改成 2，变成 A₀: [0, 2)
3 切回 T1 R(A) 1 仍落在 [0,2)，所以还是读 A₀。这就是可重复读

注意第 2 步。一次写其实动了两个版本：新建 A₁，再改 A₀ 的 end-ts。

为什么需要 end-ts？（课堂追问）

end-ts 一是给版本划边界，二是给垃圾回收用。15:19

  1. 划定边界：后来的事务要知道，每个版本管到哪儿。
  2. 给垃圾回收用：判断还有没有活跃事务能看到这个版本。
// 最老的活跃事务都已经在 end_ts 之后，这个版本就没人看得见了
bool Reclaimable(const Version &v, ts_t oldest_active_ts) {
  return v.end_ts <= oldest_active_ts;
}
// 考点：end-ts 有两个用处，划边界，以及给垃圾回收做判断

但光靠时间戳还不够：事务状态表

时间戳只说版本何时有效，不说创建者提交了没有。16:05 所以还要一张全局的事务状态表。

事务状态表（内存里的哈希表）
  ├─ T1: ts=1, 状态 = ACTIVE
  ├─ T2: ts=2, 状态 = ACTIVE
  └─ T3: ts=3, 状态 = COMMITTED

考点：光有时间戳不够，还要事务状态表查创建者提交了没有

时间戳像草稿上写的日期。日期对得上，还得去查这份稿子有没有正式签发。

完整的可见性判断 = 时间戳区间 + 创建者的提交状态。

写冲突的检测

想写一个对象，先看它最新版本的创建者提交了没有。18:15 没提交，就算写冲突。

T2 想写 A：
  ① 扫版本链，找到最新版本 A₁（end-ts = ∞）
  ② 看 A₁ 的 begin-ts → 查事务状态表 → 是 T1 创建的
  ③ T1 状态 = ACTIVE（还没提交）
  ④ 不能在它之后建新版本 → 【写冲突】→ T2 中止

考点：T2 读到的是 A₀，写的时候却要看到 A₁
考点：物理上看得见，不等于逻辑上可见

这像排队办业务。前面有人占着窗口还没办完，你就不能插进去。

踩坑：T2 这时"读"和"写"看到的不是同一个版本。

读的时候，T2 看到的是 A₀。因为 A₁ 未提交，逻辑上不可见。

写的时候，T2 必须一路走到 A₁。物理上得看到 A₁，才知道自己不能写。

物理上看得见 ≠ 逻辑上可见。

4快照隔离

难度 ★★★★★必会P4 实现的就是它，含先写者胜规则

上面这套行为有个正式名字，叫快照隔离。21:56 事务看到的，是它开始那一刻数据库的一个一致快照。

BEGIN;                                   -- T1
UPDATE t SET v = 'new' WHERE k = 'A';
UPDATE t SET v = 'new' WHERE k = 'B';
COMMIT;
-- 别的事务：A 和 B 要么都看到新值，要么都看不到
-- 考点：快照只含开始前已提交的改动，所以不会有撕裂的写

这像拍一张合影。快门按下那一刻就定格了。后面谁换了姿势，都不影响这张照片。

快照隔离（Snapshot Isolation）：事务只看它开始那一刻的一致快照。

"一致"的含义：快照里只放已提交的改动。这些事务必须在本事务开始之前就已提交。

所以你不会看到撕裂的写。T1 改了 A 又改了 B。别的事务不可能只看到 A 的改动，却看不到 B 的。

写冲突的裁决规则

两个事务抢着写同一个对象，先写的赢，后来的中止。

T1：W(A)，先建好新版本
T2：W(A)，发现最新版本的创建者 T1 还没提交
T2：中止
考点：裁决规则是 first writer wins，课上口误说成了 last writer wins

这像抢车位。先停进去的算数，后到的只能开走。

First Writer Wins（先写者胜）。

踩坑：Andy 在课上口误说成"last writer wins"，立刻自己纠正了。是第一个写的人赢，后来者中止。

踩坑：快照隔离在 #19 那张隔离级别表 里，是正交的一支。它不是"比 READ COMMITTED 弱"，而是另一条轨道上的东西。

5写偏斜：Jim Gray 的弹珠

难度 ★★★★★重要VerifyTxn 不测试、HW5 不考；P4 指南点名要懂

快照隔离有一个独特异常，叫写偏斜。24:04 2PL 和 OCC 都没有它。

补充：这个例子来自 Jim Gray。#17 提过 Jim Gray。Jim Gray 是 1990 年代的图灵奖得主，也是两阶段封锁的发明人。Jim Gray 极擅长把复杂概念讲成大白话。

设定：数据库里有 4 颗弹珠，2 黑 2 白。

T1：把所有【白】弹珠变成【黑】
T2：把所有【黑】弹珠变成【白】
      ↓ 两个事务同时开始
两者都看到一致的快照：黑 黑 白 白
      ↓ 各自执行
T1：把那两颗白的 → 黑     T2：把那两颗黑的 → 白
      ↓ 都提交
结果：白 白 黑 黑    ← 还是 2 黑 2 白，只是【颜色互换了】

真正的串行执行会得到什么？

T1 → T2：先全变黑（黑黑黑黑），再全变白 → 白白白白
T2 → T1：先全变白（白白白白），再全变黑 → 黑黑黑黑

考点：任何串行顺序下，弹珠都是同一个颜色

任何串行顺序下，所有弹珠必然是同一个颜色。 快照隔离下却出现了两种颜色。这就是写偏斜（Write Skew）。

写成 SQL，就是两条再普通不过的语句：

UPDATE marbles SET color = 'black' WHERE color = 'white';  -- T1
UPDATE marbles SET color = 'white' WHERE color = 'black';  -- T2
-- 两边的 WHERE 都按各自的快照去读，看不见对方的写
-- 考点：2PL 读时要拿共享锁，对方拿不到排他锁，写偏斜就出不来

这像两个人对着同一张旧地图改路。各改各的，都没错。合起来一看，路全乱了。

为什么 2PL 没有这个问题：第一步读的时候要拿共享锁。另一个事务就拿不到排他锁去写。而 MVCC 里读者不阻塞写者，于是这个异常就出现了。

踩坑：两个事务改的是不同的弹珠，没有写写冲突。所以先写者胜的规则拦不住它。

7决策一：并发协议

难度 ★★★★★重要P4 不走 2PL，HW5 Q4 和清单都没列

前两讲的协议都能叠在 MVCC 上。29:28 叠上 2PL 之后，读不再需要共享锁。

MVCC + 2PL 的效果

排他锁还在。它只管一件事：同一时刻只让一个事务装新版本。

T1: R(A) → A₀
T1: W(A) → 拿 A 的【排他锁】，建 A₁，A₀.end = 1
T2: R(A) → 读到 A₀，【不需要共享锁！】
T2: W(A) → 申请排他锁被挡（T1 持有）→ 阻塞等待
T1: R(A) → 读到自己写的 A₁
T1: COMMIT → 释放锁
T2: 拿到锁，建 A₂

考点：T1 持有排他锁时，T2 照样读到了 A，纯 2PL 做不到
考点：这里根本没有共享锁，锁加在逻辑对象 A 上

排他锁像会议室门口挂的"正在改稿"牌子。它只拦想改稿的人，不拦来看旧稿的人。

和纯 2PL 的关键差别（课堂追问）：

  • T1 持有排他锁时，T2 仍然读到了 A。纯 2PL 下这做不到。
  • 这里根本没有共享锁。排他锁的作用只是保证"同一时刻只有一个事务能装新版本"。

补充：锁加在逻辑对象 A 上，不是加在某个物理版本上。

8现场演示：PostgreSQL 与 MySQL

难度 ★★★★★重要P4 调试法的出处；系统细节清单明说不考

同样的操作，在 PostgreSQL 和 MySQL 里结果不同。32:17 这一段信息密度非常高，全部记下来。

① PostgreSQL 默认级别 = READ COMMITTED

PostgreSQL 默认读已提交，所以 UPDATE 会读到别人刚提交的新值。

两个终端各开一个事务，表里 id=1, value=100：

步 上面的终端 下面的终端
1 BEGIN; SELECT → 100 BEGIN; SELECT → 100
2 UPDATE value = value+1 → 自己读到 101 SELECT → 仍是 100，因为上面没提交
3 UPDATE ... → 阻塞，上面持有排他锁
4 COMMIT → 释放锁 解除阻塞
5 结果是多少？

Andy 让全班投票，答案是 102。

-- 下面的终端，被阻塞的那条
UPDATE t SET value = value + 1 WHERE id = 1;
-- 解除阻塞后：先读到上面刚提交的 101，再加一
SELECT value FROM t WHERE id = 1;   -- 102
-- 考点：结果是 102 而不是 101，因为 PostgreSQL 默认 READ COMMITTED

这像排队改同一份共享文档。前一个人保存之后，你拿到的就是新版本。你在它上面接着改。

为什么是 102 而不是 101？因为 PostgreSQL 默认是 READ COMMITTED，不是 REPEATABLE READ。

9决策二：版本存储

难度 ★★★★★必会HW5 Q4 直接考，清单明列，P4 用增量式

版本存储决定旧版本放在哪、怎么串起来。50:47 这是最重要的一个决策。

基本结构是版本链（version chain）。用元组头部当指针，把版本串成链表。索引指向链头。

struct TupleHeader {
  ts_t begin_ts, end_ts;   // 可见区间
  RID  next_version;       // 指向链上的下一个版本
};
// 索引里存的是链头的位置

版本链像一串钥匙。索引只拎着第一把，其余的顺着环一把把摸过去。

三种方案

三种方案的区别，就是旧版本复制多少、放在哪。

方案 做法 谁在用
① 追加式（Append-Only） 每次更新完整复制整条元组，追加到同一个表空间 PostgreSQL 和它的所有 fork
② 时间旅行式（Time-Travel） 也是完整复制，但存进一张独立的"旧版本表" SQL Server。SAP HANA 曾用，后来废弃
③ 增量式（Delta） 只存被修改列的旧值（diff）。主表里直接覆盖成最新版 MySQL、Oracle。它们管这叫回滚段（rollback segment） 
UPDATE 改了一千列里的一列：
  追加式   → 复制整条元组，一千列全复制，放回原表
  时间旅行 → 复制整条元组，一千列全复制，放进旧版本表
  增量式   → 只记那一列的旧值，放进回滚段
考点：三种版本存储及谁在用，增量式最好

① 追加式与版本链顺序

追加式的版本链有两种排法，PostgreSQL 选了旧到新。55:00

顺序 链头是 找最新版本 更新时
旧 → 新 最旧的版本 要一路扫到底。链很长就完蛋 索引不用改，链头没变
新 → 旧 最新的版本 直接就是链头 每次都要更新所有索引

PostgreSQL 用的是旧 → 新。

// 旧 → 新：拿最新版本，要从链头一路走到链尾
Version *v = index->Lookup(key);           // 链头是最旧的版本
while (v->next != nullptr) v = v->next;    // 链越长，走得越久
// 考点：旧到新，更新不用动索引，但读最新版要扫全链
// 考点：新到旧，读最新版最快，但每次更新都要改所有索引

旧到新像翻族谱。从老祖宗那页开始，想找最小的孙辈，得翻到最后一页。

② 时间旅行式的好处

旧版本全放在独立的表里，垃圾回收只动那张表，不打扰主表。58:30

主表      ：事务都在这里跑
旧版本表  ：所有旧版本都在这里
垃圾回收  ：只扫旧版本表，完全不打扰主表
考点：时间旅行式的关键好处，是 GC 不用碰主表

这像把旧报纸搬进储藏室。大扫除只清储藏室，不打扰客厅里的人。

踩坑：PostgreSQL 的 VACUUM 必须去动主表。主表就是所有事务正在跑的地方，很可能互相干扰。

③ 增量式：为什么它最好

增量式只记被改那几列的旧值，主表永远是最新版。59:13

UPDATE 时：
  ① 把【被改的那几列】的旧值复制到【回滚段】
  ② 主表里【直接覆盖】成最新值
  ③ 主表元组的指针指向刚才那条 delta 记录

考点：读旧版本像打 patch，从最新版一路倒推回去
考点：增量式解决了 #19 OCC 私有工作区整条拷贝的痛点

要读旧版本 A₂ 时，就像打 patch。从主表拿到 A₃，然后依次应用 delta 记录倒回去。

这像文档的修订记录。正文永远是最新稿，旁边只记哪几个字改过。

补充：一千个属性只改了一个，只需要存那一个的旧值。追加式却要复制全部一千个。这正是 #19 OCC 私有工作区 那个痛点的解法。

垃圾回收也简单。只要水位线一过，整块回滚段直接丢掉，主表纹丝不动。

10决策三：垃圾回收

难度 ★★★★★必会HW5 Q4 直接考，P4 要实现，清单明列

垃圾回收要清两类版本，判断标准是一条叫水位线的线。1:01:11

  1. 已提交事务留下的过期旧版本。
  2. 被中止的事务创建的版本。这些版本肯定没人能看到，必须清掉。
ts_t watermark = txn_table.MinActiveTxnId();   // 全局最小活跃事务 ID
for (Version *v : versions)
  if (v->end_ts <= watermark || v->creator_aborted) Reclaim(v);
// 考点：GC 清两类版本，过期的旧版本，以及被中止事务建的版本

判据：水位线（watermark）

事务状态表里维护一个"全局最小活跃事务 ID"。只要这条线往前推，早于它的版本就都可以安全回收。

踩坑：前提是没有事务挂着好几天不结束。有这种事务，水位线就推不动。

两大类做法

元组级 GC 去扫版本，事务级 GC 靠事务自己记账。

A. 元组级 GC

A-1：专职 VACUUM 进程

专职进程定期扫表，把没人看得见的版本删掉。

把"当前活跃的时间戳集合"告诉 vacuum
        ↓
它顺序扫表，看每条版本的 begin/end
        ↓
没有任何活跃事务能看到的 → 删掉

考点：顺序扫全表会污染缓冲池，PostgreSQL 用可见性位图只读改过的页

这像保洁员只打扫今天有人用过的房间。没人进过的房间，就不用开门。

踩坑：顺序扫全表很糟。上次之后根本没改过的页也要读进来。这会污染缓冲池，挤掉有用的数据。

补充：PostgreSQL 的解法是可见性位图（visibility map）。它记录哪些页自上次 VACUUM 以来被改过。它不知道怎么改的，只知道改过。但这就够了，只读这些页即可。

A-2：协作式清理（Cooperative Cleaning）

事务沿版本链找版本时，顺手把没人要的版本清掉。

事务顺着版本链找自己要的版本时
        ↓
沿路遇到"任何活跃事务都看不到"的版本
        ↓
顺手把它清掉

考点：协作式清理是旧到新链顺序的好处
考点：SELECT 变成了会写数据的操作，不取 lock，要取 latch
考点：从来没人读的版本永远清不到，所以还要定期全面 VACUUM

这像下楼时顺手带走垃圾。可没人走的那段楼道，就一直没人收拾。

补充：这正是旧 → 新版本链顺序的一个好处。反正你本来就得从头扫一遍。

踩坑：代价是一个 SELECT 变成了会写数据的操作。逻辑上没改数据库，物理上改了。所以它不取逻辑锁，但要取物理 latch。这又是一次 lock vs latch 的分界。

踩坑：微软管这个叫"落灰的角落"（Dusty Corners）。协作清理只能清到有人读过的版本。从来没人读的那些，永远不会被清。

所以两种机制都得有。还是要定期跑一次全面的 VACUUM。

B. 事务级 GC

事务自己记下作废了哪些版本，提交时把清单交出去。

事务运行时自己记账："我作废了 A₂、B₆ ……"
        ↓
提交时把这份清单交给 vacuum
        ↓
vacuum 不用满世界找，直接照单清理

考点：事务级 GC 靠事务自己交清单，元组级 GC 要自己去扫版本

这像退房时自己列好清单交给前台。保洁不用一间间去敲门。

这是集中式的做法，对应上面那个去中心化的做法。

MVCC 下，索引得决定指向哪个版本。1:08:56 主键索引好办，二级索引才难。

二级索引的 value 该存什么？

方案 存什么 代价

-- 考点：MySQL 用逻辑指针，走到主键叶子时元组已经到手，几乎不亏

逻辑指针像通讯录里存名字，物理指针像存住址。朋友一搬家，住址就得改，名字不用。

补充：MySQL 用的是逻辑指针，二级索引里存的就是主键。

收益巨大：链头怎么变，二级索引都不用动。

PostgreSQL 的另一个特殊做法

多数 MVCC 系统不在索引里存版本信息，PostgreSQL 存。1:15:49

原因是 PostgreSQL 的链是旧 → 新，而且版本链可能跨越多个页。为了不用整条链扫一遍，它在索引里为不同版本放多个条目。这样你能直接跳到链的中间。

索引 key=A → 版本 A₀ 所在的位置
索引 key=A → 版本 A₁ 所在的位置   ← 同一个键，多个条目
索引 key=A → 版本 A₂ 所在的位置
考点：索引里放版本条目，扫描更快，但删除更慢

这像一本书的目录里，同一章列了好几个页码。翻得快，可改版时每个页码都要改。

踩坑：代价是扫描更快，但删除更慢。清理时，还得去删这些索引条目。

索引必须支持重复键

索引里的同一个键，可能挂着两条不同的逻辑元组。1:17:12 所以索引必须允许重复键。

T1 (活跃): R(A)
T2: 更新 A → 建新版本 → 然后【删除 A】→ COMMIT
    垃圾回收还没跑，索引里 key=A 仍指向那条链
T3: INSERT A          ← 一个【全新的逻辑元组】，但键一模一样

考点：逻辑上是两条元组，物理上索引里有两个相同的键
考点：解法是把 RecordID 或版本信息拼进索引键

这像同一个手机号。旧机主注销了，新机主又用上了。运营商底下其实记着两段记录。

逻辑上，T3 插的 A 和前面那个 A 是两条不同的逻辑元组。因为前一个已被删除，而且提交了。但物理上，索引里存了两个相同的键。

T1 还必须能读到它自己那个版本（A₁）。哪怕底下那个新的 A₃ 已经提交。

解法（呼应 #08 B+ 树处理重复键）：把 RecordID 或版本信息拼进索引键里。这样物理上的字节就能保证唯一。

踩坑：建了唯一索引，不代表索引里物理上没有重复键。
