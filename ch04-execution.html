2查询计划长什么样

难度 ★★★★★重要#12 #13 都在这棵算子树上展开

查询计划是一棵算子树。数据从叶子上的表往上流，流到根就是结果。4:03 它是一个有向的树状结构：

        [ 结果 ] ← 返回给客户端
            ↑
        [ 排序 ]
            ↑
        [ 投影 ]
            ↑
        [ 连接 ]
          ↗   ↖
    [ 过滤 ]  [ 表 B ]
        ↑
    [ 表 A ]     ← 叶子节点 = 要访问的表 / 文件

SELECT a.x, b.y
  FROM A a JOIN B b ON a.id = b.id   -- 连接
 WHERE a.v > 100                     -- 过滤（100 只是示意）
 ORDER BY a.x;                       -- 排序，最后吐给客户端

这像工厂的流水线。原料从最底下进，每个工位加工一下，成品从顶上出来。

叶子是表。数据自下而上，流经各个关系算子（过滤、连接、投影……）。每个算子做一点计算，到根节点就是最终结果。

补充：4:03 Andy 提醒了一句：树其实不是最优的。DAG（有向无环图）更好，因为子表达式可以复用。但不是所有系统都这么做，原因留到后面讲。

"箱子之间的那根线"到底传什么，有一堆设计决策（#13 详讲）：

  • 传单条元组？传一批列？还是传整个结果集？
  • 数据是从下往上推（push），还是从上往下拉（pull）？

3为什么数据库需要排序

难度 ★★★★★重要动机和四个用途，读懂就行，作业不考

数据库排序时，默认数据可能装不下内存。6:03 核心前提没变：这是面向磁盘的数据库（#03 定下的基调）。

要注意，两样东西都可能装不下内存：

  1. 要查的表装不下。
  2. 算子之间的中间结果也可能装不下。那就得先写到磁盘上，再制造"一切都在内存里"的假象。
SELECT * FROM big_table ORDER BY name;
-- 要排 1 GB，只有 800 MB 可用：快排没法一口气排完
-- 考点：面向磁盘的数据库会故意选渐近复杂度更差、但顺序 I/O 更多的算法

所以我们会故意选渐近复杂度更差、但顺序 I/O 更多的算法。 快排在全内存时最快。可一旦要溢出到磁盘，它就完蛋了。

这像在一张小桌子上整理一大摞卷子。桌子摊不开，只能分批理好，再一摞摞合起来。

补充：7:17 这又是一条"别指望 OS"的论据，呼应 #04 对 mmap 的批判。OS 完全不知道这个查询计划要干什么，我们知道。我们知道下一阶段是什么。所以能提前决定数据放哪儿。也能提前决定什么时候读、什么时候写、要不要预取。

需要排序的四个理由

排序不只为了 ORDER BY，去重、连接、建索引都要用它。7:58

理由 说明
① 用户明确要求 关系模型基于集合（SQL 里是包，可以有重复），本身无序。用户要有序，就得写 ORDER BY
② 去重变简单 数据排好序之后，DISTINCT 只需扫一遍。当前 key == 上一个 key，就丢掉。见第 10 节
③ 连接算法要用 Sort-Merge Join（#12）先排序再归并，非常高效
④ 建索引更快 先排序再建 B+ 树，只需沿叶子层"搭脚手架"。这比逐条插入快得多 
SELECT DISTINCT cid FROM enrolled;       -- 排好序，扫一遍就能去重
SELECT * FROM r JOIN s ON r.id = s.id;   -- Sort-Merge Join：先排序再归并
CREATE INDEX idx ON enrolled (sid);      -- 先排序再建树，比逐条插快
-- 考点：除了 ORDER BY，排序还用于去重、连接、建索引
-- 考点：SQL Server 的 spooling index 属于"建索引"这一条

补充：9:22 SQL Server 的 spooling index。优化器发现"要是这张表上有个 B+ 树就好了"。于是当场先排序，建一棵 B+ 树，用完立刻扔掉。这正是理由 ④ 的实战版本。

全内存就随便挑一个

表和中间结果都装得下内存，就随便挑个排序算法。10:04 这时本讲内容基本用不上。Quicksort、Timsort、Powersort……挑你喜欢的就行。

std::vector<Tuple> rows = ScanAll(table);   // 全都装得下
std::sort(rows.begin(), rows.end(), cmp);   // 直接内存排序，完事
// 考点：本讲的外部算法，只在装不下内存时才需要

补充：有个值得用的优化。如果数据基本已经有序，有些算法能识别出来。然后走快路径，比如 Vergesort。识别失败，就回落到 quicksort。

踩坑：11:24 课上关于 Python 的说法有点绕。Python 长期用 Timsort。CPython 3.11 起改用 Powersort，它是 Timsort 的改进版，归并策略最优。不是"改用 quicksort"。

什么时候知道装不下？ 11:24 我们知道 buffer pool 有多大。而且通常每个查询会分到一块固定的工作内存。要排 1 GB 数据，可只有 800 MB 可用，就得回落。

4排序的到底是什么：Run 与物化策略

难度 ★★★★★重要#12 #13 再用早晚物化，作业不直接考

排序的单位叫 run，里面装的是键值对，不只是 key。12:05 排序算法处理的单位叫 run（游程）。输入是未排序（或半排序）的 run，输出是按 key 排好序的 run。

run 里装的不是一串数字，是键值对：

run = [ (key, value), (key, value), ... ]
        ↑       ↑
    排序键    整条元组 或 指向它的 RecordID

value 存什么，取决于你在建什么系统：

策略 谁用 value 存什么 为什么
早期物化 Early Materialization 行存（#06） 整条元组的字节 反正取页时整行都拿到了，顺手带上。免得以后再回去取
晚期物化 Late Materialization 列存 RecordID / 列内偏移量 列存本来就只取需要的列。真要用其他列时，再顺着 RecordID 去拿。别在管道里搬你最后要扔掉的数据 
SELECT name FROM student ORDER BY age;
-- 行存，早期物化：run 里是 (age, 整行字节)
-- 列存，晚期物化：run 里是 (age, RecordID)，排完再去取 name
-- 考点：早期物化适合行存，晚期物化适合列存

早期物化像搬家时连箱子一起搬。晚期物化像只搬箱子上的标签，用到哪箱再去仓库取。

补充：sort key 是什么？（14:48 课堂提问）就是表里你要排序的那几列。它跟建索引的 key 是同一个概念。

15:30 晚期物化其实很有争议。 Vertica 是最早搞列存加晚期物化的系统之一。后来 Vertica 开始从 S3 读数据，又说这是个错误，把它去掉了。ClickHouse 则在 2025 年年中发了篇博客，说新加了晚期物化。行存那边，几乎一致选早期物化。

本讲后面的图里只画 key，不画 value。 但你要记得，实际上还得把 value 一路带着。

5Top-N 堆排序

难度 ★★★★★必会P3 要实现 TopN，含 Sort+Limit 改写

既要排序又限了条数，就不用全排。扫一遍，维护一个小堆就够了。17:20 这是一个特例优化。

SELECT * FROM enrolled
 ORDER BY sid ASC
 FETCH FIRST 4 ROWS WITH TIES;   -- SQL 标准写法
                                 -- MySQL/PG 的 LIMIT 4 是它的简化版

补充：WITH TIES 的意思是：并列的也要。所以哪怕限定 4 行，只要第 4 名有并列，输出就会多于 4 行。

算法：扫一遍 + 一个优先队列

边扫边往容量为 N 的堆里塞，比堆里最大值还大的直接扔。18:04 维护一个容量为 N 的排序堆，顺序扫一遍数据：

看到 堆的状态 动作
3 [] 空的，放进去 → [3]
4 [3] 4 > 3，接在后面 → [3,4]
6 [3,4] → [3,4,6]
2 [3,4,6] 2 最小，插到最前 → [2,3,4,6]
9 [2,3,4,6] 9 > 堆里最大值 6。直接跳过，连处理都不用
1 [2,3,4,6] 插最前，6 被挤出去 → [1,2,3,4]
4 [1,2,3,4] 与堆内的 4 并列，WITH TIES。扩容收下 → [1,2,3,4,4]
8 … 8 > 最大值 → 跳过 
for (auto &t : table) {
  if (heap.full() && t.key > heap.max()) continue;   // 比最大值还大，直接跳过
  heap.push(t);                                       // 否则塞进去
}
// 考点：Top-N 只扫一遍，复杂度 O(N)，靠"跳过"省掉大部分工作
// 考点：WITH TIES 会让输出多于 N 行，堆得扩容

这像选拔赛只留前四名。新来的人成绩比第四名还差，看都不用看。

复杂度：只扫一遍数据，O(N)。N 是元组数。堆的维护是常数级的小开销。

踩坑：关键在于"跳过"。 只要维护好堆里的最小值和最大值就行。绝大多数元组，连比较都不用做。

课堂讨论：内存够不够？谁来估？

只有那个堆要放在内存里，原始数据顺着 buffer pool 流过去就行。20:29 学生问：怎么知道输出装得下内存？多个查询并发怎么办？

  • 原始数据不需要装进内存。 顺序扫过去就行。淘汰谁，由 buffer pool 按 #04 的替换策略 决定。只有那个堆需要在内存里，而它通常很小。
  • PostgreSQL 的做法：每个查询给固定额度（work_mem），再限制并发查询数。比较死板。
  • 21:47 商业系统灵活得多：额度可以互相借用。我这个查询没用完 100 MB，可以借给别的查询。资源调度，是企业级系统明显更强的一块。
  • 但你要是写 FETCH FIRST 1000000000 ROWS，那就真有问题了。 好在 SQL 是声明式的，我们提前就知道你要多少行。
SET work_mem = '64MB';   -- PostgreSQL 给每个查询的固定额度（64MB 只是示意）
-- 商业系统：这个查询没用完的额度，可以借给别的查询
-- 考点：估内存宁可估大，几乎所有系统都会加一个 fudge factor

估内存像出门带钱。宁可多带点，也别走到半路才发现不够。

并列很多怎么估？ 22:32 靠直方图估计这一列里有多少个不同值。这里的数学有点玄。而且直方图只是摘要，不是真实数据。

补充：23:16 一条通用经验：估内存永远往多了估。 你不知道你不知道的东西。真跑出来之前，没人知道结果集多大。所以几乎所有系统都加一个 fudge factor（保险系数）。估出 100 条，就按 150 条分配。免得跑到一半还要 resize 哈希表。

"成本估算是数据库的黑魔法，所有人都很烂。" 这块有两讲专门讲（#15 #16）。

6外部归并排序

难度 ★★★★★必会HW4 Q1 算遍数和 I/O，P3 Sort 对应

装不下内存，就分块排好写回磁盘，再一轮轮归并。23:55 一般的 ORDER BY 没有 LIMIT。估计又装不下内存，就用外部归并排序（External Merge Sort）。

它是分治思想。每一趟（pass）分两个阶段：

  1. 排序阶段：把能装进内存的块读进来。用你喜欢的内存排序算法排好，写回磁盘。
  2. 归并阶段：把同样大小的已排序 run 凑在一起。两两（或 K 个）归并成更大的 run。

重复，直到全部有序。

原始：  [3,1] [9,4] [6,2] [8,5]     （数字只是示意）
pass 0：[1,3] [4,9] [2,6] [5,8]     每块内部先排好
pass 1：[1,3,4,9]  [2,5,6,8]        两两归并
pass 2：[1,2,3,4,5,6,8,9]           再归并一次，完成

这像整理一大堆扑克牌。先每人理好一小叠，再两叠两叠地合并。

二路归并（2-way）

二路归并每趟合并 2 个 run，最少只要 3 个缓冲页。先看最简单的情况：

  • N = 数据总页数
  • B = 可用的缓冲页数
  • 二路最少需要 B = 3：2 页放输入，1 页放输出

Pass 0（排序趟）：把磁盘上每一页读进来，页内的 key 排好，写回去。得到 N 个 1 页大小的有序 run。

Pass 1：取两个 1 页的 run 归并 → 2 页的 run Pass 2：取两个 2 页的 run 归并 → 4 页的 run Pass n：…… 直到只剩一个 run。

归并怎么做？ 28:49 两个迭代器，各自指着一个 run 的当前位置。比较两边的 key，小的写到输出页，那个迭代器往前挪一格。输出页满了，就写盘、清空、复用。

一边先走完了怎么办？33:49 把另一边剩下的整个抄过去。 因为 run 内部本来就有序。

while (l.valid() && r.valid()) {
  out.Append(*l <= *r ? *l++ : *r++);   // 两边比一比，小的写进输出页
  if (out.Full()) out.FlushAndReset();  // 输出页满了：写盘、清空、复用
}
CopyRest(l, out);  CopyRest(r, out);    // 一边走完，另一边剩下的整个抄过去
// 考点：二路归并最少要 3 个缓冲页，2 页放输入，1 页放输出

为什么只需要 3 页？（课堂高频疑问）

run 内部有序，所以每个 run 只要读当前这一页。31:38 归并两个 4 页的 run，为什么不用把 8 页全读进来？

因为 run 内部是有序的。 每个 run 我只读当前那一页。左边这一页的迭代器走过某个 key 后，我可以肯定一件事。这个 run 后面的页里，不会有更小的 key。 所以我永远不用回头看，一次只要一页。

左 run：[页1][页2][页3][页4]    内存里只放当前这一页
右 run：[页1][页2][页3][页4]    内存里只放当前这一页
输出：  [    ]                  第 3 页
考点：归并两个 4 页的 run，每个 run 只要读进一页，不用 8 页全读

这像两队按身高排好的人，要合成一队。每队只看排头那个人就够了。

这就是外部归并排序对内存要求这么低的原因。

K 路归并（一般形式）

给了 B 个缓冲页，就一次归并 B−1 个 run，留 1 页写输出。36:00 有 B 个缓冲页，就别浪费：

阶段 产生多少个 run 每个多大
Pass 0 ⌈N / B⌉ 个 B 页（全部 B 页都用来读+排）
Pass 1…n 每次归并 B−1 个 run 上一趟的 (B−1) 倍（留 1 页写输出）

公式：

遍数 = 1 + ⌈ log_(B−1) ⌈N / B⌉ ⌉
总 I/O = 2N × 遍数          （每趟都要把 N 页完整读一遍 + 写一遍）
考点：遍数和总 I/O 的公式要会写

这像打擂台赛。一轮能同时上场的人越多，比赛需要的轮数就越少。

完整例子：N = 108 页，B = 5 页

108 页数据、5 个缓冲页，要走 4 趟，一共 864 次页读写。36:43 每趟归并 B−1 = 4 路：

趟 输入 输出 run 数 每个 run 大小 最后一个
Pass 0 108 页原始数据 ⌈108/5⌉ = 22 5 页 3 页
Pass 1 22 个 run ⌈22/4⌉ = 6 20 页 8 页
Pass 2 6 个 run ⌈6/4⌉ = 2 80 页 28 页
Pass 3 2 个 run 1 108 页 无 
验算公式：1 + ⌈log₄ 22⌉ = 1 + ⌈2.23⌉ = 4 趟
总 I/O：2 × 108 × 4 = 864 次页读写
考点：N=108、B=5，验算是 4 趟、864 次 I/O
考点：多给缓冲页，减少的是趟数，不是每趟的 I/O 量

补充：规律：每趟的 I/O 量是恒定的，都是 2N。 多给内存，并不能减少单趟的 I/O。它减少的是趟数。 B 从 5 涨到 11，也就是 B−1 = 10 路归并。趟数就从 4 掉到 2。算式是 1 + ⌈log₁₀ ⌈108/11⌉⌉ = 1 + ⌈log₁₀ 10⌉ = 2。

7双缓冲：把 I/O 停顿藏起来

难度 ★★★★★重要HW4 不考，但解释 I/O 停顿这条主线

上面的算法每读写一次磁盘，整个系统就干等一次。38:13 这个明显的问题，课堂上学生也提了。

  • 机械硬盘：一次寻道 10～50 毫秒。
  • SSD 快得多。但 SSD 想跑满带宽，I/O 队列里必须同时有很多请求在并行。一次只发一个请求，性能远不如标称值。

解法：把缓冲区一分为二，乒乓切换

双缓冲就是把缓冲区劈成两半。一半在算，一半在预取，做完互换。39:34

缓冲池的一半：正在做归并 + 把输出写盘   ← CPU 在忙
缓冲池的另一半：正在从磁盘预取下一批数据 ← I/O 在忙
        ↓ 做完之后互换角色 ↓

Prefetch(buf[1], next_pages);   // 后台：磁盘往另一半里读下一批
Merge(buf[0]);                  // 前台：CPU 归并这一半
std::swap(buf[0], buf[1]);      // 做完互换角色
// 考点：双缓冲掩盖 I/O 停顿，代价是归并路数变少，可能多一趟

这像两口锅轮着炒菜。一口锅在炒，另一口在备料，谁也不闲着。

效果：CPU 计算和磁盘 I/O 重叠起来，磁盘停顿就被藏住了。

代价：能用来归并的缓冲页减半。单趟的归并路数变少，可能多出一趟。这是个真实的权衡。

补充：1:03:35 Andy 在总结里把这一点和 #10 串了起来。我们要多线程并发读写，来掩盖 I/O 停顿。正因为这样，上一讲的 latching 才是必需的。

8比较操作的工程优化

难度 ★★★★★了解工程优化，HW4 和 P3 都不碰

真实数据里，比较两个 key 很贵，得专门优化。41:03 算法课把"比较两个 key"当成 O(1) 的免费操作。可真实的 key 常常是字符串，或者多列组合。而你要比十亿次。

std::sort(rows.begin(), rows.end(), cmp);   // cmp 会被调用十亿次
// 每次调用都要跳转，里面还得查 catalog 判断类型

这像收银员每扫一件商品，都要翻一遍价目表。一件不慢，十亿件就慢了。

补充：16:44 排序在数据库里根本不是"已解决问题"。 DuckDB 在 2025 年发了篇博客。说把整个排序算法重写了一遍，用的正是下面这些技术。这就像事务，1970 年代的话题，至今也没解决完。

① 代码特化 / JIT（Code Specialization）

给每种类型备一个专用的比较函数，内联进排序里。41:45 C++ 的 std::sort 要你传一个比较函数指针。每比较一次，就跳转调用一次。函数里面还得判断"这些字节到底是整数还是字符串"。这要查 catalog。

做法：预先生成一堆比较函数，每个都针对特定类型硬编码。然后把它们内联进排序算法。跳转省了，类型判断也省了，直接 reinterpret_cast。

bool Cmp(const char *a, const char *b, Type t);   // 通用版：每次都判断类型
bool CmpInt(const char *a, const char *b) {       // 特化版：类型写死，能内联
  return *reinterpret_cast<const int *>(a) < *reinterpret_cast<const int *>(b);
}
// 考点：代码特化省掉跳转和类型判断，PostgreSQL 用 Perl 脚本是因为 C 没有模板

这像把一把万能钥匙，换成每扇门专配的钥匙。不用每次都试。

系统 做法
SingleStore（#05 客座讲座那家） 查询到达时，用 LLVM 即时 codegen 比较函数，编译成机器码
PostgreSQL 一个有趣的 hack。PostgreSQL 是 C 不是 C++，没有模板。所以从源码编译时，会先跑一个 Perl 脚本。它把比较函数复制出整数版、浮点版……编进二进制。运行时选对应的特化版本。这是手工版的模板

② 前缀比较 / 后缀截断（Suffix Truncation）

字符串先比前缀，前缀不同就直接出结果。44:21 比较两个字符串，本来要逐字节走。优化：预先取出 varchar 的前缀，比如塞进一个 32 位整数。

先比前缀（一条整数比较指令）
  ├─ 不同 → 直接出结果，绝大多数情况走这条
  └─ 相同 → 才回落到完整的慢速比较
考点：前缀比较解决的是"字符串逐字节比太慢"

这像查字典先看首字母。首字母不同，后面就不用看了。

补充：这个思路，在 #08 B+树 讲前缀压缩时出现过。同一个套路，两种用法。

③ 归一化键（Normalized Keys）

归一化键把任何类型的 key 都变成定长二进制串。之后一律用 memcmp 比。45:04 这是 1970 年代的老技术，DuckDB 那篇博客里也在用。

问题：varchar 是变长的。可我们希望所有东西都定长、紧凑，这样才能快速比较。字典编码（#06）能解决一部分。

踩坑：同一列来自不同文件时，字典码可能不一致。 所以字典编码解决不了全部问题。

做法：把任意类型的 key 变换成一个二进制表示，补齐到定长。要做到按字节比的结果，等于按原值比的结果。之后所有比较，都退化成 memcmp。

// (age, name) 变成定长字节串，字节顺序和原值顺序一致
std::string nk_a = Normalize(a.age) + PadTo(a.name, 16);   // 16 只是示意
std::string nk_b = Normalize(b.age) + PadTo(b.name, 16);
memcmp(nk_a.data(), nk_b.data(), nk_a.size());             // 一条 memcmp 搞定
// 考点：归一化键解决的是"变长、多类型的 key 比较慢"

这像把各国货币都换成同一种，再比谁的钱多。

9用 B+ 树代替排序

难度 ★★★★★重要HW4 不考；决策树串起本讲的取舍

聚簇 B+ 树可以直接顶替排序。非聚簇的，通常还不如老老实实排。45:46 学生反复问：B+ 树的叶子层本来就有序，为什么还要排序？

首先，哈希表不行，它是无序的。只有 B+ 树这种有序结构才可以。其次，得看它是不是聚簇的（#03 讲过）。

聚簇 B+ 树（元组的物理顺序 = 索引顺序） 非聚簇 B+ 树
做法 沿叶子层一路扫过去 沿叶子层扫。但每个 key 都要追指针回表取元组
I/O 类型 顺序 I/O，而且已经排好序 随机 I/O，页到处跳
结论 完胜外部归并排序 通常还不如外部归并排序

-- 聚簇索引在 sid 上：沿叶子层扫过去，天然有序，顺序 I/O
-- 非聚簇索引在 sid 上：每个 key 都要回表取元组，随机 I/O
-- 考点：非聚簇不能"先排页号再顺序取页"，因为输出顺序必须跟 ORDER BY 一致

聚簇索引像按学号排好座位的教室，从前往后点名就行。非聚簇像拿着排好的名单，满楼跑着找人。

踩坑：47:52 非聚簇为什么这么糟？ 有一招是"先把要访问的页号排序，再顺序取页"。这里用不了。因为输出必须严格按 ORDER BY 的顺序，你不能重排取页顺序。所以就是纯随机 I/O。

补充：例外：如果是 Top-N，只需要取十来页，非聚簇索引也还行。

10聚合：排序法

难度 ★★★★★重要P3 写的是哈希聚合，这里作对比

聚合就是把同一组的元组凑到一起。办法只有排序和哈希两种。49:23 聚合的核心问题是：怎么快速凑齐"同一组"的元组。

只有两条路：排序，或者哈希。 先看排序。

这像把一堆混在一起的扑克牌按花色分开。要么先整副排好序，要么按花色扔进四个筐。

例 1：DISTINCT 白嫖排序

用户本来就要排序，去重就能顺手做掉，只扫一遍。

SELECT DISTINCT cid
  FROM enrolled
 WHERE grade IN ('B','C')
 ORDER BY cid;

查询计划：

扫描 enrolled → 过滤 grade → 投影 只留 cid → 排序 cid → 去重 → 结果

52:14 去重变成一次线性扫描。 游标顺序往下走，当前记录和上一条相同，就丢掉。

for (auto &row : sorted) {
  if (row.cid == prev) continue;   // 和上一条一样，丢掉
  Emit(row);  prev = row.cid;
}
// 考点：排好序后，DISTINCT 只要一次线性扫描，还不用额外建哈希表

为什么正确？ 数据已经有序。扫到 15-826 时，就绝不可能再遇到 15-445。

为什么说白嫖？ 用户本来就要 ORDER BY cid。去重直接搭这个便车，不需要额外建哈希表。

踩坑：52:58 反过来也成立。哪怕用户没要求排序，优化器也可能主动选排序聚合。 不是必然，但有些系统会。

例 2：GROUP BY + 聚合函数

排好序后，只要盯住"key 变没变"，就知道一组什么时候结束。

SELECT cid, AVG(gpa) FROM ... GROUP BY cid;

53:41 排好序之后，维护运行中的累计值：

聚合函数 需要维护什么
MIN / MAX 见过的最小 / 最大值
COUNT 一个计数器
SUM 一个累加和
AVG 累加和 + 计数器，最后相除

扫描过程：

当前行 prev_key 动作
(15-445, 3.5) NULL 开始新组：count=1, sum=3.5，prev=15-445
(15-445, 3.9) 15-445 同组：count=2, sum=7.4
(15-721, 3.7) 15-445 key 变了。15-445 这组永远不会再出现。算出 AVG 输出，开新组
… … …
（扫完） 把最后一组也输出

  sum = 0;  count = 0;  prev = row.cid;
}
sum += row.gpa;  count++;
// 考点：排序法做 GROUP BY 时，key 一变就说明这一组结束了

11聚合：哈希法

难度 ★★★★★必会P3 Aggregation 要实现，#12 Grace 同构

不需要有序时，哈希通常明显更快，因为排序多干了活。54:58 排序做了多余的工作：你只想分组，它却把组内也排了序。

SELECT cid, COUNT(*) FROM enrolled GROUP BY cid;   -- 没有 ORDER BY
-- 排序法：连组内的顺序都排了，白干
-- 哈希法：同一个 cid 扔进同一个桶就行

这像分快递。只要按小区分好堆，用不着把每堆再按门牌号排一遍。

内存装得下：一趟搞定

扫描数据，边扫边往哈希表里塞或更新条目。完事。

std::unordered_map<Key, Agg> ht;
for (auto &row : table) ht[row.cid].Update(row);   // 边扫边塞，或者更新
for (auto &[k, agg] : ht) Emit(k, agg);            // 扫完直接输出

装不下：外部哈希聚合（两阶段）

装不下就先用 h₁ 切分区写盘。再逐个读回来，用 h₂ 聚合。57:14 又是分治。

阶段 1：分区（Partition）

用哈希函数 h₁ 扫一遍数据。每条记录扔进 B−1 个分区之一，留 1 页读输入：

输入（1 页）─── h₁ ──→  分区0 ┐
                        分区1 ├─ 每个分区是一串页。页满了就写盘、开新页
                        ...   │
                        分区B-2┘

for (auto &row : input)
  partitions[h1(row.cid) % (B - 1)].Append(row);   // 页满了就写盘
// 考点：外部哈希聚合是 1 个输入到多个输出，和外部归并排序方向相反

踩坑：注意这和外部归并排序正好相反。 归并排序是多个输入 → 1 个输出。这里是 1 个输入 → 多个输出。

阶段 2：逐分区计算（ReHash）

59:25 把分区一个一个读进内存，这是顺序 I/O。再用另一个哈希函数 h₂ 建哈希表：

  • DISTINCT：哈希到位置。没条目就放，有就忽略。
  • GROUP BY：哈希到位置，更新那一组的 running total。

一个分区处理完，把哈希表的内容写到结果缓冲区。然后清空哈希表。再处理下一个分区。

for (auto &p : partitions) {
  for (auto &row : p) ht.Upsert(h2(row.cid), row);   // 换成 h2 建表
  ht.FlushTo(result);  ht.Clear();                     // 写出结果，清空
}

为什么这是对的

同一个 key 一定落在同一个分区。所以处理完一个分区，就能放心清空。1:00:01 同一个 key 一定 hash 到同一个分区。 处理完分区 0 之后，15-445 绝不可能再出现在分区 1 里。

h1("15-445") → 分区 0，每次算都是分区 0
考点：处理完一个分区就能清空哈希表，因为同一个 key 只会落在一个分区

这像按姓氏分班点名。姓张的同学全在一个班。点完这个班，就不用再去别的班找姓张的了。

为什么第二个哈希函数必须不同？

h₁ 已经把这些 key "聚"到同一个分区了。1:00:45 h₂ 要是和 h₁ 相同，它们在新哈希表里又会全撞在一起。 换一个函数，才能把它们重新摊开。

size_t part = h1(key) % (B - 1);   // 同一分区里的 key，h1 都落在这个桶
size_t slot = h2(key) % n;         // 换个函数，才能在表里重新摊开
// 考点：第二阶段必须换哈希函数，否则全撞在一起

补充：撞了也没关系。 假设是线性探测哈希表（#07），冲突了就往下探测。

补充：清空哈希表的小技巧：1:01:25 不必真的删页。打个标志位，说"后面看到的都忽略"，就等于零成本清空。

哈希表一定装得下吗？

不能保证，只能靠估算，而且要往大了估。1:00:45 学生问了这个问题，Andy 的回答很坦率：不能保证。 只能靠估算，并且往大了估（见第 5 节）。

如果有十亿个不同 key，要几个 PB，那确实没救。但任何算法在这个规模下都会崩。

真扛不住时，可以递归分区：对装不下的分区，再做一次分区。

某个分区还是装不下 → 对它再做一次分区 → 切成更小的分区，再逐个处理

架构：Dual Execution（双端执行）

本地 DuckDB（客户端 / 浏览器）  ←→  云端 DuckDB 实例
        └────────── 一条查询被拆开：哪部分在云上跑、哪部分在本地跑

MotherDuck 靠的是 DuckDB 的扩展机制。它接管了查询生命周期的每个阶段（parse → bind → optimize → execute）：

1为什么需要连接

难度 ★★★★★了解背景动机，范式不考，不影响后面

连接算子只干一件事：把拆开的表无损地拼回去。5:31 表为什么会被拆开？因为范式。

-- 拆成 students、enrolled、courses 三张表，重复数据没了
SELECT s.name, c.title
FROM students s
JOIN enrolled e ON s.id = e.sid
JOIN courses  c ON e.cid = c.id;   -- 想拿回原来那张巨表，就得连接
-- 考点：范式把表拆开，连接负责拼回来

范式像把一套家具拆成零件装箱运输。连接就是到了地方，再照图纸装回去。

把所有学生、课程、成绩塞进一张巨表      ← 第一范式，大量重复数据
        ↓ 拆开
students 表 + enrolled 表 + courses 表   ← 更高范式，自然的表示方式
        ↓ 想拿回原来的数据？
        JOIN

补充：这是全学期唯一一次提到范式（Normal Forms）。Andy 的态度很明确。

以前这门课教范式和 Armstrong 公理，但现实世界没人用。随便拿 Rails、Django 或者任何 ORM 写个应用。出来的模式基本就是第三范式，够用了。

补充：SQL 笔记里的 3NF 那一节 讲的就是这套拆分规则。本讲讲的是拼回来时怎么快。

2范围界定：我们只做等值内连接

难度 ★★★★★重要P3 改写 HashJoin 要判等值，单条规则

本讲只做一种连接：两张表，按等值条件，做内连接。7:21

  • 等值连接（equi-join）：R.id = S.id
  • 内连接（inner join）
  • 二元（binary）：一次只连接两张表
SELECT * FROM R JOIN S ON R.id = S.id;   -- 等值、内连接、一次两张表
-- 三张表也拆成两两连接：先 R⋈S，再拿结果去 ⋈T
-- 考点：三个限定是等值、内连接、二元
-- 考点：多路连接太难，SQL Server 1998 年做了，2001 年又删了

这就像拼图一次只拼两块。拼好的一大块当成一块，再去拼下一块。

其他类型 情况
左/全外连接、反连接、θ 连接（非等值） 本讲的算法稍作改动都能支持
多路连接（一次连三张以上） 非常难。SQL Server 1998 年做了，2001 年又删掉。有时快得惊人，有时比二元连接还慢
最坏情况最优连接（Worst-Case Optimal Join） 多路连接的现代变体。图遍历场景有用，比如中间结果爆炸的自连接。几乎所有商业系统都没有。RelationalAI 和德国那批系统有。留给进阶课

所以 PostgreSQL、Oracle、MySQL 全都是二元连接。 超过两张表时，由优化器决定连接顺序。先 A⋈B 再 ⋈C，还是先 B⋈C？那是 #15#16 的事。

一条贯穿全讲的铁律

小表放外层，而且"小"按页数算。9:58 这条规矩贯穿全讲。

小表放外层（outer table）。

for (auto &r : outer) {             // 外层：outer table，只扫一遍
  for (auto &s : inner) {           // 里层：inner table，外层每来一份就重扫一遍
    if (r.key == s.key) Emit(r, s);
  }
}
// 考点："小"按页数算，不按元组数，因为开销是取页

外层像排队的人，里层像每人都要翻一遍的厚账本。排队的人越少，账本翻的遍数越少。

26:08 为什么按页数算？因为我们的开销是取页，不是取元组。

术语来自嵌套循环。 最外层的 for 循环叫 outer table，里层叫 inner table。哈希连接明明没有嵌套循环，大家还是沿用这套叫法。

踩坑：大多数查询计划图里，outer 画在左边，inner 画在右边。但这不是标准。Snowflake 就是反的。

3输出长什么样、成本怎么算

难度 ★★★★★必会HW4 成本题的记号和假设沿用 §3

连接算子要先定两件事：往上交什么，成本怎么算。

输出：又是早期 vs 晚期物化

连接往上交的，要么是完整元组，要么只是 RecordID。12:33 这沿用了 #11 的概念。放在连接这里更关键，因为输出要喂给上层算子。

struct EarlyOut { RTuple r; STuple s; };          // 早期物化：两边的列全带上
struct LateOut  { Key key; RID r_rid, s_rid; };   // 晚期物化：连接键加两边的 RecordID
// 上层要别的列？晚期物化得拿 RID 回基表取

早期物化像搬家时把整个柜子扛走。晚期物化只记下柜子在哪个房间，要用时再回去拿。

早期物化 晚期物化
输出元组 R 的全部列 ‖ S 的全部列 连接键，加上两边的 RecordID
好处 再也不用回基表取数据 不搬你最后要扔掉的列
麻烦 管道里搬的数据多 上层要别的列时，得回基表取
谁用 行存 列存

列存为什么愿意付"回表"这个代价？15:13 因为 OLAP 查询要连的表更多。而且连接常常很有选择性。下面可能有十亿条元组，连完只剩两条。再回去补几个列的数据，成本可以忽略。

成本模型：只数磁盘 I/O

成本只数磁盘 I/O 次数，读和写都算。16:32 这和算法课不一样，比较次数一概不数。

int io_count = 0;
void ReadPage(page_id_t pid)  { io_count++; }   // 读一页，记 1 次
void WritePage(page_id_t pid) { io_count++; }   // 写一页，也记 1 次
// CPU 比较、建哈希表、网络、输出结果：一律不记
// 考点：输出开销能忽略，因为所有算法的结果逻辑上完全一样

这就像算搬家成本，只数车跑了几趟。车上箱子怎么码，不算钱。

本讲统一记号：

符号 含义
M 表 R 的页数
m 表 R 的元组数
N 表 S 的页数
n 表 S 的元组数
B 可用缓冲页数

统一忽略：

  • 建哈希表、探测哈希表、比较 key 的 CPU 开销。磁盘太慢，这些不值一提。
  • 网络开销。这里假设单机，分布式见 #23#24。
  • 输出的开销。所有算法产生的结果逻辑上完全一样。顺序可能不同，但关系模型本来就无序。所以这一项对比较没有意义。

贯穿全讲的算例

全讲都用同一组数字算账。R 有 1000 页，S 有 500 页。

R：M = 1,000 页，m = 100,000 元组
S：N =   500 页，n =  40,000 元组
单次页 I/O ≈ 0.1 毫秒

踩坑：22:34 课上口误，说单次 I/O 是"100 毫秒"。幻灯片上的值是 0.1 毫秒，后面所有时间也都对得上它。用 0.1 ms 反推一下：5000 万次乘 0.1 ms，约等于 1.39 小时。

补充：24:01 一个提醒。按 4 KB 一页算，这两张表加起来才 6 MB。塞进 L3 缓存都绰绰有余。 下面那些吓人的数字，都假设每次都得真去磁盘取页。

交叉连接（CROSS JOIN）没救

交叉连接只能两层傻循环硬算。18:26 它没有连接键可用，建哈希表、预排序全都帮不上忙。

SELECT * FROM R CROSS JOIN S;   -- 没有 ON 条件，也就没有连接键
-- 每一对 (r, s) 都要输出，只能硬配

这就像让全班每两个人都握一次手。没有任何捷径，只能一对一对来。

能做的只有批处理，减少取页次数。所以本讲只谈内连接。

4嵌套循环连接（三个版本）

难度 ★★★★★必会HW4 Q1 算成本，P3 实现 NLJ 和 IndexNLJ

嵌套循环就是两层 for 循环。三个版本的差别，只在一次取多少数据，以及里层用不用索引。

朴素版（Simple Nested Loop Join）：稻草人

朴素版对 R 的每一条元组，都把 S 整张表重读一遍。20:22 它是拿来当靶子的稻草人。

for 每个元组 r ∈ R:            ← outer
    for 每个元组 s ∈ S:        ← inner，每次都把 S 整张表扫一遍！
        if r.key == s.key: 输出

这就像每来一个顾客，你就把整个仓库从头翻到尾。

成本 = M + (m × N)

1,000 + (100,000 × 500) = 50,001,000 次 I/O ≈ 1.3 小时
考点：慢在 R 每来一条元组，S 的每一页都要重读一遍
考点：小表换到外层也只省 20 分钟，依然是灾难

换成小表 S 在外层：N + (n × M) = 500 + 40,000×1000 = 40,000,500，约 1.1 小时。省了 20 分钟，依然是灾难。

踩坑：为什么这么蠢？R 里每来一个元组，就把 S 的每一页重新读一遍。

块嵌套循环（Block Nested Loop Join）

块嵌套循环把循环单位从元组换成页。24:44 页已经读进来了。这一页能做的事全做完，再换下一页。

关键洞察是：元组不是孤零零躺在磁盘上的。它们和一堆邻居挤在同一页里（#03）。

for 每个页 P ∈ R:                    ← 循环单位从"元组"变成"页"
    for 每个页 Q ∈ S:
        for 每个 r ∈ P:
            for 每个 s ∈ Q:
                if r.key == s.key: 输出
考点：渐近复杂度没变，还是 O(M×N)，变好的是常数

这就像去超市一次推满一车，而不是买一样东西跑一趟。

成本 = M + (M × N) = 1000 + 1000×500 = 501,000 次 I/O，约 50 秒

补充：26:08 课堂上有个关键澄清。学生指出，这样渐近复杂度没变，还是 O(M×N)。Andy 确认了："对，但常数变好了。在数据库世界里，常数就是一切。"

用上全部缓冲池

缓冲池有 B 页，就留 B−2 页给外表 R，剩下两页一读一写。上面的算法隐含只有 B = 3 页，真实系统当然多得多。

最优分配：

B − 2 页 → 尽量多缓存 outer 表 R 的页
    1 页 → 读 inner 表 S
    1 页 → 写输出
考点：成本 = M + ⌈M/(B−2)⌉ × N

外表一次装得越多，里表从头扫的遍数就越少。这像一次放一大批客人进门。账本每批翻一遍，不用每人翻一遍。

成本 = M + ( ⌈M / (B−2)⌉ × N )

情况 计算 I/O 次数 时间
B−2 ≥ M（全装得下） M + N 1,500 150 ms
B = 102（R 在外） 1000 + ⌈1000/100⌉×500 6,000 600 ms
B = 102（S 在外，小表在外） 500 + ⌈500/100⌉×1000 5,500 550 ms

从 1.1 小时降到不到 1 秒。 靠的仅仅是按页批处理，加上用满缓冲池。

补充：29:50 这个结论很重要。嵌套循环看着弱智，但只要数据全在内存里，它其实非常快。后面讲哈希连接时会看到这一点。有些系统等分区小到能全进内存，就故意退回内存嵌套循环。因为它跑得飞快。

索引嵌套循环（Index Nested Loop Join）

索引嵌套循环不再顺序扫里表。它拿每个 key 去里表的索引里探测。32:37 内层的顺序扫描是罪魁祸首，有索引就用索引。

for 每个元组 r ∈ R:
    用 r.key 去 S 的索引里探测   ← 不再顺序扫 S
考点：C 写不出具体值，要等到 #15 才填得上

这就像查字典直接翻索引页，而不是从第一页读起。

成本 = M + (m × C)

C 是常数，但我们写不出它的值。 它取决于三件事：

  • 索引是 B+ 树、跳表、字典树，还是哈希表。
  • 索引有多大。
  • key 是否唯一。不唯一，就得沿叶子层再扫一段。

等到 #15 查询优化 时，才有足够信息填上 C。

补充：32:37 SQL Server 有一种自动索引，就是 #11 里那个 spooling index。优化器发现"要是有个索引就好了"，就当场建、用完扔。然后给你一条警告："我又给你的查询建了一次这个索引。你要不要考虑永久留着？"决定权交给人。

嵌套循环小结

嵌套循环在内存里很快，一碰磁盘就是灾难。

适合 当心
数据全在内存：超快，很多时候是首选 要读磁盘：灾难
有可用索引：用索引嵌套循环 小表必须在外层
实现最简单。从零建数据库时，第一个实现它 尽量用满缓冲池，批处理 outer 表

5排序归并连接

难度 ★★★★★必会HW4 Q1 考最好最坏成本，回溯易错

排序归并连接先把两张表按连接键排好。然后两个游标并排往下走。34:42 它直接建立在 #11 外部归并排序 之上。

Sort(R); Sort(S);                    // 排序阶段：内部调用完整的外部归并排序
while (r && s) {                     // 归并阶段：两个游标往下走
  if (r->key < s->key) r++; else if (r->key > s->key) s++;
  else { Emit(r, s); s++; }          // 相等就输出，重复键要回溯，见下
}
// 考点：这里的"归并"和外部归并排序里的"归并"不是一回事

这像两队人先各自按身高排好。再从队头开始，一个一个对比。

踩坑：术语容易绕晕。外部归并排序自己有"排序阶段"和"归并阶段"。排序归并连接也有这两个阶段。但两个"归并"不是一回事。 连接的排序阶段，内部调用的是完整的外部归并排序。

两个阶段

先排序，再归并。

  1. 排序阶段：两张表都按连接键排序，用的是外部归并排序。
  2. 归并阶段：两个游标各自往下走，比较连接键，匹配就输出。

完整演练

排好序后，靠一个 last_value 变量决定要不要回溯。38:12 下面的连接键是 id。

R(outer):  100, 200, 200, 300, 500, 600
S(inner):  100, 100, 200, 400, 500

踩坑：需要额外维护一个 last_value。它记的是 inner 游标看到的上一个不同的值。这是回溯的关键。

步 R 游标 S 游标 比较 动作
1 100 100 = 输出，S 游标下移
2 100 100 = 输出，S 下移。值变了，记下 last_value = 100
3 100 200 200 > 100 R 下移。S 后面不可能再有 100
4 200 200 = 输出，S 下移。值变了，记下 last_value = 200
5 200 400 400 > 200 R 下移
6 200 400 R 的新值 200 等于 last_value 回溯！ 把 S 游标退回第一个 200
7 200 200 = 输出，S 下移到 400
8 300 400 300 < 400 R 下移。S 有序，绝不会再出现 300
9 400… 500 400… 500 匹配，输出
10 600 （已到底） 600 > 500 短路：直接结束。后面不可能有匹配

回溯的四个要点

回溯只发生在 inner 表上，起因是重复键。42:30

if (r->key == last_value) {      // outer 又来一个重复值
  s = first_of(last_value);      // 只把 inner 游标退回去，outer 从不回退
}
// 考点：inner 上的连接键唯一（比如主键），就完全不用回溯
// 考点：最坏情况是 inner 整列只有一个值，没有算法能救

这像点名时发现下一个人和上一个人同名。你得把名单翻回去，把同名的再对一遍。

  1. 为什么要回溯：inner 表里，同一个键可能对应多条元组。outer 表里，这个键也可能重复出现。
  2. 什么时候不用回溯：连接键在 inner 表上是唯一列或主键。这样就不会有重复，完全不需要回溯。可惜通常不知道。
  3. 只需要回溯 inner 表，永远不回溯 outer 表。
  4. 最坏情况：inner 表整列只有一个值。每次都要回溯到最开头。没有算法能救这种数据。

补充：43:55 非等值连接（θ join）能做吗？ 能，但回溯逻辑复杂得多。你得根据谓词判断，上面或下面还有没有可能匹配的。

成本

排序归并的成本，就是两次排序加一遍归并。

排序成本 = 排 R 的成本 + 排 S 的成本      （见 #11 的公式）
归并成本 = M + N                          （无回溯时的最好情况）
考点：M + N 只是最好情况，有回溯就写不进公式

算例（B = 100）：

项 I/O
排序 R（1000 页） 4,000
排序 S（500 页） 2,000
归并 1,500
合计 7,500，约 750 ms

踩坑：48:11 课上澄清过，M + N 是最好情况，也就是没有回溯。有回溯，就得知道键的分布和每个键的重复数。这些写不进公式。

补充：这引出一个贯穿 #15#16 的主题。优化器不得不对数据分布做一大堆假设。 不然公式根本没法写。

什么时候选它

数据本来有序，或者查询本来要排序，就选排序归并。

SELECT * FROM R JOIN S ON R.id = S.id
ORDER BY R.id;   -- 排序键就是连接键：排一次，两件事一起办

这就像顺路办事，一趟车办完两件。

  1. 数据本来就按连接键有序，比如聚簇 B+ 树。
  2. 查询本来就有 ORDER BY，而且排的就是连接键。一次排序，两件事一起办。

6哈希连接

难度 ★★★★★必会P3 要实现 HashJoin，HW4 判断题也考

哈希连接是最重要的连接算法。48:11 想让连接快，先实现它。

这像先把一边的人按生日分进不同房间。另一边的人来了，只去自己生日那间找。

核心性质

相同的 key 一定落进同一个槽。

同样的 key，喂给同一个哈希函数，一定得到同样的输出。

if (r.key == s.key) assert(h(r.key) == h(s.key));   // 同样的 key，哈希值一定相同
// 反过来不成立：哈希值相同，key 不一定相同，这叫冲突

所以 R 和 S 里相同的 key，必然落到同一个哈希表槽位。分区也一样，必然落进同一个分区。

基本算法：两个阶段，两个独立的 for 循环

哈希连接先扫 R 建哈希表，再扫 S 去探测。49:37 注意两个循环不再嵌套，而是先后串行执行。

# 阶段 1：Build（构建），扫 outer 表
建一个空哈希表
for 每个元组 r ∈ R:            ← R 叫 build side
    哈希表[ h(r.key) ] ← r

# 阶段 2：Probe（探测），扫 inner 表
for 每个元组 s ∈ S:            ← S 叫 probe side
    在 哈希表[ h(s.key) ] 里查找
    找到条目还要真的比一次 key（哈希会冲突！）
    if 匹配: 输出

# 考点：哈希表里必须存连接键本身，落进同一个槽还要比真值

实践中用什么哈希表？ 49:37 几乎都是线性探测哈希表（#07）。它简单、快，分布式下也好用。

踩坑：哈希表里至少要存连接键本身。哈希函数不保证没有冲突。落到槽里，还得再比一次真值。

它和索引嵌套循环有什么区别？

从高层看，两者没区别，都是拿 key 去探测一个结构。51:42 这是学生问的好问题。Andy 说，区别在下面这几处。

for (auto &r : R) btree_index.Find(r.key);   // 索引嵌套循环：现成的 B+ 树，每次 O(log n)
for (auto &s : S) hash_table.Probe(s.key);   // 哈希连接：临时现建的哈希表，每次 O(1)
// 考点：十亿条元组时，O(1) 和 O(log n) 的差距是决定性的

一个是去图书馆查现成的目录卡。一个是为这次活动现做一张签到表，活动完就扔。

索引嵌套循环 哈希连接
用什么 已有的索引 临时现建的哈希表，用完就扔
结构 通常是 B+ 树。CREATE INDEX 默认给你 B+ 树，几乎所有系统都是 哈希表

7Bloom Filter 优化（Bloom Join）

难度 ★★★★★必会#25 复习清单点名 Bloom Join

Build 侧建哈希表时，顺手再建一个 Bloom Filter，交给 probe 侧先过一遍。52:26 这是一个便宜又有效的优化。Bloom Filter 见 #09。

for (auto &s : S) {
  if (!bloom.MayContain(s.key)) continue;        // 肯定不在：直接丢，不碰哈希表
  if (auto m = ht.Probe(s.key)) Emit(*m, s);     // 可能在：再去真探测
}
// 考点：省掉的是落槽、扫槽位、逐个比 key 这段最贵的活
// 考点：选择性越高，丢掉的元组越多，收益越大

这像门口保安先对一眼名单。名单上肯定没有的人，连大厅都不让进。

Build 侧（扫 R）：      建哈希表  +  顺便建一个 Bloom Filter
                                        │
                                        │ ← 把 filter "横着"递给 probe 侧
                                        ↓
Probe 侧（扫 S）：  先查 Bloom Filter ──不在──→ 直接丢弃，不碰哈希表
                          └────可能在──→ 再去探测哈希表

为什么值？ 反正都要算哈希值。但落到哈希表、扫槽位、逐个比 key，才是真正贵的部分。 查 Bloom Filter 要快得多。

选择性越高，收益越大。 选择性高，就是丢掉的元组多。54:36 在很有选择性的连接上，可以有 2 倍提速。

补充：它的别名很多：Sideways Information Passing（侧向信息传递）、Bloom Join、半连接优化。

踩坑：它有点"违规"。查询计划里，数据本来自下而上流动。这里却在两个兄弟算子之间开了一条侧信道。但收益太大，值得破例。

8Grace 哈希连接（分区哈希连接）

难度 ★★★★★必会HW4 Q1 考成本和倾斜时的递归分区

哈希表装不下，就先把两张表切成小分区，再一对一对地连。54:36 切分用的是同一个哈希函数。上面的基本哈希连接，假设哈希表装得下内存。

这像两个班一起分组讨论。先按学号尾数把两边的人分进不同教室。每间教室只管自己的人。

踩坑：哈希表溢出到磁盘是最糟的情况。探测是随机访问，每次探测都可能是一次随机 I/O。性能会被彻底摧毁。

解法还是分治。 这和 #11 外部哈希聚合 一模一样。

两个阶段

第一阶段只管分桶，第二阶段一个桶一个桶地连。

阶段 1：分区（Partition）

用同一个哈希函数 h₁：
  扫 R → 分成 k 个桶：R₀ R₁ ... R_{k-1}
  扫 S → 分成 k 个桶：S₀ S₁ ... S_{k-1}
  桶页满了就写盘、开新页

阶段 2：逐分区连接（Probe）

for i in 0..k-1:
    把 Rᵢ 读进内存，建哈希表
    读 Sᵢ，逐条探测，输出匹配
    扔掉哈希表，处理下一个分区

为什么正确？（课堂上被追问了）

R 的第 i 个分区，只可能和 S 的第 i 个分区匹配。1:02:14 课上有学生追问。"会不会有 R 的第 0 层和 S 的第 3 层能匹配上？"

int part_r = h1(r.key) % k;   // R 这条去哪个分区
int part_s = h1(s.key) % k;   // S 这条去哪个分区
// r.key == s.key 时，part_r 一定等于 part_s
// 考点：哈希函数是确定性的，所以只需要分区 i 对分区 i

这像按姓氏分教室。姓张的不管来自哪个班，都只会进张字那间。

不可能。 哈希函数是确定性的。相同的输入得到相同的输出，再模同一个 k，一定落在同一层。

Andy 的类比是："这跟排序归并一样。因为排过序，我知道不可能凭空出现一个本该在上面的值。 要是我的排序算法错了，那我有的问题就大了。"

名字的由来

Grace 这个名字，来自一台日本的数据库专用机器。55:18 教材叫它"分区哈希连接"，文献里更常叫 "Grace Hash Join"。

GRACE 是 1980 年代日本造的一台数据库专用机器。机器早已不存在了。但它的哈希连接算法，今天全世界都在用。

递归分区

某个分区还是装不下内存，就只对它换个哈希函数再分一层。1:03:24 这种情况就是数据倾斜。

if (partition[i].pages() > budget) {   // 只有撑爆的分区才再分
  RePartition(partition[i], h2);       // 换一个哈希函数，或者换 seed
}
// 探测时，落进这个分区的 key 也要多调一次 h2，才能对齐
// 考点：所有 key 都一样时，怎么分都在一起，要回落到块嵌套循环

这像一间教室挤爆了，只把这一间再拆成几个小组。别的教室照常上课。

    ┌─ 分区 0：正常 ────────────→ 直接进第二阶段
    ├─ 分区 1：太大了 ──→ 换一个哈希函数（或换 seed）再分一层
    └─ 分区 2：正常 ────────────→ 直接进第二阶段

不需要重新分所有分区。 只对撑爆的那个再分一次，其余的原样带到下一阶段。探测时也要对那些 key 多调一次 h₂，才能对齐。

补充：1:04:06 实践经验：真实系统里通常只需要多递归一层。

踩坑：退化情况是所有 key 的值都一样。这时递归分区毫无作用，怎么分都在一起。正确的做法是回落到块嵌套循环连接。

补充：还有另一个回落。分区已经小到不值得建哈希表，就直接做内存嵌套循环。这里回看第 4 节块嵌套循环那段的结论。

成本

Grace 哈希连接的成本是 3 × (M + N)：读一遍、写一遍、再读一遍。

成本 = 3 × (M + N)
       │
       ├─ 读一遍  (M + N)     ← 分区阶段
       ├─ 写一遍  (M + N)     ← 分区写盘
       └─ 再读一遍 (M + N)    ← 探测阶段（此时全在内存）
考点：分区结果要写盘再读回来，所以是 3 倍，不是 2 倍

算例：3 × 1500 = 4,500 次 I/O，约 450 ms。

踩坑：递归分区的额外开销写不进公式。这和索引探测的 C、排序归并的回溯一样，都取决于数据分布。

分区数怎么定？

分区能用多少页，是上层规定的，算子自己说了不算。1:01:32

assert(TotalPages() <= config.max_pages);            // 上限由管理员配置，比如 1 MB

这像公司给你批了固定预算。花多少，不由你定。

桶就是一串页，写满一页就追加一页。能用多少页，是被上层规定的。 上限由管理员在配置里给出。比如"这个查询做哈希连接最多用 1 MB"。内存有限，你不能想用多少就用多少。

9混合哈希连接

难度 ★★★★★必会#25 复习清单列出混合哈希

混合哈希连接把最热的分区留在内存里。其余分区照常走 Grace。1:07:42 它是 Grace 哈希连接在 1980 年代初的改良版。

补充：说说出身。Andy 说这是 Jignesh Patel 的博士导师发明的。Jignesh Patel 是 CMU 另一位数据库教授。Andy 还说："我记得还有图灵奖得主 Jim Gray 参与。"这里 Andy 自己用的就是"我记得"。

思路：先看数据有没有倾斜。倾斜就是某个分区特别热，绝大多数元组都往那儿去。

热分区  → 直接留在内存，压根不写盘，当场建哈希表（或直接内存嵌套循环）
其余分区 → 照常走 Grace 哈希连接：写盘 → 逐个读回来处理
考点："混合"指一次查询里两种算法同时在跑

这像餐厅把最抢手的菜一直放在保温台上。其余的菜，等有人点了再从冷库拿。

"混合"是什么意思？ 热分区那部分，你可以不建哈希表，改用嵌套循环。这样一次查询里，两种算法同时在跑。

为什么难落地

混合哈希连接难落地，因为你很难提前知道哪个分区会热。1:09:06

  1. 你怎么提前知道哪个分区会热？
  2. 更根本的问题：额外的内存，该拿去特殊照顾热分区吗？干脆多缓存几页普通分区，是不是更划算？ 不一定。

补充：这个思路，PostgreSQL 和一批商业系统都做了。但术语很混乱。有的系统把它叫 "hybrid join"，有的叫 "hybrid hash join"。所以很难查清到底谁真的实现了它。

1流水线与流水线阻断算子

难度 ★★★★★必会P3 靠它分 Init/Next，HW4 Q2 也考

执行引擎先把查询计划切成一段段流水线。元组在一段流水线里一路往上流，中间不停。4:32

查询计划是一个算子的 DAG。多数系统实现成树，树是 DAG 的特例。光有这张图还不够，还要把它切成流水线（Pipeline）。

  • 流水线：一段连续的算子序列。元组在里面可以不停顿地一路向上流。
  • 流水线阻断算子（Pipeline Breaker）：位于流水线顶端的那个算子。它必须收齐子节点的全部输入，才能吐出任何一条输出。
while (auto t = left->Next())  ht.Insert(*t);   // 流水线 ①：扫 R，建哈希表
while (auto t = right->Next()) Probe(ht, *t);   // 流水线 ②：扫 S，探测，往上交
// build 不跑完，probe 一条都不能开始，所以哈希连接是阻断点
// 考点：阻断算子必须收齐全部输入，才能吐出任何一条输出
// 考点："流水线"一名来自 1970 年代，元组进了内存就一路推到顶

流水线像工厂的传送带，零件一路往前走。阻断算子像一个工位，非得等整批零件到齐才开工。

        [ 投影 ]
            ↑
        [ 哈希连接 ]  ← 流水线阻断：哈希表没建完就不能开始探测
          ↗       ↖
   [ 扫描 R ]   [ 过滤 ]        Pipeline ①：扫 R → 建哈希表
    Pipeline ①      ↑            Pipeline ②：扫 S → 过滤 → 探测 → 投影 → 输出
                [ 扫描 S ]
                Pipeline ②

常见的流水线阻断算子：

算子 为什么阻断
哈希连接的 build 侧 哈希表没建完就探测，会产生假阴性
排序 全部数据没看完，根本不知道顺序
聚合（GROUP BY） 组没扫完，算不出最终值

补充："流水线"这个名字有来历（7:08）。1970 年代，从磁盘取一条元组太贵了。所以叶子扫描算子取到一条元组后，不急着取下一条。它会尽可能把这条一路推到流水线顶端。能做的事全做完，才回头取下一条。数据进了内存就榨干它，别让它无谓地来回读写磁盘。

踩坑：有个措辞细节贯穿本讲。Andy 反复强调，数据逻辑上自下而上流动。物理上未必如此。 大多数系统其实是从顶上把数据"拉"上来的。见第 6 节。

2处理模型：控制流与数据流

难度 ★★★★★重要三模型总览，要会的都在 §3–§5

处理模型规定两件事：谁指挥算子开工，算子之间怎么传数据。8:27 它决定了系统怎么执行查询计划。

auto batch = child->Next();   // 控制流：父算子调 Next()，指挥子算子开工
Process(batch);               // 数据流：子算子把数据交上来
// 考点：三种模型的区别，就是 batch 里一次装多少条

控制流像老板喊一声"开工"。数据流像传送带上递过来的零件。

和 #06 行存 vs 列存 一样，这里也是一套对 OLTP 更好，一套对 OLAP 更好。每个处理模型都由两条通路组成：

定义
控制流 Control Flow 系统怎么指挥某个算子开始干活
数据流 Data Flow 算子怎么把数据传给下一个算子

踩坑：传的到底是什么？又回到 #11 的早期/晚期物化。可能是完整元组，也可能只是 RecordID 加几列。

三种模型一览

三种模型的区别，只在一次往上传多少条元组。

模型 一次传多少 谁在用
① 迭代器模型（Iterator / Volcano） 一条元组 绝大多数：PostgreSQL、MySQL、SQLite、BusTub。这是课上的归类。Fall 2025 的代码其实是批量版，一次最多 20 条，见 P3
② 物化模型（Materialization） 全部元组 极其罕见。Andy 说："全世界大概五六个系统，其中两个是我写的。"
③ 向量化 / 批模型（Vectorized / Batch） 一批元组 所有现代 OLAP：DuckDB、Redshift、Firebolt、ClickHouse

3迭代器模型（火山模型）

难度 ★★★★★必会BusTub 就用它，P3 所有算子照此写

迭代器模型里，算子每被调用一次，只交一条元组。11:49 它最简单，也最常见。

这像食堂的打饭窗口。你喊一声，窗口给一份。

补充：为什么又叫 Volcano 模型？Goetz Graefe 在 1980 年代末做过一个极有影响力的项目，叫 Volcano。Goetz Graefe 就是 #10 那张 lock/latch 对照表的作者。Volcano 一口气定义了三件事。一是这个迭代器模型。二是怎么并行化它（#14）。三是怎么造查询优化器（#15）。

这不是说 1980 年代之前没人这么做。1970s/80s 的系统本来就这么干。只是 Graefe 把它写成了论文，从此有了名字。教材里叫它迭代器模型。

接口：三个函数

每个算子只需实现三个函数：open、next、close。

class Operator:
    def open(self):   ...   # 构造：打开文件句柄、初始化索引迭代器
    def next(self):   ...   # 返回下一条元组，或返回 null / EOF 表示没了
    def close(self):  ...   # 析构：释放临时内存
# 考点：next() 一旦返回 null，调用者就再也不会调它

这像水龙头。拧开、接水、关上。没水了，你就不会再去拧它。

契约：某个算子的 next() 一旦返回 null，调用者就永远不会再调它。因为下面不可能再有数据了。

执行过程（伪代码）

引擎只在根节点调一次 next()。这个调用一路向下渗透，数据一路向上冒。

# ① 投影（根）
for t in child.next():
    emit(π(t))

# ② 哈希连接
for t in left_child.next():          # ← Pipeline ①：build
    build_hash_table(t)
for t in right_child.next():         # ← Pipeline ②：probe
    if hash_table.probe(t): emit(t ⋈ match)

# ③ 扫描 R                          # ⑤ 扫描 S
for page in R:                       for page in S:
    for t in page: emit(t)               for t in page: emit(t)

                                     # ④ 过滤
                                     for t in child.next():
                                         if pred(t): emit(t)

这像往井里放水桶。绳子一路放下去，水一桶一桶提上来。

补充：emit 是什么？想想 Python 生成器的 yield。它在 for 循环中间冻结状态，交出一条元组。C++ 里实现起来要多写不少机械代码，但概念一样。

一个漂亮的抽象性质

叶子扫描算子内部怎么实现，上层算子完全不需要知道。17:22

std::optional<Tuple> SeqScan::Next() {
  if (pos_ < buf_.size()) return buf_[pos_++];   // 做法一：open() 时已把整张表读进 buf_
  return std::nullopt;                           // 做法二也行：每次现去页里取下一条
}
// 考点：叶子怎么实现，上层算子的代码一个字都不用改

这像点外卖。厨房是现炒还是提前做好，你不用管，按时送到就行。

  • 可以一次性扫完整表，物化到内存缓冲区。之后每次 next() 只挪一下游标。
  • 也可以懒惰地取。每次 next() 才去页里取下一条，页扫完了再取下一页。

两种做法都行，其余算子的代码一个字都不用改。 这就是接口抽象的价值。

优缺点

迭代器模型好写、好调试，代价是每条元组都要一次函数调用。

for (int i = 0; i < 10; i++) {   // SELECT ... LIMIT 10
  auto t = child->Next();        // 拿够 10 条就不再调 Next()，下面立刻停工
  if (!t) break;
  Emit(*t);
}
// 考点：LIMIT 好实现，拿够了就不再调 Next()
// 考点：十亿条元组要调十亿次 Next()。OLTP 碰的元组少，才不在乎

这像一次只搬一块砖。搬十块无所谓，搬十亿块，光弯腰就累垮了。

优点 缺点
接口极简（open/next/close），容易实现 函数调用开销。单次调用不算什么。但十亿条元组就要调十亿次。在现代 CPU 上，这非常贵
容易调试。挂上 GDB，一路走 next 就行
LIMIT 天然好实现。拿够了就不再调 next()
一条元组能一路流到顶，不用频繁回头取数据
适合 OLTP。查询本来就只碰少量元组，开销占比小

补充：这就是 BusTub 用的模型，也是 Project 3 你要写的东西。

补充：20:09 有些系统把流水线推到极致。不只是让数据留在内存，而是设法让它一直待在 CPU 缓存里。德国那批系统（HyPer/Umbra）甚至追求让它留在 CPU 寄存器里，一路到顶。那是最快的存储。

踩坑：18:06 课堂上澄清过。单线程下，左子树没扫完，就不能走右子树。有种技术叫对称哈希连接（Symmetric Hash Join），可以两边同时来。但 Andy 说"基本没人做"。真正的并行是 #14 的事。

4物化模型

难度 ★★★★★必会#25 清单列出，HW4 和 P3 未涉及

物化模型让每个算子一次把全部结果交上去。21:29 它就是迭代器模型，只是一次交全部元组。

def output(self):
    out_buffer = []
    for t in child.output():        # ← 拿到子节点的【全部】结果
        out_buffer.append(f(t))
    return out_buffer               # ← 一次性全部返回
# 考点：只调一次，调完就不用再回头要数据

这像快递不分批发货，攒齐一整车才出发。

next() 只会被调一次。调完就再也不用回头要数据了。

明显的问题

顶上只要 10 条，下面也会把全部结果搬上来。

SELECT * FROM S LIMIT 10;   -- S 有十亿条
-- 物化模型：扫描算子先把十亿条全交上去，LIMIT 再从里面挑 10 条
-- 考点：物化模型最怕 LIMIT 这种只要一点点数据的查询

如果 S 有十亿条元组，顶上只有一句 LIMIT 10。你要在算子之间搬十亿条元组，就为了取 10 条。

缓解手段：算子融合（Operator Fusion）

算子融合把上层的逻辑塞进下层算子。下层只吐有用的数据。22:09

for (auto &t : table_S) {                // 扫描 S 的同时
  if (t.val > 100) out.push_back(t);     // 顺手把过滤也做了，只吐过滤后的
}
// 考点：融合只能在一条流水线内部做，跨流水线不行

这像在仓库门口直接挑货。不合格的，根本不装车。

原本：    扫描 S（十亿条）→ 过滤（剩十条）→ ...
融合后：  扫描 S 的同时就做过滤 ────────→ ...      ← 只吐十条

踩坑：融合只能在一条流水线内部做，跨流水线不行（26:17）。德国那批系统，在"把整条流水线全融合掉"这件事上做得最好。

那为什么还有人用它？

发明物化模型的是一个 OLAP 系统。它假设你会用到一整列的全部数据，但用不到全部的列。24:52

课堂上有学生答"因为发明的人傻"。Andy 立刻纠正：

发明它的人是史上最优秀的数据库研究者之一。

SELECT SUM(price) FROM sales;   -- 要读一整列，其他列一列不碰
-- 投影下推：扫描时只取 price 这一列，往上传的也只有这一列
-- 考点：MonetDB 的前提是用到整列的全部数据，但用不到全部的列

这像只把要用的那一列整卷抽走，别的列留在原地。

真正的理由：那是一个 OLAP 系统。它靠投影下推加算子融合，把不要的列早早扔掉。往上传的只有需要的列。这样就完全省掉了成千上万次 next() 调用的开销。

它在 OLTP 上其实很合理

OLTP 查询碰的数据少，物化模型在这里反而很合理。26:17

SELECT * FROM accounts WHERE id = 42;   -- 示意：只碰一条元组
-- 整个查询只有一条流水线，融合后塌缩成一小段代码

这像去便利店只买一瓶水。根本用不着推购物车。

OLTP 查询本来就不碰多少数据。 有时整个查询只有一条流水线。这时融合之后，它会塌缩成一段极其高效的代码。而且这对内存数据库尤其重要。不用操心磁盘，唯一的目标就是减少函数调用次数。

系统

用物化模型的系统很少，最出名的是 MonetDB。

系统 情况
MonetDB（1990 年代，荷兰 CWI） 首创者
HyRise（德国实验系统） 一开始用，重写时换成了向量化模型
RavenDB（以色列的文档数据库，类似 MongoDB） 做 OLTP，用它很合理

5向量化 / 批模型

难度 ★★★★★必会HW4 Q2 判断题考，#25 清单列出

向量化模型每次往上交一批元组。不是一条，也不是全部。27:40 这是 OLAP 的最优解，恰好卡在前两种模型中间。

def next(self):
    out_buffer = []
    for t in child.next():
        out_buffer.append(f(t))
        if len(out_buffer) >= N:      # ← N = 批大小
            emit(out_buffer)          #    满了才往上交
            out_buffer = []
# 考点：N 通常取 2 的幂，DuckDB 用 1024

这像快递按箱发货。不是一件一件送，也不是攒齐整车。

批大小 N 是多少？ 通常是 2 的幂，1024 或 2048。DuckDB 用 1024，这也是最常见的取值。

为什么这是 OLAP 的正解

一批一批地传，函数调用被摊薄，CPU 也能放开跑。

for (int i = 0; i < 1024; i++) {   // 一次 Next() 处理一整批
  out[i] = in[i].val > 100;        // 紧凑的 for 循环，没有一堆条件跳转
}
// 考点：四个收益是摊薄函数调用、SIMD、GPU 友好、分支少
收益 说明
摊薄函数调用 一次 next() 处理 1024 条，开销除以 1024
SIMD 一批同类型的数据，在内存里连续对齐。塞进 SIMD 寄存器，一条指令处理多个数据
GPU 友好 同理，可以把整批推到 GPU 上算
分支少 算子核心变成紧凑的 for 循环，没有一堆条件跳转。现代 CPU 最喜欢这个

踩坑：术语提醒。原始论文叫它 vectorized model。但今天你搜 "vectorized database"，会搜到一堆 RAG 和向量索引的东西（#09）。完全是两回事。 就当它叫"批模型"。

踩坑：有一个设计难题没细讲（28:19）。批大小是 1024，但过滤之后只剩 300 条了，怎么办？等下面补满再往上传，还是直接传一个稀疏的批？各有利弊。

历史位置

这个想法看着显而易见，但 2006-2007 年才出现。29:46

1980s/90s 的 OLAP 系统，要么用迭代器模型，要么像 MonetDB 一样用物化模型。

过去十年里，任何面向 OLAP 的新数据库都用这个模型。 连一开始用迭代器模型的系统，也纷纷改投。

6计划处理方向：拉 vs 推

难度 ★★★★★必会#25 清单点名，P3 问 BusTub 用哪个方向

数据是从顶上拉，还是从底下推，这是另一个维度。31:51 它和上面三种模型完全正交。

while (auto t = root->Next()) Send(*t);    // 拉：根节点调 Next()，一路往下要数据
scheduler.Run({build_task, probe_task});   // 推：没有 Next()，调度器按依赖启动任务
// 考点：推模型把控制流（调度器）和数据流（任务之间的缓冲区）彻底分开

拉像去食堂打饭，你喊一声，窗口给一份。推像外卖，厨房做好了，按调度单送过来。

前面所有例子都是同一个路数。从根节点调 next()，一路往下渗透，数据被"拉"上来。 但还有另一条路。

拉模型（Pull-Based，自顶向下） 推模型（Push-Based，自底向上）
谁发起 根节点调 next() 根本没有 next() 函数
调度 隐含在 next() 的递归调用链里 一个显式的调度器，管理"任务/流水线"清单
控制流 vs 数据流 混在一条通道里 彻底分离
常见度 主流，实现容易得多 较少见，但优势明显

推模型是怎么跑的

推模型里，两条流水线之间没有任何直接调用。只有两段代码，加一个调度器。34:28

调度器持有：任务清单 + 依赖关系
  ├─ 任务①（扫 R → 建哈希表）→ 输出写到某个位置（比如缓冲池的一批页）
  │      ↓ 完成
  └─ 任务②（扫 S → 过滤 → 探测 → 投影）
         ↑ 调度器告诉它："任务① 的结果在这里"
         ↓ 完成 → 最终结果的位置 → 返回给调用方

调度器像工地的工头。手里有任务清单和先后顺序，谁先干谁后干，工头说了算。

好处一：调度器有全局视野。只要不违反依赖，它能自己决定流水线的执行顺序。这比"隐式递归"能做出更聪明的决策。

好处二：算子对"数据放哪儿"有更精细的控制。融合后的流水线，甚至可以把中间值留在寄存器里。下一个任务直接读就行。

LIMIT 好实现：拿够了，就停止调 next()。推模型下，"叫下面别推了"要费事得多。

-- 假设有一个建在 salary 上的索引，扫描走的就是它
-- 考点：根本原因是元组的物理位置在执行中变了

这像食堂打饭。打完的人又绕到队尾排了一次。阿姨得认出这张脸，别再给一份。

灾难过程：

步 发生了什么
1 索引扫描沿叶子层走，找到 Andy, salary = 999
2 往上传给 UPDATE 算子，改成 1099，再写回索引
3 索引就建在 salary 上。所以 Andy 这条记录，被挪到了叶子层更靠后的物理位置

5 再加 100，变成 1199。又挪位置……

定义：

万圣节问题是一种异常。查询执行过程中，元组的物理位置变了。结果扫描算子多次看到同一个逻辑元组。

逻辑上只有一个 Andy，物理上却有好几个副本轮番出现。

  2. 在元组头里打个标记："这条我改过了，别再看它"。

执行上下文（Execution Context）

求值时，算子随身带一个执行上下文。1:06:08 里面有当前元组、查询参数、表的 schema。

struct ExecContext {
  const Tuple  *tuple;    // 当前元组
  const Params *params;   // 查询参数，比如 $1
  const Schema *schema;   // 表的 schema，知道 S.val 在第几列
};

这像厨师开工前把调料摆好。每炒一盘都伸手就拿，不用再去仓库找。

求值过程（深度优先）

求值走深度优先：先算子节点，再算父节点。以 WHERE S.val = $1 + 9、传入 $1 = 991 为例：

        [ = ]  ← ⑥ 1000 == 1000 → true
       ↗     ↖
  [S.val]     [ + ]  ← ⑤ 991 + 9 = 1000
   ① 从上下文  ↗    ↖
   查 schema  [$1]   [9]
   拿到 1000  ② 991  ③ 常量 9

顺带一提：Prepared Statement

Prepared Statement 把查询编译一次、缓存计划，之后反复复用。1:04:46

PREPARE xxx AS SELECT * FROM S WHERE S.val = $1 + 9;
EXECUTE xxx(991);
-- 考点：省掉的是每次重跑查询优化器的开销

这像把常走的路线存进导航，下次直接出发。但路况变了，存的路线未必还是最快。

动机：同一个查询跑很多遍，不想每次都重跑一遍查询优化器。

踩坑：没有免费的午餐。PREPARE 时，你还不知道参数值。而不同的参数值，可能对应完全不同的最优计划。所以它有时候是好主意，有时候是坏主意，各系统做法不同。

踩坑：课上说 PostgreSQL 会自动帮你做。同一个查询跑够 5 次，它就自动生成 prepared statement。实际不是这样。 PostgreSQL 不会把普通查询自动变成 prepared statement。只有 PL/pgSQL 这类场景会隐式准备。"5 次"说的是已经 prepared 的语句。前 5 次执行都用定制计划（custom plan）。之后才比较，要不要换成不看参数值的通用计划（generic plan）。

如果能直接调这个函数，而不是遍历树，就快得多。配合向量化模型传一批元组，编译器可能自动向量化成 SIMD。你还可以手写 intrinsics。

PostgreSQL JIT 现场演示

开了 JIT，PostgreSQL 从约 4 秒降到约 2.7 秒。1:10:14 同样的查询，DuckDB 不到 1 秒。

Andy 现场跑了一个对比。数据有 5000 万条记录。先用 pg_prewarm 把整张表预热进缓冲池，再关掉并行扫描。然后跑一个没有索引、必须全表扫的 WHERE。

SET jit = off;   -- 约 4 秒
SET jit = on;    -- 约 2.7 秒，其中 JIT 编译本身约 381 毫秒
-- 同样的查询交给 DuckDB：单线程、没有 JIT，不到 1 秒
-- 考点：PostgreSQL 只编译 WHERE 子句，德国那批系统编译整个计划
配置 耗时
关闭 JIT ≈ 4 秒
开启 JIT ≈ 2.7 秒。其中 JIT 编译本身花了约 381 毫秒
DuckDB 跑同样的查询（单线程、无 JIT） < 1 秒

踩坑：课上口误，说 JIT 开销是"381 秒"。从总耗时 2.7 秒反推，显然是 381 毫秒。

PostgreSQL 的 JIT 约在 2018 年加入。它把 WHERE 子句编译成 LLVM IR。不是遍历树，而是把树拍平，直接生成执行这段逻辑的指令。

它只编译 WHERE 子句，不编译整个计划。德国那批系统则是整个计划都编译。

PostgreSQL 有自己的成本模型，用来决定"这次值不值得 JIT"。编译要花时间，查询太短就不划算。

这像出门前花几分钟查路线。路程长就值，下楼买瓶水就不值。

最扎心的结论

架构选对了，比在错误架构上做微观优化强得多。

PostgreSQL 花了巨大的工程代价，才做到 2.7 秒。写 LLVM JIT、调 LLVM JIT，都绝非易事。DuckDB 什么 JIT 都没有，单线程不到 1 秒。

PostgreSQL：行存 + 迭代器 + 拉     → 天生为 OLTP 优化，开了 JIT 也要 2.7 秒
DuckDB：    列存 + 向量化 + 推     → 从架构上就为 OLAP 设计，不用 JIT 也不到 1 秒
考点：架构选择的收益，远大于在错误架构上做微观优化

这像给自行车装上涡轮，也追不上一辆汽车。

为什么？ 因为 DuckDB 是 列存 + 向量化 + 推模型，从架构上就是为 OLAP 设计的。PostgreSQL 是 行存 + 迭代器 + 拉模型，天生为 OLTP 优化。

架构选择的收益，远大于在错误架构上做微观优化。

表达式树的其他优化

编译器课里的老套路，数据库也会自己做一遍。1:15:06 只是在数据库里，收益放大了十亿倍。

SELECT * FROM t WHERE name = UPPER('wuwang');   -- 常量折叠：UPPER 只算一次
SELECT * FROM t WHERE POSITION('x' IN col) > 0
                   OR POSITION('x' IN col) < 5;   -- 公共子表达式：只算一次，两处复用
-- 考点：这些都是系统自动做的，不用你手工改写 SQL

这像做题时发现两处算的是同一个式子。算一次，抄两遍。

优化 例子
常量折叠（Constant Folding） UPPER('wuwang') 是常量。算一次，把结果当常量塞回去，别调十亿次
公共子表达式消除 POSITION('x' IN col) > 0 OR POSITION('x' IN col) < 5。两棵子树一模一样，那就重写表达式树，复用一次的计算结果

这些都是系统自动做的，你不需要手工改写 SQL。

补充：1:17:06 课堂上有个好问题。"LLVM、GCC、Clang 不是本来就会做这些吗？数据库为什么还要自己做一遍？"

Andy 给了两个理由。

① PostgreSQL 的 JIT 是 2018 年才加的，不是每个查询都会走 JIT。

② 德国那批系统采用两段式编译。先直接生成 x86 汇编，生成极快，立刻就能跑。同时在后台调 LLVM 编译。 后台编译有可能在查询跑完之前完成。这时就把编译好的共享对象热替换进去。而在那个"汇编版"里，这些优化就必须自己做。好在做起来并不难。

1并行数据库 vs 分布式数据库

难度 ★★★★★重要划清本讲和 #23 #24 的边界，作业不考

并行数据库就是把一个库拆到多份资源上，一起干活。4:01 资源可以是核、盘、内存区域，也可以是机器。

SELECT count(*) FROM orders;   -- 应用只写这一行
-- 底下可能是好几个核各扫一段，最后把结果加起来
-- 考点：并行和分布式的分界线，是资源离得多近、通信靠不靠得住
-- 考点：并行假设消息不会丢，分布式必须假设会丢

一个人搬不完一车砖，就叫几个人一起搬。几个人在同一个院子里，喊一声就听见，这是并行。分散在几个城市，只能打电话，还可能断线，这是分布式。

拆开有三个目的：

  • 数据太大，单核、单盘、单机都装不下。
  • 纵向扩展加横向扩展，拿到更高的性能。
  • 有时顺带拿到容错和冗余，因为数据会复制成多份。

踩坑：本讲和期末那两讲要分清。分界线看下表。

并行数据库（本讲） 分布式数据库（#23#24）
资源在哪 物理上挨得很近。同一台机器，或同一个机柜单元 不同机柜、不同可用区、不同数据中心，甚至不同国家
通信 快、便宜、可靠 慢、贵、不可靠
消息会丢吗 假设不会，除非磁盘着火了 必须假设会

补充： 7:11 Andy 顺手举了个极端例子。英伟达刚宣布了 StarCloud，要把 GPU 放到太空里。那时候的延迟，就不用说了。

SQL 是声明式的，所以这一切对应用透明

同一条 SQL，从笔记本搬到大集群上，一个字都不用改。4:39 这是声明式语言最大的红利之一。

-- 在笔记本上对着 SQLite 写的
SELECT name FROM users WHERE city = 'Pittsburgh';
-- 推到生产环境的庞大分布式系统上，原样再跑一遍
-- 考点：SQL 只说要什么，不说怎么做，所以并行化对应用完全透明

应用永远只看到一个逻辑数据库。它不知道这个库物理上被切成了多少块。数据送到哪、结果从哪收，这些细节都由查询计划处理。

这就像寄快递。你只填收件地址，不用管中途走哪条线、换几次车。

补充： 1:24 当周有条时事。那周整个互联网大面积中断，罪魁祸首是 DynamoDB。准确说是它的 DNS 出了问题，数据库本身没挂。一个数据库倒下，半个互联网跟着倒。 DynamoDB 是个分布式 KV 和文档存储，用的是一致性哈希。#23 会讲。

2进程模型：worker 到底是什么

难度 ★★★★★必会HW4 Q2 判断题考，#25 清单列出

进程模型决定了数据库怎么同时处理多个请求。8:59 干活的单位统一叫 worker，也就是数据库里的计算单元。它替上层的管理者执行任务，再把结果交回去。

// worker 只是个抽象：能领任务、能交结果就行
struct Worker {
  virtual Result Run(Task t) = 0;   // 底下可能是进程，也可能是线程
};

worker 就像工人。可以是正式工，也可以是借来的临时工，活都一样干。

补充：这里坚持说 worker，不说 thread。因为不同系统的实现单位不一样。而且 worker 不一定在跑查询。#05 LSM 里的 compaction 线程也是 worker，只是在做后台维护。

三种做法

worker 有三种来源：自己开进程，自己开线程，借应用的线程。

进程模型：每个 worker 一个进程      PostgreSQL
线程模型：每个 worker 一个线程      过去 25 年几乎所有系统
嵌入式：  借应用的线程              SQLite、RocksDB
考点：三种模型和各自的代表系统要对得上

① 每个 worker 一个进程（Process per Worker）

每个 worker 都是一个独立的操作系统进程，由 dispatcher 统一派活。

应用 ──→ [ Dispatcher ]           ← PostgreSQL 里叫 postmaster
              │ fork()
     ┌────────┼────────┐
  [进程1]  [进程2]  [进程3]        ← 各自独立地址空间
     └────── 共享内存 / IPC ──────┘

Worker *w = pool.Pick();          // dispatcher 从进程池里挑一个 worker
Reply(app, w->addr, w->port);     // 把这个 worker 的地址和端口告诉应用
// 应用重连到 w，之后直接把 SQL 发给 w

流程：应用先连 dispatcher。dispatcher 从进程池里挑一个 worker，把这个 worker 的地址和端口告诉应用。应用再重连到那个 worker，直接发 SQL。

这像银行大厅。门口的引导员给你指个窗口，之后你直接去那个窗口办事。

worker 之间怎么通信：用共享内存，PostgreSQL 就是这样。最差的情况，用 IPC，比如管道和信号。

踩坑：这种模型依赖 OS 调度。worker 什么时候跑，你没有细粒度的控制。OS 只看到一堆进程。

为什么 1980-90 年代都用进程？

因为那时线程还没有统一标准，进程有。13:37 这是本讲最有价值的历史知识点。Andy 先问学生：pthread_create 里的 P 是什么？

pthread_create(&tid, NULL, worker_main, arg);   // P 就是 POSIX
// POSIX 线程标准到 1990 年代中后期才定下来
// fork、wait、join 早就在所有 Unix 上标准化了
// 考点：1970-90 年代的数据库用进程，是因为线程 API 各家不统一
// 考点：后果是 PostgreSQL 和它的 fork 至今还是进程模型

POSIX。而 POSIX 线程标准，是 1990 年代中后期才定下来的。

在那之前，BSD、HP-UX、AIX、Solaris 各有一套线程库。每种 Unix 都不一样，API 不同，语义也不同。要支持多种 Unix，线程调度器就得重写好几遍。代码毫无可移植性。

进程原语就不一样。fork、wait、join 早就在所有 Unix 上标准化了。

所以 1970 年代到 90 年代初的数据库，全走进程模型。翻 PostgreSQL 源码，还能看到一堆按 Unix 版本分支的 #ifdef。但进程在 Linux 和 AIX 上行为基本一致，语义对得齐。

这就像出国旅行。各国插座标准不一，干电池却全球通用。想到哪都能用，就只能带电池。

踩坑：今天还在还这笔债。任何 PostgreSQL 的 fork 都还在用进程模型。改成线程，是一次伤筋动骨的重写。

② 每个 worker 一个线程（Thread per Worker）：现代做法

现代系统都在一个进程里开多个线程，每个线程当一个 worker。

        单进程
    [ Dispatcher ]
    ┌────┼────┐
 [线程1][线程2][线程3]   ← 共享同一个地址空间

std::vector<std::thread> workers;
for (int i = 0; i < n; i++)
  workers.emplace_back(WorkerLoop, &shared_state);   // 大家共用一块内存
// 考点：线程模型开销小、能自己调度，唯一但致命的缺点是一挂全挂

好处有三条：

  • 同一个地址空间，通信直接读写内存。
  • 开销远小于进程。
  • 能自己做调度。比如非抢占式协程主动 yield。暂停一个线程，比暂停一个进程轻量太多。

踩坑：共享数据结构照样要 latching。#10 讲的东西一样不能少。

唯一的缺点：一个线程 segfault，整个进程全挂。反过来，PostgreSQL 挂一个进程无所谓，postmaster 再 fork 一个就是了。所以理论上多线程架构更脆。

线程像合租一套房的室友，递个东西很方便。可一个人把厨房点着了，整套房都得撤。进程像各住各的单间，一间着火，别人照常过。

补充： Oracle 中途转过向。1970-80 年代起家时用进程模型，幻灯片标注 2014 年起支持多线程。课上说那之后默认用多线程，实际不是默认。参数 THREADED_EXECUTION 在 Linux 和 UNIX 上默认是 false，还是进程模型。只有 Windows 上默认是 true。

③ 嵌入式数据库（Embedded）

嵌入式数据库自己不开任何 worker，用的是应用借给它的线程。19:49 严格说这不算"进程模型"，而是另一种架构决策。

sqlite3 *db;
sqlite3_open("app.db", &db);                       // 只是加载一个库
sqlite3_exec(db, "SELECT ...", cb, NULL, NULL);    // 当前线程亲自进去读写数据
// 考点：嵌入式的 worker 是应用借来的，SQLite 没有后台 worker
// 考点：DuckDB 是例外，可以让它自己起线程

数据库自己不创建任何 worker。worker 是调用它的应用"借"给它的。

Web 服务器（应用）
   └─ 应用的线程 ──调用库函数──→ [ SQLite / RocksDB 库代码 ]
                                       └─ 就是这个线程在读写数据
                                  ←──返回──┘

这像自助餐厅。没有服务员，客人自己端着盘子去打饭。

典型系统：SQLite、Berkeley DB、RocksDB、LevelDB。Berkeley DB 是最早这么干的。它是 UC Berkeley 出品，2006 年被 Oracle 收购。

踩坑： SQLite 没有后台 worker。它唯一的 worker，就是应用调进来的那个线程。

补充： DuckDB 是个例外。你可以让它自己起线程。

三种模型对比

今天的默认答案是线程。进程是历史包袱，嵌入式走的是另一条路。

谁在用 备注
进程/worker PostgreSQL 和它的所有 fork，还有老牌企业系统 历史包袱
线程/worker 过去 25 年几乎所有系统 现代默认
嵌入式 SQLite、RocksDB、LevelDB、Berkeley DB 是库，不是服务器

补充： 24:24 能混用吗？理论上可以。dispatcher 单独一个进程，worker 们在另一个进程里开线程。好处是 dispatcher 可以搬到另一台机器上。但单机系统没人这么干，一律 thread-per-worker。

3调度：谁来决定跑几个 worker

难度 ★★★★★了解各系统调度水平对比，不考不写代码

查询一进来，数据库先要定并行度（degree of parallelism）。也就是派几个 worker。21:50

int dop = ChooseDOP(running_queries,   // 当前有多少查询在跑
                    data_location,     // 数据在哪儿
                    disk_speed);       // 取这些数据的磁盘有多慢
// 考点：调度不能交给 OS，因为 OS 不知道查询要干什么
// 考点：Oracle、SQL Server、DB2 调度精细，PostgreSQL 让 OS 开车

这像饭店后厨。主厨知道每道菜要几个人，也知道哪口锅空着。门口的保安只知道进来了几个人。

补充：这又是"绝不把方向盘交给 OS"，贯穿全课的主题，见 #04。数据库知道查询要干什么，也知道有哪些资源可用。所以它永远能比 OS 调度得更好。

现实中分三档：

系统 调度水平
Oracle / SQL Server / DB2，贵的那些 全套精细调度
PostgreSQL 基本"让 OS 开车"
MySQL 压根不做本讲说的这种并行

4查询间并行

难度 ★★★★★必会#25 清单列查询间 vs 查询内

查询间并行就是不同的查询各占一个 worker，同时跑。27:01 英文叫 Inter-Query Parallelism。

worker1 → 查询 ①
worker2 → 查询 ②      互不通信、互不干扰
worker3 → 查询 ③

这像超市开了好几个收银台。每个顾客只在一个台子结账，台子之间不用商量。

调度策略上，绝大多数系统就用先来先服务（FCFS）。讲到事务以后，还可以按优先级排，从 #17 开始。

只读查询下，这是最容易的并行。协调成本极低。查询一旦跑起来，彼此不用交换任何东西。

不过内部数据结构仍然要 latching，见 #10。还能白赚一样东西：缓冲池的扫描共享 / 游标共享（#04）。因为大家都从缓冲池这个中心点走。

踩坑：一旦有并发更新，问题就全变了。谁写了什么，谁能读到谁写的，完全是另一回事。#17 起会花两周专讲。

关键区分

能同时跑多条查询，不代表一条查询会拆开跑。

SELECT sum(price) FROM orders;   -- 在 MySQL 里跑
-- 机器有一千个核，这条查询也只用一个 worker
-- 考点：MySQL 只有查询间并行，单个查询永远不并行
-- 考点：PostgreSQL 两者都有

支持查询间并行 ≠ 单个查询会并行。

MySQL 就是典型。它能同时跑多个查询，但每个查询永远只用一个 worker。你有一千个核，一条查询还是只跑在一个核上。

PostgreSQL 两者都有。多条查询能并行，单条查询内部也能并行。

收银台再多，一个顾客的一大车东西，也只在一个台子上扫。

5查询内并行：三种形态

难度 ★★★★★必会HW4 Q2 考查询内并行，清单列水平垂直

查询内并行是把一条查询拆给多个 worker 一起跑。29:29 英文叫 Intra-Query Parallelism，本质是生产者-消费者模型。

// 下游 worker 生产元组，上游 worker 消费元组
while (auto t = child_queue.Pop())   // 等下游把数据送上来
  Emit(Process(*t));                 // 处理完再交给更上游
// 考点：三种形态是算子内、算子间、浓密，99% 说的是算子内
// 考点：浓密并行只有百万美元级的企业系统才有

这像工厂的流水线。下游工位做零件，上游工位拿零件组装。

形态 别名 含义 常见度
① 算子内并行（Intra-Operator） 水平并行 多个 worker 跑同一段流水线。各自处理数据的不同分片 99% 的"并行数据库"指的就是它
② 算子间并行（Inter-Operator） 垂直并行 多个 worker 同时跑查询计划的不同部分 较少见
③ 浓密并行（Bushy） 没有别名 就是 ①+② 的组合。教材把它单列了 只有百万美元级的企业系统有。SQL Server、DB2、Oracle

补充：这又是声明式的红利。用哪种并行，SQL 里不用指定。系统会根据硬件和查询自己决定。

补充：所有算法都能并行化。本学期讲过的算法，基本都能用分治拆开。比如 #12 Grace 哈希连接。分区做完之后，一个 worker 负责一个分区。数据已经按哈希分好了，worker 之间根本不用通信。

6算子内并行与 Exchange 算子

难度 ★★★★★必会水平并行本体，#25 清单列出

算子内并行就是把数据切成几份。每个 worker 拿一份，跑同一段流水线。33:18 这是最常见的并行形态。

// 按页切：3 个 worker 各扫三分之一的页（示意）
for (int w = 0; w < 3; w++)
  threads.emplace_back(ScanFilter, pages.Slice(w, 3));
// 子集互不相交。按页、按范围、按哈希值切都行

这像阅卷。一摞卷子分成三份，三个老师按同一套标准，各改一份。

但总得有人把结果收拢：Exchange 算子

Exchange 算子就是一道屏障（barrier）。所有子 worker 交齐结果之前，上面的算子不许往下走。数据库为了实现并行，才引入了它。

EXPLAIN SELECT count(*) FROM big_table;
-- PostgreSQL 并行执行时，输出里能直接看到 Gather 节点
-- 考点：Exchange 在关系代数里没有对应物
-- 考点：PostgreSQL 管它叫 Gather 和 Gather Merge

这像老师收卷。全班交齐了，才开始统一批改。

踩坑：它在关系代数里没有对应物，纯粹是实现层的产物。

补充：别的领域也有这东西。并行编程里叫 merge / gather，也就是 scatter-gather。PostgreSQL 叫它 Gather 和 Gather Merge，EXPLAIN 输出里能直接看到。

完整例子

并行哈希连接要两条流水线，每条末尾各有一道 Exchange。

SELECT ... FROM A JOIN B ON ... WHERE A.x = ... AND B.y = ...;

Pipeline ①（build 侧，扫 A）：

   A 被切成 3 份 → w1  w2  w3
                    ↓   ↓   ↓
                   过滤 过滤 过滤      三个 worker 并行
                    ↓   ↓   ↓
                  ── 建哈希表 ──       （共用一张全局哈希表）
                        ↓
                  Exchange（阻塞）     ← 三个 worker 全部报告完成，才能往下走

Pipeline ②（probe 侧，扫 B）：

   B 被切成 3 份 → w1  w2  w3
                    ↓   ↓   ↓
                   过滤 过滤 过滤
                    ↓   ↓   ↓
                  ── 探测哈希表 ──
                    ↓   ↓   ↓
                   投影 投影 投影
                        ↓
                  Exchange（阻塞）
                        ↓
                    最终结果

build_exchange.WaitAll();   // 三个 build worker 全部报告完成
StartProbe(B_parts);        // 这时哈希表才是完整的
// 考点：不等就开始 probe，会产生假阴性，漏掉本该匹配的元组

踩坑：第一个 Exchange 必须阻塞。38:53 假如 build 侧还有一个 worker 没写完哈希表，probe 就开始查了。这会产生假阴性。要找的匹配项，还没被放进哈希表。这正是 #13 流水线阻断算子 的道理。

补充：计划里还有一份元数据，记着流水线之间的依赖关系。调度器靠它知道，A 的那几个 worker 要先跑完。

Exchange 一定要阻塞吗？

不一定，要看上下是什么算子。35:26 有学生问了个好问题。有些情况，明明可以先把部分结果送上去。

Andy 说：对。

if (parent->IsPipelineBreaker())   // 哈希 build、排序、聚合
  exchange.WaitAll();              // 必须等齐
else
  exchange.Forward(batch);         // 边来边送
// 考点：阻不阻塞，看上面是不是流水线阻断算子

取决于上下算子是什么。上面是流水线阻断算子，比如哈希 build、排序、聚合，就必须阻塞。否则可以边来边送。

能不阻塞，就打开了第 7 节"算子间并行"的大门。

三种 Exchange 算子

Exchange 按进出的流数分三种。39:35 下面用的是 SQL Server 的术语。

类型 输入 → 输出 用途
Gather（聚集） 多 → 一 最常见。把多个 worker 的结果合成一条流
Distribute（分发） 一 → 多 把一条输入流重新切分，交给多个 worker 并行处理
Repartition（重分区） 多 → 多，数量不必相等 最灵活。比如 3 条进、2 条出 
// 下面数据多，开 10 个 worker。过滤完剩得不多，上面 2 个就够
auto out = Repartition(inputs /* 10 条流 */, 2 /* 收成 2 条 */);
// 考点：Gather 多变一，Distribute 一变多，Repartition 多变多
// 考点：并行度不是越高越好，协调和搬数据都有成本

踩坑：并行度不是越高越好。协调和搬数据都有成本。这就是 Repartition 有用的原因。

下面数据量大，我用 10 个 worker。一路过滤下来，数据剩得不多了，上面只需要 2 个 worker。那就把 10 条流收成 2 条。

这像高速收费站。车多的地方开十个口，进了城区车少了，并成两条道就够。

补充： Google BigQuery / Dremel 的每一个执行阶段都做这件事。所以它能动态地扩容和缩容。这本来是分布式数据库的玩法（#23），但单机上同样成立。

7算子间并行（垂直并行）

难度 ★★★★★必会垂直并行本体，#25 清单列出

算子间并行是让计划里不同的算子同时跑。上下游各占一个 worker。42:57

前提：上游能边来边处理，不用等齐全部数据。换句话说，中间的 Exchange 不阻塞。

这像两个人洗碗。一个洗，一个擦。洗好一个就递过去，不用等全洗完再擦。

例子：把昂贵的 UDF 拆到另一个 worker

把昂贵的 UDF 单独交给另一个 worker，连接和 UDF 就能同时跑。

SELECT expensive_udf(...) FROM A JOIN B ON ...;
-- expensive_udf 假设是层层哈希之类的重计算
-- 考点：前提是上游能边来边处理。收益是不用物化，代价是通信和拷贝

worker2:  [ UDF 计算 ]  ← 一边收一边算，收不到就阻塞等着
                ↑ 元组流
worker1:  [ 连接 ]      ← 一边找到匹配一边往上吐

收益：worker1 全速做连接。找到一条，就交给 worker2。两条流水线同时在跑，中间结果不用物化下来。

踩坑： 45:00 这不是免费的。要通信，还要拷贝数据。它比融合进同一个 for 循环更贵，见 #13 算子融合。拆开，是为了换并行度。

它最自然的归宿：流式数据库

流式数据库里的查询永远不结束，所以算子间并行是必需的。42:57 流式系统（Streaming DBMS）里，没有"固定大小的表"这回事。

数据源源不断流进来 ────→ 查询【永远】在跑
                          ├─ 每 5 秒输出一次结果
                          └─ 或者触发式：股价超过 $100 就输出
考点：数据无限，不可能等它到齐，所以流式系统天然需要算子间并行

这像自来水厂。水一直在流，没法等"所有的水"到齐了再消毒。

踩坑：这里数据是无限的。你根本不可能等它到齐。所以算子间并行在这里是天然的，也是必需的。

8浓密并行

难度 ★★★★★重要只是水平加垂直，清单未单列

浓密并行就是算子内和算子间一起上。45:45 英文叫 Bushy Parallelism。

              [ 连接 ]              ← 上层也在并行跑
             ↗        ↖
      [ A ⋈ B ]      [ C ⋈ D ]      ← 两组 worker 同时算两个连接
       ↗    ↖         ↗    ↖
      A      B       C      D        ← 每个还各自水平并行

这像两个装修队同时装两套房。每个队里，又分好几个人同时刷墙。

踩坑： 47:54 "浓密连接树"这个形状本身就很少见。

左深树：((A ⋈ B) ⋈ C) ⋈ D      一条链往上叠
浓密树：(A ⋈ B) ⋈ (C ⋈ D)      两组可以同时算
考点：绝大多数优化器只生成左深树，因为搜浓密树的形状太贵

绝大多数系统只会给你"左深树"。先 A⋈B，拿结果去 ⋈C，再 ⋈D。

原因：搜索浓密树形状的计算复杂度太高，不划算。#16 会详谈。

9I/O 并行

难度 ★★★★★必会#25 清单列 I/O 并行

I/O 并行是把数据库摊到多块存储设备上，把带宽叠起来。47:54 因为有一堆 CPU 不代表你就快了，瓶颈往往在磁盘。

-- PostgreSQL：用表空间把一张表放到另一块盘上
CREATE TABLESPACE fast_disk LOCATION '/mnt/ssd_b';
CREATE TABLE logs (...) TABLESPACE fast_disk;
-- PostgreSQL 只能做到这种部分控制

一根水管出水慢，就多接几根水管一起放。

补充：这里有个诚实的时代注解。过去五年磁盘变得非常快，如今很多时候 CPU 才是瓶颈。但数据要是在 S3 这类远端存储上，那它永远比 CPU 慢得多。

切法有四种：

  • 多块盘存一个库。
  • 一块盘一个库。
  • 一块盘一张表。
  • 一张表跨多块盘。
系统 控制粒度
Oracle（高端） 完全控制。表放哪儿，预写日志（WAL，#21）放哪个盘，都能指定
PostgreSQL 部分控制，靠表空间（tablespace）
MySQL 没有物理位置概念。管理员只能用符号链接，把文件挪到别的设备上。数据库自己毫不知情

条带化 vs 镜像（RAID 0 vs RAID 1）

条带化把页轮流摊到各块盘上。镜像把每页在每块盘上都存一份。下面假设有 6 个页、3 块盘。

int StripeDisk(int page_no) { return page_no % 3; }   // RAID 0：每页只落一块盘
void MirrorWrite(Page p) {
  for (auto &d : disks) d.WriteAndFsync(p);           // RAID 1：三块盘都写完，才回报应用
}
// 考点：RAID 0 写快，但丢盘就丢数据。RAID 1 写慢，但读得更好、完全冗余

条带化像把一套书拆开，分放在三个书架上。镜像像三个书架各放一整套。

RAID 0 条带化（Striping） RAID 1 镜像（Mirroring）
怎么放 轮转。页1→盘1，页2→盘2，页3→盘3…每页只存一份 每页在每块盘上都存一份
写 快。只写一块盘 慢。三块盘都要写，而且全部 fsync 成功后才能回报应用
读 能并行。不同 worker 去不同盘 更好。任何页都能从任何盘读。上面还能加负载均衡器，把带宽榨到最大
容错 丢一块盘，就丢一部分数据库。要是你的银行账户在里面，你会很在意 完全冗余

实践中一定是两者之间的某种组合。

硬件 RAID vs 数据库自己做

数据库自己用软件管多块盘，比交给硬件 RAID 更快、更灵活。53:52 可只有昂贵的企业系统才这么做。

Write("/data/table.db", page);        // 硬件 RAID：落到哪块盘，数据库一无所知
disks[Locate(page_id)].Write(page);   // 自己做：每页在哪块盘，心里有数
// 考点：自己做更快、更灵活，但只有 Oracle 这类昂贵的企业系统才做

硬件 RAID 像坐出租车，到了就行，走哪条路你不管。自己做像亲自开车，哪条路堵，你心里有数。

带 I/O 控制器的存储设备 数据库内部用软件实现
数据库看到什么 单一逻辑文件系统。底下的事它一无所知 完全掌握数据在哪儿
好处 透明 更快、更灵活。知道丢哪块盘意味着什么，能据此决策
谁做 通用方案 只有昂贵的企业系统这么做。Oracle 有一大堆这类能力

三角权衡

存储要在性能、持久性、容量三者之间权衡。真正难取舍的，是持久性和性能。

        性能
        ╱  ╲
       ╱    ╲
   持久性 ── 容量

考点：真正的权衡在持久性和性能这条边上，容量加钱就行

补充： 55:13 这是 Andy 的现实观察。真正在乎数据不能丢的机构，比如银行、Visa、Mastercard，通常也很有钱。所以容量不是问题，加钱就行。真正的权衡在持久性 vs 性能这条边上。

10分区

分区就是把一张表或一个库，切成不相交的子集。再把这些子集路由到不同的存储设备。56:30

SELECT name FROM users;   -- 应用只认识 users 这张表
-- 底下的 users 可能已经被切成几块，放在不同的盘上
-- 考点：列存 DSM 本身就是一种分区，是按列切的垂直分区

这像图书馆分馆。读者只查一个总目录，书其实放在好几个馆里。

分区对应用完全透明。 SQL 里你只看到表，不知道它被怎么切的。

本讲小结

硬件早就是多核了，数据库必须设计成能用上它们。58:24

你的手机的核数和线程数，都比 1980 年代的数据库服务器多。

多 worker 带来两件事：

  1. 掩盖磁盘和网络延迟。一个 worker 卡在 I/O 上，别的继续跑。
  2. 为并发更新做准备。系统能精确控制谁在什么时候跑。因为它知道每个查询想改什么。别的查询已经改了什么，它也知道。这正是 #17 起要展开的东西。

最后那句话最值得记

从 CPU 改到 GPU，代码几乎不用变。唯一的新约束，是输出大小必须事先知道。1:15:23 有人问讲者，从 CPU 原生改成 GPU 原生，最大的改动是什么。回答意外地朴素。

size_t out_size = OutputSize(op, input);   // GPU 上必须先知道输出多大
auto buf = gpu.Alloc(out_size);            // 大小固定且已知，才能分配
op.Execute(input, buf);
// 考点：GPU 要求输出大小固定且已知，连"什么算流水线阻断算子"都要改

代码其实相当经典。算子和流水线这套东西，"概念上已经有 20 年了"。

唯一特殊的约束是：GPU 要求输出大小是固定且已知的。也就是说，执行一个算子之前，就必须知道它的输出有多大。这一条重塑了 Spiral 整个查询规划的设计。连"什么算流水线阻断算子"的定义，都要跟着改。

Andy 顺势总结：

不管跑在 GPU、FPGA、CPU 还是下一个什么东西上，核心概念都一样。变的只是硬件实现。

讲者的收尾：

"数据库里没有太阳底下的新鲜事，但硬件一直在变。"

讲者打了个线性规划的比方。最优解永远在某个顶点上。硬件一变，约束条件跟着变，最优解就被推到了另一个顶点。于是新东西看起来和以前差别巨大，其实只是约束变了。
